# Work Management: фундамент продукта

Work Management проектируется как самостоятельный open-source продукт на Frappe Framework для управления операционной работой.

Идея продукта в первую очередь развивается из реальных потребностей первой рабочей эксплуатации, но продукт не является приложением одной компании, отрасли, департамента или организационной структуры. Реальная эксплуатация задаёт требования и проверяет жизнеспособность решений, но не должна превращаться в обязательный шаблон для остальных пользователей.

## Позиционирование

Work Management — не конструктор, из которого предполагается собрать произвольную информационную систему. Это готовая унифицированная платформа управления операционной работой с устойчивой моделью данных и набором основных возможностей, востребованных в разных организациях.

Продукт должен закрывать распространённые задачи управления работой: зоны ответственности, виды работ, исполнителей, состояния, приоритеты, сроки, ожидание, источники возникновения работы, связи с предметными объектами, права доступа, уведомления, рабочие представления и отчётность. Дополнительные first-party возможности могут расширять эту основу там, где существует самостоятельная распространённая ответственность.

Экзотический или строго отраслевой процесс не является основанием заранее усложнять Core. Если такой процесс действительно нужен конкретной установке, он реализуется стандартными средствами расширения Frappe или отдельной capability.

## Жёсткая модель данных, гибкая конфигурация

Универсальность Work Management строится вокруг зафиксированной модели данных, а не вокруг возможности произвольно конструировать само ядро.

Core определяет устойчивые сущности, их смысл, связи и инварианты. Администратор конкретного `Site` настраивает бизнес-процесс поверх этой модели средствами Frappe, но не переопределяет семантику `Work Unit`, `Work Type` и `Work Item`.

Иными словами, продукт фиксирует **что является работой и как она представлена в данных**, а организация определяет **как именно эта работа проходит через её структуру и правила**.

```text
зафиксировано продуктом
────────────────────────
Work Unit
Work Type
Work Item
их базовая семантика и инварианты

настраивается организацией
────────────────────────
структура Work Unit
набор Work Type
Roles / User Permissions
Workflow
Notifications
Custom Fields
Reports / Workspace
подключённые capabilities
```

Такой подход позволяет использовать одну и ту же модель в разных организациях без форка Core и одновременно не превращает продукт в meta-framework или универсальный конструктор произвольных сущностей.

Модель считается достаточно универсальной, если она покрывает основные повторяющиеся потребности управления операционной работой в разных организациях. Требование поддержать любой мыслимый, экзотический или уникальный процесс не является критерием Core.

## Цель

Work Management должен одновременно выполнять два условия:

1. полноценно покрывать потребности реальной рабочей эксплуатации, для которой он развивается;
2. сохранять стабильную и унифицированную модель, на основе которой другая организация может настроить собственную работу без переписывания продукта под её оргструктуру и предметную область.

Универсальность не означает попытку заранее описать все возможные бизнес-процессы. Она означает, что общая семантика операционной работы остаётся стабильной, а конкретная организация собирает свой рабочий контур из данных `Site`, штатных механизмов Frappe и нужных ей дополнительных возможностей.

## Продукт не навязывает процесс

Work Management не должен требовать от организации принять конкретную методологию, оргструктуру, набор этапов, терминологию или порядок работы только потому, что так устроена первая эксплуатация.

Продукт задаёт устойчивую модель данных и общие контракты. Типовой бизнес-процесс должен по возможности собираться администратором средствами Frappe:

```text
структура ответственности  → Work Unit
виды работы                → Work Type
пользователи и доступ      → Roles / User Permissions
этапы процесса             → Frappe Workflow
уведомления                → Notifications
дополнительные поля        → Customize Form / Custom Fields
представления              → List / Report / Workspace
предметные справочники      → обычные DocType
```

Поэтому две организации могут использовать один и тот же Core и иметь заметно разные рабочие процессы без форка продукта.

Это не обещание, что абсолютно любой уникальный процесс можно реализовать без кода. Если штатных механизмов Frappe и существующих возможностей продукта объективно недостаточно, специфическое поведение добавляется обычным DocType, controller, hook или отдельным extension App. Work Management не создаёт для этого собственный конструктор процессов поверх Frappe.

## Масштаб использования

Одна установка Work Management может быть ядром управления работой на разном организационном уровне:

```text
вся компания
    или
отдельное направление / департамент
    или
отдел
    или
одна команда
```

Масштаб не меняет архитектуру продукта. Он определяется структурой `Work Unit`, пользователями, правами, видами работ и подключёнными возможностями конкретного `Site`.

Продукт не требует, чтобы `Work Unit` совпадал с формальной оргструктурой. В одной установке это могут быть департаменты и отделы, в другой — сервисные команды, очереди, направления или иные реальные зоны ответственности.

## Универсальное ядро

Ядро отвечает только за семантику операционной работы:

```text
Work Unit
Work Type
Work Item
```

- `Work Unit` определяет, какая организационная очередь или зона ответственности владеет работой.
- `Work Type` классифицирует повторяющийся смысл работы и хранит только простые общие defaults.
- `Work Item` представляет одну конкретную исполнимую единицу работы.

Ядро не знает о конкретной отрасли, компании, клиентах, сотрудниках, технике, проектах, сменах, документах, терминалах или внешних системах.

Связь Work Item с предметными документами выполняется штатными механизмами Frappe через `Link`, `Dynamic Link` и child tables с фиксированной семантикой `sources` и `references`.

## Настройка под организацию

Конкретная организация адаптирует продукт без изменения универсальной семантики Core:

```text
структура ответственности  → Work Unit data
виды работы                → Work Type data
пользователи и доступ      → Roles / User Permissions
этапы согласования         → Frappe Workflow
уведомления                → Frappe Notifications
дополнительные поля        → Customize Form / Custom Fields
предметные объекты         → обычные DocType
отчёты и рабочие экраны     → Reports / Workspace / стандартные Views
интеграции                 → REST / Webhook / hooks / extension App
```

Если организации требуется специфическая самостоятельная ответственность, она добавляется отдельным предметным DocType или модулем. Core меняется только тогда, когда новая ответственность относится к самому понятию операционной работы и подтверждается несколькими независимыми предметными областями.

## Дополнительные возможности продукта

Развитие продукта не ограничивается только функциями, которые нужны первой эксплуатации.

Допустимо и полезно добавлять first-party возможности, которые в первой установке могут не использоваться, если они:

- закрывают самостоятельную распространённую ответственность;
- полезны нескольким различным сценариям или организациям;
- естественно строятся на Frappe;
- не меняют семантику Core ради одного частного процесса;
- могут оставаться неиспользуемыми там, где они не нужны.

Например продукт может включать готовые capabilities для:

- документальных оснований и архива связанных документов;
- учёта сотрудников и внешних справочников;
- учёта оборудования, его перемещений и состава;
- проектов и планирования;
- сменных журналов и передачи работы;
- других предметных функций с самостоятельной ответственностью.

Наличие такой capability в продукте не означает, что организация обязана её использовать. И наоборот, отсутствие потребности в первой эксплуатации не является причиной отвергать полезную универсальную возможность.

Такие возможности не должны загрязнять Core отраслевыми полями и правилами. Организация подключает и настраивает только то, что соответствует её процессам.

## Отношение к Frappe

Frappe остаётся framework продукта и отвечает за модель DocType, `Document`, ORM, Desk, permissions, Workflow, Notifications, Reports, REST API, background jobs, customization и extension points.

Work Management не создаёт поверх Frappe собственные универсальные `Entity`, `Relation`, `Process`, `Rule`, `Plugin`, workflow engine, permission engine или другой meta-framework.

Собственный код продукта добавляется только для недостающей бизнес-семантики и должен оставаться небольшим, читаемым и проверяемым тестами.

Главный принцип расширения:

> если требование можно выразить настройкой или штатной точкой расширения Frappe, продукт использует её; собственный механизм появляется только для поведения, которого Frappe действительно не предоставляет.

## Реальная эксплуатация как acceptance test

Первая рабочая эксплуатация является обязательным acceptance-сценарием продукта.

Универсализация считается неудачной, если ради абстрактной переносимости продукт перестаёт полноценно закрывать реальную операционную работу: ответственность, очередь, исполнителя, сроки, ожидание, основания изменений, связанные предметные объекты, историю и необходимые дополнительные возможности.

Одновременно требование конкретной эксплуатации не должно автоматически становиться полем или механизмом Core. Сначала определяется самостоятельная ответственность, затем выбирается уровень реализации: данные `Site`, штатная настройка Frappe, отдельная capability или изменение Core.

Первая эксплуатация также не является верхней границей функциональности продукта. Универсальная возможность может развиваться независимо от неё, если сохраняет архитектурные границы и приносит самостоятельную пользу другим установкам.

## Критерий устойчивости

Архитектура считается устойчивой, если:

- новая структура компании не требует изменения Core;
- новый вид работы не требует изменения Core;
- другой порядок согласования настраивается без форка продукта;
- новый тип предметного объекта не требует изменения Core;
- новый вид оборудования не требует изменения Work Item;
- новый специфический процесс добавляется локально;
- организация может использовать только нужные ей capabilities;
- одна установка может обслуживать компанию, департамент, отдел или команду без отдельной архитектуры;
- рабочие данные и корпоративная структура остаются данными `Site` и не попадают в публичный репозиторий;
- обновление одной capability не заставляет переписывать несвязанные части приложения.

Это фундаментальное направление Work Management. Оно меняется только при появлении объективного противоречия, технической ошибки или новой ответственности, которую существующая граница действительно не может корректно выразить.
