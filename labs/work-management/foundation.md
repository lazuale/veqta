# Work Management: фундамент продукта

Work Management проектируется как самостоятельный open-source продукт на Frappe Framework для управления операционной работой.

Продукт не привязан к одной компании, отрасли, департаменту или организационной структуре. Реальная эксплуатация используется как источник требований и проверка жизнеспособности модели, но не как граница продукта.

## Цель

Work Management должен одновременно выполнять два условия:

1. полностью покрывать потребности реальной рабочей эксплуатации, для которой он развивается;
2. сохранять универсальное ядро, которое можно использовать в других организациях без переписывания продукта под их структуру и предметную область.

Универсальность не означает попытку заранее описать все возможные бизнес-процессы. Она означает, что общая семантика операционной работы остаётся стабильной, а различия конкретной организации выражаются данными `Site`, штатными механизмами Frappe и отдельными предметными расширениями.

## Масштаб использования

Одна установка Work Management может быть ядром управления работой на разном организационном уровне:

```text
вся компания
    или
отдельное направление / департамент
    или
отдел
    или
одна команда
```

Масштаб не меняет архитектуру продукта. Он определяется структурой `Work Unit`, пользователями, правами, видами работ и подключёнными возможностями конкретного `Site`.

Продукт не требует, чтобы `Work Unit` совпадал с формальной оргструктурой. В одной установке это могут быть департаменты и отделы, в другой — сервисные команды, очереди, направления или иные реальные зоны ответственности.

## Универсальное ядро

Ядро отвечает только за семантику операционной работы:

```text
Work Unit
Work Type
Work Item
```

- `Work Unit` определяет, какая организационная очередь или зона ответственности владеет работой.
- `Work Type` классифицирует повторяющийся смысл работы и хранит только простые общие defaults.
- `Work Item` представляет одну конкретную исполнимую единицу работы.

Ядро не знает о конкретной отрасли, компании, клиентах, сотрудниках, технике, проектах, сменах, документах, терминалах или внешних системах.

Связь Work Item с предметными документами выполняется штатными механизмами Frappe через `Link`, `Dynamic Link` и child tables с фиксированной семантикой `sources` и `references`.

## Настройка под организацию

Конкретная организация адаптирует продукт без изменения универсальной семантики Core:

```text
структура ответственности  → Work Unit data
виды работы                → Work Type data
пользователи и доступ      → Roles / User Permissions
этапы согласования         → Frappe Workflow
дополнительные поля        → Customize Form / Custom Fields
предметные объекты         → обычные DocType
интеграции                 → REST / Webhook / hooks / extension App
```

Если организации требуется специфическая самостоятельная ответственность, она добавляется отдельным предметным DocType или модулем. Core меняется только тогда, когда новая ответственность относится к самому понятию операционной работы и подтверждается несколькими независимыми предметными областями.

## Дополнительные возможности

Продукт может включать готовые capabilities поверх Core, например:

- документальные основания и архив связанных документов;
- учёт сотрудников и внешних справочников;
- учёт оборудования, его перемещений и состава;
- проекты и планирование;
- сменные журналы и передачу работы;
- другие предметные функции, если у них появляется самостоятельная ответственность.

Такие возможности не должны загрязнять Core отраслевыми полями. Организация, которой конкретная capability не нужна, не должна менять модель Work Item из-за её наличия.

## Отношение к Frappe

Frappe остаётся framework продукта и отвечает за модель DocType, `Document`, ORM, Desk, permissions, Workflow, Notifications, Reports, REST API, background jobs, customization и extension points.

Work Management не создаёт поверх Frappe собственные универсальные `Entity`, `Relation`, `Process`, `Rule`, `Plugin`, workflow engine, permission engine или другой meta-framework.

Собственный код продукта добавляется только для недостающей бизнес-семантики и должен оставаться небольшим, читаемым и проверяемым тестами.

## Реальная эксплуатация как acceptance test

Первая рабочая эксплуатация является обязательным acceptance-сценарием продукта.

Универсализация считается неудачной, если ради абстрактной переносимости продукт перестаёт полноценно закрывать реальную операционную работу: ответственность, очередь, исполнителя, сроки, ожидание, основания изменений, связанные предметные объекты, историю и необходимые дополнительные возможности.

Одновременно требование конкретной эксплуатации не должно автоматически становиться полем или механизмом Core. Сначала определяется самостоятельная ответственность, затем выбирается уровень реализации: данные `Site`, штатная настройка Frappe, отдельная capability или изменение Core.

## Критерий устойчивости

Архитектура считается устойчивой, если:

- новая структура компании не требует изменения Core;
- новый вид работы не требует изменения Core;
- новый тип предметного объекта не требует изменения Core;
- новый вид оборудования не требует изменения Work Item;
- новый специфический процесс добавляется локально;
- организация может использовать только нужные ей capabilities;
- рабочие данные и корпоративная структура остаются данными `Site` и не попадают в публичный репозиторий;
- обновление одной capability не заставляет переписывать несвязанные части приложения.

Это фундаментальное направление Work Management. Оно меняется только при появлении объективного противоречия, технической ошибки или новой ответственности, которую существующая граница действительно не может корректно выразить.
