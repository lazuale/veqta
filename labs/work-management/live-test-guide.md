# Управление работой v1: проверка на живом Frappe Site

Этот сценарий нужен для проверки текущей конфигурации управления работой на реальном Frappe v16 Site. Он не заменяет [Руководство по настройке](setup-guide.md): сначала Site настраивается по нему, затем выполняются проверки ниже.

Цель — отделить поведение, подтверждённое исходным кодом Frappe, от поведения, которое важно увидеть в реальном Desk и на реальных документах.

## Стенд

Используйте отдельный чистый Site без пользовательских Client Script, Server Script, hooks и изменений стандартного `ToDo`.

Интерфейс тестовых пользователей должен быть переключён на `Russian (ru)`.

Нужны три тестовых пользователя:

```text
work-a@example.test  — Work User
work-b@example.test  — Work User
plain@example.test   — обычный System User без Work User и без административных ролей
```

Административную настройку выполняет `Administrator` или пользователь с необходимыми штатными административными ролями.

Перед началом настройте Site полностью по [Руководству по настройке](setup-guide.md), включая записи `Translation`.

## 1. Русский интерфейс

Под `work-a@example.test` проверьте отображение пользовательских элементов.

Ожидается:

```text
Work Item → Работа
Low       → Низкий
Medium    → Средний
High      → Высокий
```

Проверьте также, что у `Work Item` видны русские метки:

```text
Название
Описание
Статус
Приоритет
Срок
Связи
```

Технические fieldname и значения `priority` в данных при этом не меняются.

## 2. Общая очередь

Под `work-a@example.test` создайте:

```text
Название: Проверка общей очереди
Статус: Открыто
Приоритет: Средний
Срок: пусто
```

Под `work-b@example.test` откройте список работ.

Проверьте:

- документ виден второму `Work User`;
- документ попадает в `Открытые`;
- документ попадает в `Активные`;
- документ попадает в `Без исполнителя`.

## 3. Самоназначение

Под `work-b@example.test` откройте созданный Work Item и выполните:

```text
Assign To
→ Assign to me
```

Проверьте:

- `Work Item.status` остаётся `Открыто`;
- создаётся связанный `ToDo`;
- Work Item исчезает из `Без исполнителя`;
- Work Item находится через `Assigned To → Me` под `work-b@example.test`.

## 4. Ожидание

Под `work-b@example.test` добавьте комментарий:

```text
Ожидаем внешний ответ.
```

Переведите:

```text
Открыто → Ожидание
```

Проверьте:

- Work Item появляется в фильтре `Ожидание`;
- назначение остаётся активным;
- комментарий остаётся в Timeline;
- Work Item больше не считается открытым.

Затем верните:

```text
Ожидание → Открыто
```

Проверьте, что существующее назначение сохраняется.

## 5. Завершение

Под `work-b@example.test` закройте собственное назначение.

Проверьте, что Work Item сам не становится `Закрыто`.

Затем вручную переведите Work Item в:

```text
Закрыто
```

Проверьте:

- Work Item исчезает из `Активные`;
- Work Item не появляется в `Открытые` и `Ожидание`;
- закрытие Work Item не создаёт новой автоматической операции над уже закрытым ToDo.

## 6. Отмена

Создайте новый Work Item и назначьте его `work-a@example.test`.

Снимите назначение, затем установите:

```text
Отменено
```

Проверьте:

- документ сохраняется;
- документ не входит в `Активные`;
- удаление Work Item для обычного `Work User` недоступно.

## 7. Несколько исполнителей

Создайте новый Work Item и назначьте одновременно:

```text
work-a@example.test
work-b@example.test
```

Проверьте:

- создаются два отдельных `ToDo`;
- каждый пользователь видит своё назначение;
- закрытие назначения одного пользователя не закрывает назначение другого;
- `Work Item.status` от этого автоматически не меняется.

## 8. Граница прав

Под `plain@example.test` попробуйте открыть список Work Item и прямой URL существующего Work Item.

Проверьте, что обычный System User без `Work User` и без административной роли не получает прикладной доступ к Work Item.

Отдельно убедитесь, что штатный административный доступ `Administrator` / `System Manager` не был удалён при настройке DocType.

## 9. Снятие чужого назначения

Создайте Work Item, назначенный `work-a@example.test`.

Под `work-b@example.test`, который также имеет `Work User`, попробуйте снять назначение `work-a@example.test`.

Проверьте фактическое поведение Desk и документа. Текущая модель допускает, что пользователь с `Write` на общей очереди может снять чужое назначение; этот сценарий важно подтвердить на живом Site.

## 10. Сроки

Создайте Work Item со сроком на текущую дату.

Проверьте:

- он попадает в Number Card `Срок сегодня`;
- он отображается в `Работы по сроку`;
- shortcut `Календарь` в Workspace открывает именно этот именованный Calendar View;
- Work Item без `due_date` не отображается как календарное событие.

Не используйте `ToDo.date` как критерий этой проверки.

## 11. Kanban

Откройте Kanban Board `Работы`.

Проверьте, что колонки имеют русские имена:

```text
Открыто
Ожидание
Закрыто
Отменено
```

Перетащите тестовый Work Item:

```text
Открыто → Ожидание
Ожидание → Открыто
```

Проверьте, что изменяется реальное поле `Work Item.status` и изменение видно после повторного открытия документа.

Дополнительно подтвердите, что перенос в `Закрыто` сам по себе не закрывает активный `ToDo`.

## 12. Auto Repeat

Создайте отдельный тестовый Work Item:

```text
Название: Проверка Auto Repeat
Описание: Повторяющаяся тестовая работа
Статус: Открыто
Приоритет: Высокий
Срок: любая дата
Связи: добавьте одну тестовую связь
```

Техническое значение `priority` должно оставаться `High`.

Создайте для него Auto Repeat без Assignee.

После появления нового экземпляра проверьте:

```text
subject      → скопирован
description  → скопирован
priority     → High, в интерфейсе Высокий
status       → Открыто
due_date     → пусто
links        → пусто
назначение   → отсутствует
```

Если для проверки пришлось ждать расписание, не меняйте модель ради ускорения теста: используйте минимальную штатную частоту или отдельный временный тестовый документ.

## 13. Workspace и аналитика

Под `work-a@example.test` откройте Workspace `Управление работой`.

Проверьте:

- `Новая работа` открывает создание документа;
- `Список работ` открывает List View;
- `Доска` открывает Kanban Board `Работы`;
- `Календарь` открывает `Работы по сроку`;
- Number Cards `Активные работы`, `Ожидание`, `Без исполнителя`, `Высокий приоритет`, `Срок сегодня` показывают значения, совпадающие с текущими тестовыми документами;
- клик по Number Card открывает отфильтрованный список;
- графики `Активные по статусу`, `Активные по приоритету` и `Новые работы` отображаются без ошибок.

## Что фиксировать как результат лаборатории

После фактического прогона в документацию переносятся только наблюдаемые отклонения от описанной модели или подтверждённые важные особенности Frappe.

Для каждого отклонения достаточно четырёх фактов:

```text
сценарий
что ожидалось по текущей модели
что фактически произошло
влияет ли это на архитектуру или только на инструкцию
```

Если фактическое поведение совпадает с текущей моделью, отдельный отчёт ради самого факта прохождения не нужен. Если выявлено расхождение, сначала исправляется соответствующая документация или конфигурация; собственный код рассматривается только если штатный Frappe действительно не закрывает требуемую ответственность.
