# R01. Модель управляемой работы

Первое исследование Work Management начинается не с Workflow, Kanban или отчётов, а с самой модели данных.

Вопрос:

> Что в управляемой работе является самостоятельными данными, что достаточно хранить как поле `Work Item`, а что Frappe уже предоставляет как системное состояние `Document`?

## Почему недостаточно просто выбрать поля

Frappe даёт несколько технически допустимых способов выразить одно и то же пользовательское понятие.

Например, тип работы можно хранить как:

```text
Select
```

или как:

```text
Link → Work Type
```

Оба варианта штатные. `Select` хранит одно значение из списка, заданного в metadata DocType. `Link` связывает Document с записью другого DocType.

Документация объясняет механику этих полей, но выбор между ними зависит от смысла данных: является ли тип работы частью структуры приложения или самостоятельными данными, которыми нужно управлять на Site.

Первичные источники:

- https://docs.frappe.io/framework/user/en/basics/doctypes
- https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes
- https://docs.frappe.io/framework/user/en/tutorial/types-of-doctype
- https://docs.frappe.io/framework/user/en/basics/doctypes/naming

Контрольная версия эксперимента — **Frappe Framework v16.33.0**.

## Границы исследования

На R01 не добавляются:

```text
status
Workflow
Assign To
assignee
priority
SLA
история переходов
KPI
агрегаты
отчёты
Kanban
```

У этих данных пока нет самостоятельного требования.

R01 должен сначала получить устойчивый объект, на который смогут опираться следующие исследования.

## Что Frappe уже хранит у Document

Для обычного DocType Framework создаёт системные поля, среди которых:

```text
name
creation
modified
modified_by
owner
docstatus
```

Поэтому в модель Work Item не добавляются дублирующие поля вроде:

```text
created_at
updated_at
created_by
internal_id
```

пока не появится отдельный предметный смысл, отличный от системных полей Frappe.

Документация Frappe показывает, что `name` является первичным ключом Document, а стандартные поля создаются Framework автоматически.

## Что считаем управляемой работой на R01

Минимальная единица работы должна иметь:

```text
стабильную идентичность
человекочитаемое название
тип работы
```

Название не используется как идентификатор: пользователь может исправить формулировку работы без смены ссылки на сам Work Item.

Для Work Item используется отдельное имя Document:

```text
WORK-.#####
```

а отображаемый текст хранится в поле:

```text
title
```

Это разделяет:

```text
identity
≠
display value
```

## Вариант A — тип как Select

Первая реализация содержит один DocType:

```text
Work Item Select
├── title      Data, required
└── work_type  Select, required
```

Options:

```text
TASK
CHECK
```

Здесь множество допустимых типов является частью metadata `Work Item Select`.

Нужно проверить на живом Site:

1. создание нескольких Work Item;
2. изменение отображаемого набора типов;
3. добавление нового типа `REQUEST`;
4. что именно меняется в App при изменении списка `Select`;
5. что происходит с уже сохранёнными значениями при изменении Options.

Главный вопрос варианта:

> Подходит ли `Select`, если тип работы должен восприниматься как конфигурация самого приложения?

## Вариант B — тип как самостоятельный Document

Вторая реализация содержит:

```text
Work Type
├── code   Data, required, unique
└── title  Data, required

Work Item Link
├── title      Data, required
└── work_type  Link → Work Type, required
```

Для `Work Type` используется:

```text
name = code
```

а `title` остаётся отображаемым названием.

Пример:

```text
TASK   → Задача
CHECK  → Проверка
```

Нужно проверить:

1. создание типов как обычных Documents;
2. создание Work Item со ссылкой на тип;
3. изменение `title` у существующего `Work Type` без изменения его `code`;
4. добавление `REQUEST` без изменения metadata `Work Item`;
5. поведение ссылки при попытке удалить используемый `Work Type`;
6. отображение title и сохранённого значения Link;
7. какие изменения относятся к App, а какие остаются данными конкретного Site.

Главный вопрос варианта:

> Подходит ли отдельный DocType, если тип работы должен иметь собственную идентичность и жить как данные Site?

## Отдельно проверить идентичность Work Item

В обеих реализациях создать Work Item и затем изменить его `title`.

Нужно убедиться, что:

```text
name Work Item не меняется
Link на Work Item остаётся стабильным
изменяется только отображаемый title
```

Это проверяет практическую границу между системным идентификатором и пользовательским названием.

## Что сравнивать

Сравнение должно опираться не на количество кликов, а на семантику модели.

### Select

Проверяем:

```text
тип является частью metadata приложения?
набор значений мал и стабилен?
у типа нет собственных атрибутов?
изменение набора типов должно поставляться вместе с App?
```

### Link

Проверяем:

```text
тип имеет самостоятельную идентичность?
ему нужен отдельный title?
его записи должны существовать как данные Site?
тип может получить собственные атрибуты позже по реальному требованию?
нужна обычная ссылочная целостность между Work Item и типом?
```

## Что не является аргументом

Отдельный `Work Type` не выбирается только потому, что "справочник выглядит правильнее".

`Select` не выбирается только потому, что у него меньше таблиц.

Решение должно следовать из ответственности данных.

## Какой результат должен дать R01

После выполнения эксперимента нужно зафиксировать четыре вещи:

1. какой вариант используется для `Work Type` и почему;
2. какие поля действительно принадлежат `Work Item`;
3. какие данные уже предоставляет Frappe и не должны дублироваться;
4. какие данные принадлежат App, а какие — конкретному Site.

Только после этого можно переходить к следующему вопросу карты Labs: какие операции и ответственность появляются вокруг уже определённого Work Item.
