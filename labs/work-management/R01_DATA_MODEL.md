# R01. Модель управляемой работы

Первое исследование Work Management начинается не с Workflow, Kanban или отчётов, а с самой модели данных.

Вопрос:

> Что в управляемой работе является самостоятельными данными, что достаточно хранить как поле `Work Item`, а что Frappe уже предоставляет как системные свойства `Document`?

R01 не ищет «самую красивую схему». Он сравнивает две штатные модели Frappe на одинаковом наборе данных и фиксирует, какая семантика подходит предметной области.

Контрольная версия — **Frappe Framework v16.33.0**.

Первичные источники:

- https://docs.frappe.io/framework/user/en/basics/doctypes
- https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes
- https://docs.frappe.io/framework/user/en/basics/doctypes/naming
- https://docs.frappe.io/framework/user/en/basics/doctypes/form_%26_view_settings
- https://docs.frappe.io/framework/user/en/tutorial/create-a-doctype
- https://docs.frappe.io/framework/user/en/tutorial/types-of-doctype

## Границы исследования

На R01 не добавляются:

```text
status
Workflow
Assign To
assignee
priority
SLA
история переходов
KPI
агрегаты
отчёты
Kanban
```

У этих данных пока нет самостоятельного требования. Сначала нужен устойчивый объект, на который смогут опираться следующие исследования.

## Что уже является фактом Frappe

Эти вещи не нужно «доказывать» экспериментом.

Для обычного DocType Framework создаёт `Document` с системными полями, включая:

```text
name
creation
modified
modified_by
owner
docstatus
```

`name` является первичным ключом Document. Поэтому в `Work Item` не вводятся дублирующие `internal_id`, `created_at`, `updated_at` или `created_by`, пока не появится отдельный предметный смысл.

`Select` хранит значение из списка Options, заданного в metadata поля.

`Link` связывает поле с Document другого DocType. Для связанной сущности можно отдельно задать `Title Field` и включить отображение title в Link fields, не меняя сохранённый `name` связанного Document.

Удаление обычного Document, на который ссылается живой Link, Framework проверяет на наличие входящих ссылок и без специального обхода не разрешает такое удаление.

R01 исследует не эти механики, а предметный вопрос:

> `Work Type` — это часть структуры приложения или самостоятельные данные?

## Минимальная единица работы

На R01 единице управляемой работы нужны только:

```text
стабильная идентичность
человекочитаемое название
тип работы
```

Название не используется как идентификатор: формулировка работы может быть исправлена без смены ссылки на сам объект.

Для обеих экспериментальных реализаций используется независимое имя Document по шаблону:

```text
WORK-.#####
```

и отдельное поле:

```text
title
```

То есть:

```text
identity
≠
display value
```

Одинаковый naming pattern у двух экспериментальных DocTypes допустим: `name` уникален внутри конкретного DocType. После выбора модели останется только один итоговый `Work Item`.

## Вариант A — тип как Select

Первая реализация содержит один Standard DocType:

```text
Work Item Select
├── title      Data, required
└── work_type  Select, required
```

Настройки:

```text
Autoname    : WORK-.#####
Title Field : title
```

Options:

```text
TASK
CHECK
```

Здесь множество типов принадлежит metadata `Work Item Select`.

Гипотеза A:

> Такая модель подходит, если набор типов мал, стабилен, не имеет собственных атрибутов и должен изменяться вместе с версией App.

## Вариант B — тип как самостоятельный Document

Вторая реализация содержит два Standard DocType:

```text
Work Type
├── code   Data, required, unique
└── title  Data, required

Work Item Link
├── title      Data, required
└── work_type  Link → Work Type, required
```

Настройки `Work Type`:

```text
Autoname                  : field:code
Title Field               : title
Show Title in Link Fields : yes
```

Настройки `Work Item Link`:

```text
Autoname    : WORK-.#####
Title Field : title
```

Контрольные записи:

```text
TASK   → Задача
CHECK  → Проверка
```

Гипотеза B:

> Такая модель подходит, если тип работы имеет собственную идентичность и должен существовать как управляемые данные Site, независимо от metadata `Work Item`.

## Стенд

Эксперимент выполняется в отдельном App и Site, чтобы изменения модели не смешивались с учебными приложениями VEQTA Learn.

Рекомендуемые имена:

```text
App  : work_management_lab
Site : work-management.localhost
```

Если совместимый Bench уже существует, новый Bench создавать не нужно.

Проверить версию:

```bash
bench version
```

На контрольном стенде ожидается:

```text
frappe 16.33.0
```

Создать App и Site обычными командами Bench:

```bash
bench new-app work_management_lab
bench new-site work-management.localhost
bench --site work-management.localhost install-app work_management_lab
```

Включить Developer Mode для стенда и перезапустить процессы Bench. Standard DocTypes нужно создавать внутри `work_management_lab`, чтобы их metadata появились в исходниках App, а не как случайная site customization.

Официальный tutorial Frappe использует Developer Mode именно для генерации и отслеживания файлов Standard DocType в App.

Перед экспериментом:

```bash
git -C apps/work_management_lab status --short
```

Рабочее дерево должно быть чистым.

## Эксперимент A — Select

### 1. Создать модель

В Desk создать Standard DocType `Work Item Select` с полями и настройками варианта A.

После сохранения проверить исходники:

```bash
git -C apps/work_management_lab status --short
```

В App должен появиться обычный набор файлов Standard DocType, включая его JSON metadata.

Зафиксировать исходное состояние Git отдельным commit, чтобы последующие изменения Options были видны как самостоятельный diff.

### 2. Создать одинаковые данные

Создать две записи:

```text
Подготовить недельный отчёт → TASK
Проверить исходные данные   → CHECK
```

Сохранить их `name`.

### 3. Изменить только title

У первой записи изменить:

```text
Подготовить недельный отчёт
→
Подготовить отчёт за неделю
```

Проверить:

```text
name до изменения
name после изменения
```

Они должны совпасть. Это не выбор между A и B, а проверка принятого разделения identity и title.

### 4. Добавить REQUEST

В metadata `work_type` добавить:

```text
REQUEST
```

Сохранить DocType и посмотреть:

```bash
git -C apps/work_management_lab diff
```

Зафиксировать, где именно появилось новое значение.

После этого создать:

```text
Запросить исходные документы → REQUEST
```

### 5. Удалить CHECK из Options

Временно убрать `CHECK` из Options, не удаляя существующий Work Item со значением `CHECK`.

Проверить отдельно:

```text
открывается ли существующий Document
что отображается в поле
можно ли сохранить Document без смены значения
какую ошибку возвращает Framework, если значение больше не входит в текущие Options
```

Это важная эксплуатационная характеристика Select: изменение metadata и уже сохранённые бизнес-данные могут жить в разных моментах времени.

После наблюдения вернуть `CHECK`, чтобы не оставлять экспериментальный App в заведомо повреждённом состоянии.

## Эксперимент B — Link

### 1. Создать модель

Создать Standard DocTypes `Work Type` и `Work Item Link` с настройками варианта B.

Зафиксировать metadata App отдельным commit.

### 2. Создать Work Type как данные

В Desk создать:

```text
code=TASK   title=Задача
code=CHECK  title=Проверка
```

После этого выполнить:

```bash
git -C apps/work_management_lab status --short
```

Нужно зафиксировать наблюдение: изменился ли репозиторий App от создания обычных `Work Type` records.

### 3. Создать те же Work Item

Создать:

```text
Подготовить недельный отчёт → TASK
Проверить исходные данные   → CHECK
```

Сохранить `name` обеих записей.

### 4. Изменить отображаемое название Work Type

У `TASK` изменить:

```text
Задача
→
Работа
```

Проверить:

```text
name Work Type = TASK
сохранённое значение work_type у Work Item = TASK
отображаемый текст Link после reload
```

Изменение title не должно требовать изменения идентификатора связанной записи.

### 5. Добавить REQUEST без изменения Work Item metadata

Создать обычную запись:

```text
code=REQUEST
 title=Запрос
```

Проверить Git App и затем создать:

```text
Запросить исходные документы → REQUEST
```

Ключевое наблюдение:

```text
нужно ли было изменять metadata Work Item Link
или достаточно было добавить новый Work Type Document
```

### 6. Проверить ссылочную целостность

Попытаться удалить `Work Type = TASK`, пока на него ссылается `Work Item Link`.

Не использовать `force`, raw SQL или другие способы обхода штатной проверки.

Зафиксировать фактический отказ Framework и связанную запись, которая блокирует удаление.

## App-owned и Site-owned

После двух экспериментов сравнить Git и данные Site.

Нужно разделить:

```text
структура DocType / поля / Select Options
→ metadata App

созданные Work Item records
→ данные Site

созданные Work Type records
→ данные Site, пока отдельное требование не сделает их обязательным состоянием App
```

Последний пункт принципиален: наличие отдельного master DocType ещё не означает, что конкретные `TASK`, `CHECK` и `REQUEST` автоматически должны поставляться приложением. Если позже эти записи окажутся обязательным состоянием App, способ их воспроизводимой доставки станет отдельным техническим решением.

## Сравнение

Результат оценивается по семантике, а не по количеству кликов или таблиц.

| Вопрос | Select | Link → Work Type |
| --- | --- | --- |
| Где живёт набор допустимых типов? | проверить metadata | проверить records |
| Нужно ли менять App для нового типа? | проверить | проверить |
| Есть ли у типа самостоятельный `name`? | нет отдельного Document | проверить |
| Можно ли менять отображаемый title отдельно от идентификатора типа? | отдельного объекта нет | проверить |
| Что происходит со старым значением после изменения набора типов? | проверить | не тот механизм |
| Что происходит при удалении используемого типа? | не тот механизм | проверить Link protection |
| Что меняется в Git? | проверить | проверить |

Таблица не является оценкой «победитель по количеству плюсов». Она нужна, чтобы увидеть разницу ответственности данных.

## Критерий выбора

`Select` выбирается, если исследование подтверждает такую ответственность:

```text
тип — часть схемы приложения
набор мал и стабилен
у типа нет собственной жизни
изменение набора поставляется как изменение App
```

`Link → Work Type` выбирается, если подтверждается другая ответственность:

```text
тип — самостоятельная сущность
имеет стабильный идентификатор и отображаемое название
набор управляется данными Site
добавление типа не требует изменения Work Item metadata
нужна обычная ссылочная целостность
```

Не являются аргументами сами по себе:

```text
«справочник архитектурно красивее»
«Select проще»
«меньше таблиц лучше»
«больше нормализации правильнее»
```

4. что остаётся системными данными Frappe;
