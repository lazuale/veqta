# R01. Модель управляемой работы

R01 — первый эксперимент Work Management Lab. Он проверяет минимальную модель данных для единицы управляемой работы на Frappe Framework.

Эксперимент должен быть понятен и воспроизводим без знания предыдущих обсуждений VEQTA. Достаточно иметь рабочий Frappe Bench, доступ к Desk и терминалу.

## Вопрос исследования

Нужно определить, чем в модели должен быть **тип работы**:

```text
вариант A
Work Item
└── work_type: Select

вариант B
Work Type
└── Work Item
    └── work_type: Link → Work Type
```

Оба варианта штатно поддерживаются Frappe. Исследование не ищет вариант с меньшим числом полей или кликов. Оно отвечает на предметный вопрос:

> `Work Type` — часть metadata приложения или самостоятельные данные, которыми управляют на Site?

Одновременно проверяется минимальная модель самого `Work Item`: стабильный идентификатор, отображаемое название и тип работы.

## Что не входит в R01

На этом этапе не добавляются:

```text
status
Workflow
Assign To
assignee
priority
SLA
история переходов
KPI
агрегаты
отчёты
Kanban
```

Эти ответственности относятся к следующим исследованиям. R01 должен сначала получить устойчивую модель объекта.

## Что уже известно из Frappe

Эти свойства Framework не являются результатом эксперимента.

Обычный DocType создаёт `Document` с системными полями, включая `name`, `creation`, `modified`, `modified_by`, `owner` и `docstatus`. `name` является идентификатором Document, поэтому отдельные `internal_id`, `created_at`, `updated_at` и `created_by` в R01 не вводятся.

`Select` хранит значение из списка Options, заданного в metadata поля.

`Link` связывает поле с Document другого DocType. Связанный DocType может иметь отдельный `Title Field`; Frappe умеет показывать этот title в Link field, сохраняя в ссылке `name` Document.

Standard DocType, созданный в Developer Mode внутри App, сохраняет metadata в файлы App. Для этого при создании DocType нельзя оставлять его как Custom.

Источники:

- https://docs.frappe.io/framework/user/en/basics/doctypes
- https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes
- https://docs.frappe.io/framework/user/en/basics/doctypes/naming
- https://docs.frappe.io/framework/user/en/basics/doctypes/form_%26_view_settings
- https://docs.frappe.io/framework/user/en/tutorial/create-a-doctype
- https://docs.frappe.io/framework/user/en/tutorial/types-of-doctype

Контрольная версия эксперимента — **Frappe Framework v16.33.0**.

# 1. Что понадобится

Нужны:

- Frappe Bench с Frappe v16.33.0;
- доступ к терминалу в каталоге Bench;
- браузер и вход в Desk как `Administrator`;
- Git;
- отдельный App и Site для эксперимента.

Рекомендуемые имена:

```text
App  : work_management_lab
Site : work-management.localhost
```

Отдельный Bench не нужен, если уже есть совместимый Bench, где можно безопасно создать экспериментальный Site.

## Проверить версию

Из корня Bench выполнить:

```bash
bench version
```

Для контрольного прогона должна использоваться:

```text
frappe 16.33.0
```

Если версия отличается, её нужно записать вместе с результатами. Результат другой версии нельзя автоматически считать результатом контрольного прогона R01.

# 2. Подготовить чистый стенд

Если App ещё не создан:

```bash
bench new-app work_management_lab
```

Если Site ещё не создан:

```bash
bench new-site work-management.localhost
```

Установить App:

```bash
bench --site work-management.localhost install-app work_management_lab
```

Включить Developer Mode:

```bash
bench set-config -g developer_mode true
bench --site work-management.localhost clear-cache
```

Если Bench запущен через `bench start`, перезапустить процесс после изменения конфигурации.

Открыть:

```text
http://work-management.localhost:8000
```

и войти как `Administrator`.

## Проверить исходное состояние App

Из корня Bench:

```bash
git -C apps/work_management_lab status --short
```

Перед созданием экспериментальных DocTypes должно быть понятно, какие изменения уже есть в App. Лучше начинать с чистого рабочего дерева, чтобы изменения metadata R01 не смешивались с другими изменениями.

# 3. Общие данные для сравнения

Оба варианта должны использовать одинаковые смысловые данные.

Типы работы:

| Код | Название |
| --- | --- |
| `TASK` | Задача |
| `CHECK` | Проверка |
| `REQUEST` | Запрос |

Работы:

| Название | Тип |
| --- | --- |
| Подготовить недельный отчёт | `TASK` |
| Проверить исходные данные | `CHECK` |
| Запросить исходные документы | `REQUEST` |

Первые две работы создаются сразу. `REQUEST` добавляется позже в каждом варианте — это часть эксперимента.

Для Work Item используется отдельный технический `name` по шаблону:

```text
WORK-.#####
```

и пользовательское поле:

```text
title
```

Таким образом проверяется разделение:

```text
identity
≠
display value
```

# 4. Эксперимент A — `Select`

## 4.1. Создать Standard DocType

В Desk:

1. открыть `DocType List` через поиск;
2. нажать `New`;
3. создать DocType `Work Item Select`;
4. выбрать module экспериментального App `work_management_lab`;
5. убедиться, что DocType создаётся как Standard, а не Custom;
6. добавить поля из таблицы ниже.

| Label | Fieldname | Field Type | Mandatory | Options |
| --- | --- | --- | --- | --- |
| Title | `title` | Data | yes | — |
| Work Type | `work_type` | Select | yes | `TASK` и `CHECK` |

Настройки DocType:

```text
Autoname    : WORK-.#####
Title Field : title
```

Сохранить DocType.

## 4.2. Убедиться, что metadata попали в App

В терминале:

```bash
git -C apps/work_management_lab status --short
```

Открыть созданный JSON DocType и убедиться, что `work_type` действительно содержит Options:

```text
TASK
CHECK
```

Зафиксировать текущее состояние App отдельным Git commit либо иным способом, который позволит увидеть следующий diff только от изменения Options.

### Что записать

- путь к JSON `Work Item Select`;
- исходные Options `work_type`;
- вывод `git status --short` после создания DocType.

## 4.3. Создать первые две работы

В `Work Item Select` создать:

```text
Подготовить недельный отчёт → TASK
Проверить исходные данные   → CHECK
```

Для каждой записи записать фактический `name`, присвоенный Frappe.

Ожидаемый формат:

```text
WORK-00001
WORK-00002
```

Номера могут отличаться. Важен сам факт отдельного стабильного `name`.

## 4.4. Проверить `name` и `title`

Открыть первую работу и записать её `name`.

Изменить:

```text
Подготовить недельный отчёт
```

на:

```text
Подготовить отчёт за неделю
```

Сохранить и перезагрузить Document.

Записать:

```text
name до изменения:
name после изменения:
title после изменения:
```

Цель проверки — убедиться на живом Site, что изменение пользовательского названия не меняет identity Work Item.

## 4.5. Добавить новый тип `REQUEST`

Открыть metadata `Work Item Select` и добавить в Options поля `work_type`:

```text
REQUEST
```

Сохранить DocType.

В терминале выполнить:

```bash
git -C apps/work_management_lab diff
```

Записать:

- какой файл изменился;
- какое изменение появилось в diff;
- понадобилось ли создавать отдельный Document для нового типа.

После этого создать:

```text
Запросить исходные документы → REQUEST
```

## 4.6. Проверить уже сохранённое значение после изменения Options

В `Work Item Select` существует работа:

```text
Проверить исходные данные → CHECK
```

Теперь временно удалить `CHECK` из Options поля `work_type` и сохранить DocType.

Не менять и не удалять сам Work Item.

После reload проверить последовательно:

1. открывается ли существующий Work Item;
2. что отображается в `work_type`;
3. можно ли сохранить Document без изменения `work_type`;
4. если Frappe запрещает сохранение — записать точный текст ошибки;
5. можно ли выбрать `CHECK` для новой записи после удаления его из Options.

Не предполагать результат заранее: записывается только фактически наблюдаемое поведение.

После проверки вернуть `CHECK` в Options и сохранить DocType.

## Результат варианта A

После ручного прогона должны быть заполнены фактические ответы:

| Проверка | Наблюдение |
| --- | --- |
| Где хранится набор типов | |
| Что изменилось в Git при добавлении `REQUEST` | |
| Нужен ли отдельный Document для нового типа | |
| Что произошло со старым `CHECK` после удаления из Options | |
| Изменился ли `name` Work Item при смене `title` | |

# 5. Эксперимент B — `Link → Work Type`

## 5.1. Создать `Work Type`

В Desk создать Standard DocType `Work Type` в module экспериментального App.

Поля:

| Label | Fieldname | Field Type | Mandatory | Дополнительно |
| --- | --- | --- | --- | --- |
| Code | `code` | Data | yes | Unique |
| Title | `title` | Data | yes | — |

Настройки:

```text
Autoname                  : field:code
Title Field               : title
Show Title in Link Fields : yes
```

Сохранить DocType.

## 5.2. Создать `Work Item Link`

Создать Standard DocType `Work Item Link`.

Поля:

| Label | Fieldname | Field Type | Mandatory | Options |
| --- | --- | --- | --- | --- |
| Title | `title` | Data | yes | — |
| Work Type | `work_type` | Link | yes | `Work Type` |

Настройки:

```text
Autoname    : WORK-.#####
Title Field : title
```

Сохранить DocType.

## 5.3. Зафиксировать metadata модели

В терминале:

```bash
git -C apps/work_management_lab status --short
```

Убедиться, что в App появились metadata обоих Standard DocTypes.

Зафиксировать состояние так, чтобы последующее создание обычных records можно было отличить от изменения исходников App.

## 5.4. Создать первые два `Work Type`

В Desk создать:

```text
code=TASK
 title=Задача

code=CHECK
 title=Проверка
```

После создания записей выполнить:

```bash
git -C apps/work_management_lab status --short
```

Записать фактический результат: появились ли изменения в Git только от создания обычных `Work Type` records.

## 5.5. Создать те же две работы

В `Work Item Link` создать:

```text
Подготовить недельный отчёт → TASK
Проверить исходные данные   → CHECK
```

Записать `name` обеих работ.

## 5.6. Изменить title связанного типа

Открыть `Work Type`:

```text
name = TASK
```

Изменить:

```text
Задача
```

на:

```text
Работа
```

Сохранить запись.

Перезагрузить Work Item, который ссылается на `TASK`.

Записать:

```text
name Work Type:
сохранённое значение work_type:
что показывает Link field пользователю:
```

Цель — увидеть на живом Site, отделены ли identity типа и его отображаемое название так, как предполагала модель.

## 5.7. Добавить `REQUEST` как обычные данные

Создать:

```text
code=REQUEST
 title=Запрос
```

После создания выполнить:

```bash
git -C apps/work_management_lab status --short
```

Не изменяя metadata `Work Item Link`, создать:

```text
Запросить исходные документы → REQUEST
```

Записать:

- пришлось ли менять DocType;
- изменился ли Git;
- достаточно ли было создать новый `Work Type` Document.

## 5.8. Проверить удаление используемого типа

Убедиться, что существует Work Item со ссылкой:

```text
work_type = TASK
```

Открыть `Work Type = TASK` и попытаться удалить его обычной командой Desk.

Не использовать raw SQL, `force` и другие способы обхода Framework.

Записать:

- удалось ли удалить `TASK`;
- точный текст сообщения Frappe;
- какую связанную запись показывает сообщение, если показывает.

## Результат варианта B

После ручного прогона заполнить:

| Проверка | Наблюдение |
| --- | --- |
| Где хранится набор типов | |
| Изменился ли Git при создании `REQUEST` | |
| Понадобилось ли менять metadata `Work Item Link` | |
| Можно ли менять title типа без смены его `name` | |
| Что произошло при удалении используемого типа | |

# 6. Сравнить App-owned и Site-owned состояние

После обоих экспериментов нужно ответить не по предположению, а по фактическому стенду:

| Объект | Где обнаружено состояние |
| --- | --- |
| структура `Work Item Select` | |
| Options `work_type` у `Work Item Select` | |
| структура `Work Type` | |
| структура `Work Item Link` | |
| записи `TASK`, `CHECK`, `REQUEST` | |
| созданные Work Item records | |

Важно различать две вещи:

```text
существование DocType Work Type
```

и:

```text
существование конкретных records TASK / CHECK / REQUEST
```

То, что App поставляет DocType, само по себе ещё не означает, что он поставляет конкретные записи этого DocType.

# 8. Критерий архитектурного вывода

`Select` соответствует модели, если после эксперимента предметное требование можно честно сформулировать так:

```text
тип работы — часть схемы приложения;
набор мал и стабилен;
у типа нет собственной identity и отдельных атрибутов;
изменение набора типов является изменением App.
```

`Link → Work Type` соответствует модели, если требование выглядит иначе:

```text
тип работы — самостоятельная сущность;
у типа есть стабильная identity и отдельное отображаемое название;
набор типов управляется как данные Site;
новый тип не требует изменения схемы Work Item.
```

Нельзя выбирать `Work Type` только потому, что «справочник архитектурно красивее». Нельзя выбирать `Select` только потому, что он проще.
