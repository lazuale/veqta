# VEQTA — разработка

## Frappe baseline

VEQTA разрабатывается на актуальной stable-линии Frappe v16. На 2026-08-29 проверена версия `v16.32.0`.

Перед стендом или решением, зависящим от поведения Framework, версия проверяется повторно.

Порядок источников:

1. официальная документация Frappe;
2. исходники `frappe/frappe` используемой версии;
3. release / migration notes;
4. официальные issues и PR при необходимости.

Функция из `develop` не считается доступной, пока она не вошла в используемую stable-линию.

## Frappe first

Перед добавлением собственного механизма проверяется по порядку:

1. умеет ли это используемый Frappe;
2. можно ли решить задачу штатной конфигурацией;
3. относится ли требование к текущей модели VEQTA;
4. нарушается ли обязательное свойство текущего prototype без собственного кода.

Собственный механизм не создаётся до подтверждённого ограничения штатного Frappe.

## Site → Git

Локальный site — среда разработки. Repository — состояние продукта.

```text
Desk / код
    ↓
файлы app или штатный экспорт конфигурации
    ↓
git diff
    ↓
commit
    ↓
push
```

Для стандартных DocType используется Developer Mode. DB-backed конфигурация переносится в app штатным механизмом Frappe.

Контрольный критерий:

```text
чистый совместимый Frappe site
+ lazuale/veqta
+ install-app / migrate
= согласованное состояние VEQTA
```

## Git hygiene

Коммитим только то, что относится к текущему коду, конфигурации, тестам и документации VEQTA.

Не коммитим:

- весь Bench и исходники Frappe;
- локальные БД и dumps;
- `site_config.json` и секреты;
- пароли и private SSH keys;
- пользовательские данные стенда, если они не являются тестовыми fixtures.

Рабочий цикл:

```bash
cd ~/frappe/veqta-bench/apps/veqta
git status
git pull --ff-only origin main
```

После изменения:

```bash
git status
git diff
git add .
git diff --cached
git commit -m "Описание изменения"
git push origin main
```

## Scope hygiene

Рабочие документы содержат только:

- подтверждённые решения;
- модель и проверки текущего prototype;
- фактические результаты.

Будущие возможности не добавляются в README, `DECISIONS.md`, `MODEL_V0_1.md` или `PROTOTYPE_V0_1.md`, пока не входят в активную проверку. Если появится согласованная дорожная карта, она ведётся отдельно.

При чистке кода или документации действует консервативное правило:

1. сначала сравнить текущее состояние с Git history;
2. выделить уникальный смысл удаляемого фрагмента;
3. убедиться, что это история, дубль, неподтверждённая гипотеза или неактуальный материал;
4. отдельно проверить, не является ли фрагмент действующим инвариантом, требованием или тестом;
5. при сомнении не удалять до отдельной проверки.

Удаление не должно быть первым способом упрощения.
