# Work Management — эксперимент v0.1

Эксперимент проверяет, насколько далеко можно зайти с небольшой предметной моделью, используя штатные возможности Frappe для процесса вокруг неё.

Собственная модель описана в [`MODEL_V0_1.md`](MODEL_V0_1.md).

## Что проверяется

```text
собственные DocTypes
├── Work Type
└── Work Item

штатные механизмы Frappe
├── Workflow / Workflow State
├── Assign To / ToDo
├── Version / Timeline
├── Desk
└── Kanban
```

Для каждой проверки важен наблюдаемый результат: механизм либо выражает нужное поведение, либо обнаруживается конкретное ограничение.

## 1. Work Type и Work Item

Создаются два Standard DocType:

```text
Work Type
├── code
└── title

Work Item
├── title
└── work_type → Link → Work Type
```

Проверяется создание, изменение отображаемого названия `Work Type` и сохранение корректной ссылки из `Work Item`.

## 2. Workflow

Для `Work Item` настраивается один Workflow с двумя вариантами маршрута:

```text
TASK
New → In Progress → Done

CHECK
New → In Progress → Review → Done
```

Проверяется, достаточно ли Transition Conditions для того, чтобы один Workflow обслуживал оба вида работы и не разрешал переходы, которые не относятся к выбранному `Work Type`.

## 3. Assignment

Назначение пользователей выполняется через `Assign To`.

Проверяются:

- одно назначение;
- несколько одновременных назначений;
- снятие одного назначения без потери остальных;
- отображение назначений в стандартном интерфейсе.

Цель — понять, нужен ли `Work Item` отдельный предметный атрибут ответственного или штатной модели `ToDo` достаточно.

## 4. История состояния

После нескольких переходов Workflow проверяются `Version`, Timeline и связанные записи процесса.

Интерес представляют четыре значения:

```text
from_state
to_state
changed_by
changed_at
```

Если штатная история хранит их в форме, пригодной не только для просмотра человеком, но и для последующего анализа, отдельная таблица истории не нужна.

## 5. Desk и Kanban

`Work Item` открывается и изменяется через стандартный Desk.

Kanban проверяется отдельно, потому что изменение колонки не должно создавать обход серверных правил Workflow. Перетаскивание карточки должно приводить либо к корректному переходу, либо к отказу, если переход недопустим.

## 6. Воспроизводимость

Конфигурация, которая считается частью приложения, должна быть представлена в репозитории как код или штатно экспортируемая конфигурация Frappe.

Контрольный результат эксперимента:

```text
чистый совместимый Frappe Site
+ экспериментальный App из Git
+ install-app / migrate
= та же проверяемая модель и процесс
```

## Результат эксперимента

Этот Lab сохранён как исследование границы между небольшой собственной моделью и готовыми механизмами Frappe. Он не задаёт общую предметную модель VEQTA и сам по себе не является продуктом.
