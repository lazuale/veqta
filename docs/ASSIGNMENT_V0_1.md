# VEQTA — assignment v0.1

Статус: **рабочая гипотеза для прототипа, не замороженный контракт**.

Цель — определить, как использовать штатный Assignment Frappe без дублирования фактов и без создания собственного responsibility engine.

## 1. Проверенная база Frappe v16

Проверено для `version-16` / стабильной линии v16 на 2026-08-29 по официальной документации и исходникам `frappe/frappe`.

Штатный `Assign To`:

- создаёт отдельный `ToDo` для каждого назначенного пользователя;
- связывает `ToDo` с исходным документом через `reference_type` и `reference_name`;
- хранит пользователя в `allocated_to`;
- хранит состояние назначения в `status` (`Open`, `Closed`, `Cancelled`);
- хранит `assigned_by`;
- поддерживает несколько назначенных пользователей на один документ;
- поддерживает назначения через стандартный Desk UI.

Системный `_assign` исходного документа содержит JSON-представление назначенных для UI Frappe, но это не единственное место хранения назначения: первичные структурированные записи находятся в `ToDo`.

Официальные исходники:

- `frappe/desk/form/assign_to.py`;
- `frappe/desk/doctype/todo/todo.json`;
- `frappe/public/js/frappe/form/sidebar/assign_to.js`.

## 2. Почему `assigned_to` на Work Item пока НЕ добавляем

Frappe имеет специальное поведение: если целевой DocType содержит поле `assigned_to`, при каждом новом назначении туда записывается очередной пользователь.

Но штатный Assignment допускает несколько пользователей.

Следовательно:

- новое назначение перезаписывает одно Link-поле `assigned_to`;
- при закрытии или снятии assignment Frappe очищает `assigned_to`;
- при нескольких открытых ToDo одно поле `assigned_to` не может достоверно представить полную картину.

Поэтому использование `assigned_to` одновременно со штатным multiple assignment создаёт второй, потенциально противоречивый источник истины.

Это противоречит принципу VEQTA:

> **Один бизнес-факт — один источник истины.**

## 3. Рабочая гипотеза прототипа

В prototype v0.1:

- `Work Item` не получает отдельное поле `responsible` или `assigned_to`;
- используется штатный `Assign To`;
- источником данных о текущих назначениях являются открытые связанные `ToDo`;
- `_assign` рассматривается как системное представление Frappe для UI, а не как аналитический источник;
- не создаётся собственный Assignment UI;
- не создаётся отдельный Responsibility/Ownership DocType.

## 4. Что проверит прототип

Нужно проверить на живом Frappe v16:

1. насколько штатный Assign To удобен для реальной работы VEQTA;
2. достаточно ли стандартных фильтров и представлений для "назначено мне";
3. насколько удобно получать текущих назначенных через `ToDo` в Report/API/SQL;
4. нужен ли продукту принцип ровно одного ответственного вообще;
5. если один ответственный действительно нужен — можно ли минимально ограничить стандартный Assignment, не создавая свою подсистему.

## 5. Важное различие

`ToDo` Frappe не становится `Work Item` VEQTA.

Модель:

```text
Work Item
    │
    └── штатные Frappe Assignments / ToDo
```

`Work Item` остаётся бизнес-объектом работы.

`ToDo` используется как штатный инфраструктурный механизм назначения пользователей на этот объект.

## 6. Аналитика

Для аналитики назначений не требуется разбирать `_assign` JSON.

Структурированные поля `ToDo` уже содержат:

```text
allocated_to
reference_type
reference_name
status
assigned_by
creation
modified
```

Если позднее понадобится собственная бизнес-история ответственности, её необходимость должна быть доказана отдельно. Не создаём её заранее.

## 7. Что пока не создаём

- `responsible` в `Work Item`;
- `assigned_to` в `Work Item`;
- Responsibility Engine;
- RACI;
- Team Ownership;
- Role Ownership;
- Participants model;
- собственный Assignment UI;
- отдельную историю назначения.
