# Архитектурный паспорт второго учебного практикума Frappe

Статус: **черновик архитектуры для согласования**.

Этот практикум является второй отдельной ступенью после принятого [`docs/frappe-training`](../frappe-training/ARCHITECTURE_PASSPORT.md), но не продолжает его предметную область и не зависит от `rental_training`.

Нормативная база — [`docs/frappe-architecture-standard`](../frappe-architecture-standard/README.md). Если учебное решение конфликтует со стандартом, исправляется практикум.

---

# 1. Назначение второго практикума

Первый практикум отвечает на вопрос:

> **Как правильно построить собственную модель Frappe App?**

Второй отвечает на другой вопрос:

> **Как обычный Document превращается в управляемый бизнес-процесс и зафиксированный транзакционный факт, не изобретая собственный workflow engine?**

Главная учебная ось:

```text
обычный предметный Document
        ↓
рабочее состояние
        ↓
ограничения переходов по ролям
        ↓
Workflow
        ↓
условные уровни согласования
        ↓
момент фиксации факта
        ↓
Is Submittable / docstatus
        ↓
Cancel / Amend
        ↓
операционная работа после approval
```

Практикум не строится как каталог:

```text
Workflow → Notification → Assignment → Print → ...
```

Каждый следующий механизм появляется только после нового требования с соответствующей ответственностью.

---

# 2. Что ученик уже должен понимать

Второй практикум не повторяет с нуля:

```text
Bench / Site / App / Module
Standard DocType
DocField
name / Title Field
Controller
Role / DocType Permissions
Desk Form / List
fixtures
migrate
tests
clean install
```

Эти знания являются входом из первого CORE-практикума.

При этом второй практикум создаёт **отдельный учебный App и отдельную предметную модель**, чтобы lifecycle-решения не зависели от Rental.

---

# 3. Нейтральная предметная область

Предметная задача — **внутренняя заявка на закупку**.

Сотруднику нужно приобрести товар или услугу для работы. Он создаёт заявку. Заявку должны рассмотреть уполномоченные сотрудники. После окончательного одобрения заявка становится зафиксированным разрешением на закупку: ключевые согласованные данные нельзя просто переписать обычным Save.

Это даёт естественные требования:

- заявка имеет рабочее состояние;
- не каждый пользователь может выполнить любой переход;
- дорогая заявка требует дополнительного уровня согласования;
- окончательное одобрение имеет более сильную семантику, чем просто значение поля;
- после фиксации ошибочный документ нельзя бесследно переписать;
- исполнение закупки можно назначить сотруднику;
- участникам нужны уведомления;
- к заявке прикладываются файлы и ведётся обсуждение;
- нужна история изменений;
- одобренную заявку можно представить как печатный документ.

---

# 4. Минимальная предметная модель

Стартовая модель намеренно мала:

```text
Purchase Request
├── subject
├── description
├── requested_amount
└── needed_by
```

На старте нет:

```text
Purchase Request Item
Supplier
Department
Budget
Cost Center
Purchase Category
Approval Log
Approver
Executor
Purchase Request Status
Purchase Request Comment
Purchase Request Attachment
```

Причина: второй практикум изучает прежде всего lifecycle и процесс. Новые сущности не создаются ради большей «реалистичности», пока без них можно честно выразить учебные требования.

Если позднее появится реальное требование к строкам закупки, поставщику, бюджету или другому самостоятельному объекту, модель пересматривается обычным способом из первого практикума.

---

# 5. Почему одного Purchase Request достаточно на старте

`Purchase Request` — самостоятельный рабочий Document:

- имеет собственную identity;
- создаётся пользователем;
- проходит несколько состояний;
- участвует в согласовании;
- после окончательного решения может стать зафиксированным фактом;
- остаётся объектом для Assignment, Comment, File, Version и Print.

Нет оснований создавать отдельные `Approval`, `Approval Step` или `Request State` только потому, что процесс имеет несколько этапов.

Сначала проверяются встроенные lifecycle-механизмы Frappe.

---

# 6. Первая граница — обычное бизнес-состояние

Первое требование:

> Пользователь должен понимать, где находится заявка.

Для начала достаточно предметного состояния.

Пример смыслов:

```text
Draft
Pending Manager
Pending Senior
Rejected
Approved
Cancelled
```

Но наличие нескольких значений само по себе **не доказывает необходимость Workflow**.

Архитектурная проверка:

```text
нужно только хранить состояние?
→ обычное поле

нужно ограничить переходы по ролям/условиям?
→ появляется кандидат Workflow
```

Цель ученика — увидеть момент, когда обычный status перестаёт выражать всю ответственность.

---

# 7. Вторая граница — политика переходов

Следующее реальное требование:

```text
Requester
может:
Draft → Pending Manager

Manager
может:
Pending Manager → Approved
Pending Manager → Rejected

Requester
не может:
Pending Manager → Approved
```

Появились одновременно:

```text
состояния
+
переходы
+
роли
+
правила допустимого действия
```

Первый штатный кандидат — `Workflow`.

Не создаются собственные:

```text
approve() только ради обхода Workflow
if "Manager" in frappe.get_roles() в разных местах
JS-кнопки как единственная защита перехода
Approval Log как движок процесса
```

Если стандартный Workflow действительно выражает требование, процесс остаётся на нём.

---

# 8. Третья граница — условный уровень согласования

Следующее требование:

```text
requested_amount <= лимит
→ достаточно Manager

requested_amount > лимит
→ после Manager нужен Senior Approver
```

Это первая причина использовать условия переходов Workflow.

Пример смысловой схемы:

```text
Draft
  ↓ Requester
Pending Manager
  ↓ Manager + небольшая сумма
Approved

Pending Manager
  ↓ Manager + большая сумма
Pending Senior
  ↓ Senior Approver
Approved
```

Лимит на этом этапе может оставаться частью зафиксированного учебного сценария.

Отдельный Settings DocType не создаётся только ради демонстрации `Single DocType`.

Если появится самостоятельное требование:

> администратор должен менять лимит без изменения Workflow,

тогда настройки рассматриваются отдельно.

---

# 9. Self approval — отдельная политика, а не случайная проверка

Следующий вопрос процесса:

> Может ли пользователь, имеющий роль Approver, одобрить собственную заявку?

Это отдельная бизнес-политика.

Первым проверяется штатное поведение Workflow и его настройка self approval.

Не пишется собственная проверка `doc.owner == frappe.session.user`, пока Workflow уже владеет этой ответственностью.

Если штатной семантики недостаточно конкретному требованию, только тогда появляется дополнительная серверная логика.

---

# 10. Четвёртая граница — окончательное одобрение как факт

Следующее требование меняет архитектуру сильнее:

> После окончательного одобрения сумма, назначение и срок заявки считаются согласованными. Их нельзя незаметно переписать обычным редактированием.

Теперь `Approved` — не просто удобная метка.

Появилась транзакционная семантика:

```text
до approval
→ документ рабочий и изменяемый

после final approval
→ документ зафиксирован
```

Первый штатный кандидат — `Is Submittable` / `docstatus`.

Frappe использует:

```text
0 = Draft
1 = Submitted
2 = Cancelled
```

Рабочая модель практикума должна специально показывать, что Workflow state и docstatus различаются.

Пример:

```text
Draft            → docstatus 0
Pending Manager  → docstatus 0
Pending Senior   → docstatus 0
Rejected         → docstatus 0
Approved         → docstatus 1
Cancelled        → docstatus 2
```

Это не обязательные финальные названия состояний, а архитектурная семантика, которую должна сохранить будущая матрица.

---

# 11. Workflow и docstatus используются вместе, но отвечают на разные вопросы

```text
business state
= предметный смысл состояния

Workflow
= кто и при каких условиях может выполнить переход

docstatus
= системный транзакционный lifecycle
```

`Workflow` может управлять переходами, которые приводят к разным значениям `docstatus`, но это не превращает эти понятия в одно и то же.

Ключевой учебный результат:

```text
Rejected может оставаться docstatus 0
Approved может стать docstatus 1
```

потому что решение определяется предметной семантикой, а не названием состояния.

---

# 12. Cancel / Amend вместо бесследного переписывания

После `Submitted` появляется новое пользовательское требование:

> Что делать, если после approval обнаружена ошибка в сумме или назначении?

Если изменение меняет смысл согласованного факта, обычный Edit не подходит.

Первый штатный путь:

```text
Cancel
→ Amend
→ новый исправленный Document
```

Практикум должен показать, что `Allow on Submit` не является универсальным способом вернуть обычное редактирование Submitted Document.

---

# 13. Allow on Submit — только под отдельное безопасное требование

Механизм рассматривается только если появляется поле, которое действительно может измениться после approval без изменения смысла согласованной заявки.

Например, потенциальное позднее требование:

> После approval исполнитель должен записать внешний номер заказа, но это не меняет сумму, назначение и решение согласования.

Тогда можно отдельно проверить `Allow on Submit`.

Без такого требования механизм не включается в обязательный маршрут только ради знакомства.

---

# 14. Assignment — текущая рабочая ответственность

После approval появляется новая задача:

> Конкретный сотрудник должен фактически выполнить закупку.

Первый механизм — `Assignment` / `ToDo`.

Смысл:

```text
кто сейчас должен сделать работу
→ Assignment / ToDo
```

Не следует автоматически создавать поле:

```text
executor → Link → User
```

если нужен только текущий рабочий исполнитель.

Но если позднее появится требование хранить исполнителя как неизменяемый предметный факт, это уже другая ответственность и обычное поле может стать оправданным.

---

# 15. Workflow action alert и Notification — не дублировать

Frappe Workflow уже умеет уведомлять пользователей о доступных действиях процесса.

Поэтому отдельная `Notification` не создаётся только для дублирования обычного workflow approval alert.

Для `Notification` нужен другой смысл, например:

> За два дня до `needed_by` ответственный по уже одобренной заявке должен получить напоминание.

Тогда первым кандидатом становится штатная `Notification`, потому что Frappe поддерживает условия и события по датам.

Scheduler/background job не вводится, пока Notification правильно выражает требование.

---

# 16. File / Comment / Version — встроенные спутники Document

Три типовых требования:

## Файл

> Приложить коммерческое предложение или обоснование.

Первый кандидат:

```text
File / Attach
```

а не `Purchase Request Attachment`.

## Обсуждение

> Участники должны обсудить заявку.

Первый кандидат:

```text
Comment / Timeline
```

а не `Purchase Request Comment`.

## История изменений

> Нужно видеть, кто менял сумму или описание до согласования.

Первый кандидат:

```text
Track Changes / Version
```

а не собственный `Approval History` только ради аудита обычных изменений.

Если позднее нужен отдельный юридически значимый журнал с другой семантикой, модель пересматривается отдельно.

---

# 17. Print — сначала штатное представление

После final approval появляется реальное требование:

> Одобренную заявку нужно показать или сохранить как печатный документ/PDF.

Первый шаг — проверить стандартный Print View Frappe.

Если его представление удовлетворяет требованию, отдельный формат не создаётся.

Если нужна специальная утверждённая форма, первым кандидатом становится `Print Format`.

Собственный PDF generator или отдельный frontend не вводится без дополнительного требования.

---

# 18. Permission model второго практикума

Базовая безопасность по-прежнему начинается со штатных:

```text
User
Role
DocType Permissions
Workflow transition roles
```

Предполагаемые роли процесса:

```text
Purchase Requester
Purchase Approver
Senior Purchase Approver
```

Дополнительная роль исполнителя закупки появляется только если она действительно нужна для Assignment/permissions.

`Permission Type [v16+]` не включается автоматически для approve, потому что разрешение перехода уже является ответственностью Workflow.

Он будет отдельным кандидатом только для нестандартного действия, которое не выражается Workflow или обычным DocPerm.

---

# 19. Что второй практикум намеренно не покрывает

В обязательный маршрут не входят автоматически:

```text
REST API
custom whitelisted API
Webhook
background jobs
custom scheduler code
foreign DocType customization
doc_events
extend_doctype_class
override_doctype_class
Web Form
Portal
custom frontend
Query Report
Script Report
complex User Permission model
Permission Type без отдельной команды
concurrency / locking
external integration
production deployment
```

Это будущие архитектурные контуры, а не «оставшиеся уроки» второго практикума.

---

# 20. Что второй практикум не должен повторять ради количества

Не нужно снова строить большой набор справочников, сложную child-модель и междокументный агрегат только для повторения первого CORE.

Минимальный Document выбран специально, чтобы внимание ученика было на переходе:

```text
данные
→ состояние
→ политика переходов
→ транзакционная фиксация
→ операционная работа вокруг Document
```

---

# 21. Архитектурная карта второго практикума

```text
Purchase Request
        ↓
обычное business state
        ↓
появились role-controlled transitions
        ↓
Workflow
        ↓
появились amount-based approval conditions
        ↓
conditional Workflow transitions
        ↓
final approval стал фиксированным бизнес-фактом
        ↓
Is Submittable / docstatus
        ↓
ошибка после submit
        ↓
Cancel / Amend
        ↓
нужно выполнить работу
        ↓
Assignment / ToDo
        ↓
нужно напомнить по дате
        ↓
Notification
        ↓
файлы / обсуждение / история
        ↓
File / Comment / Version
        ↓
утверждённый документ нужно представить
        ↓
Standard Print / Print Format
```

Каждая стрелка должна быть подтверждена будущей матрицей требований. Если реального требования нет, механизм удаляется из маршрута.

# 23. Источники, на которых основан паспорт

**[ДОКУМЕНТАЦИЯ FRAPPE]** `docstatus`:

- https://docs.frappe.io/framework/doctypes/docstatus

Frappe определяет транзакционный lifecycle `Draft (0) → Submitted (1) → Cancelled (2)`; non-submittable Documents остаются Draft.

**[ОФИЦИАЛЬНАЯ ДОКУМЕНТАЦИЯ ЭКОСИСТЕМЫ]** Workflow:

- https://docs.frappe.io/erpnext/workflows

Workflow задаёт состояния, переходы, роли, условия и `Doc Status`; для submittable DocType он заменяет обычный Save/Submit flow и должен сам описывать необходимые submit/cancel transitions.

**[ДОКУМЕНТАЦИЯ FRAPPE]** Assignment / ToDo:

- https://docs.frappe.io/framework/assignments-and-todos

Assignment создаёт связанный `ToDo` и выражает текущую рабочую ответственность пользователя за Document.

**[ДОКУМЕНТАЦИЯ FRAPPE]** Notification:

- https://docs.frappe.io/framework/notifications

Notification поддерживает условия, роли/поля получателей и события, включая привязку к датам.

**[ДОКУМЕНТАЦИЯ FRAPPE]** Printing:

- https://docs.frappe.io/framework/user/en/desk/printing

Frappe имеет штатный Print View и Print Format/PDF pipeline.

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Allow on Submit`:

- https://docs.frappe.io/framework/doctypes/allow-on-submit

Механизм разрешает изменение только отдельных безопасных полей Submitted Document и не является способом отменить смысл submit.

# 24. Критерий принятия архитектурного паспорта

Перед созданием матрицы требований нужно ответить `да` на все вопросы:

```text
1. Purchase Request действительно подходит для изучения lifecycle, а не просто маскирует каталог функций?
2. Минимальная предметная модель не перегружена сущностями из первого практикума?
3. Workflow появляется только после требований к ролям и переходам?
4. Conditional Workflow появляется из реального amount-based approval?
5. docstatus появляется только после требования зафиксировать final approval?
6. Rejected и Approved не смешиваются автоматически с Cancelled/Submitted только из-за названия?
7. Cancel / Amend используется для изменения смысла зафиксированного факта?
8. Allow on Submit остаётся исключением для безопасного пост-фактического поля?
9. Assignment не подменяется предметным executor field без необходимости?
10. Notification не дублирует Workflow alert?
11. File / Comment / Version проверяются раньше собственных спутников документа?
12. Print Format появляется только если Standard Print недостаточен?
13. Второй практикум не захватывает API/async/extension/integration ради покрытия?
14. Первый и второй практикумы учат разным архитектурным классам задач?
```

Если хотя бы один ответ отрицательный, сначала исправляется паспорт. Матрица, граф и roadmap до этого не создаются.
