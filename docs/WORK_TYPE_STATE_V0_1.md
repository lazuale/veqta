# VEQTA — Work Type и State v0.1

Статус: **рабочая гипотеза, не принятое решение**.

Цель — определить минимальную реализацию `Work Type` и текущего состояния `Work Item`, максимально используя штатные возможности Frappe и не создавая lifecycle engine поверх Framework.

## 1. Проверенные ограничения Frappe

На один DocType в Frappe может быть активен только один `Workflow`.

При активации Workflow Frappe деактивирует другие Workflow для того же DocType.

При этом Transition поддерживает `Condition`, которая может обращаться к полям документа. Поэтому один Workflow для `Work Item` может содержать разные ветки переходов в зависимости от `work_type`.

Frappe при настройке Workflow создаёт для целевого DocType поле состояния типа `Link` на штатный `Workflow State`, если такого поля ещё нет.

Следствие: на первой версии нет доказанной необходимости создавать собственный `Work State` или собственный workflow engine.

## 2. Work Type

`Work Type` остаётся собственной сущностью VEQTA.

Назначение — классифицировать единицы работы, не создавая отдельный DocType для каждого сценария.

### Минимальная модель

```text
Work Type
---------
code            required, stable machine identifier
title           required, user-facing name
description     optional
disabled        optional flag
```

Предлагаемая Frappe-модель:

- `code` используется как `name` документа (`autoname` по полю);
- `title` задаётся как Title Field;
- в Link-полях пользователю показывается `title`, а машинная ссылка остаётся стабильным `code`;
- `disabled` позволяет перестать использовать тип без удаления исторически связанных данных.

Пример:

```text
code: CHECK
title: Проверка
```

В `Work Item.work_type` хранится ссылка `CHECK`, а интерфейс может показывать `Проверка`.

## 3. State

На v0.1 не создаём собственный `Work State`.

Кандидатная реализация:

```text
Work Item
    ↓
Frappe Workflow
    ↓
Frappe Workflow State
```

Поле текущего состояния предоставляет Workflow Frappe как `Link` на `Workflow State`.

VEQTA не дублирует это вторым полем `state`, если штатное workflow-state поле удовлетворяет требованиям.

## 4. Разные процессы для разных Work Type

Поскольку активный Workflow для `Work Item` один, его transitions могут ветвиться по `work_type` через Condition.

Пример концепции:

```text
Work Type SIMPLE
New → Doing → Done

Work Type CHECK
New → Analysis → Review → Done
```

В одном Workflow переходы ограничиваются условиями вида:

```text
doc.work_type == "SIMPLE"
```

или:

```text
doc.work_type == "CHECK"
```

Это позволяет на первой версии сохранить настройку через Desk и не писать собственный lifecycle engine.

## 5. Осознанное ограничение

Один общий Workflow может стать неудобным, если количество Work Type и уникальных процессов сильно вырастет.

На v0.1 это принимается как ограничение платформы, а не как причина заранее создавать новый движок.

Критерий пересмотра:

> Если реальные процессы VEQTA невозможно поддерживать в одном Workflow без чрезмерной сложности и дублирования transitions, это становится доказанной причиной рассмотреть минимальное расширение lifecycle-модели.

До такого факта собственный workflow engine не проектируется.

## 6. Что пока не создаём

- собственный `Work State`;
- `Lifecycle Scheme`;
- `Transition` DocType VEQTA;
- policy engine;
- отдельный Workflow на каждый Work Type;
- конструктор workflow VEQTA.

## 7. Аналитическая оговорка

Текущее состояние будет структурированным Link-полем, а не текстом или JSON.

Отдельный вопрос истории переходов остаётся открытым: необходимо отдельно проверить, достаточно ли штатных данных Frappe для аналитики или требуется минимальный `Work State Change`.

## 8. Что нужно проверить прототипом

1. Создать `Work Type` со стабильным `code` и отображаемым `title`.
2. Создать `Work Item` с `work_type`.
3. Настроить один Workflow для `Work Item`.
4. Создать минимум два Work Type с различающимися ветками transitions.
5. Ограничить transitions через Conditions по `work_type`.
6. Проверить UX формы, List и Kanban.
7. Проверить, насколько удобно администратору поддерживать такой Workflow через Desk.
8. Проверить фактические данные, которые Frappe оставляет после переходов, для последующей аналитики.

Только результаты этого прототипа должны решить, достаточно ли штатного Workflow для VEQTA.
