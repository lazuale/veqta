## Обязательный формат каждой работы

```text
# XX. Название

## Где мы сейчас

Кратко фиксируем состояние проекта после предыдущей работы.
Не повторяем предыдущую главу.

## Что получим после работы

Один конкретный новый рабочий результат.

## Что нового в Frappe

Минимальное объяснение механизма простыми словами.
Только то, что требуется для выполнения текущей практики.

## Проверено на

- Frappe Framework: v16.x
- ветка core при проверке исходников: `version-16`
- дата проверки: YYYY-MM-DD

## Официальные источники

Ссылки только на официальную документацию Frappe Framework, официальный `frappe/frappe` или официальные migration notes v16.

## Исходные тестовые данные

Точные записи/пользователи/значения, необходимые для воспроизводимого результата.

## Практика

### Шаг 1

Действие → ожидаемый результат.

### Шаг 2

Действие → ожидаемый результат.

...

## Проверка результата

Чёткий сценарий PASS/FAIL.

## Намеренно меняем или ломаем настройку

Только безопасное обратимое изменение.

## Почему поведение изменилось

Связываем наблюдаемое поведение с конкретной штатной настройкой Frappe.

## Возвращаем правильное состояние

Пошагово возвращаем проект к состоянию, необходимому следующей работе.

## Контрольное задание

Небольшая самостоятельная задача на уже изученный механизм без введения новой функции.

## Результат работы

Краткий чек-лист того, что теперь реально умеет проект.

## Что изменилось в проекте

Новые DocTypes, поля, роли, настройки, документы или представления.

## Следующая работа

Одна фраза: какая новая потребность проекта приводит к следующему этапу.
```

## Жёсткие правила написания

1. **Одна работа — один осмысленный прирост проекта.** Не создавать отдельную работу на каждую кнопку или параметр.
2. **Один сквозной Site.** Все работы `00–25` выполняются на основном учебном Site. Второй Site появляется только в `26_PACKAGE_PORTABILITY.md` для проверки Package Import.
3. **Один сквозной проект.** Не вводить несвязанные демонстрационные DocTypes ради одной функции. Исключение — `Work Approval`, который осознанно нужен для естественного изучения Submit/Cancel/Amend.
4. **Никакого программирования.** Не использовать Python, JavaScript, SQL, Server Script, Client Script, hooks, custom app code, Query Report, Script Report или ручной Jinja/HTML/CSS.
5. **Не писать кодоподобные условия.** Не использовать Python/JS expressions в Workflow Conditions, Assignment Rule Conditions, Notification Conditions, DocType Layout Conditions и подобных полях. Если функция без такого выражения не решает учебную задачу — она переносится на Development-уровень.
6. **Custom DocTypes принадлежат модулю Practicum.** Не создавать учебные DocTypes внутри `Core`, `Desk` или чужих системных модулей.
7. **Package создаётся раньше DocTypes.** Это контейнер no-code конфигурации проекта.
8. **Work Item не делать submittable.** Для lifecycle используется отдельный `Work Approval`.
9. **Category создаётся сразу как Tree DocType.** Не переделывать плоский справочник задним числом.
10. **Email Notification не использовать до Email Account.** В работе 16 используются System Notifications; Email channel добавляется в работе 23.
11. **Number Card и Chart не использовать в Workspace до работы 21.** В работе 10 Workspace служит навигацией и рабочим входом.
12. **Website User не вводить до Web Form.** В работе 11 создаются обычные System Users; Website User появляется в работе 24.
13. **Calendar не считать просто кнопкой.** В работе 09 явно создаётся и настраивается штатный `Calendar View` для Work Item.
14. **Map View проверяется на реальных данных.** У Work Item к этому моменту должно быть Geolocation-поле и несколько записей с координатами.
15. **DocType Layout — без JS Condition.** В работе 18 альтернативный Layout открывается штатной ссылкой Workspace; автоматические условия переключения относятся к следующему уровню.
16. **Package Release и Backup — разные вещи.** Работа 26 проверяет перенос конфигурации; работа 27 — восстановление полного Site с данными и файлами.
17. **Permissions проверяются не Administrator.** Для каждого ограничения явно указывается пользователь/роль, под которыми выполняется проверка.
18. **После каждого важного действия указывать ожидаемый результат.** Никаких длинных серий кликов с проверкой только в конце.
19. **Ошибки должны быть безопасными и обратимыми.** Не создавать риск потерять учебный стенд до отдельной работы backup/restore.
20. **Не добавлять advanced-функциональность ради полноты.** Матрица покрывает базовый no-code уровень, а не весь Developer API Frappe.

## Требование к официальности

Каждое утверждение о поведении или доступности функции должно быть проверено именно для **Frappe Framework 16**.

Приоритет источников:

1. официальная документация Frappe Framework;
2. официальный репозиторий `frappe/frappe`, ветка `version-16`;
3. официальные migration notes v16.

Документация ERPNext, HRMS, CRM и других приложений сама по себе **не доказывает**, что функция входит в core Frappe. Если удобная UI-инструкция находится там, сначала подтверждаем наличие соответствующего DocType/механизма в `frappe/frappe version-16`.

Если документация и фактический v16 UI расходятся:

- не придумывать обходной путь;
- не переносить инструкцию из старой версии;
- проверить `version-16`;
- явно описать фактическое поведение;
- при невозможности выполнить функцию без кода удалить её из базовой работы и зафиксировать как Development/Advanced.

## Критерий завершения отдельной работы

Работа считается завершённой только если:

- итоговый объект/настройка реально создан;
- контрольный сценарий проходит;
- проверка выполнена правильным пользователем;
- намеренное изменение показало ожидаемую разницу поведения;
- состояние проекта возвращено в норму;
- не появились скрытые prerequisites для следующей работы;
- следующий файл может начинаться ровно с описанного состояния проекта.
