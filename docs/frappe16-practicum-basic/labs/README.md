## Жёсткие правила написания

1. **Native-first.** Сначала ищем готовый декларативный механизм Frappe. Не начинаем со script.
2. **Один сквозной продукт.** Все работы развивают `frappe_practicum`; отдельный демонстрационный объект создаётся только когда функция естественно не подходит основному Work Item.
3. **App создаётся штатно.** `bench new-app` и нормальный App/Module — часть базового пути.
4. **Не править core.** Никогда не изменять исходники `frappe` для решения задачи практикума.
5. **Встроенный low-code допустим.** Client Script, Server Script, expressions, Query Report, custom Script Report, Jinja, Web Form script и Webhook допустимы, когда они являются штатной поверхностью Frappe.
6. **Не подменять Frappe скриптами.** Если задача решается DocType property, Permission, Workflow, Assignment Rule, Notification, Report Builder или другим готовым механизмом — используем его.
7. **Файловая бизнес-логика не входит.** Не писать собственные controllers, hooks, Python modules, custom JS assets, patches, overrides или frontend bundles.
8. **Client Script не является серверной защитой.** Любая лаборатория Client Script обязана показать, что browser-side поведение можно обойти.
9. **Server Script используется осознанно.** Показывать restricted environment и назначение конкретного Script Type; не превращать его в универсальный костыль.
10. **Expressions изучаются по месту.** Условия Assignment Rule, Workflow, Notification и других механизмов вводятся внутри соответствующей работы, а не отдельным курсом языка.
11. **Reports идут от простого к сложному.** Report Builder → Query Report → Custom Script Report. Нельзя перепрыгивать сразу к SQL/script.
12. **Print идёт от простого к сложному.** Standard Print → Print Format Builder → Jinja. Нельзя начинать печать с ручного шаблона.
13. **API идёт от простого к сложному.** Сначала автоматически предоставляемый REST CRUD, затем Server Script API для отдельной доказанной потребности.
14. **Website идёт от простого к сложному.** Сначала штатная Web Page/Web Form, затем встроенные CSS/Client Script только при необходимости.
15. **Permissions проверяются обычными пользователями.** Administrator не считается доказательством корректного доступа.
16. **Workflow Transition Tasks изучаются только после Workflow, Server Script и Webhook.**
17. **Package — отдельная stock-возможность, не фундамент проекта.** Основной продукт живёт в обычном App.
18. **Git deployment и backup — разные навыки.** Git воспроизводит App; backup восстанавливает Site с данными.
19. **Каждый важный шаг имеет ожидаемый результат.** Никаких длинных серий действий с одной проверкой в конце.
20. **Ошибки безопасны и обратимы.** Учебный стенд не должен разрушаться до лаборатории backup/restore.
21. **Не добавлять сторонние библиотеки, плагины или приложения для закрытия функции, которую должен показать stock Frappe.**
22. **Не добавлять developer-level решение ради полноты.** Если stock/low-code Frappe достигает своей естественной границы — эту границу и фиксируем.

## Требование к официальности

Каждое утверждение о поведении должно быть проверено именно для Frappe Framework 16.

Приоритет:

1. официальная документация Frappe Framework;
2. `frappe/frappe` branch `version-16`;
3. официальные migration notes v16.

Если документация и фактический v16 UI расходятся:

- не придумывать обходной путь;
- проверить `version-16`;
- описать фактическое поведение;
- если штатный механизм реально требует app-level файловой разработки, зафиксировать границу и перенести продолжение в Development.

## Критерий завершения отдельной работы

Работа завершена только если:

- итоговый объект/настройка реально создан;
- контрольный сценарий проходит;
- выбран максимально нативный механизм для текущей задачи;
- ученик понимает, почему более простой уровень уже недостаточен или, наоборот, почему script не понадобился;
- permissions проверены правильным пользователем;
- намеренное изменение показало ожидаемую разницу поведения;
- состояние проекта возвращено в норму;
- следующий файл может начинаться ровно с описанного состояния проекта.
