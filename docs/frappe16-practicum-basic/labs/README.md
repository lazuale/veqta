## Как писать одну работу

Не нужно превращать каждую главу в одинаковую анкету из двадцати разделов. Достаточно такого каркаса:

```text
# XX. Название

## Зачем это нужно

Коротко объясняем, какую реальную проблему сейчас решаем.

## Что понадобится

Только нужные для этой работы данные, пользователи или настройки.
Если ничего особенного не нужно — раздел можно пропустить.

## Делаем

Пошаговые действия.
После важных шагов сразу пишем, что должно появиться на экране или измениться в системе.

## Проверяем

Несколько конкретных проверок с понятным PASS/FAIL результатом.

## Самостоятельно

Небольшая задача на тот же механизм без новой темы.

## Что теперь умеет приложение

Короткий итог без повторения всей главы.

## Источники

Официальная документация и дата проверки на Frappe 16.
```

Если в конкретной работе полезно специально получить ошибку, сравнить два способа или показать ограничение механизма — добавляем такой раздел именно там. Делать это обязательным в каждой главе не нужно.

## Шесть правил курса

1. **Пишем для новичка.** Не предполагаем знание Frappe и не объясняем простое через ещё более сложные термины.
2. **Одна работа — один заметный результат.** После главы приложение должно уметь что-то новое, что можно увидеть и проверить.
3. **Сначала используем готовую возможность Frappe.** Скрипт появляется только тогда, когда обычной настройки действительно недостаточно.
4. **Не уходим в полноценную разработку.** На базовом уровне не пишем controllers, собственные Python-модули, overrides, patches, файловые JS-расширения и свой frontend.
5. **Не теряем настройки между Site.** Если важная часть продукта создаётся через Desk, проверяем, попадёт ли она в App. При необходимости используем Export Customizations или fixtures.
6. **Проверяем всё на Frappe 16.** Если документация и реальный интерфейс расходятся, ориентируемся на `version-16` и описываем фактическое поведение.

## Как использовать встроенные скрипты

Client Script, Server Script, Query Report, Custom Script Report, Jinja и Web Form Script входят в курс, но мы не учим соответствующие языки с нуля.

В работе даётся небольшой законченный пример. Ученик:

- вставляет его;
- видит результат;
- разбирает только те строки, которые нужны для текущей задачи;
- меняет одно-два значения и снова проверяет поведение.

Если тот же результат проще получить штатной настройкой Frappe, скрипт не нужен.

## Что обязательно проверять

Permissions проверяем под обычным пользователем, а не под Administrator.

Client Script проверяем с пониманием, что это браузерное поведение и оно не заменяет серверное правило.

Server Script вводим только после явного включения этой возможности на учебном стенде и объяснения, почему по умолчанию она выключена.

После Customize Form используем Export Customizations там, где изменение должно стать частью App.

После появления DB-based настроек отдельно проверяем fixtures и то, что реально хранится в Git.

Перед финалом App обязательно ставится на второй чистый Site. Любая скрытая ручная настройка, без которой он там не работает, должна быть либо перенесена в App, либо явно признана настройкой конкретного Site.

## Источники

В каждой работе используем в первую очередь:

1. официальную документацию Frappe Framework;
2. репозиторий `frappe/frappe`, ветку `version-16`;
3. официальные заметки по Frappe 16.

Документацию ERPNext, HRMS, CRM и других приложений можно использовать как подсказку по интерфейсу только после проверки, что нужный механизм действительно входит в Frappe Framework 16.
