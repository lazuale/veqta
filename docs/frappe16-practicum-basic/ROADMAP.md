# Дорожная карта базового практикума Frappe Framework 16

Дорожная карта показывает не перечень функций, а **эволюцию одного учебного проекта** от пустого стенда до законченной рабочей системы.

## Фаза I. Поднять платформу

**Практические работы:** `00–01`

Цель:

> Понимать, где работает Frappe, и уметь самостоятельно поднять и проверить учебный Site.

Эволюция:

```text
чистая Linux-система
        ↓
      Bench
        ↓
       Site
        ↓
       Desk
```

На выходе:

- Frappe 16 работает;
- ученик умеет входить в Desk;
- понимает базовые компоненты стенда;
- умеет найти системную настройку и журнал;
- не зависит от готового чужого окружения.

---

## Фаза II. Построить данные

**Практические работы:** `02–07`

Цель:

> Научиться описывать реальные рабочие объекты и отношения между ними только штатными средствами Frappe.

Эволюция:

```text
Work Item
   ↓
поля и форма
   ↓
имя и поиск
   ↓
Project / Category
   ↓
Link / Child / Single
   ↓
Tree
   ↓
lifecycle и audit
```

На выходе формируется предметная модель:

```text
Project
│
├── Work Item
│   ├── Project
│   ├── Category
│   ├── Status
│   ├── Priority
│   ├── Due Date
│   ├── Checklist
│   └── Files
│
├── Category
├── Work Item Step
└── Practicum Settings
```

Ключевой результат фазы: ученик понимает DocType не как «форму», а как тип документа с данными, связями, представлением и жизненным циклом.

---

## Фаза III. Сделать систему удобной

**Практические работы:** `08–09`

Цель:

> Научиться использовать одну модель данных в разных рабочих сценариях без написания собственного frontend.

Эволюция:

```text
Documents
   ↓
List / Report View
   ↓
Kanban / Calendar / Gantt / Tree
   ↓
Workspace
```

На выходе:

- данные можно смотреть и обрабатывать через несколько штатных views;
- пользователь получает единый Workspace;
- основные действия и показатели находятся на рабочем экране.

---

## Фаза IV. Добавить людей и контроль доступа

**Практические работы:** `10–11`

Цель:

> Сделать систему многопользовательской и доказуемо разграничить доступ.

Эволюция:

```text
User
  ↓
Role
  ↓
Role Permissions
  ↓
Permission Level
  ↓
If Owner
  ↓
User Permission
  ↓
Share
```

На выходе:

- минимум три рабочих пользователя;
- разные роли получают разные операции;
- доступ ограничивается не только меню, но и конкретными Documents/полями;
- проверка выполняется под обычными пользователями, а не под Administrator.

---

## Фаза V. Превратить данные в работу

**Практические работы:** `12–17`

Цель:

> Перейти от хранения записей к управляемой работе людей.

Эволюция:

```text
Work Item
   ↓
Assign / ToDo
   ↓
Assignment Rule
   ↓
Workflow
   ↓
Notification
   ↓
Auto Repeat
   ↓
штатная кастомизация
```

На выходе:

- Work Item имеет исполнителя и срок;
- новые записи могут распределяться автоматически;
- процесс проходит управляемые стадии;
- Frappe уведомляет участников;
- регулярные документы создаются автоматически;
- ученик понимает, как менять систему через Customize Form, не трогая код.

Контрольный процесс:

```text
Новая
  ↓
В работе
  ↓
На проверке
  ├──→ Завершена
  └──→ На доработку
```

## Фаза VI. Научиться работать с массивом данных и результатом

**Практические работы:** `18–22`

Цель:

> Научиться не только вести отдельные Documents, но и загружать, анализировать, представлять и передавать накопленные данные.

Эволюция:

```text
Data Import / Export
        ↓
   Report Builder
        ↓
Number Card / Charts
        ↓
     Dashboard
        ↓
   Print / PDF
        ↓
      Email
```

На выходе:

- данные массово загружаются и обновляются;
- пользователь сам строит отчёты без SQL;
- руководитель получает Dashboard;
- Work Item можно распечатать в PDF;
- Email остаётся частью истории документа.

---

## Фаза VII. Выйти за пределы Desk

**Практические работы:** `23–24`

Цель:

> Показать, что одна и та же модель Frappe может обслуживать внутреннего пользователя, внешнего пользователя и внешнюю систему без собственного backend-кода.

Эволюция:

```text
                  Desk User
                     │
                     │
Web Form User ─── Work Item ─── REST API Client
```

На выходе:

- внешний пользователь создаёт Work Item через Web Form;
- Website User работает со своими документами в рамках permissions;
- отдельный API User работает с теми же Documents через автоматически предоставляемый REST API;
- права Frappe продолжают действовать независимо от интерфейса доступа.

---

## Фаза VIII. Доказать жизнеспособность системы

**Практические работы:** `25–26`

Цель:

> Доказать, что система не только работает сейчас, но и может быть восстановлена и снова пройти полный рабочий сценарий.

Эволюция:

```text
полностью настроенный Site
          ↓
        backup
          ↓
        restore
          ↓
проверка полного сценария
```

Финальный сценарий:

```text
Web Form
   ↓
Work Item
   ↓
Assignment
   ↓
Workflow
   ↓
Notification
   ↓
Comments / Files
   ↓
Completed
   ↓
Report Builder
   ↓
Dashboard
   ↓
Print / PDF
   ↓
Email
   ↓
REST API
   ↓
Backup
   ↓
Restore
   ↓
повторная проверка
```

Если этот сценарий проходит после восстановления, базовый практикум завершён.

# Правило перехода между фазами

Следующая фаза начинается только после прохождения контрольного результата предыдущей.

Например:

- нельзя переходить к Permissions, пока нет нескольких реальных Users и Roles;
- нельзя переходить к Workflow, пока не освоены lifecycle и permissions;
- нельзя строить Dashboard, пока нет накопленных данных и Report Builder;
- нельзя изучать Web Form, пока не понятны Users и permissions;
- REST API показывается только после того, как та же модель уже понятна через Desk и Web Form;
- backup считается изученным только после реального restore и повторной проверки системы.

Так сохраняется принцип **«от атома к организму»** без скрытых скачков в знаниях.
