# Дорожная карта базового практикума Frappe Framework 16

Дорожная карта показывает **эволюцию одного no-code проекта** от чистого стенда до переносимой и восстанавливаемой рабочей системы.

Она не дублирует подробный состав работ из `MATRIX.md`. Здесь фиксируются только фазы, зависимости и логика порядка.

## Фаза I. Поднять платформу

**Работы:** `00–01`

Цель:

> Понимать, где работает Frappe 16, уметь поднять учебный Site и ориентироваться в Desk и навигации v16.

Эволюция:

```text
чистая Linux-система
        ↓
      Bench
        ↓
       Site
        ↓
       Desk
        ↓
Desktop / Workspace Sidebar / Awesome Bar
```

На выходе:

- Frappe 16 работает;
- ученик умеет запускать и останавливать учебный стенд;
- входит в Desk;
- понимает базовые компоненты Site;
- ориентируется в Desktop, Workspace Sidebar, Awesome Bar, System Settings и журналах.

Следующая фаза невозможна, пока ученик не может самостоятельно вернуть стенд в рабочее состояние после остановки.

---

## Фаза II. Создать no-code контейнер проекта

**Работа:** `02`

Цель:

> Отделить учебный проект от системных модулей Frappe без создания собственного Python App.

Эволюция:

```text
Frappe Site
    ↓
Package: Frappe Practicum
    ↓
Custom Module: Practicum
```

На выходе:

- у проекта есть собственный Package;
- создан отдельный Custom Module;
- все дальнейшие Custom DocTypes создаются внутри модуля Practicum;
- ученик понимает разницу между Site, Package, Module и полноценным Frappe App.

Package вводится в начале не ради deployment, а как штатный контейнер no-code конфигурации. Его переносимость проверяется только ближе к финалу.

---

## Фаза III. Построить данные

**Работы:** `03–08`

Цель:

> Научиться описывать реальные рабочие объекты, связи, иерархию и lifecycle только штатными средствами Frappe.

Эволюция:

```text
Work Item
   ↓
поля и форма
   ↓
имя и поиск
   ↓
Project / Child / Single / Connections
   ↓
Category [Tree]
   ↓
Work Approval [Submittable]
   ↓
lifecycle / audit
```

Основная рабочая модель:

```text
Project
│
├── Work Item
│   ├── Project
│   ├── Category
│   ├── Status
│   ├── Priority
│   ├── Start Date
│   ├── Due Date
│   ├── Location
│   ├── Checklist
│   └── Files
│
├── Category [Tree]
├── Work Item Step [Child]
├── Practicum Settings [Single]
└── Work Approval [Submittable]
```

Ключевое методическое решение:

- `Work Item` остаётся обычным рабочим Document и дальше используется в Assign, Workflow и Web Form;
- lifecycle `Submit / Cancel / Amend` изучается на отдельном `Work Approval`, для которого подтверждение естественно;
- Category создаётся сразу как Tree DocType, а не переделывается из плоского справочника задним числом.

На выходе ученик понимает DocType не как форму, а как тип документа с данными, связями, представлением и жизненным циклом.

---

## Фаза IV. Научиться видеть те же данные по-разному

**Работы:** `09–10`

Цель:

> Использовать одну модель данных в разных рабочих сценариях без собственного frontend.

Эволюция:

```text
Documents
   ↓
List / Report View
   ↓
Kanban
   ↓
Calendar View → Calendar / Gantt
   ↓
Map View
   ↓
Tree View
   ↓
Workspace
```

Почему порядок такой:

- Calendar изучается только после появления реальных date fields;
- Map View — только после появления Geolocation;
- Workspace собирается только после того, как уже существуют реальные DocTypes и views;
- Number Card и Chart пока не добавляются: они появятся после аналитической фазы.

На выходе:

- пользователь умеет выбирать подходящее представление тех же Documents;
- создан единый Workspace;
- понятна навигация v16 через Desktop и Workspace Sidebar.

## Фаза V. Добавить людей и контроль доступа

**Работы:** `11–12`

Цель:

> Сделать систему многопользовательской и доказуемо разграничить доступ.

Эволюция:

```text
System User
  ↓
Role
  ↓
Role Profile
  ↓
Role Permissions
  ↓
Permission Level
  ↓
If Owner
  ↓
User Permission
  ↓
Share
```

На выходе:

- минимум три обычных Desk User;
- разные роли получают разные операции;
- доступ ограничивается не только меню, но и конкретными Documents и полями;
- проверки выполняются под обычными пользователями, не Administrator.

Website User здесь ещё не вводится: он появляется только тогда, когда впервые нужен внешний пользователь Web Form.

## Фаза VI. Превратить данные в работу

**Работы:** `13–18`

Цель:

> Перейти от хранения Documents к управляемой совместной работе без программирования.

Эволюция:

```text
Work Item
   ↓
Assign / ToDo
   ↓
Comments / Mentions / Tags / Following
   ↓
Assignment Rule
   ↓
Workflow
   ↓
System Notification
   ↓
Auto Repeat
   ↓
Customize Form / DocType Layout
```

Контрольный процесс:

```text
Новая
  ↓
В работе
  ↓
На проверке
  ├──→ Завершена
  └──→ На доработку
```

Ограничения фазы:

- Assignment Rule используется без script conditions;
- Workflow используется без кодовых transition conditions;
- Notification используется без script condition;
- на этапе Notification применяется только System Notification;
- Email channel подключается позже, когда Email Account уже реально настроен;
- DocType Layout используется без JS Condition: альтернативный layout открывается из Workspace link.

На выходе система уже является полноценным внутренним рабочим инструментом.

---

## Фаза VII. Работать с массивом данных и результатом

**Работы:** `19–23`

Цель:

> Загружать, анализировать, представлять и передавать накопленные данные штатными no-code средствами.

Эволюция:

```text
Data Import / Export
        ↓
   Report Builder
        ↓
Number Card / Dashboard Chart
        ↓
Workspace analytics
        ↓
   Print / PDF
        ↓
Email Account / Communication / Email Queue
        ↓
Email Notification
```

Почему Email находится здесь:

- сначала ученик настраивает реальный Email Account;
- затем видит Communication и Email Queue;
- только после этого возвращается к Notification и включает Email channel.

Почему аналитика не находится в раннем Workspace:

- Workspace создаётся раньше как навигационный экран;
- Number Card и Chart появляются только когда накоплены данные и изучена отчётность;
- затем готовая аналитика встраивается в уже существующий Workspace.

На выходе:

- данные массово загружаются и обновляются;
- отчёты строятся без SQL;
- руководитель получает Dashboard;
- Work Item выводится в PDF;
- Email остаётся частью истории документа.

## Фаза VIII. Выйти за пределы Desk

**Работы:** `24–25`

Цель:

> Показать, что одна и та же модель Frappe обслуживает внутреннего пользователя, внешнего пользователя и внешнюю систему без собственного backend-кода.

Эволюция:

```text
                  Desk User
                     │
                     │
Website User ──── Work Item ──── REST API User
     │
 Web Form
```

Порядок принципиален:

1. Website User появляется вместе с Web Form, а не заранее;
2. сначала внешний человек работает с той же моделью через штатный UI;
3. только затем показывается автоматически предоставляемый REST API;
4. API проверяется отдельным пользователем и теми же Role Permissions.

На выходе:

- внешний пользователь создаёт и просматривает свои Work Items без Desk;
- API User работает с теми же Documents через REST;
- права Frappe остаются общей границей доступа независимо от интерфейса.

---

## Фаза IX. Доказать переносимость конфигурации

**Работа:** `26`

Цель:

> Доказать, что построенный no-code проект не привязан навечно к одному Site.

Эволюция:

```text
Site A
  │
  └── Package: Frappe Practicum
          ↓
     Package Release
          ↓
     Package Import
          ↓
        Site B
```

В этой фазе ученик специально проверяет границу Package:

- что входит в переносимую конфигурацию;
- что не является частью Package;
- чем конфигурация отличается от операционных Documents и пользовательских данных Site.

Это не backup.

Результат:

> На втором чистом Site воспроизводится no-code конфигурация учебного проекта штатным Package Import.

---

## Фаза X. Доказать восстановимость полного Site

**Работы:** `27–28`

Цель:

> Доказать, что система не только переносима как конфигурация, но и восстанавливается целиком вместе с рабочими данными.

Эволюция:

```text
полностью настроенный Site A
          ↓
        backup
          ↓
        restore
          ↓
проверка полного сценария
```

Финальный сценарий:

```text
Web Form
   ↓
Work Item
   ↓
Assignment
   ↓
Workflow
   ↓
System / Email Notification
   ↓
Comments / Files
   ↓
Completed
   ↓
Report Builder
   ↓
Dashboard
   ↓
Print / PDF
   ↓
Email
   ↓
REST API
   ↓
Backup / Restore
   ↓
повторная проверка
```

Package переносимость проверена отдельно на Site B и не подменяет backup/restore.

Если полный сценарий проходит после восстановления Site A, базовый практикум завершён.

# Правило перехода между фазами

Следующая фаза начинается только после прохождения контрольного результата предыдущей.

Ключевые зависимости:

- нельзя создавать учебные DocTypes до создания Package и Custom Module;
- нельзя переходить к views, пока модель не содержит реальные даты, статус, Geolocation и Tree-справочник;
- нельзя переходить к Permissions, пока нет нескольких реальных Users и Roles;
- нельзя переходить к Workflow, пока не освоены lifecycle и permissions;
- нельзя включать Email Notification до настройки Email Account;
- нельзя добавлять Number Cards/Charts в Workspace до аналитической фазы;
- нельзя изучать Web Form, пока не понятны Users, Roles и Permissions;
- REST API показывается после Desk и Web Form, когда одна модель уже понятна через два пользовательских интерфейса;
- Package Release проверяет перенос конфигурации, но не заменяет backup;
- backup считается изученным только после реального restore и повторной проверки системы.

Так сохраняется принцип **«от атома к организму»** без скрытых скачков и без программирования.
