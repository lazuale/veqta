# Дорожная карта базового практикума Frappe Framework 16

Практикум идёт по одному маршруту: от пустого стенда до приложения, которое можно поставить на второй Site и восстановить из backup.

Подробности каждой работы находятся в [`MATRIX.md`](MATRIX.md). Здесь только общий путь и смысл этапов.

## 1. Поднимаем Frappe и создаём App

**Работы 00–02**

Сначала ставим Frappe 16, создаём Site и разбираемся, из чего состоит система. После этого создаём обычный App `frappe_practicum`, устанавливаем его на Site, включаем Developer Mode и начинаем хранить App в Git.

```text
Linux
  ↓
Bench
  ↓
Site
  ↓
bench new-app
  ↓
frappe_practicum
  ↓
Developer Mode
  ↓
Git
```

После этого курса не должно быть зависимости от заранее подготовленного чужого стенда.

## 2. Строим модель и интерфейс

**Работы 03–10**

Создаём первый DocType, добавляем поля, naming и связи. Затем пробуем Child, Single и Tree DocType, отдельный submittable-документ и основные представления.

К концу этапа уже есть маленькое, но настоящее приложение:

```text
Project
  ↓
Work Item ← Category
  │
  ├─ Work Item Step
  └─ Files

Practicum Settings
Work Approval
```

Те же данные смотрим через List, Kanban, Calendar, Map и другие штатные представления, после чего собираем Workspace.

## 3. Добавляем людей и рабочий процесс

**Работы 11–18**

Создаём пользователей и роли, настраиваем права, Assign и ToDo. Затем автоматизируем назначение, строим Workflow, добавляем Notification и Auto Repeat.

Здесь важно увидеть, сколько Frappe умеет без скриптов.

```text
User / Role
    ↓
Permissions
    ↓
Assign / ToDo
    ↓
Assignment Rule
    ↓
Workflow
    ↓
Notification
    ↓
Auto Repeat
```

В конце этапа пробуем Customize Form и сохраняем нужные изменения в App через Export Customizations.

## 4. Пробуем встроенные скрипты и учимся не терять настройки

**Работы 19–22**

Только теперь переходим к Client Script и Server Script.

Сначала добавляем небольшое поведение на форме. Затем включаем Server Script на учебном стенде и проверяем серверное правило. После этого пробуем Scheduler Event и Permission Query.

Главная часть этапа — понять, где живут такие настройки.

```text
Client Script
Server Script
Workflow
Notification
другие записи Desk
        ↓
что осталось только в Site?
        ↓
Export Customizations / fixtures
        ↓
Git
```

К концу этапа важные для продукта настройки не должны зависеть от памяти ученика и ручного повторения на новом Site.

## 5. Работаем с данными и результатом

**Работы 23–27**

Загружаем данные пачкой, строим отчёты, Dashboard, печатный документ и подключаем Email.

Отчётность идёт от простого к сложному:

```text
Report Builder
      ↓
Query Report
      ↓
Custom Script Report
```

Печать — так же:

```text
Standard Print
      ↓
Print Format Builder
      ↓
Jinja Print Format
```

SQL и Jinja здесь нужны только для знакомства со штатными возможностями Frappe. Это не отдельный курс программирования.

## 6. Выходим из Desk и подключаем внешние системы

**Работы 28–32**

Сначала создаём обычную публичную страницу, затем Web Form для внешнего пользователя.

После этого проверяем два направления интеграции:

```text
внешняя система → REST API → Frappe
Frappe → Webhook → внешняя система
```

Готовый REST CRUD пробуем раньше Server Script API. Отдельный API-метод создаём только для задачи, которую неудобно решать обычным CRUD.

В конце связываем уже знакомые Workflow, Server Script и Webhook через Workflow Transition Tasks v16.

## 7. Переносим и восстанавливаем систему

**Работы 33–35**

Сначала отдельно смотрим Package, чтобы понимать ещё один штатный способ упаковки конфигурации Frappe.

Затем ставим основной `frappe_practicum` на второй чистый Site из Git. Именно здесь проверяется вся предыдущая работа с Developer Mode, Export Customizations и fixtures.

```text
Git
 ↓
второй Site
 ↓
install-app
 ↓
migrate
 ↓
та же конфигурация приложения
```

После этого делаем backup первого Site и реально восстанавливаем его.

Важно не смешивать две вещи:

- Git переносит App и его конфигурацию;
- backup восстанавливает конкретный Site вместе с пользовательскими данными и файлами.

## 8. Финальная проверка

**Работа 36**

В финале ничего нового не изучаем. Проходим весь рабочий сценарий на восстановленном Site и проверяем второй Site после установки App из Git.

```text
Web Form
  ↓
Work Item
  ↓
Assignment
  ↓
Workflow
  ↓
Notification
  ↓
Comments / Files
  ↓
Report / Dashboard
  ↓
Print / Email
  ↓
REST API / Webhook
```

Если для работы второго Site приходится вспоминать и вручную повторять скрытую настройку, курс ещё не закончен: нужно понять, должна ли эта настройка быть частью App или действительно относится к конкретному Site.

## Весь маршрут коротко

```text
00–02  Стенд и App
03–10  Модель и интерфейс
11–18  Люди и рабочий процесс
19–22  Встроенные скрипты и перенос настроек
23–27  Данные, отчёты, печать и Email
28–32  Website, Web Form и интеграции
33–35  Package, второй Site и backup/restore
36     Финальная проверка
```

Такой порядок нужен не ради красивой структуры. Каждая следующая часть опирается на то, что уже реально работает в приложении.
