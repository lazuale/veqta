# VEQTA — Work Item v0.1

Статус: **рабочая гипотеза, не замороженный контракт**.

Цель этого документа — зафиксировать минимальную модель `Work Item`, от которой продолжается проектирование.

## 1. Определение

`Work Item` — единица управляемой работы.

Это не обязательно задача, тикет, проектная карточка или инцидент. Конкретный смысл определяется `Work Type` и пользовательским процессом.

`Work Item` должен хранить текущее операционное состояние работы, а не пытаться одновременно быть журналом истории, отчётом и универсальным контейнером предметных данных.

## 2. Текущий минимальный набор данных

### Обязательные

| Поле | Назначение |
|---|---|
| `title` | краткое человеческое название работы |
| `work_type` | ссылка на тип работы |
| `state` | текущее состояние; в прототипе кандидат — штатное workflow-state поле Frappe |

### Необязательные

| Поле | Назначение |
|---|---|
| `description` | контекст и описание работы |
| `due_at` | реальный срок, если он существует |

### Системные поля Frappe

Используются штатные поля и не дублируются без отдельной причины:

- `name`;
- `owner`;
- `creation`;
- `modified`;
- `modified_by`.

## 3. Текущая схема

```text
Work Item
---------
name                [Frappe]
title               required
work_type            required
state                required / workflow-managed candidate

description          optional
due_at               optional

owner                [Frappe]
creation             [Frappe]
modified             [Frappe]
modified_by          [Frappe]
```

Назначение пользователей в prototype v0.1 не дублируется отдельным полем `responsible/assigned_to`; проверяется использование штатного Assignment/ToDo Frappe. Подробно: `ASSIGNMENT_V0_1.md`.

## 4. Почему `work_type` обязателен

Без явного типа разные классы работы быстро начинают различаться через заголовки, теги и случайные Custom Fields.

`Work Type` позволяет классифицировать единицы работы, сохраняя общий `Work Item`.

Примеры пользовательских типов:

- Поручение;
- Проверка;
- Запрос;
- Инцидент.

VEQTA не должна навязывать этот список.

## 5. Почему `state` обязателен

Для управляемой работы должно существовать одно текущее состояние.

Конкретные состояния и их переходы определяет пользовательский процесс.

VEQTA пока не фиксирует обязательный набор `New / Active / Waiting / Done` и не создаёт собственный workflow engine до проверки штатных возможностей Frappe.

В prototype v0.1 проверяется использование стандартного `Workflow State` и workflow-state Link-поля, которое Frappe создаёт для активного Workflow.

## 6. Назначение пользователей

После проверки исходников Frappe v16 отдельное поле `responsible` исключено из минимального прототипа.

Причина: стандартный `Assign To` уже создаёт нормальные структурированные записи `ToDo`, связанные с Work Item, и допускает несколько назначенных пользователей.

Добавление отдельного `responsible/assigned_to` до определения реального требования к кардинальности ответственности создало бы дублирующий источник истины.

Поэтому сначала проверяется штатный Frappe Assignment.

## 7. `due_at`

Срок необязателен.

VEQTA не должна требовать искусственный дедлайн для каждой работы.

Не храним отдельно производные признаки вроде:

- `is_overdue`;
- `age_days`;
- `days_open`.

Они вычисляются из первичных данных.

## 8. Что сейчас сознательно не входит в `Work Item`

Не добавляем заранее:

- responsible / assigned_to;
- priority;
- workstream/context;
- outcome;
- project;
- sprint;
- SLA;
- handoff;
- approval;
- dependencies;
- parent/child hierarchy;
- recurrence;
- team ownership;
- аналитические агрегаты.

Это не запрет навсегда. Это защита Core от преждевременного разрастания.

## 9. Один факт — одно место

Не допускаются дубли вроде:

```text
state + status_text
responsible + current_owner + executor
owner + created_by
```

если эти поля выражают один и тот же факт.

Текущее состояние хранится в одном согласованном state-механизме.

Назначение пользователей в прототипе хранится штатным Assignment/ToDo Frappe.

Системный создатель — штатное `owner` Frappe, если не появится отдельный бизнес-смысл инициатора.

## 10. Текущее состояние и история

`Work Item` должен отвечать прежде всего на вопрос:

> **Что с этой работой сейчас?**

Прошлые значения не должны храниться полями вроде:

- `previous_state`;
- `old_assignee`;
- `previous_due_date`.

Для истории изменения состояния рассматривается отдельная структурированная запись `Work State Change`:

```text
work_item
from_state
to_state
changed_by
changed_at
```

Но это пока **кандидат**, а не окончательно принятая сущность. Проверка исходников v16 показала, что `Version` является техническим audit trail и хранит изменения в сериализованном `data`, поэтому аналитическая история переходов требует отдельной проверки прототипом.

## 11. Следующий шаг

Следующая задача — минимальный prototype v0.1 на актуальном стабильном Frappe v16:

- один `Work Item`;
- один `Work Type` DocType;
- два разных типа работы;
- один штатный Workflow с Conditions по `work_type`;
- штатный Assign To / ToDo;
- проверка технической и аналитической истории State.

До результатов этого прототипа не проектируем SLA, Handoff, Projects и другие расширения.
