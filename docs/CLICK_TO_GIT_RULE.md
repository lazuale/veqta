# VEQTA — правило Click → Git

Статус: **обязательное правило разработки**.

## 1. Главный принцип

Любая согласованная часть VEQTA, созданная или изменённая через Desk на dev-стенде, должна быть представлена воспроизводимыми файлами приложения и отправлена в `lazuale/veqta`.

Изменение, которое существует только в локальной базе site, **не считается частью исходников VEQTA**.

Коротко:

```text
Desk / click
    ↓
files in apps/veqta
    ↓
git diff
    ↓
commit
    ↓
push to lazuale/veqta
```

## 2. Что происходит автоматически

Для стандартных DocType приложения VEQTA при включённом Developer Mode Frappe сохраняет метаданные и boilerplate в исходное дерево app.

Типичный результат:

```text
apps/veqta/veqta/.../doctype/work_item/
├── work_item.json
├── work_item.py
├── work_item.js
└── ...
```

После создания или изменения такого DocType через Desk обязательно проверить:

```bash
cd ~/frappe/veqta-bench/apps/veqta
git status
git diff
```

## 3. Что может не попасть в Git автоматически

Часть настроек Frappe является записями базы данных site и сама по себе не обязана появиться в исходном дереве app.

Для таких настроек используются штатные механизмы Frappe:

- fixtures;
- `bench --site <site> export-fixtures`;
- export customizations для Custom Field / Property Setter / Custom DocPerm и связанных кастомизаций;
- другие штатные механизмы экспорта, если конкретный DocType Frappe этого требует.

Не вводить собственный механизм экспорта VEQTA, пока штатного механизма достаточно.

## 4. Обязательная проверка после каждого согласованного изменения

После кликов в Desk:

```bash
cd ~/frappe/veqta-bench/apps/veqta
git status
git diff
```

Если ожидаемого изменения в Git нет:

1. не считать работу законченной;
2. определить по актуальной документации и исходникам Frappe, где хранится эта конфигурация;
3. использовать штатный механизм экспорта в app;
4. снова проверить `git status` и `git diff`;
5. только после этого commit/push.

## 5. Commit и push

После проверки:

```bash
git add .
git diff --cached
git commit -m "Краткое описание изменения"
git push origin main
```

На стадии prototype допускается прямой `main`.

## 6. Что является источником истины

Для продукта VEQTA источником истины является Git repository `lazuale/veqta`, а не локальная база prototype site.

Site — среда разработки и проверки.

Repository — воспроизводимое состояние продукта.

Новый чистый site после установки app и выполнения штатных migrations/import fixtures должен получать ту же согласованную конфигурацию VEQTA без ручного повторного накликивания.

Это является критерием того, что настройка действительно стала частью продукта.

## 7. Что не пушим

Не отправляются в repository:

- вся база MariaDB;
- `site_config.json` с секретами;
- Administrator password;
- private SSH keys;
- пользовательские тестовые данные;
- весь `veqta-bench`;
- исходники Frappe.

Пушатся только исходники app VEQTA, экспортированная продуктовая конфигурация и документация проекта.

## 8. Контрольное правило

> **Если после удаления локального site и создания чистого site VEQTA нельзя восстановить из Git без повторного ручного накликивания продуктовой конфигурации — значит что-то не было корректно зафиксировано в исходниках.**
