# 02. Desk, Desktop, Sidebar, Workspace и навигация Frappe 16

Эта глава разбирает штатный пользовательский интерфейс **чистого Frappe Framework 16**.

Цель — понять:

- куда пользователь попадает после входа;
- что такое Desk;
- как устроена навигация v16;
- чем отличаются Desktop, Sidebar и Workspace;
- какие рабочие экраны Frappe строит штатно;
- когда собственного frontend ещё не требуется.

> Здесь речь именно о **Frappe Framework**, а не об интерфейсе ERPNext, CRM, Helpdesk, HRMS или другого приложения.

Проверено: **2026-08-30**.

---

## 1. Что такое Desk

`Desk` — основной встроенный интерфейс Frappe для системных пользователей.

Через Desk пользователь работает с:

```text
Workspaces
DocTypes
Documents
Lists
Forms
Reports
Kanban
Calendar
Tree
настройками
пользователями
правами
автоматизацией
```

Главная идея:

```text
DocType metadata
      │
      ▼
     Desk
      │
      ├── List View
      ├── Form View
      ├── Report View
      ├── Kanban View
      ├── Calendar View
      └── другие представления
```

То есть для каждого нового DocType не требуется вручную создавать базовую административную страницу.

---

## 2. Desk — не весь Frappe

Важно не путать Frappe с Desk.

Framework также предоставляет:

```text
REST API
Web Forms
website-механизмы
background jobs
scheduler
printing
email
files
server-side API
```

Desk — одна из пользовательских поверхностей Framework.

---

## 3. System User и Website User

Desk предназначен прежде всего для **System User**.

Упрощённо:

```text
System User
    ↓
   Desk

Website / portal user
    ↓
Web Form / website surface
```

Если человеку нужно только заполнить внешнюю форму, это ещё не означает, что ему нужен полный Desk.

Web-интерфейсы будут разобраны отдельно в следующих главах.

---

## 4. Почему интерфейс v16 нужно изучать отдельно

Frappe 16 заметно изменил навигацию относительно старых версий.

Среди основных изменений:

- постоянная боковая панель;
- `Workspace Sidebar`;
- Desktop для публичных Workspaces;
- изменённое расположение поиска, уведомлений и пользовательских действий;
- обновлённая модель List View.

Поэтому видео и скриншоты старых версий могут быть концептуально полезны, но не всегда совпадают с v16 по расположению элементов.

---

## 5. Общая карта Desk

Упрощённо интерфейс можно представить так:

```text
┌────────────────┬────────────────────────────────────┐
│                │                                    │
│    Sidebar     │            Current Page            │
│                │                                    │
│ Search         │ Workspace                          │
│ Navigation     │ List                               │
│ Workspaces     │ Form                               │
│ Notifications  │ Report                             │
│ User           │ Settings / Page / ...              │
│                │                                    │
└────────────────┴────────────────────────────────────┘
```

Левая часть отвечает в первую очередь за навигацию.

Правая — за текущий рабочий экран.

---

## 6. Desktop

Desktop — один из верхних уровней навигации v16.

Его задача — дать пользователю понятные точки входа в доступные Workspaces.

Концептуально:

```text
Desktop
├── Workspace A
├── Workspace B
├── Workspace C
└── My Workspaces
```

Desktop не является бизнес-сущностью.

Не нужно создавать отдельный DocType только потому, что требуется новый раздел в интерфейсе.

---

## 7. Sidebar

В v16 боковая панель является постоянной частью Desk.

В ней находятся или через неё доступны:

```text
поиск / Awesomebar
Workspace navigation
уведомления
пользовательское меню
системные переходы
```

Sidebar — штатная оболочка навигации Frappe, а не меню конкретного бизнес-модуля.

---

## 8. Workspace Sidebar

В v16 навигация Workspaces связана с механизмом `Workspace Sidebar`.

Практический смысл:

> для типичного Frappe-приложения сначала следует использовать и настроить штатную навигацию, а не писать отдельную боковую панель.

Это не означает, что собственный frontend запрещён. Просто необходимость в нём должна появиться из реального ограничения Desk.

---

## 9. Awesomebar

Awesomebar — глобальный поиск и command palette Frappe.

Через него удобно быстро находить:

```text
DocTypes
Documents
Reports
Pages
Settings
```

Для администратора это один из основных способов навигации.

Новичку полезно выработать привычку:

> не искать каждый системный экран по меню вручную, а сначала попробовать найти его через глобальный поиск.

---

## 10. Workspace

Workspace — рабочая стартовая страница внутри Desk.

Он объединяет:

```text
навигацию
быстрые действия
ссылки
небольшие списки
показатели
графики
```

Пример:

```text
REQUESTS
──────────────────────────────

Open                 Overdue
 24                     3

[New Request]
[All Requests]

Recent Requests
REQ-001
REQ-002
REQ-003

Chart
...
```

Такой экран можно собрать штатными средствами без отдельного SPA.

---

## 11. Public Workspace

Public Workspace является общей частью интерфейса для пользователей, которым он доступен.

Он подходит для стандартной навигации приложения или общего рабочего раздела.

Если такой Workspace является частью поставляемого App, его стабильная конфигурация должна быть воспроизводима вместе с приложением, а не зависеть только от ручной настройки одного Site.

---

## 12. Private Workspace

Private Workspace принадлежит конкретному пользователю и подходит для персональной организации.

Например:

```text
мои ссылки
мои отчёты
мой рабочий экран
```

Главное различие:

```text
Public Workspace
→ общий интерфейс

Private Workspace
→ персональная настройка
```

Критическая бизнес-логика не должна зависеть от личного Workspace конкретного пользователя.

---

## 13. Иерархия Workspaces

Workspaces могут образовывать навигационную иерархию.

Например:

```text
Operations
├── Requests
├── Reviews
└── Directory
```

Но структура Workspaces должна отражать реальные пользовательские сценарии.

Не нужно механически копировать в навигацию внутреннюю структуру Python-пакетов или Module Def.

---

## 14. Workspace Blocks

Workspace строится из штатных блоков.

К важным относятся:

```text
Shortcut
Quick List
Number Card
Chart
Onboarding
Cards / Links
Heading / Text
```

Отдельно разберём их глубже в главе по Workspace.

Сейчас важно понять, что Workspace — не просто список URL.

---

## 15. Shortcut

Shortcut — быстрый переход к нужному объекту или представлению.

Например:

```text
[Open Requests]
```

может вести не просто в DocType, а сразу в List View с подготовленными фильтрами.

Это позволяет создавать удобные сценарии:

```text
All Requests
My Requests
Open Requests
Critical Requests
```

без создания четырёх разных сущностей данных.

---

## 16. Quick List

Quick List показывает небольшой набор документов прямо на Workspace.

Например:

```text
Recent Requests
────────────────
REQ-001
REQ-002
REQ-003
```

Quick List хорош для быстрого обзора.

Для полноценного поиска, фильтрации и массовой работы используется List View.

---

## 17. Number Card

Number Card показывает один показатель.

Например:

```text
Open
 143
```

или:

```text
Overdue
   7
```

Это удобно для оперативных метрик на Workspace.

Но Number Card сам по себе не является полноценной BI-системой.

---

## 18. Chart

Dashboard Charts могут использоваться на Workspace для простой прикладной аналитики.

Например:

```text
документы по статусам
динамика создания
распределение по категориям
```

Если аналитика требует сложных витрин, больших объёмов или нескольких источников, вопрос уже выходит за рамки обычного Workspace Chart.

---

## 19. List View

List View — основной рабочий экран для множества Documents одного DocType.

Например:

```text
Request
────────────────────────────────────────────
REQ-001   Ошибка отчёта       Open
REQ-002   Проверить договор   In Progress
REQ-003   Подготовить акт     Closed
```

List View — это гораздо больше, чем вывод таблицы.

Он обычно используется для:

```text
поиска
фильтрации
сортировки
открытия документов
массовых действий
переключения представлений
```

---

## 20. Filters

Фильтры — один из ключевых механизмов ежедневной работы в Desk.

Пример:

```text
Status = Open
Priority = High
Department = Operations
```

Поэтому при проектировании DocType важно не только создать поля, но и решить, какие из них должны быть удобными стандартными фильтрами.

Это позже свяжется со свойством DocField `In Standard Filter`.

---

## 21. Saved Filters и повторяемая навигация

Если пользователь постоянно повторяет одну и ту же выборку, её не нужно каждый раз собирать вручную.

Frappe предоставляет механизмы сохранения и повторного использования фильтров/представлений в зависимости от конкретного экрана.

Практическая идея:

```text
данные остаются одним DocType
разные рабочие выборки создаются через views и filters
```

---

## 22. Form View

Form View — экран одного конкретного Document.

Например:

```text
Request: REQ-0001
```

Форма строится на базе metadata DocType и DocFields.

Поэтому расположение полей, секции, вкладки, обязательность и многие другие свойства можно менять без создания собственного HTML-шаблона формы.

Подробно Form View будет разобран отдельно.

---

## 23. Другие представления

В зависимости от типа и настройки данных Frappe предоставляет дополнительные views:

```text
Report
Kanban
Calendar
Gantt
Tree
```

Главный принцип:

```text
Document data
     │
     ├── List View
     ├── Form View
     ├── Kanban View
     ├── Calendar View
     └── другие views
```

Представление не обязательно является новой сущностью данных.

---

## 24. Kanban как пример

Если один DocType содержит поле состояния, его документы могут отображаться колонками.

Например:

```text
NEW        IN PROGRESS       DONE

REQ-1      REQ-2             REQ-4
REQ-3      REQ-5
```

Здесь:

```text
Request
→ бизнес-данные

Status
→ состояние данных

Kanban
→ способ отображения
```

Это различие крайне важно при моделировании приложения.

---

## 25. Notifications в интерфейсе

Системные уведомления доступны из общей оболочки Desk.

Но UI уведомлений и механизм `Notification` — не совсем одно и то же понятие.

Позже отдельно разберём:

```text
уведомления в интерфейсе
Notification DocType
email notifications
условия и события
```

На этом этапе достаточно понимать, где пользователь видит системные уведомления.

---

## 26. Пользовательское меню

Из пользовательской части навигации доступны действия, связанные с текущей учётной записью и системными настройками, в зависимости от прав пользователя.

Важно понимать:

> набор видимых пунктов Desk зависит не только от установленного App, но и от ролей и permissions текущего пользователя.

Поэтому два пользователя одного Site могут видеть разный интерфейс.

---

## 27. Интерфейс и permissions связаны

Desk не должен рассматриваться как слой безопасности сам по себе.

Правильная логика:

```text
Permissions
     ↓
что пользователь имеет право делать
     ↓
Desk показывает доступные ему действия и данные
```

Скрытая кнопка не является заменой серверного permission rule.

Permissions будут подробно разобраны в отдельном блоке курса.

---

## 28. Customize Form и стандартный Desk

Если штатная Form View почти подходит, это ещё не повод писать свою страницу.

Frappe позволяет изменять существующие формы через metadata и `Customize Form`.

Прежде чем писать frontend, обычно проверяют такую лестницу:

```text
DocType layout
      ↓
DocField properties
      ↓
Customize Form
      ↓
Client Script
      ↓
Custom Desk Page
      ↓
отдельный frontend
```

Каждый следующий уровень увеличивает объём собственной разработки.

---

## 29. Когда штатного Desk обычно хватает

Desk особенно хорошо подходит для внутренних информационных систем, где пользователи работают с:

```text
реестрами
карточками
справочниками
заявками
проверками
согласованиями
документами
отчётами
```

Если пользовательский сценарий естественно выражается через Documents, Forms, Lists, Reports и Workspaces, собственный frontend может вообще не понадобиться.

---

## 30. Когда надо изучать дальнейшие уровни UI

Причиной переходить от стандартного Desk к custom Page или собственному frontend должно быть конкретное ограничение.

Например:

```text
нужен принципиально другой interaction model
стандартные Form/List не подходят
нужна специализированная визуализация
нужен отдельный публичный продуктовый интерфейс
```

Но решение принимается после понимания штатных возможностей, а не заранее.

---

## 31. Практическое упражнение

На чистом тестовом Site:

1. Войти под Administrator.
2. Осмотреть Desktop.
3. Найти Sidebar.
4. Открыть глобальный поиск.
5. Через поиск найти `User`.
6. Открыть его List View.
7. Открыть один User в Form View.
8. Вернуться назад.
9. Найти `Workspace`.
10. Посмотреть существующие Public/Private Workspaces.
11. Найти `DocType`.
12. Открыть List View DocType.
13. Открыть конкретный DocType.
14. Обратить внимание, как один и тот же Framework переключает List, Form и другие рабочие экраны.

Цель упражнения — пока ничего не настраивать, а научиться **ориентироваться в Desk**.

## 32. Что нужно запомнить

```text
Frappe Framework
      │
      └── Desk
           │
           ├── Desktop
           ├── Sidebar
           ├── Awesomebar
           ├── Workspace
           ├── List View
           ├── Form View
           ├── Report
           └── другие Views
```

Главные выводы:

1. **Desk — готовая application shell Frappe.**
2. **Workspace — рабочая страница и точка навигации, а не бизнес-сущность.**
3. **List/Form/Kanban — разные представления Documents.**
4. **Навигация v16 отличается от старых версий.**
5. **Роли и permissions влияют на то, что видит пользователь.**
6. **Собственный frontend — не первый, а один из последних уровней кастомизации UI.**
