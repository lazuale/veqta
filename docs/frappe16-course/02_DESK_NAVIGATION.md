# 02. Desk, Desktop, Sidebar, Workspace и навигация Frappe 16

Эта глава разбирает штатный пользовательский интерфейс **чистого Frappe Framework 16**. Цель — понять, где пользователь вообще находится после входа, как устроена навигация и какие части интерфейса строятся самим Framework.

> Важно: здесь речь именно о **Desk Frappe Framework 16**, а не об интерфейсе ERPNext, CRM, Helpdesk или другого приложения.

Проверено: **2026-08-30**.

---

## 1. Что такое Desk

`Desk` — встроенный административный интерфейс Frappe Framework для пользователей типа **System User**.

Framework читает metadata DocTypes и на её основе строит, среди прочего:

```text
Workspace
List View
Form View
Report View
Tree View
Calendar View
Gantt View
Kanban View
```

Поэтому Desk нельзя воспринимать как отдельную вручную написанную админку для каждого DocType.

Концептуально:

```text
DocType metadata
      │
      ▼
     Desk
      │
      ├── List
      ├── Form
      ├── Report
      └── другие views
```

### Практический смысл

Если внутреннему приложению хватает Desk, отдельный frontend писать не требуется.

Собственный frontend становится оправданным только тогда, когда штатный UX Framework действительно не закрывает задачу.

---

## 2. System User и Website User — не одно и то же

Desk предназначен для **System Users**.

Это принципиальная граница:

```text
System User
    ↓
   Desk

Website / portal user
    ↓
Web Form / website / portal surface
```

Не нужно выдавать пользователю Desk только потому, что ему надо заполнить одну форму. Для внешних или упрощённых сценариев у Frappe есть отдельные web-механизмы, которые разберём позже.

---

## 3. Главное изменение навигации в v16

В Frappe 16 навигация заметно изменилась по сравнению со старыми версиями.

В v16 введена **постоянная боковая панель** (`persistent sidebar`). Она работает на базе DocType `Workspace Sidebar`.

Также введён отдельный **Desktop**, который показывает публичные Workspaces.

Поэтому старые видео по v14/v15 могут показывать другую структуру Desk и другой путь навигации.

Упрощённо v16 выглядит так:

```text
┌──────────────┬───────────────────────────────┐
│              │                               │
│   Sidebar    │           Page                │
│              │                               │
│ Search       │   Workspace / List / Form     │
│ Workspaces   │   Report / Settings / ...     │
│ Notifications│                               │
│ User         │                               │
│              │                               │
└──────────────┴───────────────────────────────┘
```

Sidebar остаётся доступной при переходах между основными экранами Desk.

---

## 4. Маршрут Desk в v16

В migration guide v16 отдельно зафиксировано изменение frontend route:

```text
старые версии:
/app

v16:
/desk
```

То есть при чтении старой документации нужно учитывать, что URL-примеры могут относиться к предыдущей модели маршрутизации.

Это не значит, что каждую внутреннюю ссылку нужно строить вручную через `/desk`: в приложении следует использовать штатные механизмы маршрутизации Frappe.

---

## 5. Desktop

Desktop — верхний уровень навигации v16.

Его задача — показать пользователю доступные **публичные Workspaces** как основные точки входа.

Концептуально:

```text
Desktop
├── Workspace A
├── Workspace B
├── Workspace C
└── My Workspaces
```

Private Workspaces в v16 доступны через `My Workspaces`.

### Что Desktop НЕ означает

Desktop — не новый уровень предметной модели.

Не надо создавать отдельные сущности приложения ради того, чтобы показать человеку раздел системы.

Это навигационный уровень UI.

---

## 6. Apps Page и Desktop — не путать

В документации Frappe также существует понятие Apps Page — интерфейса перехода между установленными приложениями.

Для собственного приложения можно зарегистрировать элемент через `add_to_apps_screen` в `hooks.py`.

Например концептуально:

```python
add_to_apps_screen = [
    {
        "name": "my_app",
        "logo": "/assets/my_app/logo.png",
        "title": "My App",
        "route": "/desk/my-workspace"
    }
]
```

Однако migration guide v16 отдельно отмечает, что старый маршрут `/apps` deprecated.

Для курса важно не запоминать конкретный старый URL, а понимать уровни:

```text
установленное App
      ↓
точка входа приложения
      ↓
Desktop / Workspace / route
```

---

## 7. Sidebar

В v16 Sidebar — постоянная часть Desk.

Через неё пользователь получает быстрый доступ к рабочим разделам и системным инструментам.

Migration guide v16 отдельно указывает, что:

- Awesomebar перемещён в Sidebar;
- Notifications отображаются в Sidebar;
- пользовательский профиль и настройки находятся в нижней части Sidebar;
- help/system settings доступны через Sidebar;
- Workspace navigation также строится вокруг Sidebar.

То есть Sidebar — это не декоративное меню приложения, а системная навигационная оболочка Desk.

---

## 8. Workspace Sidebar

В v16 постоянная навигация powered by DocType:

```text
Workspace Sidebar
```

Большая часть структуры может генерироваться автоматически, но migration guide рекомендует для собственного приложения сделать стандартную и осмысленно подготовленную структуру, если требуется хороший UX.

Это важный архитектурный урок:

> Frappe уже предоставляет механизм навигации. Наше приложение должно **настроить его**, а не писать второй sidebar без доказанной необходимости.

---

## 9. Что такое Workspace

Workspace — рабочая страница внутри Desk.

Она одновременно является:

```text
точкой навигации
+
рабочим дашбордом
+
контейнером ссылок и показателей
```

Workspace может содержать блоки, ведущие к DocTypes, Reports и другим страницам.

Пример:

```text
WORK
────────────────────────────

Open Items        Overdue
    27               4

[New Work Item]
[All Work Items]

Recent Items
...

Chart
...
```

Это всё может существовать без отдельного frontend-приложения.

---

## 10. Public Workspace

Public Workspace доступен пользователям согласно общей конфигурации и является частью общей структуры Desk.

В Sidebar публичные Workspaces находятся в разделе `PUBLIC`.

Создавать, редактировать и удалять публичные Workspaces может пользователь с ролью:

```text
Workspace Manager
```

### Для продукта

Если Workspace является частью стандартного UX нашего App и должен воспроизводиться на других Sites, его состояние должно поставляться/экспортироваться как часть приложения, а не существовать только как ручная настройка одного dev-site.

---

## 11. Private Workspace

Private Workspace принадлежит конкретному пользователю.

В документации он отображается в разделе:

```text
MY WORKSPACES
```

Такой Workspace полезен для личной организации работы:

```text
мои ссылки
мои выборки
мой рабочий экран
```

### Важное различие

```text
Public Workspace
≈ общий продуктовый UX

Private Workspace
≈ персональная пользовательская настройка
```

Не следует проектировать обязательный процесс приложения так, чтобы он зависел от private Workspace конкретного человека.

---

## 12. Workspace может иметь иерархию

Workspace можно сделать дочерним через `Parent`.

Например:

```text
Work
├── Operations
├── Reviews
└── Administration
```

Но иерархию не нужно создавать автоматически только ради красивого дерева.

Хорошая навигация должна отражать реальные пользовательские сценарии, а не внутреннюю структуру Python-модулей.

---

## 13. Workspace Blocks

Workspace строится из блоков.

В зависимости от версии и конфигурации используются такие элементы, как:

```text
Shortcut
Quick List
Number Card
Chart
Onboarding
Links / Cards
Text / Heading
```

Они позволяют превратить Workspace из списка ссылок в рабочую стартовую страницу.

### Пример

```text
Requests
────────────────────────────

OPEN                 OVERDUE
 24                     3

[New Request]
[My Requests]
[All Requests]

Recent Requests
REQ-001
REQ-002
REQ-003
```

Для подобного экрана собственный Vue-компонент обычно не нужен.

---

## 14. Shortcut

Shortcut — быстрый переход к нужному объекту или представлению.

Его ценность не только в ссылке.

Можно сделать точку входа вроде:

```text
My Open Items
```

которая открывает DocType уже с нужными фильтрами.

Например логически:

```text
Work Item
status != Done
assigned to current user
```

Это позволяет проектировать UX по пользовательским действиям, не создавая новые сущности ради каждого списка.

---

## 15. Quick List

Quick List показывает небольшой список документов прямо на Workspace.

Например:

```text
Recent Work Items
─────────────────
WORK-017
WORK-021
WORK-024
```

Использовать Quick List разумно для небольшого контекстного списка.

Если человеку нужен полноценный поиск, фильтры, сортировка и массовые действия — лучше вести его в обычный List View.

---

## 16. Number Card

Number Card показывает один показатель:

```text
Overdue
   7
```

или:

```text
Open
 143
```

Это хороший вариант для оперативного рабочего dashboard.

Но Number Card не превращает Frappe в полноценный BI-инструмент.

---

## 17. Chart

Workspace может отображать Dashboard Charts.

Их стоит использовать для простой прикладной аналитики:

```text
количество по статусам
динамика документов
распределение по категориям
```

Если потребуется тяжёлая аналитика по большим витринам или нескольким источникам — это уже другой уровень задачи.

---

## 18. Read Only Mode и Edit Mode Workspace

Workspace имеет два основных режима:

```text
Read Only Mode
Edit Mode
```

Через Edit Mode можно изменять layout страницы.

Официальная документация отдельно предупреждает, что лучший способ редактировать расположение блоков — использовать Workspace Builder UI, потому что простое изменение документа Workspace не всегда корректно описывает позицию нового блока.

Это важный практический момент:

> metadata существует как Documents, но это не значит, что любые сложные UI-структуры лучше вручную править напрямую в записи DocType.

---

## 19. Что можно менять через Sidebar

Workspace navigation позволяет, среди прочего:

```text
редактировать свойства Workspace
создавать duplicate
удалять
скрывать
менять порядок
делать parent/child
```

Позиция в Sidebar может изменяться drag-and-drop.

Public Workspace управляется строже, чем личный.

---

## 20. Awesomebar в v16

Awesomebar — глобальный командный поиск Frappe.

В v16 он находится в Sidebar и открывается как command palette.

Клавиатурный shortcut:

```text
Cmd + K
```

На других платформах сочетание может отображаться соответствующим системным аналогом.

Awesomebar умеет помогать:

```text
переходить к DocTypes
искать Documents
открывать Reports и Pages
создавать новые записи
находить Settings
```

Для администратора и разработчика это один из главных способов навигации.

### Практический совет

Вместо запоминания длинных путей меню привыкай искать:

```text
DocType
Role Permission Manager
Workflow
Notification
Customize Form
System Console
```

через Awesomebar.

---

## 21. Notifications в Sidebar

В v16 уведомления перенесены в Sidebar и получили отдельное list-представление вместо старого popup-подхода.

Это касается **UI системных уведомлений**, а не определения правил Notification, которое мы изучим позже.

Не путать:

```text
Notifications UI
=
где пользователь читает уведомления
```

и:

```text
Notification DocType
=
правило, когда и кому отправлять уведомление
```

---

## 22. User Settings

Профиль пользователя и связанные настройки в v16 находятся в нижней части Sidebar.

Это системная часть Desk.

Не надо добавлять в Workspace отдельный пункт «мой профиль», если стандартной навигации достаточно.

---

## 23. Help и системные настройки

Migration guide v16 указывает, что Help и другие system-related settings доступны через верхнюю часть Sidebar.

Для обычного конечного пользователя важно не количество доступных системных экранов, а корректно выданные Roles и Permissions.

Хорошая структура приложения не должна рассчитывать, что каждый пользователь является System Manager.

---

## 24. List View в навигации v16

В v16 List View тоже изменился.

Из migration guide:

- удалён старый правый List Sidebar;
- Saved Filters перенесены в верхнюю часть List View;
- пользователь может настраивать quick filters прямо из List View;
- такие quick-filter настройки являются user-specific.

Это особенно важно при просмотре старых обучающих видео: расположение фильтров может отличаться.

---

## 25. Что это означает для проектирования UX

Предположим пользователю каждый день нужны:

```text
My Work
Overdue
Waiting
Completed Today
```

Плохая первая реакция:

```text
создать четыре новых страницы
написать четыре endpoint
создать свой sidebar
```

Сначала нужно проверить:

```text
Workspace Shortcut
Saved Filters
List quick filters
Number Cards
Quick List
```

Во многих случаях Framework уже закрывает задачу.

---

## 26. Desk Page

Workspace — не единственный возможный экран Desk.

Framework имеет Page API: каждый экран Desk рендерится внутри объекта `frappe.ui.Page`, а приложение может создавать custom Desk Pages.

Это уже developer-level инструмент.

Лестница должна быть такой:

```text
обычный DocType View
      ↓
Workspace
      ↓
настройка стандартных views
      ↓
Custom Desk Page
      ↓
отдельный frontend
```

Не начинать с последней ступени.

---

## 27. Form, List, Report — это не отдельные приложения

Очень важно закрепить:

```text
DocType Work Item
       │
       ├── List View
       ├── Form View
       ├── Report View
       ├── Kanban
       ├── Calendar
       └── Gantt
```

Это разные представления **одной модели данных**.

Нельзя автоматически проектировать отдельные сущности:

```text
Work Item Card
Work Item Board Record
Work Item Report Record
```

только потому, что данные показываются в разных местах.

---

## 28. Как мысленно читать Desk

Когда видишь экран Frappe, задавай вопрос:

```text
Что передо мной?
```

Один из типичных ответов:

```text
Desktop
Workspace
List View
Form View
Report
Custom Page
System DocType
```

Это намного полезнее, чем запоминать, где визуально находится конкретная кнопка.

Положение кнопки может измениться между версиями, а концепция останется.

## 29. Практика на чистом Frappe 16

На учебном Site выполни только навигационные действия — ничего пока не создавай.

### Шаг 1

Войди как Administrator/System User и найди постоянную Sidebar.

### Шаг 2

Открой Desktop и посмотри, какие Public Workspaces предоставляет чистый установленный набор Apps.

### Шаг 3

Через Awesomebar найди:

```text
User
DocType
Workspace
Role Permission Manager
```

Пока ничего не редактируй.

### Шаг 4

Открой любой обычный DocType и последовательно определи:

```text
List View
Form View
```

### Шаг 5

Вернись в Workspace и найди переключение Edit Mode, если твои права его позволяют.

### Шаг 6

Посмотри разделы:

```text
PUBLIC
MY WORKSPACES
```

### Шаг 7

В List View обрати внимание на:

```text
Saved Filters
Quick Filters
View switcher
```

Цель упражнения — начать узнавать **типы экранов Frappe**, а не запоминать координаты кнопок.

## 30. Что пока НЕ делаем

На этом этапе не нужно:

```text
писать Client Script
создавать custom Page
менять hooks.py
создавать собственный sidebar
делать Vue frontend
переписывать тему Desk
```

Сначала нужно увидеть настоящий объём штатного интерфейса.

---

## 31. Граница штатной возможности

### Frappe уже предоставляет

```text
Desk shell
Desktop
Sidebar
Workspace
Public/Private Workspaces
Awesomebar
Notifications UI
List/Form/Report views
базовый dashboard layout
навигацию между объектами
```

### Наш App должен решать

```text
какие предметные сущности нужны
какие Workspaces действительно полезны
какие shortcuts и показатели нужны пользователю
какие роли видят какие части системы
какой UX является стандартом продукта
```

### Собственный frontend нужен только если

можно сформулировать конкретное доказанное ограничение Desk, которое нельзя разумно закрыть штатными views, Workspace или custom Desk Page.

---

## 32. Что это означает для VEQTA

Для VEQTA на текущем этапе нельзя заранее утверждать:

```text
"нам обязательно нужен свой интерфейс"
```

Сначала prototype обязан проверить:

```text
Desk
Workspace
List
Form
Kanban
штатную Sidebar-навигацию
```

и только затем фиксировать конкретные UX-недостатки.

Иначе мы рискуем начать разработку frontend раньше, чем доказали необходимость.
