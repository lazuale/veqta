# 16. Границы штатного UI: Form, List, Views, Workspace и Page

За главы 11–15 мы уже собрали почти весь базовый интерфейс учебного приложения **без собственного frontend**.

Теперь нужно научиться выбирать минимальный штатный инструмент и понимать, **когда действительно появляется необходимость в Desk Page**.

Проверено для **Frappe Framework v16.32.0**.

---

## Что уже есть на стенде

К началу главы существуют:

```text
Request Form View
Request List View
Request Status Kanban
Request Calendar
Request Gantt
Training Category Tree
Training Workspace
Training Settings Single Form
```

Также у `Request` есть site-level customization:

```text
custom_local_note
Property Setter для description поля estimate_hours
```

То есть у нас уже есть достаточно живых экранов, чтобы сравнивать их не по теории, а в работающем Desk.

---

## Главный вопрос этой главы

Не:

> Как написать свой экран?

А:

> Какой самый простой штатный экран уже решает задачу?

Практический порядок такой:

```text
1. Form View
2. List View
3. готовый специальный View
4. Workspace
5. только затем собственный Page
```

Это не запрет на разработку. Это способ не писать код там, где Framework уже решил задачу.

---

# Form View

## Когда выбирать Form

Если пользователь работает в основном с **одним Document**, первым кандидатом является Form View.

Наш пример:

```text
открыть один Request
изменить Priority
выбрать Responsible
добавить Items
сохранить
```

Для этого уже есть:

```text
Request Form View
```

Не нужен отдельный Page только потому, что форма содержит несколько секций и вкладок.

---

## Что сначала пробовать внутри Form

До собственного UI у формы уже есть:

```text
DocField types
Tab / Section / Column Break
Mandatory / Read Only / Hidden
Display Depends On
Fetch From
Child Table
Table MultiSelect
Customize Form
```

Позже появится Client Script, но даже он не означает, что нужен новый Page.

---

# List View

## Когда выбирать List

Если пользователь работает с **множеством Documents одного DocType**, сначала проверяем List View.

Пример:

```text
показать все Request
отобрать Open
отобрать High
отсортировать по Due Date
открыть нужную запись
```

Это ровно задача List View.

Собственная полноэкранная таблица не нужна только ради фильтров и сортировки.

---

# Специальные Views

## Kanban

Подходит, когда основной вопрос:

```text
в каком состоянии находится Document?
```

У нас:

```text
Request.status
→ Open / In Progress / Done
```

## Calendar

Подходит, когда важно увидеть Documents во времени.

У нас:

```text
start_date
end_date
```

## Gantt

Подходит, когда нужен именно временной интервал и его длительность.

## Tree

Подходит только для настоящей иерархической модели.

У нас:

```text
Training Category
```

Нельзя решить проблему неправильной модели данных выбором красивого View.

---

# Workspace

## Когда выбирать Workspace

Workspace нужен как **рабочая стартовая страница**, где собираются готовые части.

Наш `Training` уже содержит:

```text
Shortcuts
Quick List
Number Card
Dashboard Chart
```

Если задача звучит:

> Дать пользователю удобный вход в основные экраны и несколько показателей,

то Workspace уже подходит.

Не нужно писать Page только ради страницы с кнопками и графиком.

---

# Single Form

Иногда даже отдельный список не нужен.

Для одной глобальной настройки Site у нас есть:

```text
Training Settings
Is Single = 1
```

Пользователь открывает одну Form View настроек.

Это ещё один пример того, что правильная metadata может убрать необходимость в собственном UI.

---

# Когда штатных экранов действительно мало

Представим требование:

```text
Один полноэкранный пульт оператора.

Слева — несколько независимых фильтров.
Сверху — сводные показатели.
В центре — две разные интерактивные таблицы.
Справа — собственная панель действий.
Изменение выбора в одной области мгновенно перестраивает другие области.
```

Такой экран уже не описывается как:

```text
форма одного Document
или
список одного DocType
или
Workspace из готовых блоков
```

Вот здесь появляется кандидат:

```text
Desk Page
```

---

## Что такое Desk Page

`Page` — системный DocType Frappe для собственного экрана внутри Desk.

Для Standard Page приложение получает файлы страницы, а разработчик сам управляет её содержимым.

В `v16.32.0` controller `Page` явно проверяет:

```text
создание нового Page → Developer Mode должен быть включён
редактирование → Administrator
```

То есть Page — не случайная low-code галочка. Это уже часть разработки App.

---

## Почему Page не создаём в этой лабораторной

Чтобы получить пользу от Page, нужно уже понимать как минимум:

```text
JavaScript страницы
получение данных
действия пользователя
серверные операции
permissions
```

Эти темы ещё впереди.

Создать пустую Page сейчас только ради появления файла — не практика, а ритуал.

Поэтому в обязательном маршруте главы 16 мы **не создаём Page**.

Мы учимся правильно определить момент, когда она нужна.

---

## Что Frappe создаёт при Standard Page

Это полезно знать как границу, но пока не выполнять.

При создании Standard Page Frappe экспортирует metadata в App и создаёт JS-файл, если его ещё нет.

Условно:

```text
training/<module>/page/<page_name>/
├── <page_name>.json
└── <page_name>.js
```

Именно с этого момента разработчик начинает сам строить содержимое экрана.

Подробная разработка такого UI не относится к базовому low-code маршруту блока C.

# Простая таблица выбора

| Требование | Первый штатный выбор |
|---|---|
| открыть и изменить один Request | Form View |
| найти набор Requests | List View |
| двигать Request по Status | Kanban |
| смотреть даты | Calendar |
| смотреть интервалы | Gantt |
| работать с иерархией категорий | Tree |
| собрать точки входа и показатели | Workspace |
| редактировать одну глобальную настройку | Single Form |
| построить собственный сложный интерактивный экран | Page |

---

## Metadata сначала, код потом

В лабораторной будет требование:

```text
скрывать Due Date у Done Request
```

Оно выражается простым условием DocField:

```text
Display Depends On
```

Значит Page для него точно избыточен.

Мы сначала намеренно напишем условие наоборот, увидим неправильное поведение, исправим его и затем полностью вернём поле в исходное состояние.

Это важнее пустой демонстрации Page: ученик видит, **как выбирать минимальный механизм**.

---

## Page не является permission layer

Даже когда позже появится собственный Page, его наличие не должно давать доступ к данным само по себе.

Разделяем:

```text
Page
→ экран

Document permissions
→ доступ к данным и действиям
```

В следующем блоке как раз начнём изучать пользователей, роли и permissions.

---

## Что произойдёт в лабораторной

Ты:

1. откроешь реальные Form/List/Kanban/Calendar/Gantt/Tree/Workspace/Single Form;
2. для каждого назовёшь его назначение;
3. разберёшь набор конкретных требований и выберешь минимальный штатный UI;
4. решишь простое условие через `Display Depends On`;
5. намеренно задашь условие наоборот;
6. исправишь его;
7. в конце полностью очистишь экспериментальное условие;
8. зафиксируешь, для какого требования действительно понадобился бы Page.

---

## Что запомнить

1. Не каждый новый сценарий требует собственного экрана.
2. Form работает с одним Document, List — с набором Documents.
3. Kanban/Calendar/Gantt/Tree отвечают на конкретные способы просмотра данных.
4. Workspace собирает готовые блоки и переходы.
5. Page нужен для действительно собственного интерактивного интерфейса.
6. В v16 Standard Page является developer-level объектом.
7. UI и permissions — разные уровни.
