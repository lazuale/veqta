# 16. Desk Page и границы штатного интерфейса

До этого почти весь интерфейс мы получали бесплатно из metadata:

- DocType дал нам Form View;
- тот же DocType дал List View;
- нужные поля позволили включить Kanban, Calendar, Gantt или Tree;
- Workspace собрал ссылки, списки, показатели и графики на одном экране.

Во многих приложениях этого хватает очень надолго.

Но иногда нужен экран, который уже не похож ни на форму одного документа, ни на список, ни на дашборд из готовых блоков.

Тогда во Frappe есть **Desk Page** — собственная страница внутри Desk.

Проверено: **2026-08-30**.

---

## 1. Сначала простой пример

Представим, что есть DocType `Request`.

Обычную работу с ним уже можно закрыть штатно:

```text
Form View
└── открыть одну Request

List View
└── найти и отфильтровать много Request

Kanban
└── разложить Request по этапам

Workspace
└── собрать ссылки, счётчики и графики
```

А теперь появляется задача:

> Сделать единый экран оператора, где слева выбирается подразделение, сверху задаётся дата, в центре одновременно показываются три связанные выборки, а кнопка запускает специальную серверную операцию над выбранными строками.

Такой экран уже неудобно изображать обычной Form View.

Workspace тоже не очень подходит: он хорошо **компонует готовые блоки**, но не предназначен для произвольного интерактивного интерфейса.

Вот здесь Desk Page уже выглядит логично.

---

## 2. Что такое Desk Page

Desk Page — это собственный экран внутри Desk, которым управляет JavaScript приложения.

Он остаётся частью интерфейса Frappe:

```text
Desk
├── Sidebar
├── Workspace
├── Form View
├── List View
└── Custom Page
```

То есть пользователь по-прежнему находится внутри Desk, с той же сессией Frappe и доступом к стандартному JavaScript API.

Но содержимое страницы разработчик уже собирает сам.

Это принципиальная граница.

### До Page

Frappe в основном строит UI за нас из metadata.

### После перехода к Page

мы уже сами отвечаем за:

- разметку;
- состояние экрана;
- кнопки;
- загрузку данных;
- обработчики событий;
- обновление частей интерфейса;
- удобство работы пользователя.

Поэтому **Page — это уже application code**, а не обычная настройка формы.

---

## 3. Где находится Page во Frappe

Во Framework есть системный DocType `Page`.

У него, среди прочего, есть поля:

```text
Page Name
Title
Module
Standard
Roles
Restrict To Domain
```

`Page Name` становится техническим именем страницы.

Например:

```text
Page Name: request-console
Title: Request Console
Module: Training
```

Для стандартной страницы код хранится в App.

Упрощённо структура выглядит так:

```text
training_app/
└── training_app/
    └── training/
        └── page/
            └── request_console/
                ├── request_console.json
                ├── request_console.js
                └── ...
```

При необходимости рядом могут использоваться CSS, HTML-шаблоны и Python-код.

---

## 4. Page — не low-code объект

Это важно запомнить сразу.

В Frappe 16 создание нового `Page` требует **Developer Mode**.

Кроме того, исходный controller `Page` не разрешает обычное редактирование Page кому угодно: его редактирование жёстко ограничено Administrator, если Framework сам не выполняет специальную системную операцию.

То есть Page задуман как часть разработки приложения.

Не стоит мыслить так:

```text
не хватает Workspace
→ накликаю Custom Page
```

Правильнее:

```text
не хватает стандартных View и Workspace
→ появилась доказанная необходимость в своём UI
→ пишем Page как часть App
```

---

## 5. Минимальная Page

В JavaScript страницы обычно есть обработчик `on_page_load`.

Минимальный пример:

```javascript
frappe.pages["request-console"].on_page_load = function (wrapper) {
    const page = frappe.ui.make_app_page({
        parent: wrapper,
        title: "Request Console",
        single_column: true,
    });
};
```

Здесь происходит всего две вещи:

1. Frappe открывает Page;
2. `frappe.ui.make_app_page()` создаёт стандартный каркас страницы Desk.

В результате мы получаем привычную оболочку Frappe, но центральное содержимое можем строить сами.

На первом проходе курса код заучивать не нужно.

Главное понять принцип:

```text
Page
  ↓
Frappe даёт каркас Desk
  ↓
разработчик наполняет страницу своим UI
```

---

## 6. Что даёт `frappe.ui.Page`

Не нужно рисовать вообще всё с нуля.

Page API уже умеет типичные элементы интерфейса Desk:

- заголовок страницы;
- дополнительный текст рядом с заголовком;
- indicator;
- primary action;
- обычные кнопки;
- меню;
- actions menu;
- стандартные поля управления в шапке страницы.

То есть Page занимает промежуточное положение:

```text
полностью готовая Form View
        ↓
Custom Desk Page
        ↓
полностью отдельный frontend
```

У Page свободы уже много, но он всё ещё использует оболочку и API Desk.

---

## 7. Lifecycle страницы простыми словами

У Form View были свои события вроде `refresh`.

У Page тоже есть жизненный цикл.

Чаще всего достаточно помнить три события:

### `on_page_load`

Страница создаётся впервые.

Подходит для первоначальной сборки интерфейса.

### `on_page_show`

Пользователь снова переходит на уже созданную страницу.

### `refresh`

Страница должна обновить состояние.

Упрощённо:

```text
первое открытие
     ↓
on_page_load
     ↓
on_page_show
     ↓
refresh

ушли на другой экран
     ↓
вернулись
     ↓
on_page_show
     ↓
refresh
```

Это полезно, потому что Desk является SPA: переход между экранами не означает полную перезагрузку браузерной страницы.

---

## 8. Откуда Page берёт данные

Сам Page — это интерфейс.

Бизнес-данные по-прежнему должны жить в нормальной модели Frappe:

```text
DocType
├── Request
├── Department
└── другие документы
```

Page может читать их через стандартные API или вызывать серверные методы.

Например, логика экрана может выглядеть так:

```text
Page
  ↓
пользователь нажал «Обновить»
  ↓
JavaScript вызывает сервер
  ↓
сервер получает Request
  ↓
возвращает результат
  ↓
Page перерисовывает таблицу
```

Не нужно создавать отдельную параллельную модель данных только потому, что появился свой экран.

---

## 9. Где должна жить бизнес-логика

Очень частая ошибка — превратить большой `.js` Page в сердце приложения.

Например:

```text
request_console.js
├── проверки прав
├── расчёты
├── правила статусов
├── изменение документов
├── интеграции
└── ещё 2000 строк UI
```

Так делать не стоит.

Page должен в первую очередь управлять интерфейсом.

Правила, которые должны работать независимо от конкретного экрана, лучше держать на серверной стороне приложения.

Например:

```text
UI Page
   ↓
"закрыть выбранные Request"
   ↓
server method / controller
   ↓
проверка правил
   ↓
изменение документов
```

Тогда та же операция останется корректной, даже если позже её вызовет:

- другой Page;
- Form View;
- background job;
- REST API;
- внешняя система.

---

## 10. Page и permissions

У самого `Page` можно задать Roles.

Если Roles указаны, Frappe проверяет, имеет ли текущий пользователь хотя бы одну разрешённую роль перед загрузкой страницы.

Это управляет **доступом к самому экрану**.

Но есть важное правило:

> Доступ к Page не заменяет permissions на данные и серверные проверки.

Представим:

```text
Role Operator
    ↓
может открыть Request Console
```

Это ещё не должно автоматически означать:

```text
может читать и изменять любые Request
```

Серверные методы и операции с Document всё равно должны соблюдать реальные permissions и бизнес-правила.

### Почему это важно

Спрятанная кнопка — не защита.

Закрытая страница — тоже не защита данных сама по себе.

Безопасность должна обеспечиваться на сервере.

---

## 11. Page и Workspace — не одно и то же

Это одна из главных развилок.

### Workspace выбираем, если нужно

- сделать главную страницу раздела;
- дать быстрые ссылки;
- показать несколько Quick List;
- вывести Number Card;
- вывести Chart;
- собрать готовые блоки на одном экране.

Пример:

```text
Requests Workspace
├── New Request
├── All Requests
├── Open Requests: 27
└── Requests by Status
```

Здесь собственный Page не нужен.

### Page выбираем, если нужно

- своё расположение элементов;
- собственное состояние интерфейса;
- сложное взаимодействие между несколькими частями экрана;
- специальные кнопки и действия;
- нестандартные таблицы или панели;
- UI, который не выражается готовыми Workspace blocks.

Пример:

```text
Request Console

Department: [ Production ▼ ]
Date:       [ 30.08.2026 ]

[ Unassigned: 12 ] [ Overdue: 4 ] [ In Work: 18 ]

┌──────────────────────────────────────────┐
│ собственная интерактивная рабочая зона │
└──────────────────────────────────────────┘

[ Assign selected ] [ Recheck ]
```

---

## 12. Page и Form View

Если экран в основном редактирует **один документ**, сначала почти всегда нужно проверить Form View.

Например, плохая причина создавать Page:

> Мне нужна красивая форма Request.

Уже есть:

```text
DocType
→ Form View
→ Customize Form
→ Client Script
```

Page оправдан, когда пользователь работает уже не с одной карточкой, а с отдельным сценарием взаимодействия.

Простой тест:

> Можно ли описать экран фразой «это форма одного Document»?

Если да — вероятнее всего нужен Form View, а не Page.

---

## 13. Page и List View

Точно так же не нужно заменять Page обычный список.

Если задача звучит так:

> Покажи все Request, дай фильтры, сортировку и массовые действия.

Сначала проверяем List View.

Он уже умеет очень много из этого штатно.

Page нужен, когда обычная модель:

```text
строки + фильтры + actions
```

реально перестала подходить.

---

## 14. Desk Page и Web Form — совершенно разные вещи

Названия могут путать новичка.

### Desk Page

Это собственный экран **внутри Desk**.

Обычно он предназначен для System User.

### Web Form

Это штатный web-интерфейс для создания или изменения Document вне обычного Desk-интерфейса.

Его мы подробно разберём позже.

Условно:

```text
сотрудник работает внутри системы
→ Desk / Page

внешнему или website user нужна простая форма
→ Web Form
```

---

## 15. Desk Page и Portal Page

Во Frappe есть ещё website/portal pages.

Это тоже не одно и то же.

Portal Page живёт в web-части приложения и обычно соответствует файлам в папке `www`.

Например:

```text
training_app/www/help.html
```

может дать web-route вроде:

```text
/help
```

А Desk Page работает внутри административного SPA Desk.

Поэтому сначала спрашиваем:

```text
кто пользователь этого экрана?
```

Если это внутренний System User — Desk может быть естественным местом.

Если это посетитель сайта или Website User — нужно смотреть в сторону web/portal возможностей.

---

## 16. Когда уже нужен отдельный frontend

Custom Page очень мощный, поэтому легко попасть в ловушку:

> Раз можно написать любой JavaScript внутри Desk, значит весь продукт можно сделать одной огромной Page.

Технически можно зайти далеко.

Архитектурно это не всегда хорошая идея.

Отдельный frontend стоит рассматривать, когда интерфейс уже системно расходится с Desk.

Например, нужны одновременно:

- полностью собственная навигация;
- отдельный дизайн-системный слой;
- другой layout всего приложения;
- сложное клиентское состояние между десятками экранов;
- мобильный UX как самостоятельный продукт;
- публичный интерфейс;
- frontend-команда работает независимо от Desk;
- приложение фактически перестало выглядеть и вести себя как Desk.

Тогда разумная архитектура может стать такой:

```text
Custom frontend
       ↓
REST / RPC API
       ↓
Frappe backend
       ↓
DocType / permissions / business logic
```

Frappe при этом не обязательно выбрасывать.

Он может остаться backend-платформой.

---

## 17. Vue внутри Desk Page

Frappe позволяет использовать Vue внутри Desk Page.

Это полезно, если страница стала достаточно интерактивной и обычный JavaScript/DOM-код начинает разрастаться.

Схема примерно такая:

```text
Desk Page
   ↓
frappe.ui.make_app_page()
   ↓
Vue component
   ↓
Frappe API / server methods
```

Но сам факт наличия Vue ещё не означает, что Page автоматически является хорошей архитектурой для большого самостоятельного frontend-приложения.

Vue решает способ организации клиентского кода.

Он не отменяет вопрос:

> Этот интерфейс вообще должен жить внутри Desk или уже заслуживает отдельного frontend?

---

## 18. Лестница выбора UI

Теперь можно собрать весь блок интерфейса курса в одну лестницу.

```text
Нужно показать или изменить один Document?
        ↓ да
     Form View
        ↓ не хватает
     Customize Form
        ↓ не хватает
     Client Script

Нужно работать со многими Document?
        ↓
     List / Report / Kanban / Calendar / Gantt / Tree

Нужна главная страница раздела?
        ↓
     Workspace

Нужен нестандартный рабочий сценарий внутри Desk?
        ↓
     Desk Page

Интерфейс системно перестал быть похож на Desk?
        ↓
     отдельный frontend
```

Это не жёсткий закон.

Но как стартовая архитектурная проверка эта схема очень полезна.

---

## 19. Пять типичных ошибок

### Ошибка 1. Page вместо Form View

Пишем собственную форму для объекта, который уже прекрасно описывается DocType.

**Результат:** вручную повторяем то, что Frappe даёт бесплатно.

### Ошибка 2. Page вместо Workspace

Пишем сотни строк JavaScript только ради трёх ссылок, счётчика и графика.

**Результат:** ненужный код.

### Ошибка 3. Вся бизнес-логика живёт в Page JS

Правила работают только пока пользователь нажимает кнопки конкретного экрана.

**Результат:** API и фоновые операции начинают обходить эти правила.

### Ошибка 4. Считать скрытую кнопку системой прав

```javascript
if (!allowed) {
    button.hide();
}
```

Это UX, а не полноценная защита.

### Ошибка 5. Делать отдельный frontend слишком рано

Иногда команда пишет SPA с нуля, хотя задача закрывалась DocType + Form + List + Workspace.

**Результат:** резко растёт количество кода, который нужно разрабатывать и сопровождать.

## 20. Мини-практика: выбери правильный экран

Для каждого случая выбери минимальный подходящий инструмент.

### Случай A

Нужно редактировать одну `Request`.

**Ответ:** Form View.

### Случай B

Нужно увидеть все просроченные `Request` и отфильтровать их по подразделению.

**Ответ:** сначала List View + filters.

### Случай C

Нужно на одной стартовой странице показать:

- кнопку New Request;
- последние Request;
- число открытых Request;
- график по статусам.

**Ответ:** Workspace.

### Случай D

Нужен специальный диспетчерский экран, в котором несколько взаимосвязанных таблиц обновляются от одного набора фильтров и есть собственные пакетные операции.

**Ответ:** Desk Page уже имеет смысл рассматривать.

### Случай E

Нужен публичный клиентский интерфейс с собственной навигацией и дизайном, не похожим на Desk.

**Ответ:** сначала web/portal возможности; для полноценного самостоятельного продукта может понадобиться отдельный frontend.

---

## 21. Что запомнить

1. **Desk Page — это application code, а не просто настройка.**
2. **Сначала используй Form/List/Workspace и другие штатные View.**
3. `frappe.ui.make_app_page()` даёт каркас страницы внутри Desk.
4. Page может иметь ограничения по Roles, но безопасность данных всё равно должна обеспечиваться сервером.
5. Page отвечает прежде всего за нестандартный UI, а не должен становиться единственным местом бизнес-логики.
6. Если собственный интерфейс перестал естественно жить внутри Desk, нужно честно рассмотреть отдельный frontend.
