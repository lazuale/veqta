# 09. Single, Tree, Submittable и Virtual DocType

Обычный DocType хранит много Documents одного типа. Но иногда нужна другая модель: одна глобальная настройка, дерево категорий, подтверждаемый документ или данные из внешнего источника.

Для таких случаев у Frappe есть специальные режимы DocType.

Проверено: **2026-08-30**.

## 1. Сначала вся картина на одной таблице

| Режим | Простыми словами | Пример |
|---|---|---|
| `Single` | существует одна запись на весь Site | App Settings |
| `Tree` | документы образуют иерархию | Category |
| `Submittable` | документ можно официально подтвердить и отменить | Approval Record |
| `Virtual` | данные берутся не из обычной таблицы Frappe | External Device |

Это не четыре варианта одной функции. Каждый режим меняет **разную часть поведения DocType**.

## 2. Single — когда запись нужна ровно одна

Представим настройки приложения:

```text
App Settings
- Default Department
- Notification Email
- Enable Feature X
```

Нам не нужны:

```text
Settings 1
Settings 2
Settings 3
```

Нужна одна форма с текущими настройками.

Для этого подходит:

```text
Is Single = ✓
```

## 3. Как хранится Single

Обычный DocType получает собственную таблицу вида:

```text
tabRequest
```

Single работает иначе: его значения хранятся в общей таблице `tabSingles`.

Поэтому у него нет обычного списка множества Documents.

На пальцах:

```text
обычный DocType → «таблица записей»
Single          → «одна страница настроек»
```

## 4. Как работать с Single в коде

Для чтения настроек есть специальные Database API методы, например:

```python
frappe.db.get_single_value("App Settings", "notification_email")
```

Можно получить Single и как Document:

```python
settings = frappe.get_doc("App Settings")
```

Точный API будет подробнее разобран позже. Сейчас важна сама модель: **имя отдельной записи выбирать не нужно, потому что экземпляр один**.

## 5. Когда Single использовать не стоит

Плохой пример:

```text
Employee Settings
```

если настройки должны быть отдельными для каждого Employee.

Тогда записей будет много, и Single уже не подходит.

Хороший вопрос перед включением:

> На всём Site действительно должна существовать только одна такая конфигурация?

Если да — Single кандидат.

## 6. Ограничение Single

В текущем Frappe при включении `Is Single` DocType не остаётся одновременно обычным Submittable/Child Table. Framework выставляет соответствующие ограничения на уровне metadata.

Это логично: «одна глобальная форма настроек» и «набор подтверждаемых транзакционных документов» — разные модели.

## 7. Tree — когда объекты образуют настоящую иерархию

Пример:

```text
Categories
├── Electronics
│   ├── Computers
│   └── Phones
└── Furniture
    ├── Tables
    └── Chairs
```

Здесь каждый Category — самостоятельный Document, но у него может быть parent.

Для такого DocType используют:

```text
Is Tree = ✓
```

## 8. Tree — не просто красивый Tree View

Это важный момент.

При Tree Frappe использует `NestedSet` model. В DocType появляются служебные поля и логика иерархии, в том числе:

```text
parent field
old_parent
lft
rgt
is_group
```

`lft` и `rgt` помогают быстро понимать положение узла и его потомков в дереве.

Новичку не нужно вручную считать эти числа. Их обслуживает Framework.

## 9. Что пользователь делает с Tree

Он может работать с иерархией примерно так:

```text
Electronics
└── Computers
    └── Laptops
```

Если переместить `Laptops` в другое место, Frappe обновляет nested-set индексы.

То есть Tree — это не поле «parent» плюс нарисованный интерфейс. Framework поддерживает структуру дерева.

## 10. Когда Tree подходит

Хорошие кандидаты:

```text
категории
организационная иерархия
структура папок/разделов
иерархические классификаторы
```

Плохой кандидат:

```text
Request → Subrequest → Subsubrequest
```

только потому, что хочется визуально вложить задачи. Сначала нужно убедиться, что предметная модель действительно является деревом, а не сетью связей.

## 11. Submittable — когда Save недостаточно

Обычный Document можно создавать и редактировать.

Но для некоторых документов нужен момент:

> «Всё, документ подтверждён. Теперь это не просто черновик».

Тогда DocType делают:

```text
Is Submittable = ✓
```

У него появляется системный lifecycle:

```text
Draft (0)
   ↓ Submit
Submitted (1)
   ↓ Cancel
Cancelled (2)
```

## 12. Пример Submittable

Пусть есть `Approval Record`:

```text
Subject: Проверка оборудования
Result: Approved
Date: 30.08.2026
```

Пока документ Draft, его можно спокойно готовить.

После `Submit` мы говорим системе:

> эта версия документа подтверждена.

После этого обычное редактирование большинства полей блокируется.

Если подтверждённый документ нужно отменить, применяется `Cancel`, а не простое удаление статуса.

## 13. Submittable и Workflow — не одно и то же

`Submittable` отвечает за **системный статус документа**:

```text
Draft / Submitted / Cancelled
```

`Workflow` отвечает за бизнес-состояния и разрешённые переходы:

```text
New → Review → Approved
```

Они могут работать вместе, но решают разные задачи.

Пример: Workflow может провести документ через проверку и в финальном переходе выполнить Submit.

Подробный lifecycle `docstatus` — следующая глава.

## 14. Virtual DocType — когда данные живут не в обычной таблице

Обычный DocType читает и сохраняет записи в своей таблице Frappe.

Virtual DocType говорит:

> интерфейс и Document-модель нужны, но источник данных будет другим.

Например:

```text
External Device
```

а реальные устройства лежат:

- в другой базе;
- во внешнем API;
- в файле;
- в нестандартном хранилище.

## 15. Как это выглядит концептуально

Обычный DocType:

```text
Desk / API
    ↓
Document
    ↓
tabMyDocType
```

Virtual DocType:

```text
Desk / API
    ↓
Virtual Document controller
    ↓
внешний источник данных
```

Собственной обычной таблицы для данных Virtual DocType Frappe не создаёт.

## 16. Virtual требует кода

Framework не может сам догадаться, как получить запись из чужой базы или API.

Поэтому controller Virtual DocType должен реализовать нужные операции чтения/записи/списка в зависимости от сценария.

Это уже developer-level инструмент.

Если данные нормально могут жить в Frappe — обычный DocType почти всегда проще.

## 17. Virtual — не способ «сэкономить таблицу»

Плохая причина:

> «Не хочу, чтобы Frappe создавал таблицу, поставлю Virtual».

Virtual нужен, когда **источник данных действительно внешний или нестандартный**.

Иначе ты добровольно берёшь на себя CRUD, который обычный DocType уже даёт бесплатно.

## 18. Custom Virtual DocType

В текущем v16 Framework не разрешает создать Virtual DocType как обычный Custom DocType Site. Это standard/developer-level механизм с controller-кодом.

Такое ограничение логично: без кода App виртуальному документу просто негде реализовать свой storage behavior.

## 19. Быстрая шпаргалка выбора

```text
Нужна одна глобальная запись настроек?
→ Single

Нужна настоящая иерархия parent → child?
→ Tree

Нужен официальный переход Draft → Submitted → Cancelled?
→ Submittable

Данные должны приходить из внешнего/нестандартного хранилища?
→ Virtual

Ничего из этого не нужно?
→ обычный DocType
```

## 20. Эти режимы не заменяют обычное моделирование

Не стоит включать специальный флаг только потому, что он кажется мощнее.

Например:

- Tree не заменяет обычные Link-связи;
- Single не заменяет справочник;
- Submittable не заменяет Workflow;
- Virtual не заменяет обычный ORM.

Специальный режим хорош тогда, когда его смысл совпадает со смыслом твоих данных.

## Мини-практика

Определи подходящий режим:

1. Общие настройки приложения → **Single**.
2. Категории товаров с вложенностью → **Tree**.
3. Документ, который после подтверждения нельзя свободно переписывать → **Submittable**.
4. Просмотр устройств, которые реально живут во внешнем API → **Virtual**.
5. Обычный справочник отделов без иерархии → **обычный DocType**.

## Что запомнить

- `Single` меняет **количество экземпляров и способ хранения**.
- `Tree` добавляет **иерархию и Nested Set behavior**.
- `Submittable` добавляет **системный lifecycle `docstatus`**.
- `Virtual` меняет **источник хранения данных**.
- Специальный режим выбирают по смыслу данных, а не по количеству галочек в интерфейсе.
