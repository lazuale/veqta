# Аудит курса Frappe 16: теория ↔ лабораторная ↔ стенд

Дата аудита: **2026-08-31**  
Объём: **глава 0, главы 1–45, 45 лабораторных, README и PRACTICE_TRACK**.

## Итог

Основа курса теперь правильная: есть отдельный учебный стенд, один сквозной объект `Request`, отдельные лабораторные и контрольное состояние между блоками.

Но курс **ещё нельзя считать готовым к линейному прохождению новичком от 0 до 45**.

Причина не в нехватке материала. Материала, наоборот, местами слишком много. Проблема в связке:

```text
теория
→ что именно ученик должен сделать
→ что он должен увидеть
→ что остаётся на стенде дальше
```

Сейчас эта цепочка работает неравномерно.

По результатам аудита:

| Статус | Глав | Смысл |
|---|---:|---|
| **BLOCKER** | 7 | лабораторная не воспроизводится либо теория и практика расходятся настолько, что новичок вынужден сам исследовать Frappe |
| **MAJOR** | 21 | пройти можно, но есть существенная неоднозначность, преждевременный термин или другой набор объектов/полей |
| **EDIT** | 8 | механика в целом правильная, нужен человеческий редакторский проход |
| **OK** | 9 | теория и практика уже достаточно хорошо сцеплены |

Главный вывод:

> **Курс нужно не расширять, а свести в одну учебную реальность и сделать каждую лабораторную детерминированной.**

До устранения блокеров продолжать писать главы 46+ не стоит.

# 1. Что должно быть единым во всём курсе

Новичку нельзя одновременно держать в голове учебный стенд и второй вымышленный стенд из примеров.

Для глав 1–45 нужен один словарь.

## Стенд

```text
Bench:   ~/frappe/frappe16-course-bench
Site:    learn.localhost
App:     training
Module:  Training
Frappe:  v16.32.0
URL:     http://learn.localhost:8000
```

## Основной DocType

```text
Request
```

Базовые поля, которые постепенно появляются по курсу:

```text
subject
Description / description
status            Open / In Progress / Done
priority          Low / Medium / High, default Medium
due_date
is_urgent
estimate_hours
notes
reference_file
responsible       Link → User
responsible_name  Fetch From
items             Table → Request Item
area              Link → Training Area
internal_cost     Perm Level 1
custom_local_note Custom Field
start_date        для Calendar/Gantt, если оставляем этот опыт
end_date          для Calendar/Gantt, если оставляем этот опыт
result            появляется перед Client/Server Script
```

## Child Table

```text
Request Item
- title
- qty
- rate
- amount
```

## Пользователи и роли

```text
student.user@example.test
student.manager@example.test

Training User
Training Manager
```

## User Permission

```text
Training Area
- North
- South
```

## Workflow

```text
Draft
→ Review
→ Approved
→ Rejected
```

Это **Workflow State**, а обычный `Request.status` продолжает жить отдельно:

```text
Open / In Progress / Done
```

Если в теории нужен другой пример — например `Department`, `Invoice` или `Activity` — он должен быть явно помечен как короткая аналогия. После аналогии текст сразу возвращается к реальному `Request`.

# 2. Главные системные проблемы

## 2.1. Теория и лаборатория местами живут в разных мирах

Самый ранний пример — глава 1:

```text
теория:
training.localhost
training_app
Module Requests

лабораторная:
learn.localhost
training
Module Training
```

Для разработчика это мелочь. Для человека, который только понял слова Bench, Site и App, это четыре новых сущности без причины.

То же повторяется дальше:

```text
теория: Department, amount, Closed, Request Operator, Request Manager
лаборатория: Area, estimate_hours/internal_cost, Done, Training User, Training Manager
```

Особенно сильно это ломает главы 26 и 34–37.

### Правило исправления

Основной пример каждой главы должен использовать **текущее состояние учебного `Request`**.

---

## 2.2. Поздние главы стали справочниками, а лабораторные остались короткими планами

Начиная примерно с аналитики объём теории резко растёт:

```text
36 Script Report              ~52 KB
37 Dashboard Chart            ~62 KB
38 Data Import / Export       ~56 KB
39 Web Form                   ~63 KB
40 Website / Portal           ~64 KB
41 REST API                   ~53 KB
42 RPC                        ~51 KB
43 Authentication             ~60 KB
44 Client Script              ~59 KB
45 Server Script              ~68 KB
```

При этом лабораторная обычно занимает 1.5–3 KB.

Получилась обратная пропорция:

```text
теория знает почти всё
лабораторная говорит «создай согласно текущему v16»
```

Для новичка нужно наоборот:

```text
в главе — только необходимая модель
в лабораторной — точный рабочий маршрут
после практики — дополнительные возможности как справка
```

Полезная информация не должна удаляться. Её нужно вынести из основного маршрута в разделы вроде:

```text
После первого прохода
Дополнительные возможности
Под капотом
Справка
```

---

## 2.3. Лаборатория не должна заставлять ученика исследовать версию

Плохие формулировки для зафиксированного `v16.32.0`:

```text
если UI позволяет
если доступно
если применимо
выбери вариант, который доступен в текущем v16
согласно структуре файлов текущего v16
используй документированный механизм текущей версии
адаптируй к фактическим fieldnames
```

Это нормальные оговорки в ответе консультанта. В лабораторной они означают:

> «автор сам не зафиксировал путь, найди его сам».

Для книги нужен один основной маршрут:

```text
нажми / создай / введи
→ получи конкретный результат
```

Альтернативы можно описать после него.

---

## 2.4. Ошибка в лабораторной должна быть гарантированной

Сейчас встречаются задания вида:

```text
попробуй создать конфликт, если интерфейс это допускает
попробуй неподходящий сценарий
посмотри, как Frappe отреагирует
```

Это не лабораторный опыт.

Хорошая намеренная ошибка выглядит так:

```text
1. сделай конкретное изменение;
2. повтори конкретное действие;
3. получи конкретный класс ошибки/запрета;
4. верни ровно одно значение назад;
5. убедись, что действие снова работает.
```

Лабораторные 32 и 41 уже показывают правильный стиль.

---

## 2.5. Будущая тема не должна внезапно становиться обязательным инструментом

Примеры:

- глава 8 внезапно требует `bench console` и Python;
- глава 16 говорит `client controller`, `server method`, `route` до нормального изучения этих вещей;
- глава 19 отправляет ученика проверять поле через REST, хотя REST будет в 41-й;
- глава 42 заставляет редактировать Python-файл App до отдельных глав про структуру App.

Иногда такой ранний взгляд полезен. Но тогда нужна короткая рамка:

> «Сейчас мы не изучаем Python/структуру App. Выполняем две строки только как инструмент наблюдения. Что это за код, разберём в главе N.»

Без такой рамки ученик не понимает, что он обязан знать, а что пока просто повторяет.

---

## 2.6. Английский нужен для имён Frappe, а не для обычной русской фразы

Нормально оставить:

```text
DocType
Document
Workflow
Client Script
Server Script
Link
Role Permission Manager
frappe.call()
```

Не нужно без причины писать:

```text
business rule
permission boundary
application code
surface
subsystem
engine
rendering
contract
current v16 source
```

Если термин не является именем объекта/API Frappe, его обычно можно сказать по-русски.

---

## 2.7. Повторяющийся «LLM-ритм» нужно вычистить

Сам по себе любой из оборотов нормален. Шум появляется из-за постоянного повторения:

```text
Главная мысль...
Упрощённо...
На пальцах...
Это важно...
Не нужно...
Правильная граница...
Правильная архитектура...
В текущем v16...
```

Текст начинает звучать как серия карточек, а не как учебник одного автора.

Нужен обычный русский рассказ:

```text
сначала проблема
→ затем механизм
→ один пример
→ что произошло
→ где механизм перестаёт подходить
```

Не надо в каждом разделе заново объявлять «главную мысль».

# 5. Эталон связки «глава → лабораторная»

Лучше всего сейчас устроены главы, где текст объясняет один механизм, а лаборатория заставляет увидеть его физически.

Хороший эталон — Email/Communication:

```text
теория:
Email Account
Email Queue
Communication

лабораторная:
локальный SMTP :1025
→ отправили письмо
→ увидели его в aiosmtpd
→ увидели Email Queue
→ увидели Communication
→ сломали порт на 1026
→ получили понятную ошибку
→ вернули 1025
→ снова работает
```

Такой опыт запоминается без зубрёжки.

REST API построен похожим образом:

```text
вошли
→ GET
→ POST
→ PUT
→ DELETE
→ увидели тот же Request в Desk
```

Именно к этому уровню нужно привести остальные лабораторные.

# 6. Каким должен быть основной текст главы для чайника

Не нужен жёсткий шаблон из десяти одинаковых заголовков. Нужен естественный порядок.

Обычно достаточно:

```text
1. С какой проблемой столкнулись на нашем Request.
2. Какой штатный механизм Frappe это решает.
3. Из каких 2–5 частей он состоит.
4. Один пример на текущем стенде.
5. Что реально происходит после действия пользователя.
6. Где этот механизм уже не подходит.
7. Переход в лабораторную.
```

Сложные детали, которые не нужны для первого успешного опыта, уходят ниже:

```text
Дополнительно
Под капотом
После первого прохода
```

Это особенно нужно главам 24, 26–27 и 34–45.

# 7. Каким должна быть лабораторная

Для обязательного маршрута:

```text
Что уже должно существовать

Что получим в конце

Шаг 1
точное действие

Проверка
точно что увидеть

Шаг 2
точное действие

Проверка
точно что увидеть

Эксперимент
меняем одну вещь

Намеренная ошибка
гарантированный failure

Восстановление
точно вернуть состояние

После главы
что остаётся на стенде
```

Главное правило:

> **У основной лабораторной не должно быть развилок «сделай A или B».**

Сначала один рабочий путь. Варианты — после него.

# 8. Редакторские правила против LLM-шума

1. Не повторять в каждом разделе «главная мысль», «это важно», «упрощённо», если фраза ничего не добавляет.
2. Не писать «правильная архитектура», если можно объяснить конкретную причину выбора.
3. Не использовать английское слово, если это не имя сущности/API Frappe и по-русски короче.
4. Не перечислять все возможности объекта до первой практики. Сначала минимальный рабочий набор.
5. Не страховаться фразой «в текущем v16», если курс целиком уже зафиксирован на v16.32.0.
6. Если поведение действительно зависит от окружения, написать **от чего именно** оно зависит.
7. Не говорить «можно сделать» там, где ученик **должен сделать** конкретный шаг.
8. Не задавать вопрос «что здесь происходит?» до того, как ученик увидел конкретный результат.
9. Не использовать абстрактные `Company A`, `Department B`, `foo/bar`, если уже существует учебный `Request`, `North`, `South`, `Training User`.
10. Не дублировать теорию в лабораторной. Лабораторная должна заставлять сделать и увидеть.
