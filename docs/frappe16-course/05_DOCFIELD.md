# 05. DocField: как свойства поля меняют живой `Request`

После лабораторной 04 у нас уже есть настоящий Standard DocType `Request` и несколько Documents.

Теперь не будем создавать новый пример. Возьмём существующий `Request` и расширим его полями разных типов, а затем руками проверим, как свойства `DocField` меняют поведение формы и списка.

Проверено для **Frappe Framework v16.32.0**.

---

## Что уже есть на стенде

```text
DocType: Request
Module: Training
Title Field: subject
Auto Name: ещё не настроен
```

Поля:

```text
subject      Data        Mandatory
description  Small Text
status       Select      Open / In Progress / Done
due_date     Date
```

Есть минимум четыре Request Documents.

---

## Что такое DocField

`DocType` описывает тип документа целиком.

`DocField` описывает одно поле внутри этого типа.

Например:

```text
Label:      Due Date
Fieldname:  due_date
Field Type: Date
```

Эти три свойства отвечают на разные вопросы.

### Label

Название, которое видит человек:

```text
Due Date
```

### Fieldname

Техническое имя поля:

```text
due_date
```

Именно `fieldname` позже будет использоваться в фильтрах, API и коде. Поэтому в курсе имена полей фиксируются и дальше не меняются без явной причины.

### Field Type

Определяет смысл значения и подходящий элемент интерфейса:

```text
Data       → короткий текст
Small Text → многострочный текст
Select     → выбор из списка
Date       → календарная дата
Check      → да / нет
Int        → целое число
Attach     → файл
Text Editor→ форматированный текст
```

---

## Почему тип поля имеет значение

Можно было бы хранить срок как текст:

```text
"3 сентября"
```

Но `Date` лучше описывает реальный смысл поля. Frappe понимает дату как дату и позже сможет нормально фильтровать, сортировать и показывать её в календарных представлениях.

То же правило работает для чисел, ссылок, флагов и других типов:

> выбираем Field Type по смыслу данных, а не потому, что `Data` проще всего добавить.

---

## Какие поля добавим сейчас

К существующему `Request` добавим:

| Label | Fieldname | Field Type | Зачем |
|---|---|---|---|
| Priority | `priority` | Select | фиксированный уровень приоритета |
| Is Urgent | `is_urgent` | Check | простой флаг да/нет |
| Estimate Hours | `estimate_hours` | Int | целое количество часов |
| Notes | `notes` | Text Editor | форматируемые заметки |
| Reference File | `reference_file` | Attach | один связанный файл |

Для `Priority` варианты будут:

```text
Low
Medium
High
```

Именно эти fieldnames сохраняем дальше по курсу.

---

## Mandatory

`Mandatory` означает: документ нельзя сохранить без значения поля.

На `Request` это уже работает для:

```text
subject
```

В лабораторной мы временно включим Mandatory для `due_date`, попробуем сохранить документ без срока, получим отказ, а затем вернём свойство назад.

Это важное различие:

```text
Mandatory
→ правило metadata поля

2026-09-03
→ значение конкретного Document
```

---

## Default

`Default` задаёт стартовое значение для нового Document.

Для `Priority` установим:

```text
Default = Medium
```

После этого новый Request сразу будет показывать `Medium`.

Но старые Documents не должны внезапно переписаться только потому, что изменился Default.

Default отвечает за начальное значение нового документа, а не за массовое изменение уже сохранённых данных.

---

## Read Only

`Read Only` оставляет поле видимым, но запрещает обычное редактирование через форму.

В лабораторной временно применим его к `Estimate Hours`, увидим результат и вернём настройку.

Позже Read Only будет полезен для значений, которые заполняет сама система.

---

## Hidden

`Hidden` убирает поле из обычного Form View.

В лабораторной временно скроем `Reference File`, убедимся, что поле исчезло, а затем вернём его.

`Hidden` — это свойство интерфейса, а не средство безопасности. Если значение действительно должно быть недоступно определённым пользователям, для этого существуют permissions, которые будут отдельным блоком.

---

## In List View

Форма показывает один Document, а список — несколько.

Для коротких полезных полей можно включить:

```text
In List View
```

На нашем `Request` оставим в списке:

```text
Status
Priority
Due Date
```

Так ученик сразу увидит, что одна metadata-настройка поля влияет не только на Form View.

Детально List View будем изучать в главе 12. Сейчас только наблюдаем эффект свойства.

---

## Description

У DocField есть текстовое пояснение для пользователя.

Например, для `Estimate Hours` можно написать:

```text
Оценка трудозатрат целым числом часов
```

Это не данные Document. Это часть metadata поля, которая помогает человеку правильно его заполнить.

---

## Что пока не используем

У DocField есть гораздо больше свойств:

```text
Unique
Set Only Once
No Copy
Allow on Submit
Permission Level
Fetch From
Depends On
Search Index
```

Они реальны, но сейчас не нужно превращать главу в каталог всех флагов.

В этом же блоке отдельно появятся:

```text
Fetch From        → глава 07
Allow on Submit   → глава 10
```

Permission Level будет в блоке прав.

Условное поведение формы подробнее проверим в блоке интерфейса.

---

## Что произойдёт в лабораторной

На существующем `Request` ты:

1. добавишь пять новых полей;
2. поставишь `Priority = Medium` как Default;
3. увидишь, что Default применяется к новому Document, но не переписывает старые;
4. включишь `In List View` и увидишь колонки в списке;
5. временно проверишь `Read Only` и `Hidden`;
6. временно сделаешь `Due Date` Mandatory и получишь гарантированный отказ при сохранении без срока;
7. восстановишь итоговую нормальную metadata.

После лабораторной все добавленные поля останутся и станут входом главы 06.

---

## Что запомнить

1. `Label` — название для человека.
2. `fieldname` — стабильное техническое имя поля.
3. `Field Type` выбирается по смыслу данных.
4. `Mandatory`, `Default`, `Read Only`, `Hidden` и `In List View` — metadata, которая реально меняет поведение интерфейса и сохранения.
5. Default для нового Document не равен массовому обновлению старых Documents.
6. Мы продолжаем изменять один `Request`, а не создаём отдельный пример для каждого свойства.
