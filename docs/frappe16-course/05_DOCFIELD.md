# 05. DocField и свойства полей

`DocField` — это описание одного поля внутри DocType.

Если DocType — это бланк «Заявка», то DocField — это конкретная строка на бланке: «Тема», «Статус», «Срок» и правила вокруг неё.

Проверено: **2026-08-30**.

## 1. У каждого поля есть три базовые вещи

Возьмём поле «Срок выполнения».

```text
Label:      Срок выполнения
Fieldname:  due_date
Field Type: Date
```

### Label

То, что видит человек на форме.

Его можно позже переименовать, не ломая код.

### Fieldname

Техническое имя поля.

Именно его использует код:

```python
doc.due_date
```

```javascript
frm.doc.due_date
```

Fieldname лучше считать частью API модели: после начала эксплуатации без причины его не переименовывают.

### Field Type

Определяет, что хранится и какой элемент интерфейса увидит пользователь.

Например:

```text
Data   → короткая строка
Date   → дата
Check  → да/нет
Link   → ссылка на другой DocType
Table  → дочерние строки
```

## 2. Почему нельзя делать всё полем Data

Технически строкой можно представить почти что угодно. Но тогда Frappe теряет смысл данных.

Плохой вариант:

```text
Дата рождения → Data
Количество    → Data
Отдел         → Data
```

Лучше:

```text
Дата рождения → Date
Количество    → Int
Отдел         → Link → Department
```

Тогда Frappe сможет нормально фильтровать даты и числа, проверять ссылки и строить правильный UI.

## 3. Основные типы полей: не зубри, а выбирай по смыслу

Ниже — практическая карта. Полный список кажется большим, но в обычных приложениях постоянно используются лишь несколько групп.

### Короткий текст и выбор

| Type | Для чего | Пример |
|---|---|---|
| `Data` | короткая строка | код, название |
| `Autocomplete` | строка с подсказками | часто вводимое значение |
| `Select` | выбор из фиксированного списка | Open / Done |
| `Check` | да/нет | Active |
| `Password` | пароль/секретное значение | API secret |
| `Phone` | телефон | контактный номер |
| `Color` | цвет | цвет метки |
| `Icon` | иконка | визуальный значок |

Для `Data` в `Options` могут использоваться специальные варианты валидации, например `Email`, `Phone`, `URL`, `Name`, `IBAN`.

### Длинный текст

| Type | Для чего |
|---|---|
| `Small Text` | небольшой многострочный текст |
| `Text` | обычный многострочный текст |
| `Long Text` | большой объём текста |
| `Text Editor` | форматированный rich text |
| `Markdown Editor` | Markdown |
| `HTML Editor` | HTML-контент |
| `Code` | код или структурированный текст с подсветкой |
| `JSON` | JSON-данные |

Если форматирование не нужно, не выбирай HTML/Rich Text «на всякий случай».

### Числа

| Type | Для чего | Пример |
|---|---|---|
| `Int` | целые числа | 12 |
| `Float` | дробные числа | 12.5 |
| `Currency` | денежные значения | 1250.00 |
| `Percent` | проценты | 15% |
| `Rating` | рейтинг | 4/5 |
| `Duration` | длительность | 2 ч 30 мин |

Для `Float`, `Currency` и похожих полей может задаваться `Precision`.

### Дата и время

| Type | Для чего |
|---|---|
| `Date` | дата без времени |
| `Datetime` | дата и время |
| `Time` | время |

Пример выбора:

```text
день рождения         → Date
время создания встречи → Datetime
начало смены           → Time
```

### Связи

| Type | Для чего |
|---|---|
| `Link` | ссылка на Document конкретного DocType |
| `Dynamic Link` | ссылка, где DocType цели определяется другим полем |
| `Table` | набор дочерних строк |
| `Table MultiSelect` | выбор нескольких связанных значений через child table |

Эти типы подробно разбираются в главах 07–08.

### Файлы и визуальные данные

| Type | Для чего |
|---|---|
| `Attach` | файл |
| `Attach Image` | изображение |
| `Attachment Gallery` | набор вложений в галерее |
| `Image` | отображение изображения |
| `Signature` | подпись |
| `Geolocation` | координаты/геоданные |
| `Barcode` | штрихкод |

### Элементы интерфейса, а не обычные данные

| Type | Что делает |
|---|---|
| `Section Break` | новая секция формы |
| `Column Break` | новая колонка |
| `Tab Break` | новая вкладка |
| `Heading` | заголовок |
| `HTML` | HTML-блок интерфейса |
| `Button` | кнопка |
| `Fold` | разделитель/сворачивание в поддерживаемом UI |
| `Read Only` | отображаемое read-only значение |

У таких полей назначение в первую очередь визуальное. Не каждый Field Type соответствует отдельной бизнес-колонке.

## 4. Пример нормального набора полей

Для учебного `Request`:

| Label | Fieldname | Type | Почему |
|---|---|---|---|
| Subject | `subject` | Data | короткий заголовок |
| Description | `description` | Text | многострочное описание |
| Status | `status` | Select | небольшой фиксированный набор |
| Due Date | `due_date` | Date | нужна именно дата |
| Department | `department` | Link | выбираем существующий Department |
| Urgent | `urgent` | Check | да/нет |

Уже по этой таблице видно, что тип поля несёт смысл.

## 5. Mandatory

`Mandatory` (`reqd`) означает: без значения документ сохранить нельзя.

Например:

```text
Subject → Mandatory
```

Пользователь не сможет сохранить пустую заявку.

Не делай обязательным всё подряд. Чем больше обязательных полей, тем тяжелее создание документа.

## 6. Default

`Default` задаёт начальное значение.

Например:

```text
Status
Default = Open
```

Новая заявка сразу получает `Open`, но пользователь может изменить его, если поле не Read Only.

Default — это стартовое значение, а не правило, которое навсегда прибивает поле к одной величине.

## 7. Read Only и Hidden

### Read Only

Пользователь видит поле, но не может обычно менять его через форму.

Пример:

```text
Created Total
Read Only = ✓
```

### Hidden

Поле не показывается обычным образом в форме.

Скрытое поле всё ещё может участвовать в данных и логике. `Hidden` не является механизмом безопасности: секретность обеспечивается permissions и правильной серверной логикой.

## 8. Unique

`Unique` требует уникального значения поля.

Например:

```text
External ID
Unique = ✓
```

Тогда два документа не должны иметь один и тот же `External ID`.

Используй это только для данных, которые действительно уникальны по смыслу.

## 9. Set Only Once

`Set Only Once` разрешает установить значение, но потом Frappe не позволит обычным сохранением его поменять.

Пример:

```text
Original Source
Set Only Once = ✓
```

Подходит для факта, который после создания документа должен оставаться неизменным.

## 10. No Copy

При копировании документа поля с `No Copy` не переносятся в новый Document.

Хороший пример:

```text
external_id
```

Если скопировать старую запись, новый документ не должен наследовать уникальный внешний идентификатор.

## 11. Allow on Submit

Это свойство имеет смысл для Submittable DocType.

После Submit почти все обычные поля менять нельзя. Если у поля включено:

```text
Allow on Submit = ✓
```

его можно изменять через режим Update after Submit.

Пример: поле `Internal Note` может быть разрешено к изменению после подтверждения документа, а сумма или ключевые реквизиты — нет.

Подробно это разберём в главе 10.

## 12. Условия: показывать, требовать или блокировать поле по ситуации

У DocField есть условные свойства:

```text
Display Depends On
Mandatory Depends On
Read Only Depends On
```

Они позволяют менять поведение формы без написания большого Client Script.

### Пример

Показывать `closed_reason`, только если статус `Closed`:

```text
eval:doc.status=="Closed"
```

Сделать это поле обязательным в той же ситуации:

```text
Mandatory Depends On:
eval:doc.status=="Closed"
```

Теперь обычная заявка не перегружена лишним полем, а при закрытии причина становится обязательной.

## 13. In List View

Если включить `In List View`, поле может показываться прямо в списке документов.

Например для `Request` полезно видеть:

```text
Subject | Status | Due Date
```

А длинное `Description` в List View обычно только мешает.

## 14. In Standard Filter

`In Standard Filter` делает поле удобным стандартным фильтром в List View.

Для заявки логично добавить:

```text
Status
Department
Due Date
```

Не нужно добавлять в стандартные фильтры все 40 полей формы. Оставляй то, по чему реально ищут каждый день.

## 15. Search Index

`Search Index` просит создать индекс для поля, чтобы ускорять подходящие запросы.

Индекс полезен не «для красоты», а для полей, по которым действительно часто фильтруют или связывают большие объёмы данных.

У индексов есть цена: они занимают место и усложняют записи в БД. Поэтому включать их на каждом поле не нужно.

## 16. In Global Search и Search Fields

Некоторые поля можно использовать в глобальном поиске и поиске ссылок.

Пример:

```text
Customer
name = CUST-0042
customer_name = Ромашка
phone = +7...
```

Пользователю удобнее искать клиента не только по `CUST-0042`, но и по названию или телефону. Для этого metadata поиска настраивают осмысленно.

## 17. Perm Level

`Permission Level` (`permlevel`) позволяет дать отдельным полям более высокий уровень доступа.

Например:

```text
Subject       → permlevel 0
Internal Cost → permlevel 1
```

Дальше Role Permissions определят, кто имеет read/write для уровня 1.

Это не отдельная система прав для каждого поля, а часть общего permission engine Frappe.

## 18. Fetch From

`Fetch From` позволяет автоматически скопировать значение из связанного документа.

Например:

```text
department           Link → Department
manager_name         Data
Fetch From: department.manager_name
```

Выбрали Department — Frappe подставил имя руководителя.

Это **копирование значения**, а не live JOIN. Если руководитель позже поменяется, старое сохранённое значение не обязано магически обновиться во всех документах.

Подробнее — в главе 07.

## 19. Fetch If Empty

Если включён режим fetch only when empty, Frappe не будет затирать уже заполненное значение при повторном fetch.

Это полезно, когда автоматически подставляется стартовое значение, но пользователь имеет право потом скорректировать его вручную.

## 20. Layout: Section, Column и Tab

Поля формы можно разложить без собственного HTML.

Например:

```text
[Основное]
Subject | Status
Due Date | Department

[Описание]
Description

[Служебное]
Internal Note
```

Для этого используют `Section Break`, `Column Break`, `Tab Break`.

Хорошая форма — это не форма, где всё помещается, а форма, где пользователь быстро понимает порядок работы.

## 21. Печать, экспорт и отчёты

У полей есть свойства, влияющие на то, где они участвуют: print, report, export/import и другие представления.

Здесь действует простой принцип: если поле служебное и человеку не нужно видеть его в печатной форме, не тащи его туда только потому, что оно существует в DocType.

## 22. Virtual Field

В v16 поле может быть виртуальным: значение вычисляется или предоставляется кодом и не обязано храниться обычной колонкой таблицы.

Это уже продвинутый инструмент. Если значение должно нормально сохраняться и фильтроваться как обычное бизнес-поле, начни с обычного DocField.

## 23. Несколько продвинутых свойств

В текущей metadata Frappe есть и более специальные флаги, например настройки маскирования, `Not Nullable`, поведения XSS-фильтра и другие.

На первом проходе их не стоит включать без конкретной задачи.

Особенно осторожно относись к опциям, ослабляющим проверки безопасности, например `Ignore XSS Filter` или `Ignore User Permissions`: название свойства уже говорит, что оно обходит стандартную защиту Framework.

## 24. Как выбирать Field Type

Перед созданием поля задай четыре вопроса:

```text
1. Что это за факт?
2. Это самостоятельное значение или ссылка на другой Document?
3. Нужны ли Frappe специальные сравнения/фильтры для него?
4. Это данные или только элемент layout?
```

Пример:

```text
«Отдел»
```

Если отделы — самостоятельный справочник, правильнее `Link → Department`, а не `Data`.

```text
«Срок»
```

Если это календарная дата — `Date`, а не строка `31.08.2026`.

## Мини-практика

Для `Request` создай или мысленно спроектируй поля:

```text
Subject      Data      Mandatory
Status       Select    Open / In Progress / Done
Due Date     Date
Department   Link      Department
Urgent       Check
Description  Text
```

Затем ответь:

1. Какое поле стоит показать в Standard Filter? Например `Status`.
2. Какое поле не стоит пихать в List View? Скорее всего длинный `Description`.
3. Что выбрать для Department: Data или Link? **Link**, если это отдельный DocType.

## Что запомнить

- `Label` — имя для человека, `fieldname` — техническое имя.
- Field Type выбирают по смыслу данных, а не по принципу «Data проще».
- `Mandatory`, `Default`, `Read Only`, `Unique` и другие флаги реально меняют поведение Framework.
- Условные свойства часто позволяют обойтись без Client Script.
- Layout-поля не являются обычными бизнес-данными.
