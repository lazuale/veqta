# 06. Naming и системное поле `name`

Эта глава разбирает механизм именования документов во **Frappe Framework 16**.

Цель — понять:

- что такое системное поле `name`;
- почему это не просто «номер документа»;
- чем `name` отличается от `Title Field`;
- какие способы Naming существуют штатно;
- как работают Naming Series и Expression;
- когда использовать UUID, а когда человекочитаемый идентификатор;
- как работают Document Naming Rules;
- что происходит при Rename;
- какие последствия Naming имеет для Link, API, импорта и миграций.

Проверено: **2026-08-30**.

---

## 1. `name` — первичный идентификатор документа

У каждого обычного Document во Frappe есть системное поле:

```text
name
```

Это **primary key документа**.

Официальная документация прямо определяет `name` как уникальный идентификатор, по которому Framework находит и изменяет запись через ORM.

Например:

```text
DocType: Request
name: REQ-00042
```

или:

```text
DocType: Employee
name: EMP-0017
```

или:

```text
DocType: Country
name: Netherlands
```

Во всех трёх случаях `name` выполняет одну и ту же техническую функцию.

Упрощённо:

```text
DocType
  +
name
  =
точный адрес конкретного Document
```

---

## 2. `name` нельзя воспринимать как обычное поле

В таблице обычного DocType есть колонка `name`, но она особенная.

Она участвует в:

```text
primary key
ORM
REST API
Link
Dynamic Link
routes
attachments
comments
versions
assignments
references
```

Например Python:

```python
frappe.get_doc("Request", "REQ-00042")
```

Здесь:

```text
Request
```

— DocType,

а:

```text
REQ-00042
```

— его `name`.

В REST API тот же принцип:

```text
/api/resource/Request/REQ-00042
```

Поэтому изменение `name` гораздо существеннее изменения обычного поля вроде `subject`.

---

## 3. `name` и Title Field — разные вещи

Одна из самых частых ошибок новичка — считать, что красивое название документа обязательно должно быть его primary key.

Во Frappe это разделено.

Например:

```text
name:
REQ-00042

subject:
Проверить документы за август
```

В DocType можно назначить:

```text
Title Field = subject
```

Тогда интерфейс может показывать человеку понятный заголовок, сохраняя стабильный системный идентификатор.

Концептуально:

```text
name
= идентичность документа

Title Field
= удобное отображение документа
```

Это очень полезное разделение.

---

## 4. Когда `name` и название могут совпадать

Для небольших стабильных справочников иногда разумно использовать само значение как `name`.

Например:

```text
Country
name = Netherlands
```

или:

```text
Priority
name = High
```

Но это оправдано только если значение действительно является хорошим стабильным идентификатором.

Плохой пример:

```text
Employee
name = Иван Иванов
```

Причины:

```text
имена могут совпадать
имя может измениться
разные написания
транслитерация
локализация
```

Поэтому человекочитаемость сама по себе ещё не делает значение хорошим primary key.

---

# Штатные Naming Methods

## 5. В Frappe 16 есть девять основных методов Naming

Текущая официальная документация перечисляет:

```text
1. Set by user
2. Autoincrement
3. By fieldname
4. By "Naming Series" field
5. Expression
6. Expression (Old Style)
7. Random
8. UUID
9. By script
```

В metadata DocType ветки `version-16` присутствует тот же набор вариантов.

Разберём каждый отдельно.

---

# 1. Set by user

## 6. Пользователь задаёт `name` вручную

Режим:

```text
Naming Rule:
Set by user
```

При создании документа пользователь сам задаёт идентификатор.

Например:

```text
Warehouse
name = MAIN-WAREHOUSE
```

или:

```text
External Reference
name = EXT-2026-77
```

### Когда это разумно

Когда идентификатор:

```text
уже существует во внешней предметной области
известен пользователю
должен вводиться вручную
гарантированно уникален
```

### Когда это плохо

Для обычных рабочих документов.

Если человеку постоянно предлагают придумать уникальный primary key, это лишняя нагрузка и источник ошибок.

---

# 2. Autoincrement

## 7. Простая числовая последовательность

Режим:

```text
Autoincrement
```

создаёт имена:

```text
1
2
3
4
5
```

В Frappe 16 этот режим использует отдельный механизм последовательности БД.

### Важные свойства

Официальная документация подчёркивает:

- счёт начинается с `1`;
- удалённые номера повторно не используются;
- схема не является gap-safe;
- переключение на Autoincrement или с него ограничено, если DocType уже содержит документы.

Например:

```text
1
2
3
4
```

удалили `3`.

Следующий документ:

```text
5
```

а не:

```text
3
```

### Не путать с юридической нумерацией

Autoincrement гарантирует техническую последовательность идентификаторов, но не следует автоматически считать её юридически значимой «непрерывной нумерацией документов».

---

# 3. By fieldname

## 8. Значение поля становится `name`

Например есть поле:

```text
code
```

и настройка:

```text
Naming Rule:
By fieldname

Autoname field:
code
```

Документ:

```text
code = ABC-17
```

получает:

```text
name = ABC-17
```

В metadata это фактически выражается через:

```text
field:<fieldname>
```

### Главное требование

Значение должно быть уникальным.

Если два документа получают одинаковое значение, второй не сможет использовать тот же primary key.

### Хорошие случаи

```text
ISO-код страны
уникальный внешний код
стабильный артикул
технический идентификатор оборудования
```

### Плохие случаи

```text
ФИО
название задачи
описание
название отдела, которое часто переименовывают
```

---

# 4. By "Naming Series" field

## 9. Серия выбирается на уровне самого документа

Для этого DocType должен иметь поле:

```text
naming_series
```

Обычно это `Select`.

Например варианты:

```text
REQ-.#####
INC-.#####
EXT-.#####
```

Один документ может получить:

```text
REQ-00001
```

другой:

```text
INC-00001
```

третий:

```text
EXT-00001
```

### Практический смысл

Один DocType может использовать несколько нумерационных серий.

Это удобно, если разные категории документов должны иметь разные префиксы, но оставаться одной сущностью.

### Важное требование

Штатный механизм ожидает поле именно:

```text
naming_series
```

---

## 10. Naming Series — это шаблон + счётчик

Пример шаблона:

```text
REQ-.#####
```

Результат:

```text
REQ-00001
REQ-00002
REQ-00003
```

Количество `#` определяет ширину числовой части.

Например:

```text
###
```

даёт:

```text
001
002
003
```

а:

```text
######
```

даёт:

```text
000001
000002
```

---

## 11. Счётчик относится к серии

Концептуально:

```text
prefix/series
      │
      └── current counter
```

Разные серии имеют независимые счётчики.

Например:

```text
REQ-00017
INC-00004
EXT-00102
```

Это не одна глобальная последовательность DocType.

---

# 5. Expression

## 12. Современный гибкий способ построения `name`

Expression позволяет собрать имя из нескольких частей.

Например:

```text
REQ-.YYYY.-.#####
```

может дать:

```text
REQ-2026-00001
```

Другой пример:

```text
EXAMPLE-.MM.-.{department}.-.#####
```

может использовать:

```text
статический текст
дату
значения полей
последовательный номер
```

Официальная документация v16 перечисляет среди поддерживаемых частей:

```text
MM
YYYY
DD
WW
timestamp
{fieldname}
#####
```

### Почему Expression часто удобнее собственного Python

Если идентификатор является простой комбинацией:

```text
prefix + year + field + counter
```

писать `autoname()` в controller обычно не требуется.

---

## 13. Пример Expression с полем

Допустим документ имеет:

```text
department = OPS
```

Шаблон концептуально:

```text
REQ-.{department}.-.YYYY.-.#####
```

Результат:

```text
REQ-OPS-2026-00001
```

Но прежде чем помещать бизнес-данные в primary key, нужно спросить:

> может ли это значение когда-нибудь измениться?

Если `department` изменится после создания документа, `name` автоматически вслед за ним не станет новым.

Первичный идентификатор уже был создан.

---

## 14. Не перегружай идентификатор информацией

Можно построить чудовище:

```text
REQ-OPS-MOSCOW-HIGH-2026-08-USER17-00042
```

Но это редко хорошая идея.

Проблемы:

```text
часть данных меняется
ID становится длинным
структура ID превращается в скрытую бизнес-логику
интеграции начинают парсить name
переезд данных становится сложнее
```

Лучше:

```text
name = REQ-2026-00042
```

а остальные данные хранить в нормальных полях.

---

# 6. Expression (Old Style)

## 15. Старый синтаксис не нужен для новых решений

В v16 всё ещё существует совместимость со старым `format:`-подходом.

Исходный код ветки `version-16` прямо содержит логику, которая распознаёт старый `format:` и показывает предупреждение:

```text
Usage of 'format:' is discouraged.
```

Поэтому для нового DocType используем:

```text
Expression
```

а не:

```text
Expression (old style)
```

Старый вариант нужен в первую очередь для совместимости существующих приложений.

---

# 7. Random

## 16. Случайный технический идентификатор

Режим:

```text
Random
```

генерирует случайное имя.

Он полезен, когда:

```text
человеческий номер не нужен
ID не должен нести бизнес-смысл
достаточен технический уникальный ключ
```

### Плюс

Не требуется управление сериями.

### Минус

Пользователю трудно диктовать, читать и искать такие ID вручную.

Поэтому для документов, с которыми активно работают люди, часто удобнее короткая последовательная серия + Title Field.

---

# 8. UUID

## 17. UUID как primary key

DocType v16 поддерживает:

```text
Naming Rule = UUID
```

Это подходит для систем, где важнее техническая уникальность и распределённая генерация, чем человекочитаемая нумерация.

Пример формы UUID:

```text
0198c8c0-....
```

### Важное уточнение именно для v16

На странице документации Naming всё ещё написано, что используется **UUID v4**.

Однако фактический исходный код ветки `version-16` импортирует:

```python
from uuid import UUID, uuid7
```

и при создании нового имени вызывает:

```python
doc.name = str(uuid7())
```

Поэтому для реального поведения Frappe 16 ориентируемся на **UUIDv7**, несмотря на отставшую формулировку документации.

Это хороший пример общего правила курса:

> если документация и конкретная ветка исходного кода расходятся, для фактического поведения версии проверяем код этой ветки.

---

## 18. Когда UUID подходит

Хорошо:

```text
интеграционные сущности
технические записи
распределённые системы
объекты, которым не нужен человекочитаемый номер
```

Не всегда удобно:

```text
заявки
акты
заказы
оперативные документы, номер которых человек сообщает голосом
```

Можно использовать UUID как `name`, а человеку показывать отдельное поле с коротким номером, но это уже две разные задачи.

---

# 9. By script

## 19. Полный контроль через controller

Если штатных схем недостаточно, DocType может использовать:

```text
By script
```

и метод controller:

```python
class Request(Document):
    def autoname(self):
        self.name = "..."
```

Это полноценный server-side код.

### Когда это оправдано

Когда идентификатор действительно зависит от логики, которую нельзя нормально выразить штатной Expression или Document Naming Rule.

Например:

```text
сложный внешний алгоритм
несколько зависимых источников
специальная совместимость со старой системой
```

### Когда это лишнее

Если требуется всего лишь:

```text
REQ-2026-00042
```

или:

```text
REQ-OPS-00042
```

штатная Naming Series / Expression проще и прозрачнее.

---

# Document Naming Rule

## 20. Conditional Naming без собственного Python

Кроме основного Naming Rule DocType существует системная сущность:

```text
Document Naming Rule
```

Она позволяет применять разные правила к одному DocType по условиям.

Например:

```text
если priority = High
→ HIGH-001

если priority = Normal
→ NOR-001
```

Или:

```text
если department = OPS
→ OPS-00001

если department = FIN
→ FIN-00001
```

---

## 21. Что содержит Document Naming Rule

Штатная модель включает:

```text
Document Type
Priority
Conditions
Prefix
Prefix Digits
Counter
```

То есть правило отвечает примерно на вопрос:

```text
если документ удовлетворяет условиям
→ использовать такую серию
```

---

## 22. Priority Naming Rules

Для одного DocType можно создать несколько правил.

Если потенциально подходят несколько, используется `Priority`.

В исходном коде правила загружаются с сортировкой:

```text
priority desc
```

то есть более высокий приоритет проверяется раньше.

Как только правило присвоило `doc.name`, дальнейшие Naming Rules уже не применяются.

---

## 23. Naming Rule имеет собственный счётчик

Document Naming Rule хранит:

```text
counter
```

и увеличивает его при каждом применении.

Например:

```text
Prefix: todo-high-
Digits: 3
```

даёт:

```text
todo-high-001
todo-high-002
todo-high-003
```

---

# Реальный порядок присвоения имени

## 24. Что происходит внутри Frappe 16

Фактический `set_new_name()` в ветке `version-16` делает упрощённо следующее:

```text
before_naming
    ↓
Autoincrement?
    ↓
UUID?
    ↓
Amended document?
    ↓
name уже задан?
    ↓
Single DocType?
    ↓
Document Naming Rule
    ↓
controller.autoname()
    ↓
DocType autoname / metadata rule
    ↓
fallback hash
    ↓
validate_name
```

Это важно: Naming — не только одно поле настройки в DocType, а полноценный этап lifecycle создания документа.

---

## 25. `before_naming`

Перед основным присвоением имени Framework вызывает:

```text
before_naming
```

Это controller event.

Он позволяет подготовить данные, которые понадобятся Naming.

Например заполнить поле, участвующее в Expression.

Но использовать его стоит только тогда, когда действительно нужна server-side подготовка.

---

## 26. Fallback hash

Если никакой другой механизм не присвоил `name`, Framework не оставляет документ без primary key.

Он генерирует технический hash-like идентификатор.

Это объясняет, почему даже DocType без явно настроенной красивой серии всё равно может создавать документы.

Но для пользовательских документов лучше сознательно определить naming strategy.

---

# Special cases

## 27. Single DocType

Для `Single DocType` обычная схема Naming не имеет смысла.

В `set_new_name()`:

```text
name = doctype
```

То есть единственный экземпляр идентифицируется самим именем DocType.

Например:

```text
DocType: Application Settings
name: Application Settings
```

---

## 28. Child DocType

Официальная документация отдельно указывает:

> Child DocTypes do not follow naming rules.

Child rows являются частью родительского документа и управляются отдельной внутренней моделью.

Поэтому не надо проектировать бизнес-нумерацию строк Child Table через Naming Rule самого Child DocType.

---

## 29. Amended documents

Для Submittable DocType после Cancel + Amend новый документ получает имя с суффиксом относительно исходного документа.

Например:

```text
INV-00042
```

после amendment:

```text
INV-00042-1
```

следующий amendment может стать:

```text
INV-00042-2
```

То есть Amendment не создаёт новую независимую Naming Series с нуля.

Связь с `docstatus` и `amended_from` подробно разберём в отдельной главе.

---

# Rename

## 30. `name` можно менять, но это отдельная операция

Обычное изменение поля:

```text
subject
```

не меняет:

```text
name
```

Чтобы изменить primary key документа, используется Rename.

Python API:

```python
frappe.rename_doc(
    "Request",
    "REQ-00042",
    "REQ-00043"
)
```

Но Rename разрешён только если в DocType включено:

```text
Allow Rename
```

---

## 31. Rename — это не простой SQL UPDATE

Исходный механизм Frappe делает намного больше, чем:

```sql
UPDATE table SET name = ...
```

Он обрабатывает, среди прочего:

```text
Link fields
Dynamic Links
Child rows
attachments
Version
password records
user settings
assignments
search index
comments/history
```

и вызывает hooks:

```text
before_rename
after_rename
```

Именно поэтому вручную менять `name` SQL-запросом — плохая идея.

---

## 32. Rename обновляет Link references

Если есть:

```text
Department
name = OPS
```

и множество документов с:

```text
department → OPS
```

корректный `frappe.rename_doc()` обновляет Link references на новое имя.

Это одна из причин, почему Frappe может позволить безопасное переименование в штатном механизме.

Но внешние системы об этом автоматически не узнают.

---

## 33. Внешние интеграции — главный риск Rename

Представим внешний сервис хранит:

```text
Request.name = REQ-00042
```

Во Frappe документ переименовали:

```text
REQ-00042 → REQ-00043
```

Внутренние Link Frappe могут быть обновлены.

Но внешняя БД, Excel, API consumer или сохранённая сторонняя ссылка могут продолжать использовать старый ID.

Поэтому для интеграционных сущностей `name` желательно делать максимально стабильным.

---

## 34. `name` — плохое место для изменяемого бизнес-смысла

Например:

```text
name = DEPARTMENT-MOSCOW-HIGH
```

Если подразделение или приоритет изменятся, возникает вопрос:

```text
переименовывать document?
или оставить старый name?
```

Оба варианта создают когнитивную проблему.

Лучше:

```text
name = REQ-00042

department = Moscow
priority = High
```

---

# Naming и Link

## 35. Link хранит `name` целевого Document

Если поле:

```text
department
Field Type = Link
Options = Department
```

и выбран документ:

```text
Department.name = OPS
```

Link сохраняет именно:

```text
OPS
```

а не его `title_field`.

UI может показывать красивое название, но реальная ссылка опирается на primary key.

Это ключевой момент для понимания связей во Frappe.

---

## 36. Title Field не заменяет `name` в API

Допустим:

```text
name = CUST-00017
customer_name = Example Company
```

и:

```text
Title Field = customer_name
```

Пользователь может видеть:

```text
Example Company
```

Но API по-прежнему обращается к документу через:

```text
CUST-00017
```

Именно поэтому UI-friendly title можно свободнее изменять, чем primary key.

---

# Naming и API

## 37. `name` является частью resource URL

Типичный REST endpoint:

```text
/api/resource/Request/REQ-00042
```

Следовательно:

```text
rename
```

меняет и адрес конкретного resource.

Если внешняя система сохраняет URL или `name`, переименование должно рассматриваться как изменение внешнего идентификатора.

---

# Naming и Data Import

## 38. При импорте важно понимать выбранную стратегию

Если DocType сам генерирует `name`, обычно импортируем предметные поля и позволяем Framework применить naming rule.

Если же внешнее значение должно стать `name`, стратегия должна быть определена заранее:

```text
Set by user
By fieldname
или осознанная migration logic
```

Не стоит сначала импортировать тысячи записей с одним naming, а потом без необходимости массово менять primary keys.

# Naming и миграции

## 39. Naming strategy лучше выбрать рано

Пока DocType пустой, менять концепцию Naming сравнительно легко.

После появления:

```text
тысяч Documents
Links
API consumers
external exports
saved URLs
integrations
```

изменение primary key strategy становится полноценной migration-задачей.

Особенно строг Autoincrement: документация v16 прямо ограничивает переход на него и с него при существующих документах.

---

## 40. Не кодируй всю предметную модель в `name`

Хороший ID обычно:

```text
короткий
уникальный
стабильный
предсказуемый настолько, насколько нужно
не зависит от часто изменяемых полей
```

Плохой ID часто пытается одновременно рассказать:

```text
тип
отдел
год
месяц
приоритет
регион
исполнителя
статус
```

Для этого существуют обычные поля.

# Как выбрать Naming strategy

## 41. Практическое дерево решений

```text
Есть внешний стабильный уникальный ID,
который должен быть primary key?
        │
        ├── да → By fieldname / Set by user
        │
        └── нет
             │
             ▼
Нужен человекочитаемый последовательный номер?
        │
        ├── да
        │    │
        │    ├── одна схема → Expression
        │    │
        │    └── несколько выбираемых схем → Naming Series field
        │
        └── нет
             │
             ▼
Нужен простой числовой PK?
        │
        ├── да → Autoincrement
        │
        └── нет
             │
             ▼
Нужен технический глобально уникальный ID?
        │
        ├── да → UUID
        │
        └── нет
             │
             ▼
Нужно условное именование по данным?
        │
        ├── да → Document Naming Rule
        │
        └── нет
             │
             ▼
Штатные варианты реально недостаточны?
        │
        ├── да → By script / autoname()
        └── нет → не писать код
```

---

## 42. Типовые рекомендации

### Справочник со стабильным кодом

```text
By fieldname
```

Пример:

```text
Currency.name = EUR
```

### Операционный документ

```text
Expression
```

Пример:

```text
REQ-2026-00042
```

### Один DocType с несколькими нумерационными сериями

```text
By "Naming Series" field
```

### Чисто техническая сущность

```text
UUID
```

### Очень простая внутренняя таблица

```text
Autoincrement
```

### Сложная условная нумерация

Сначала:

```text
Document Naming Rule
```

и только потом:

```text
By script
```

# Частые ошибки

## 43. Ошибка: использовать название как primary key только ради красоты

Например:

```text
name = Очень важная заявка по ремонту автомобиля
```

Лучше:

```text
name = REQ-00042
subject = Очень важная заявка по ремонту автомобиля
```

---

## 44. Ошибка: хранить два независимых идентификатора без причины

Например:

```text
name = REQ-00042
request_id = REQ-00042
```

Если оба всегда должны совпадать, второй столбец обычно не нужен.

Но отдельный business number оправдан, если он действительно отличается от технического `name` по смыслу или lifecycle.

---

## 45. Ошибка: парсить бизнес-данные из `name`

Например код приложения делает:

```python
parts = doc.name.split("-")
department = parts[1]
```

Это создаёт скрытую зависимость от формата ID.

Гораздо надёжнее:

```python
department = doc.department
```

`name` должен идентифицировать документ, а не заменять нормальную модель данных.

---

## 46. Ошибка: менять `name` прямым SQL

Поскольку Frappe должен обновить связанные механизмы, raw SQL rename может оставить систему в несогласованном состоянии.

Используем:

```python
frappe.rename_doc(...)
```

или штатный UI Rename.

---

## 47. Ошибка: считать последовательные номера гарантированно бездырочными

Удаления, отмены, откаты и другие жизненные ситуации могут приводить к пропускам.

Naming Series — механизм технической нумерации, а не автоматически юридическая гарантия непрерывности последовательности.

---

## 48. Ошибка: писать `autoname()` раньше времени

Перед Python всегда проверяем:

```text
By fieldname
Naming Series
Expression
Document Naming Rule
UUID
```

Большая часть обычных схем уже реализована Framework.

# Что нужно запомнить

## 50. Главная схема

```text
Document
│
├── name
│     └── primary key / identity
│
├── Title Field
│     └── human-readable display
│
└── ordinary fields
      └── business data
```

А Naming отвечает только за создание первой части:

```text
name
```

---

## 51. Итоговая таблица

| Метод | Для чего подходит | Код |
|---|---|---:|
| Set by user | ручной внешний ID | нет |
| Autoincrement | простой числовой PK | нет |
| By fieldname | стабильный уникальный код | нет |
| Naming Series field | несколько серий в одном DocType | нет |
| Expression | составной последовательный ID | нет |
| Expression old style | legacy compatibility | нет, но не использовать в новом дизайне |
| Random | технический случайный ID | нет |
| UUID | технический глобально уникальный ID | нет |
| Document Naming Rule | условные схемы по данным | нет |
| By script | нестандартная логика | Python |
