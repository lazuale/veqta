# 06. Naming и системное поле `name`

У `Request` уже есть Documents, но мы пока специально не настраивали их имена. Благодаря этому сейчас можно увидеть разницу между системным идентификатором записи и человекочитаемым заголовком.

В этой главе настроим стабильную серию для **новых** Requests:

```text
REQ-.YYYY.-.#####
```

Проверено для **Frappe Framework v16.32.0** и исходного кода `frappe/model/naming.py` тега `v16.32.0`.

---

## Что уже есть на стенде

`Request` содержит поля:

```text
subject
description
status
due_date
priority
is_urgent
estimate_hours
notes
reference_file
```

`Title Field` уже равен:

```text
subject
```

`Auto Name` пока не настроен.

Есть несколько сохранённых Request Documents.

---

## Что такое `name`

У каждого обычного Document во Frappe есть системное поле:

```text
name
```

Пара:

```text
DocType + name
```

однозначно определяет запись внутри Site.

Например после этой лабораторной:

```text
DocType: Request
name:    REQ-2026-00001
```

Это техническая идентичность конкретного Request.

---

## `name` и `Subject` — разные вещи

У одного Request может быть:

```text
name    = REQ-2026-00001
subject = Проверить отчёт
```

`name` нужен Framework как стабильный идентификатор.

`subject` нужен человеку как смысловой заголовок.

Поэтому у нас уже настроено:

```text
Title Field = subject
```

Изменение `Subject` обычным Save не должно автоматически переименовывать Document.

Это позволяет отделить:

```text
идентичность записи
от
текста, который пользователь может менять
```

---

## Почему первые Requests уже имеют `name`

Даже без нашей серии Frappe обязан присвоить Document уникальное имя.

Если для обычного DocType не задан собственный naming rule, Framework может использовать внутреннее автоматически сгенерированное имя.

Поэтому Requests из лабораторных 04–05 уже существуют и имеют свои `name`.

Мы не переименовываем их задним числом.

В главе 06 меняем правило **для новых Documents**.

---

## Auto Name и naming series

Для `Request` зададим:

```text
Auto Name = REQ-.YYYY.-.#####
```

Frappe разбирает такую строку по частям:

```text
REQ-
YYYY
-
#####
```

В `v16.32.0`:

```text
YYYY  → четырёхзначный текущий год
##### → пятизначный счётчик серии
```

На стенде курса в 2026 году свежая серия будет давать:

```text
REQ-2026-00001
REQ-2026-00002
REQ-2026-00003
```

Счётчик обслуживает Framework. Пользователь не вводит следующий номер вручную.

---

## Почему в шаблоне важны точки

Naming series во Frappe имеет собственный синтаксис.

Рабочий шаблон:

```text
REQ-.YYYY.-.#####
```

Здесь части разделены точками, а перед числовыми `#####` есть точка-разделитель.

Например шаблон:

```text
REQ-#####
```

для этого механизма некорректен: числовой placeholder должен быть оформлен как отдельная часть серии.

В лабораторной мы намеренно поставим неправильный вариант и получим штатную ошибку naming при создании нового Request.

---

## Naming применяется в момент создания

Упрощённая последовательность:

```text
создаём новый Request
        ↓
Frappe определяет его name
        ↓
проверяет уникальность
        ↓
сохраняет Document
```

Поэтому изменение Auto Name не переписывает автоматически имена старых Documents.

Новая стратегия начинает влиять на новые записи.

---

## Почему не используем `Subject` как `name`

Технически Frappe умеет брать имя из поля, например через:

```text
field:some_field
```

Но для нашего `Request` это плохой выбор.

`Subject` может:

```text
измениться
повториться у двух Requests
быть длинным
```

Поэтому оставляем:

```text
name    → стабильная серия REQ-...
subject → изменяемый Title Field для человека
```

---

## Другие способы naming существуют, но сейчас не нужны

Frappe v16 поддерживает и другие режимы, например:

```text
Set by user
Autoincrement
By fieldname
Expression
Random
UUID
By script
Document Naming Rule
```

Они нужны для других моделей данных.

В рамках сквозного `Request` сейчас изучаем один воспроизводимый вариант — series.

Особенно не используем `By script`: код App ещё не изучался.

---

## Rename — это не обычный Save

Если изменить:

```text
Subject
```

это изменение обычного поля.

Если менять:

```text
REQ-2026-00001
→ REQ-2026-00420
```

это уже Rename Document — отдельная операция Framework.

В этой главе Rename не выполняем. Сейчас достаточно понять, что `name` — часть идентичности записи, а не обычное редактируемое поле формы.

---

## Что произойдёт в лабораторной

Ты:

1. сравнишь `name` и `Subject` существующих Requests;
2. задашь `Auto Name = REQ-.YYYY.-.#####`;
3. создашь три новых Request и увидишь последовательную серию;
4. изменишь `Subject` уже сохранённого Request и проверишь, что `name` не изменился;
5. временно установишь неправильный `REQ-#####`;
6. получишь гарантированную ошибку naming на новом Document;
7. вернёшь правильную серию и снова успешно создашь Request.

После лабораторной правильная series остаётся постоянной частью `Request`.

---

## Что запомнить

1. `name` — системный уникальный идентификатор Document.
2. `Title Field = subject` отвечает за удобное отображение и не заменяет `name`.
3. Новая naming strategy действует на новые Documents и не переименовывает старые автоматически.
4. Для `Request` используем стабильную series `REQ-.YYYY.-.#####`.
5. Naming series имеет синтаксис; неправильный шаблон должен приводить к понятной ошибке, а не к угадыванию результата.
6. Rename — отдельная операция и будет нужен только тогда, когда действительно требуется изменить идентичность записи.
