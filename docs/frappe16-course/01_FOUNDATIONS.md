# 01. Bench → Site → App → Module → DocType → Document

Начнём с карты местности. Во Frappe легко запутаться не потому, что всё сложно, а потому что одни и те же слова относятся к разным уровням системы.

После этой главы достаточно понимать шесть вещей: **Bench, Site, App, Module, DocType и Document**.

Проверено: **2026-08-30**.

## 1. Frappe Framework — что это вообще

Frappe Framework — это платформа для создания приложений, которые работают с данными.

Он уже умеет много технических вещей: хранить записи, строить формы и списки, проверять права, давать API, запускать фоновые задачи и так далее.

На пальцах:

> Ты описываешь, **какие данные существуют**, а Frappe берёт на себя большую часть типовой работы вокруг них.

Например, мы описали сущность `Request` с полями `Subject`, `Status` и `Due Date`. Из этого Frappe уже может построить базовую форму, список записей и API. Не нужно сначала вручную писать HTML-страницу, SQL-таблицу и CRUD.

Это и есть смысл выражения **metadata-driven**: поведение системы во многом строится из описания данных.

## 2. Frappe — не ERPNext

Это стоит запомнить сразу.

```text
Frappe Framework — платформа
ERPNext         — приложение на этой платформе
CRM             — отдельное приложение
Helpdesk        — отдельное приложение
своё App        — ещё одно приложение
```

Если ты увидел красивый экран в ERPNext, это не значит, что такой экран входит в чистый Framework.

Простая аналогия: наличие функции в одном приложении на Android не означает, что эта функция встроена в сам Android. Аналогия не идеальная, но границу показывает хорошо.

## 3. Вся базовая иерархия

Вот схема, которую стоит держать в голове:

```text
Bench
└── Site
    └── App
        └── Module
            └── DocType
                └── Document
```

Теперь разберём её сверху вниз.

## 4. Bench

`Bench` — это окружение Frappe и набор команд для управления им.

Типичный каталог выглядит примерно так:

```text
frappe-bench/
├── apps/
├── sites/
├── config/
└── logs/
```

Через команду `bench` создают Sites, получают и устанавливают Apps, запускают миграции, делают backup и управляют окружением.

Например:

```bash
bench new-site training.localhost
bench --site training.localhost install-app training_app
bench --site training.localhost migrate
```

Не нужно пока заучивать команды. Запомни смысл:

> **Bench — это не твои бизнес-данные. Это уровень окружения, в котором живут Sites и Apps.**

## 5. Site

`Site` — один работающий экземпляр Frappe со своей базой данных, пользователями, файлами и настройками.

Например:

```text
training.localhost
```

Один Bench может держать несколько Sites:

```text
frappe-bench
├── dev.localhost
├── test.localhost
└── demo.localhost
```

Они могут использовать один и тот же код приложения, но данные у них будут разные.

### Простой пример

Допустим, `training_app` установлен на двух Sites:

```text
dev.localhost   → 120 тестовых заявок
test.localhost  → 5 заявок для проверки
```

Код App один и тот же. Записи — разные.

Поэтому Site проще всего воспринимать как **отдельную установленную систему**.

## 6. App

`App` — устанавливаемый пакет функциональности Frappe.

Примеры:

```text
frappe
training_app
erpnext
helpdesk
```

Сам Framework тоже поставляется как App с именем `frappe`.

Свой App нужен, когда функциональность должна нормально жить как код:

- храниться в Git;
- устанавливаться на другой Site;
- обновляться;
- тестироваться;
- иметь версии.

App может быть очень маленьким. Например, один DocType и немного Python-кода — это уже нормальное приложение.

## 7. Module

`Module` — логический раздел внутри App.

Представь приложение с такими разделами:

```text
Training App
├── Requests
├── Directory
└── Settings
```

Module помогает разложить по местам DocTypes, Reports, Pages и код.

Сам Module обычно не является записью вроде «Заявка №123». Это скорее раздел проекта.

## 8. DocType

`DocType` — один из главных объектов Frappe. Он описывает **тип документа**.

Например, создадим DocType `Request`:

| Поле | Тип |
|---|---|
| Subject | Data |
| Description | Text |
| Status | Select |
| Due Date | Date |

Для обычного DocType Frappe создаст хранение данных и даст стандартные механизмы работы с записями.

DocType — это не просто SQL-таблица. В нём также задаются, например, naming, права, настройки формы, представлений и часть поведения.

Удобная аналогия:

> **DocType — это бланк плюс правила работы с этим бланком.**

## 9. Document

`Document` — одна заполненная запись конкретного DocType.

Если есть DocType `Request`, документы могут быть такими:

```text
REQ-0001 — Купить бумагу
REQ-0002 — Проверить отчёт
REQ-0003 — Обновить инструкцию
```

То есть:

```text
DocType  = что такое «Заявка» вообще
Document = одна конкретная заявка
```

В коде это тоже видно напрямую:

```python
request = frappe.get_doc("Request", "REQ-0002")
```

Здесь `Request` — DocType, а `REQ-0002` — конкретный Document.

## 10. Соберём всё в один пример

Допустим, мы делаем учебное приложение.

```text
Bench: frappe-bench
Site: training.localhost
App: training_app
Module: Requests
DocType: Request
Document: REQ-0001
```

Это уже вся цепочка от окружения до конкретной записи.

Если завтра мы установим `training_app` на новый Site, код DocType останется тем же, но `REQ-0001` там сам по себе не появится — данные Site отдельные.

## 11. Где чаще всего путаются

| Фраза | Что на самом деле нужно |
|---|---|
| «Хочу ещё одно поле в заявке» | изменить DocType/DocField |
| «Хочу отдельную тестовую систему» | отдельный Site |
| «Хочу переносить функциональность между серверами» | App |
| «Хочу ещё один раздел внутри приложения» | возможно Module или Workspace |
| «Хочу создать конкретную заявку» | новый Document |

Эта таблица полезнее, чем заучивание определений.

## 12. Небольшая особенность v16

В Frappe 16 заметно изменился Desk и навигация, а часть функций, которые раньше находились внутри `frappe`, вынесли в отдельные Apps. Поэтому старые видео по v14/v15 могут показывать другой интерфейс или другой состав Framework.

Именно поэтому курс ориентирован на v16 и сверяется с текущей документацией и веткой `version-16`.

## Мини-практика

Попробуй ответить без подсказки:

1. У тебя один код приложения, но нужны отдельные базы для dev и test. Что создаём? **Два Site.**
2. Нужно добавить тип записи `Request`. Что создаём? **DocType.**
3. `REQ-0042` — это DocType или Document? **Document.**
4. Где должен жить код, который нужно переносить между Sites? **В App.**

Если это стало очевидным, база уже есть.

## Что запомнить

- **Bench** — окружение и управление им.
- **Site** — один экземпляр системы со своими данными.
- **App** — устанавливаемый пакет функциональности.
- **Module** — логический раздел App.
- **DocType** — описание типа документов.
- **Document** — одна конкретная запись.
