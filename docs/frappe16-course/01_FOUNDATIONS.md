# 01. Основа Frappe: Bench → Site → App → Module → DocType → Document

Это первая глава курса. Здесь не создаём бизнес-логику и не пишем код. Цель — понять, **из каких уровней состоит Frappe и что именно мы называем приложением**.

## 1. Что такое Frappe Framework

Frappe Framework — full-stack web framework на Python и JavaScript для приложений, работающих с данными. Его ключевое отличие — метаданные являются частью модели приложения: описание DocType используется не только для хранения данных, но и для построения интерфейса и других механизмов Framework.

Практическое следствие:

```text
описали сущность
        ↓
Frappe уже знает значительную часть того,
как её хранить, показывать и обслуживать
```

Поэтому Frappe нельзя воспринимать ни как обычную библиотеку Python, ни как готовую ERP-систему.

## 2. Frappe Framework не равен ERPNext

Нужно сразу разделить уровни:

```text
Frappe Framework
      │
      ├── ERPNext
      ├── CRM
      ├── Helpdesk
      ├── другие приложения
      └── VEQTA
```

Framework предоставляет техническую платформу. Конкретное приложение добавляет предметную модель.

Если в ERPNext существует, например, конкретная бизнес-сущность, это ещё не значит, что такая сущность входит в чистый Frappe Framework.

## 3. Главная иерархия

Для старта достаточно держать в голове такую схему:

```text
Bench
└── Site
    └── App
        └── Module
            └── DocType
                └── Document
```

Это не просто терминология. Каждый уровень отвечает за разную часть системы.

---

## 4. Bench

Слово `bench` во Frappe используется в двух близких смыслах:

1. **Bench CLI** — командный инструмент управления Frappe-окружением.
2. **Bench directory** — каталог окружения, содержащий Apps, Sites, config и logs.

Упрощённо:

```text
frappe-bench/
├── apps/
├── sites/
├── config/
├── logs/
└── ...
```

Bench нужен не для описания предметных сущностей. Это уровень управления окружением.

Через него выполняются операции вроде:

```text
создать Site
получить App
установить App
выполнить migrate
запустить процессы разработки
сделать backup
```

### Что важно новичку

Не надо на старте учить десятки bench-команд. Пока достаточно понимать:

> Bench управляет окружением Frappe; бизнес-модель приложения живёт ниже.

---

## 5. Site

`Site` — конкретный экземпляр Frappe-системы со своей базой данных, пользователями, настройками, файлами и установленными приложениями.

Например:

```text
veqta.localhost
```

или:

```text
dev.example.internal
```

Один Bench может содержать несколько Sites:

```text
frappe-bench
├── site A
├── site B
└── site C
```

При этом они могут использовать один и тот же код Apps, но иметь разные данные.

### Пример

```text
App VEQTA
   │
   ├── установлен на dev Site
   └── установлен на test Site
```

Код приложения одинаковый, данные сайтов разные.

### Что хранится на уровне Site

Концептуально:

```text
данные Documents
Users
site-specific настройки
Customizations
Files
установленные Apps
```

### Что важно для VEQTA

Dev-site не должен становиться единственным местом, где существует принятое состояние продукта. Если изменение является частью VEQTA, оно должно быть воспроизводимо из репозитория приложения.

---

## 6. App

`App` — устанавливаемый пакет функциональности Frappe.

Примеры:

```text
frappe
veqta
erpnext
helpdesk
```

Сам Framework также поставляется как приложение `frappe`.

Собственный App создаётся Bench CLI и затем устанавливается на нужный Site.

Концептуально:

```text
Site
├── frappe
└── veqta
```

### Что должно жить в App

Если функциональность является частью продукта и должна:

```text
храниться в Git
переезжать между Sites
тестироваться
обновляться
воспроизводиться после установки
```

ей место в App или в штатно экспортируемой конфигурации App.

### Чего App не означает

App не обязан быть огромной отдельной системой. Он может добавлять всего несколько DocTypes и немного логики, используя остальное из Framework.

Это особенно важно для VEQTA.

---

## 7. Module

Module — логическая группировка объектов внутри App.

Условный пример:

```text
VEQTA
├── Work
├── Settings
└── Administration
```

Module помогает организовать код и metadata приложения.

Сам по себе Module обычно не является бизнес-сущностью и не хранит пользовательские записи.

---

## 8. DocType

`DocType` — центральный building block приложения Frappe.

Если нужно хранить сущность:

```text
Work Item
```

мы описываем DocType:

```text
Work Item
├── Title
├── Description
├── Status
└── Due Date
```

Frappe использует это описание как metadata модели.

Обычный DocType определяет, среди прочего:

```text
поля
типы данных
layout формы
naming
permissions
часть поведения
связи с другими сущностями
```

Для обычного DocType Framework создаёт соответствующее хранение в базе данных и предоставляет ORM-работу с документами.

Но главное для понимания новичка:

```text
DocType
≠ просто SQL-таблица
```

Это описание модели **и значительной части её представления во Frappe**.

---

## 9. Document

Если DocType — тип сущности, то Document — одна конкретная запись этого типа.

Например:

```text
DocType: Work Item

Documents:
WORK-0001
WORK-0002
WORK-0003
```

В упрощённой SQL-аналогии:

```text
DocType ≈ model + table metadata + UI metadata
Document ≈ одна запись / объект
```

Но Document нельзя сводить только к строке таблицы: вокруг него работают permissions, lifecycle, validation, comments, attachments, API и другие механизмы Frappe.

---

## 10. Почему эта иерархия важна

Типичная ошибка новичка — смешивать уровни.

Например:

```text
"Нужно поле"
```

не означает:

```text
"нужно новое App"
```

А:

```text
"нужен отдельный тестовый экземпляр"
```

не означает:

```text
"нужно копировать код приложения"
```

Правильная карта:

| Задача | Уровень |
|---|---|
| управлять окружением | Bench |
| отдельные данные/настройки экземпляра | Site |
| поставляемая функциональность продукта | App |
| логическая группировка внутри App | Module |
| тип данных / сущность | DocType |
| конкретная запись | Document |

---

## 11. Что Frappe начинает давать вокруг DocType

Подробно это разберём в следующих главах, но уже сейчас важно увидеть масштаб.

После определения DocType Framework может использовать одну и ту же metadata-модель для:

```text
хранения данных
ORM
Form View
List View
permissions
REST API
reports
import/export
attachments
printing
и других штатных механизмов
```

Именно поэтому перед созданием собственной инфраструктуры в VEQTA всегда нужно сначала проверять возможности самого Frappe.

---

## 12. Что изменилось в v16 и почему старые видео опасны

Frappe v16 отличается от предыдущих веток не только внутренним кодом.

Для v16, в частности:

- обновлены минимальные версии ключевых зависимостей;
- введена постоянная sidebar-навигация на базе `Workspace Sidebar`;
- появился Desktop для публичных Workspaces;
- некоторые ранее встроенные модули вынесены из `frappe` в отдельные Apps.

Поэтому материал по v14/v15 нельзя автоматически считать точной инструкцией по интерфейсу или составу чистого Framework v16.
