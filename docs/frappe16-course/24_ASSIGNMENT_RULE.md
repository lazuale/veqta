# 24. Assignment Rule

В прошлой главе мы вручную назначали пользователю работу через **Assign**.

Схема была такой:

```text
Request REQ-0001
        ↓ Assign
      ToDo
        ↓
boris@example.com
```

Но если документов много, вручную выбирать исполнителя каждый раз неудобно.

Для этого во Frappe есть штатный механизм:

```text
Assignment Rule
```

Он автоматически решает:

> нужно ли назначать этот документ и кому именно?

Проверено: **2026-08-31**.

---

## 1. Самый простой пример

Есть DocType:

```text
Request
├── subject
├── status
└── priority
```

Хотим правило:

> все новые Request со статусом `Open` по очереди распределять между Анной и Борисом.

Создаём `Assignment Rule`:

```text
Document Type: Request
Assign Condition: status == "Open"
Rule: Round Robin
Users:
- anna@example.com
- boris@example.com
```

Теперь сохраняется новый документ:

```text
REQ-0001
status = Open
```

Frappe проверяет правило и создаёт связанный `ToDo`.

Следующий подходящий Request назначается следующему пользователю.

То есть:

```text
Document изменился
        ↓
проверить Assignment Rule
        ↓
условие подходит?
        ↓ да
выбрать User
        ↓
создать ToDo
```

Это всё ещё обычный Assignment из прошлой главы.

Разница только в том, что пользователя выбирает Framework автоматически.

---

## 2. Assignment Rule не создаёт новую систему задач

Важно сразу правильно представить архитектуру.

`Assignment Rule` не хранит отдельную очередь работ и не заменяет `ToDo`.

Он только автоматизирует уже знакомый механизм:

```text
Assignment Rule
      ↓
выбирает пользователя
      ↓
Assign
      ↓
ToDo
```

Поэтому после автоматического назначения мы всё равно увидим обычный `ToDo` со знакомыми полями:

```text
allocated_to
reference_type
reference_name
status
priority
date
assigned_by
assignment_rule
```

В поле `assignment_rule` сохраняется правило, которое создало назначение.

---

## 3. Где правило применяется

В `Assignment Rule` сначала выбирается:

```text
Document Type
```

Например:

```text
Request
```

После этого правило относится именно к документам этого DocType.

Одно правило нельзя одновременно назначить сразу на десять разных DocType.

Если автоматизация нужна для другого DocType, создаётся другое правило.

---

## 4. Для `ToDo` Assignment Rule создать нельзя

Это специальное ограничение Framework.

Почему оно логично:

```text
Assignment Rule
→ создаёт ToDo
```

Если разрешить правило непосредственно для `ToDo`, легко получить бессмысленную рекурсивную схему:

```text
ToDo
→ Assignment Rule
→ новый ToDo
→ Assignment Rule
→ ...
```

Поэтому текущий v16 прямо запрещает:

```text
Document Type = ToDo
```

---

# Условия

## 5. `Assign Condition`

Главное поле правила:

```text
Assign Condition
```

Это простое Python-выражение, которое должно вернуть истину или ложь.

Например:

```python
status == "Open"
```

или:

```python
status == "Open" and priority == "High"
```

или:

```python
amount > 10000
```

Если выражение истинно, документ подходит под правило назначения.

Если ложно — правило его не назначает.

---

## 6. Это `PythonExpression`, а не полноценный Python-скрипт

В metadata v16 поле `Assign Condition` имеет тип:

```text
Code
Options: PythonExpression
```

То есть здесь ожидается выражение:

```python
status == "Open"
```

а не программа из нескольких строк:

```python
x = 10
if status == "Open":
    ...
```

Для новичка достаточно правила:

> в Assignment Rule пишем условие, а не отдельный Python-модуль.

---

## 7. Поля документа доступны прямо по fieldname

Например, у `Request` есть:

```text
status
priority
department
```

В условии можно написать:

```python
status == "Open" and priority == "High"
```

Или:

```python
department == "Support"
```

Именно поэтому хорошие технические `fieldname` важны не только для базы данных, но и для автоматизации.

---

## 8. `Unassign Condition`

Допустим, Request был назначен исполнителю:

```text
status = Open
→ Assignment создан
```

Потом документ изменился:

```text
status = Cancelled
```

Мы хотим автоматически убрать назначение.

Для этого есть:

```text
Unassign Condition
```

Например:

```python
status == "Cancelled"
```

Когда условие становится истинным, активный Assignment очищается.

Связанный `ToDo` при этом переводится в:

```text
Cancelled
```

То есть:

```text
Unassign
≠ удалить историю

Unassign
→ прекратить назначение
```

---

## 9. `Close Condition`

Есть похожее, но другое поле:

```text
Close Condition
```

Например:

```python
status == "Closed"
```

Тогда при выполнении условия связанный `ToDo` закрывается:

```text
Open → Closed
```

Это отличается от Unassign:

| Условие | Что происходит с ToDo |
|---|---|
| Assign Condition | создаётся `Open` ToDo |
| Unassign Condition | назначение отменяется, ToDo становится `Cancelled` |
| Close Condition | ToDo становится `Closed` |

Простой смысл:

```text
Cancelled
→ работа больше не должна выполняться

Closed
→ работа считается выполненной/закрытой
```

---

## 10. Закрытый Assignment в v16 может открыться снова

В текущем коде v16 есть полезная деталь.

Если `Close Condition` раньше выполнялось и `ToDo` стало `Closed`, а затем документ изменился так, что условие закрытия больше не выполняется, Framework умеет снова открыть связанный Assignment:

```text
Closed → Open
```

Это позволяет автоматическому назначению следовать за текущим состоянием документа.

Но такую автоматику нужно проектировать осознанно: странные или постоянно меняющиеся условия могут заставлять Assignment прыгать между состояниями.

---

# Как выбирается исполнитель

В текущем Frappe v16 есть **четыре** стратегии Assignment Rule:

```text
Round Robin
Load Balancing
Based on Field
Weighted Distribution
```

Последний вариант особенно важно отметить: старые статьи и часть документации перечисляют только первые три, но в актуальном `version-16` `Weighted Distribution` уже присутствует и в metadata, и в серверном коде.

---

## 11. `Round Robin`

Самый простой вариант.

Есть пользователи:

```text
Anna
Boris
Charlie
```

Документы распределяются по очереди:

```text
REQ-0001 → Anna
REQ-0002 → Boris
REQ-0003 → Charlie
REQ-0004 → Anna
REQ-0005 → Boris
```

В самом Assignment Rule хранится:

```text
last_user
```

Framework использует его, чтобы выбрать следующего пользователя.

Подходит, когда:

```text
все исполнители примерно равнозначны
и
нужно просто равномерно крутить очередь
```

---

## 12. `Load Balancing`

Здесь Framework смотрит, у кого меньше открытых Assignment.

Например:

```text
Anna   → 8 Open ToDo
Boris  → 3 Open ToDo
Charlie→ 5 Open ToDo
```

Следующий документ получит:

```text
Boris
```

Потому что у него минимальная текущая нагрузка.

---

## 13. Важная деталь Load Balancing

В актуальном v16 нагрузка считается не как «все задачи пользователя во всей системе».

Сервер считает `Open ToDo` для:

```text
reference_type = Document Type этого Assignment Rule
```

То есть правило для `Request` сравнивает открытую нагрузку именно по `Request`.

Например, у Анны могут быть ещё 50 ToDo другого типа, но они не обязательно попадут в расчёт этого правила.

Это важнее, чем абстрактная фраза «выбирается наименее загруженный пользователь».

---

## 14. `Based on Field`

Иногда исполнителя уже хранит сам документ.

Например:

```text
Request
└── reviewer
    Link → User
```

Тогда правило можно настроить:

```text
Rule: Based on Field
Field: reviewer
```

Документ:

```text
REQ-0001
reviewer = anna@example.com
```

получит Assignment:

```text
Anna
```

Здесь не нужна очередь пользователей.

Framework просто берёт User из выбранного поля документа.

---

## 15. Какие поля предлагаются для `Based on Field`

Текущий интерфейс v16 предлагает подходящие поля примерно таких видов:

```text
Link → User
Data
Dynamic Link
```

а также системный:

```text
Owner
```

Но сервер в итоге проверяет, что полученное значение действительно соответствует существующему `User`.

Поэтому наиболее понятный вариант для своей модели:

```text
Link → User
```

---

## 16. `Weighted Distribution`

В актуальном v16 появился ещё один вариант:

```text
Weighted Distribution
```

Он нужен, если документы надо распределять не поровну.

Например:

```text
Anna  weight = 1
Boris weight = 2
```

Это означает соотношение примерно:

```text
1 : 2
```

То есть на каждые три слота распределения:

```text
Anna  → 1
Boris → 2
```

Последовательность текущей реализации выглядит примерно так:

```text
Anna
Boris
Boris
Anna
Boris
Boris
...
```

Это полезно, если один сотрудник работает полную смену, а другой — половину, либо у исполнителей объективно разная пропускная способность.

---

## 17. Weight — это относительный вес, а не количество задач

Например:

```text
Anna  = 2
Boris = 4
```

имеет то же отношение, что:

```text
Anna  = 1
Boris = 2
```

Поэтому нет смысла ставить огромные числа без необходимости.

Обычно достаточно небольших понятных весов:

```text
1 / 1
1 / 2
2 / 3
```

В v16 дочерняя строка `Assignment Rule User` имеет поле:

```text
weight
```

с default:

```text
1
```

# Дополнительные настройки

## 18. `Assignment Days`

Правило можно ограничить днями недели.

Например:

```text
Monday
Tuesday
Wednesday
Thursday
Friday
```

Тогда в субботу и воскресенье правило пропускается.

В интерфейсе v16 есть быстрые варианты:

```text
Weekdays
Weekends
All Days
```

То есть необязательно добавлять все дни вручную.

---

## 19. Assignment Days — это не календарь рабочих смен

Эта настройка отвечает только на простой вопрос:

```text
в какой день недели правило может сработать?
```

Она сама по себе не знает:

```text
отпуск пользователя
больничный
рабочую смену
праздник
часовой интервал
нагрузку подразделения
```

Если нужна полноценная сложная маршрутизация по графикам людей, одного Assignment Rule уже может быть мало.

---

## 20. `Due Date Based On`

У Assignment можно автоматически выставить срок.

Допустим, в `Request` есть поле:

```text
due_date
Date
```

В Assignment Rule выбираем:

```text
Due Date Based On: due_date
```

Тогда созданный ToDo получит:

```text
ToDo.date = Request.due_date
```

В интерфейсе сюда предлагаются поля исходного DocType типов:

```text
Date
Datetime
```

---

## 21. Срок ToDo обновляется вместе с исходным документом

Допустим:

```text
Request.due_date = 2026-09-05
```

Assignment создан со сроком:

```text
ToDo.date = 2026-09-05
```

Потом срок Request поменяли:

```text
2026-09-05 → 2026-09-08
```

В текущем v16 Framework обновляет дату открытого ToDo, который был создан соответствующим Assignment Rule:

```text
ToDo.date → 2026-09-08
```

То есть здесь нет необходимости писать отдельный Client Script только для синхронизации срока.

---

## 22. `Description`

У правила есть Description, которая попадёт в создаваемый Assignment.

Можно использовать значения документа через template.

Например:

```text
Проверить заявку {{ name }}: {{ subject }}
```

Для:

```text
REQ-0001
subject = Проверить отчёт
```

получится описание примерно:

```text
Проверить заявку REQ-0001: Проверить отчёт
```

Под капотом текущий v16 рендерит Description как template на данных документа.

---

## 23. `Priority` у Assignment Rule

На один DocType можно создать несколько Assignment Rule.

Например:

```text
Rule A
priority = 100
condition = priority == "High"

Rule B
priority = 10
condition = status == "Open"
```

Framework сортирует правила по:

```text
priority desc
```

То есть сначала проверяет правило с большей Priority.

Если оно успешно назначило документ, перебор правил на этом заканчивается.

Удобно мыслить так:

```text
более специфичное правило
→ выше Priority

общее резервное правило
→ ниже Priority
```

---

## 24. Не путай две Priority

Здесь легко запутаться.

Есть:

```text
Assignment Rule.priority
```

и есть:

```text
ToDo.priority
```

Первое отвечает:

> какое правило проверить раньше?

Второе отвечает:

> насколько приоритетна сама назначенная работа?

Это разные вещи.

---

## 25. `Disabled`

Если правило временно не нужно, его можно отключить:

```text
Disabled = ✓
```

Framework выбирает для автоматического применения только правила:

```text
disabled = 0
```

Это лучше, чем удалять правило и потом собирать его заново.

---

# Когда именно правило запускается

## 26. Assignment Rule связан с lifecycle документа

В Frappe v16 обработчик Assignment Rule подключён к общим событиям документов.

В частности, Framework вызывает его на:

```text
on_update
on_cancel
on_update_after_submit
```

А обновление срока Assignment также подключено к обновлению документа.

Поэтому Assignment Rule — это не отдельный cron, который раз в час ищет подходящие записи.

Упрощённо:

```text
Document сохраняется/меняется
        ↓
Framework вызывает Assignment Rule
        ↓
проверяются текущие условия
```

---

## 27. Assignment не обязательно появляется только при первом создании

Представим:

```text
REQ-0001
status = Draft
```

Условие:

```python
status == "Open"
```

При первом сохранении оно ложно.

Assignment нет.

Позже статус меняют:

```text
Draft → Open
```

Документ снова сохраняется.

Теперь условие истинно — Assignment Rule может создать ToDo.

То есть автоматизация реагирует на состояние документа, а не только на сам факт его создания.

---

## 28. Существующие Assignment имеют значение

Текущая серверная логика не создаёт бесконечно новые ToDo при каждом сохранении.

Если активное назначение уже существует, Framework сначала рассматривает условия снятия/закрытия.

Новое автоматическое назначение применяется, когда текущие назначения очищены или их нет.

Это защищает от простого сценария:

```text
Save
→ новый ToDo
Save
→ ещё один ToDo
Save
→ ещё один ToDo
```

---

## 29. Assignment Rule фактически управляет текущим Assignment

Есть важная архитектурная деталь v16.

Когда правило выполняет новое назначение, сервер перед этим вызывает очистку существующих assignments документа.

То есть Assignment Rule лучше воспринимать как механизм:

```text
определить текущего автоматического исполнителя
```

а не как способ бесконечно добавлять параллельных исполнителей.

Если бизнес-процесс требует одновременно:

```text
исполнитель
+
проверяющий
+
наблюдатель
```

то не стоит автоматически превращать это в три конкурирующих Assignment Rule. Возможно, эти роли являются разными сущностями процесса и должны моделироваться отдельно.

---

## 30. Ручные и автоматические назначения надо смешивать осторожно

Поскольку автоматическое правило умеет очищать существующие Assignment при переназначении или Unassign, схема вроде:

```text
один человек назначен правилом
+
ещё один вручную
```

может вести себя не так, как ожидает новичок.

Если ручной второй исполнитель является обязательной частью модели, сначала проверь реальное поведение на тестовом DocType.

Не стоит считать Assignment Rule полноценным движком команд и ролей участников документа.

---

# Четыре стратегии рядом

## 31. Как выбрать Rule

| Требование | Rule |
|---|---|
| Просто выдавать по очереди | **Round Robin** |
| Давать тому, у кого меньше открытых назначений этого DocType | **Load Balancing** |
| Исполнитель уже указан в поле документа | **Based on Field** |
| Распределять в заданной пропорции | **Weighted Distribution** |

Примеры:

```text
3 одинаковых оператора
→ Round Robin

3 оператора с постоянно разной текущей очередью
→ Load Balancing

Request.reviewer уже заполнен
→ Based on Field

Senior должен получать вдвое больше заявок, чем Junior
→ Weighted Distribution
```

# Assignment Rule и другие механизмы

## 32. Assignment Rule ≠ Workflow

Assignment Rule отвечает:

```text
кто должен работать с документом?
```

Workflow отвечает:

```text
какие переходы между состояниями разрешены
и кому?
```

Например:

```text
Assignment Rule
→ назначить Request Анне

Workflow
→ разрешить Анне перевести его из Review в Approved
```

Это разные механизмы, которые могут работать вместе.

Workflow подробно разберём в главах 25–26.

---

## 33. Assignment Rule ≠ permissions

Автоматически назначить документ пользователю не означает автоматически построить всю схему доступа.

Однако стандартный механизм Assign, который использует Assignment Rule, умеет при необходимости выдать assignee Share на конкретный документ, если у него нет доступа и Sharing разрешён.

Это полезный fallback.

Но нормальная постоянная схема безопасности всё равно должна проектироваться через:

```text
Role Permission
User Permission
и другие permissions
```

а не через надежду на случайные Share после назначения.

---

## 34. Assignment Rule ≠ Notification

Assignment Rule создаёт работу:

```text
ToDo
```

Notification сообщает о событии:

```text
email
system notification
и другие каналы
```

При Assignment пользователь может получить штатное уведомление о назначении, но сам Assignment Rule не является универсальным конструктором уведомлений.

Notification отдельно разберём в главе 27.

---

## 35. Assignment Rule ≠ SLA

Поля:

```text
Due Date Based On
Priority
Load Balancing
```

могут создать ощущение, что перед нами полноценная SLA-система.

Но базовый Assignment Rule не отвечает сам по себе на вопросы:

```text
сколько рабочих часов осталось
какие праздники исключить
когда эскалировать просрочку
как считать pause time
```

Он решает более узкую задачу:

```text
автоматически назначить документ
и при необходимости поставить срок ToDo
```

---

# Что происходит под капотом

## 36. Упрощённая последовательность

Для документа `REQ-0001` можно представить работу Framework так:

```text
REQ-0001 сохранён
        ↓
найти активные Assignment Rule для Request
        ↓
отсортировать по Priority
        ↓
учесть Assignment Days
        ↓
проверить существующие ToDo
        ↓
Unassign / Close при необходимости
        ↓
если активного Assignment нет
        ↓
проверять Assign Condition по порядку
        ↓
первое подходящее правило
        ↓
выбрать User
        ↓
создать ToDo
        ↓
обновить _assign
        ↓
уведомить пользователя
```

Этой схемы достаточно, чтобы понимать почти всё поведение Assignment Rule без чтения Python-кода Framework.

---

## 37. Ошибка условия не должна валить весь документ

Текущий v16 выполняет условия через безопасное вычисление выражения.

Если условие Assignment Rule падает с ошибкой, Framework показывает сообщение вроде:

```text
Auto assignment failed: ...
```

и возвращает для этого условия `False`.

В коде прямо есть комментарий, что ошибка auto assignment не должна блокировать документ, потому что сохранение может происходить, например, в процессе получения email.

Это удобно эксплуатационно, но означает другое:

> плохое Assignment Rule может молча оставить документ без нужного исполнителя.

Поэтому автоматические правила нужно тестировать на реальных примерах, а не только сохранять и считать готовыми.

# Когда Assignment Rule действительно подходит

## 38. Хорошие сценарии

Assignment Rule хорошо подходит, когда задача формулируется так:

```text
если документ удовлетворяет условию
→ выбрать одного исполнителя
→ создать ему Assignment
```

Например:

```text
новые заявки
→ по очереди между операторами
```

или:

```text
High Priority
→ пользователь из поля duty_manager
```

или:

```text
входящие обращения
→ наименее загруженному сотруднику
```

или:

```text
70% потока → Senior
30% потока → Junior
```

---

## 39. Когда не надо насильно использовать Assignment Rule

Не стоит пытаться запихнуть в него задачу вида:

```text
выбрать бригаду по сменному графику,
проверить компетенции,
проверить участок,
проверить отпуск,
проверить лимит часов,
назначить двух исполнителей и одного проверяющего,
построить цепочку эскалаций
```

Технически часть этого можно начать обкладывать условиями и дополнительным кодом.

Но в какой-то момент это уже отдельная доменная логика маршрутизации.

Правильный вопрос:

```text
Assignment Rule всё ещё выражает правило понятно?
```

Если нет — пора проектировать собственную серверную логику, а не превращать настройку в скрытый программный модуль.

# Типичные ошибки

## 40. Создавать `assigned_to` вместо проверки штатного Assignment

Если задача просто:

> назначить пользователю работу с документом

сначала используй:

```text
Assignment / ToDo / Assignment Rule
```

И только потом добавляй собственные поля ответственности, если они имеют отдельный бизнес-смысл.

---

## 41. Путать Assignment со статусом документа

```text
REQ-0001 assigned to Anna
```

не означает автоматически:

```text
REQ-0001.status = In Progress
```

И наоборот:

```text
status = Closed
```

само по себе не закрывает ToDo, если соответствующее Close Condition не настроено.

Эти механизмы связаны только теми правилами, которые ты явно задаёшь.

---

## 42. Делать десять пересекающихся правил без Priority

Если несколько правил подходят одному документу, нужно понимать, какое должно выигрывать.

Например:

```text
High Priority Requests
priority = 100

All Open Requests
priority = 10
```

Так поведение читается.

Если у всех Priority одинаковая и условия пересекаются, система становится сложнее для сопровождения.

---

## 43. Считать Load Balancing интеллектуальным планировщиком

Он решает очень конкретную задачу:

```text
посчитать открытые ToDo данного reference_type
и выбрать минимальное число
```

Он не оценивает автоматически:

```text
сложность заявки
реальное время выполнения
скорость сотрудника
занятость в календаре
```

Если такие факторы нужны, нужна другая логика.

---

## 44. Использовать огромные условия вместо нормальной модели данных

Плохой признак:

```python
(status == "Open" and department == "A" and ...)
or (...)
or (...)
or (...)
```

на несколько экранов.

Иногда проблема не в Assignment Rule, а в том, что сама модель документа не выражает нужные признаки простыми полями и связями.

Сначала исправляется модель данных, потом автоматизация.

# Мини-практика

## Практика 1. Round Robin

Возьми учебный DocType `Request`.

Создай пользователей:

```text
anna@example.com
boris@example.com
```

Создай Assignment Rule:

```text
Document Type: Request
Description: Проверить {{ name }} — {{ subject }}
Assign Condition: status == "Open"
Rule: Round Robin
Assignment Days: All Days
Users:
- anna@example.com
- boris@example.com
```

Создай три Request со статусом `Open`.

Ожидаем:

```text
REQ-0001 → Anna
REQ-0002 → Boris
REQ-0003 → Anna
```

Открой созданные ToDo и найди:

```text
allocated_to
reference_type
reference_name
assignment_rule
```

---

## Практика 2. Unassign

Добавь:

```text
Unassign Condition:
status == "Cancelled"
```

Возьми назначенный Request и поменяй:

```text
Open → Cancelled
```

Проверь связанный ToDo.

Ожидаем:

```text
Open → Cancelled
```

---

## Практика 3. Due Date

Добавь в `Request` поле:

```text
due_date
Date
```

В Assignment Rule выбери:

```text
Due Date Based On: due_date
```

Создай Request со сроком.

Проверь:

```text
Request.due_date
=
ToDo.date
```

Потом измени срок Request и снова посмотри ToDo.

---

## Практика 4. Based on Field

Добавь в `Request`:

```text
reviewer
Link → User
```

Создай второе Assignment Rule:

```text
Rule: Based on Field
Field: reviewer
```

Укажи в Request:

```text
reviewer = boris@example.com
```

Проверь, кому создастся ToDo.

Не забудь выставить Priority правил так, чтобы понимать, какое из них должно примениться первым.

---

## Практика 5. Weighted Distribution

Создай отдельное правило:

```text
Rule: Weighted Distribution

Anna  weight 1
Boris weight 2
```

Создай несколько одинаковых подходящих документов и посмотри последовательность назначений.

Цель здесь не получить идеальную статистику на трёх документах, а увидеть принцип:

```text
1 слот Anna
2 слота Boris
цикл повторяется
```

---

# Что запомнить

1. **Assignment Rule автоматизирует обычный Assignment и создаёт обычный `ToDo`.**
2. **`Assign Condition` решает, подходит ли документ под назначение.**
3. **`Unassign Condition` отменяет Assignment, а `Close Condition` закрывает ToDo.**
4. **В актуальном v16 есть четыре стратегии: Round Robin, Load Balancing, Based on Field и Weighted Distribution.**
5. **Load Balancing считает открытые ToDo соответствующего Document Type, а не всю абстрактную занятость человека.**
6. **Несколько правил проверяются по Priority; первое успешно применившееся правило выигрывает.**
7. **`Due Date Based On` умеет брать Date/Datetime из исходного документа и обновлять срок открытого ToDo.**
8. **Assignment Days ограничивает правило днями недели, но не заменяет рабочий календарь сотрудников.**
9. **Assignment Rule управляет текущим автоматическим назначением; это не универсальная модель команд, ролей и SLA.**
10. **Сначала используй штатный Assignment Rule, а собственный код добавляй только когда правило уже невозможно понятно выразить настройкой.**
