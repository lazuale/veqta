# VEQTA — история состояния v0.1

Статус: **рабочая гипотеза, не принятое решение**.

Цель — понять, достаточно ли штатной истории Frappe для аналитики жизненного цикла `Work Item`.

## 1. Что штатно сохраняет Frappe

При Workflow transition Frappe сохраняет новое текущее состояние документа и добавляет Workflow comment с названием нового состояния.

Для DocType с tracking Frappe также использует `Version`. У `Version` изменения хранятся в скрытом поле `data` типа Code, то есть техническая история представлена сериализованными данными, а не отдельными аналитическими колонками перехода.

Это хорошо подходит для UI-аудита и просмотра изменений, но плохо подходит как стабильный аналитический источник жизненного цикла VEQTA.

## 2. Почему не использовать Version как бизнес-факт

Для аналитики нам потенциально нужны прямые поля:

```text
work_item
from_state
to_state
changed_by
changed_at
```

Если извлекать их из `Version.data` или Workflow comments, аналитика начинает зависеть от внутреннего формата технического аудита Frappe и от разбора сериализованных/текстовых данных.

Это противоречит принятому принципу VEQTA: ключевые аналитические факты должны быть структурированы.

## 3. Минимальный кандидат

Если прототип подтверждает необходимость аналитики времени по состояниям, добавить один технический DocType VEQTA:

```text
Work State Change
-----------------
work_item       Link -> Work Item
from_state      Link -> Workflow State
to_state        Link -> Workflow State
changed_by      Link -> User
changed_at      Datetime
```

Он не заменяет `Version`, Timeline или Workflow comments.

Назначение различается:

```text
Frappe Version / Timeline
= технический аудит

Work State Change
= структурированный бизнес-факт для VEQTA
```

## 4. Что не строим

- универсальный Event Store;
- Event Sourcing;
- собственный Audit Engine;
- JSON payload событий;
- копирование всех изменений Work Item.

Фиксируется только доказанно важный доменный факт: переход состояния.

## 5. Когда сущность действительно нужна

`Work State Change` принимается в модель только если требуется хотя бы одна из задач:

- время в состоянии;
- история прохождения процесса;
- количество переходов;
- восстановление последовательности состояний;
- аналитика ожидания/обработки;
- независимый от технического audit Frappe источник переходов.

Для исходной идеи VEQTA эти требования выглядят вероятными, но решение должно быть подтверждено прототипом.

## 6. Требование целостности при реализации

Если `Work State Change` будет принят, изменение state и создание записи перехода должны происходить в одной транзакции. Не должно быть состояния, когда `Work Item.state` изменён, а соответствующий бизнес-факт отсутствует.

Это не требует нового framework: достаточно небольшого server-side обработчика/хука VEQTA поверх штатной транзакции Frappe.
