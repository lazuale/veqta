# VEQTA — фундамент проекта

Статус: **актуальная базовая концепция**.

Этот документ фиксирует точку, от которой проект развивается после пересмотра ранних архитектурных идей.

## 1. Исходная проблема

Большинство готовых систем управления работой предлагают не только инструменты, но и собственную модель мира: проекты, тикеты, Scrum, CRM-сущности, service desk процессы и т. п.

В результате реальную работу часто приходится подгонять под продукт.

VEQTA исходит из обратного принципа:

> **Система должна позволять адаптировать процесс под организацию, не разрушая структуру и качество данных.**

## 2. Роль Frappe

Frappe Framework является технической платформой VEQTA.

По умолчанию VEQTA использует штатные возможности Frappe для:

- DocType и ORM;
- базы данных и транзакций;
- пользователей и аутентификации;
- ролей и permissions;
- форм и списков;
- Kanban и Workspace;
- Workflow и его условий;
- комментариев и файлов;
- уведомлений;
- API;
- background jobs;
- reports;
- Version/Timeline;
- Custom Fields и настройки форм.

VEQTA не должна создавать собственный аналог перечисленного, пока не доказано, что штатного механизма принципиально недостаточно.

## 3. Роль VEQTA

Frappe даёт универсальные технические primitives, но сам по себе не определяет предметную модель управляемой работы.

VEQTA должна добавить **небольшую устойчивую модель работы**, на основе которой пользователь сможет настраивать собственный процесс.

Текущая минимальная гипотеза:

- `Work Item` — единица управляемой работы;
- `Work Type` — тип работы;
- `State` — текущее состояние.

Другие понятия не включаются в фундамент заранее.

## 4. Что настраивает пользователь

VEQTA не должна навязывать Scrum, Kanban, ITIL, Project Management или другую конкретную методологию.

Пользователь должен по возможности штатными средствами Frappe настраивать:

- свои типы работы;
- свои состояния;
- переходы и workflow;
- роли и доступ;
- форму и дополнительные поля;
- представления;
- отчёты;
- уведомления.

Важно: это не означает, что VEQTA обязана написать собственный конструктор. Напротив, сначала используются возможности Desk/Frappe.

## 5. Где VEQTA должна быть строгой

Свобода процесса не должна превращать данные в неструктурированную помойку.

Базовые требования:

1. Один бизнес-факт имеет один источник истины.
2. Значимые данные имеют явный тип и семантику.
3. Ключевая модель не хранится в произвольном JSON или EAV.
4. Производные показатели не выдаются за первичные факты.
5. История, необходимая для аналитики, не должна требовать разбора комментариев и текста.
6. Названия для пользователя не должны быть единственными машинными идентификаторами там, где нужна стабильность.
7. Новые предметные сущности не добавляются в `Work Item` просто ради удобства одного сценария.

## 6. OLTP и аналитика

VEQTA является операционной системой и хранит первичные данные в OLTP-модели.

Аналитика строится поверх этих данных и при необходимости может быть вынесена в отдельный слой или хранилище.

Принцип:

```text
VEQTA OLTP = источник истины
        ↓
аналитическая обработка
        ↓
OLAP / marts / BI при необходимости
```

В Core не должны появляться поля вроде `age_days`, `cycle_hours`, `monthly_count` только ради отчётов, если они вычисляются из первичных фактов.

## 7. Что VEQTA сейчас сознательно НЕ строит

До доказанной необходимости не создаём:

- собственный framework поверх Frappe;
- собственный ORM;
- собственный permission engine;
- собственный form builder;
- собственный notification engine;
- собственный plugin engine;
- универсальный BPM engine;
- микросервисную архитектуру;
- отдельные apps для каждой потенциальной capability;
- полноценный DWH;
- Sprint, Epic, Project, SLA, Handoff, Approval и другие сущности как обязательную часть Core.

## 8. Граница применения

VEQTA имеет смысл там, где задачу можно описать так:

> **Есть единица работы, которую необходимо провести через некоторый пользовательский процесс.**

Потенциальные области:

- операционная работа;
- внутренние поручения;
- проверки и контроль;
- back office;
- обработка обращений и исключений;
- диспетчерская работа;
- case management;
- согласования;
- shared services.

VEQTA не должна пытаться заменить специализированные системы, где основным объектом являются, например, бухгалтерская проводка, складское движение, телеметрия, Git commit или юридически значимый документ.

## 9. Правило разработки

Для каждого нового требования задаются вопросы по порядку:

1. Уже умеет ли это Frappe?
2. Можно ли решить задачу конфигурацией?
3. Нужна ли эта функция универсальной модели работы?
4. Нужен ли вообще новый код или новая сущность?

Только после этого начинается разработка.

## 10. Короткая формула

> **Frappe даёт инструменты. VEQTA даёт модель работы. Пользователь задаёт процесс.**

И дополнительное ограничение:

> **Гибкость процесса не должна разрушать чистоту данных.**
