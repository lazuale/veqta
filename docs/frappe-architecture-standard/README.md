# Архитектурный стандарт Frappe

> Внутренний архитектурный стандарт проектирования приложений на Frappe Framework 16.

Этот раздел отвечает на один вопрос: **как принимать архитектурные решения, исходя из устройства самого Frappe, а не из привычек команды или шаблонов другого фреймворка**.

Стандарт не является официальным документом Frappe Technologies. Он собран из официальной документации Frappe, актуального исходного кода и практики официальных приложений экосистемы, прежде всего ERPNext. Там, где правило является нашим архитектурным выводом, это должно быть указано прямо.

## Границы стандарта

Стандарт покрывает решения, которые влияют на:

- модель данных и `Document`;
- жизненный цикл и бизнес-правила;
- аутентификацию и права доступа;
- транзакции и фоновые задачи;
- API и интеграции;
- расширение и настройку Frappe и других Apps;
- интерфейс, отчётность и realtime-взаимодействие;
- воспроизводимую доставку изменений, миграции и тестирование.

Стандарт **не является энциклопедией всех API Frappe**. Он не описывает эксплуатацию Bench, настройку ОС, полное системное администрирование и каждую пользовательскую функцию Framework. Механизм включается сюда тогда, когда его наличие меняет архитектурное решение и помогает не изобретать параллельную подсистему.

## Правило языка

Аудитория стандарта русскоязычная, поэтому обычный текст пишется по-русски. Английский сохраняется только там, где он нужен для точности или совпадения с реальным интерфейсом и API Frappe.

Не переводим:

- официальные названия сущностей и механизмов Frappe: `DocType`, `Document`, `Workflow`, `Client Script`, `Server Script`, `User Permission`, `Assignment`, `Notification`, `Webhook`, `Workspace`, `Web Form` и т. п.;
- имена методов, полей, hooks и параметров: `validate`, `on_submit`, `frappe.db.get_list`, `ignore_permissions`, `extend_doctype_class` и т. п.;
- общепринятые технические обозначения: REST API, SQL, Python, JavaScript, Git, JSON.

В поясняющем тексте используем русский язык:

```text
lifecycle        → жизненный цикл
ownership        → принадлежность / владелец ответственности
design review    → архитектурная проверка
red flag         → тревожный признак
snapshot         → снимок значения
runtime          → выполнение / работа системы
side effect      → внешний эффект
bypass           → обход проверок
background job   → фоновая задача
scheduler        → планировщик
custom frontend  → собственный интерфейс / фронтенд
```

Если английский термин является официальным названием Frappe, при первом появлении его можно пояснить по-русски, но само название не искажается.

### Короткий словарь технических терминов

- **CRUD** — создание, чтение, изменение и удаление записей.
- **ORM** — программный слой работы с записями базы данных как с объектами.
- **ACL** — модель правил доступа; в Frappe основной механизм прав строится вокруг Roles и permissions.
- **RPC** — вызов серверного метода через API.
- **hook** — предусмотренная Frappe точка расширения или реакции на событие.
- **fixture** — запись конфигурации, экспортированная в App и поставляемая вместе с ним.
- **patch** — одноразовое изменение данных при миграции.
- **fork** — собственная копия Framework или другого App, которую команда поддерживает отдельно от исходного проекта.
- **endpoint** — адрес конкретной операции API.
- **worker** — отдельный процесс, выполняющий фоновые задачи.
- **callback** — функция, вызываемая после определённого события или результата.
- **идемпотентность** — свойство операции, при котором безопасный повтор не создаёт нежелательный второй результат.

## Базовый принцип

Frappe — фреймворк с метаданными как основой модели, полным набором прикладных возможностей и поддержкой low-code. Его стандартная модель уже включает `DocType`/`Document`, права доступа, жизненный цикл, интерфейс, REST API, фоновые задачи, планировщик, уведомления, отчёты и точки расширения.

Поэтому штатное для Frappe решение строится так:

```text
требование
    ↓
какая ответственность нужна?
    ↓
какой штатный механизм Frappe уже отвечает за эту ответственность?
    ↓
совпадает ли его смысл с задачей?
    ↓
ДА → используем штатный механизм
НЕТ → ищем официальную точку расширения
    ↓
только при отсутствии подходящего механизма
вводим собственную архитектурную конструкцию
```

Важно: это **не означает «никакого кода»**. Python Controller, сервисный модуль, собственный API, фоновая задача или отдельный интерфейс могут быть совершенно нормальными для Frappe. Тревожный признак — не наличие собственного кода, а **дублирование уже существующей ответственности фреймворка без причины**.

## Как маркируются утверждения

Для существенного или спорного архитектурного решения используется полный шаблон:

```text
ФАКТ FRAPPE
что Framework действительно предоставляет или гарантирует

ПРУФ
официальная документация / исходный код нужной версии / официальная реализация

АРХИТЕКТУРНОЕ СЛЕДСТВИЕ
какое решение из этого разумно следует

ГРАНИЦА / ИСКЛЮЧЕНИЕ
когда это решение перестаёт быть лучшим вариантом
```

Для простого описания штатного механизма допускается сокращённая форма, если вывод не спорный и источник указан явно.

Используются единые русские метки:

- **[ДОКУМЕНТАЦИЯ FRAPPE]** — прямо подтверждается официальной документацией Frappe Framework;
- **[ИСХОДНЫЙ КОД]** — подтверждается исходным кодом Frappe нужной версии;
- **[РЕЛИЗ FRAPPE]** — подтверждается официальным релизом или заметками к версии;
- **[ОФИЦИАЛЬНАЯ ДОКУМЕНТАЦИЯ ЭКОСИСТЕМЫ]** — подтверждается официальной документацией ERPNext или другого приложения экосистемы;
- **[ОФИЦИАЛЬНАЯ РЕАЛИЗАЦИЯ]** — пример из исходного кода ERPNext или другого официального приложения экосистемы;
- **[АРХИТЕКТУРНЫЙ ВЫВОД]** — вывод из нескольких фактов; не выдаётся за официальное правило Frappe.

Это не позволяет превращать мнение автора в «так задумал Frappe».

## Версионная база

Стандарт ориентирован на **Frappe v16** и проверен по ветке `version-16`. Возможности, зависящие от версии, должны быть отмечены рядом с правилом.

Особенно это относится к:

- `extend_doctype_class` — v16+;
- ограничениям `Server Script`;
- REST API v2;
- изменениям и устареванию способов именования;
- требованиям к версиям Python и Node.js.

Не следует переписывать весь стандарт при каждом patch-релизе. Проверяется основная ветка версии и только те места, где поведение реально изменилось.

## Что стандарт не делает

Он не проектирует конкретное приложение.

Он не говорит:

```text
всегда делай Workflow
всегда делай Child Table
никогда не делай Service
никогда не делай собственный API
```

Он требует другой дисциплины:

> **перед созданием собственного механизма уметь назвать существующий механизм Frappe, объяснить его смысл и показать, почему его недостаточно для конкретной задачи.**

Именно это является основой архитектурной проверки решений на Frappe.
