# 08. Интерфейс и отчётность — представление модели, а не замена модели

## 1. Frappe уже предоставляет прикладной интерфейс

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe Desk — встроенный административный интерфейс. Framework автоматически предоставляет стандартные `Form`/`List` для `DocType` и дополнительные представления.

Источники:

- https://docs.frappe.io/framework/user/en/introduction
- https://docs.frappe.io/framework/user/en/api/list

Frappe поставляет основные прикладные возможности из коробки, поэтому для значительной части внутренних интерфейсов уже существует готовая основа.

### Архитектурное следствие

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Для обычной административной CRUD-работы стандартный Desk — сильный выбор по умолчанию. Собственный фронтенд не нужен только ради формы, списка и фильтров, которые Framework уже генерирует.

---

## 2. Но Desk не определяет предметную модель

Очень типичная ошибка:

> «Нам нужна Kanban-доска, значит главная сущность приложения — колонка доски».

Это проектирование базы данных из экрана.

Правильный порядок:

```text
бизнес-объект
    ↓
DocType + поля + жизненный цикл
    ↓
подходящие представления
```

Например, один рабочий объект со статусом:

```text
status = New / In Progress / Done
```

может отображаться как:

- `Form`;
- `List`;
- `Kanban`;
- `Report`;
- собственная страница.

Один и тот же `Document` не обязан менять свою сущность из-за выбранного представления.

---

## 3. Form View

`Form` — естественное представление одного `Document`.

Уместен, когда пользователь:

- просматривает карточку;
- редактирует поля;
- работает с дочерними таблицами;
- выполняет действия над `Document`.

### Тревожный признак

Создавать собственную страницу только потому, что стандартная `Form` кажется «слишком обычной», ещё до проверки её возможностей.

Собственный интерфейс оправдан функциональным требованием, а не желанием отличаться визуально.

---

## 4. DocType Layout — несколько форм одной модели [v16+]

**[ДОКУМЕНТАЦИЯ FRAPPE]** В v16 `DocType Layout` позволяет создавать несколько раскладок формы для одного `DocType`. Раскладки могут наследоваться через `Based On`, привязываться к ссылкам `DocType` в `Workspace`, а стандартные раскладки могут поставляться внутри App как JSON и синхронизироваться через `bench migrate`.

Источник:

- https://docs.frappe.io/framework/doctypes/doctype-layout

### Подходящий сценарий

Один и тот же `Document` нужен разным группам пользователей:

```text
Продажи  → компактная форма с коммерческими полями
Финансы  → форма с финансовыми полями и другой последовательностью
```

Если это всё ещё **один бизнес-объект с одной идентичностью и жизненным циклом**, различие интерфейсов само по себе не требует создавать два `DocType`.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Когда требование звучит как «одни и те же данные нужно показывать по-разному», сначала проверить `DocType Layout`, а не дублировать модель ради второй формы.

### Граница

`DocType Layout` меняет представление, но не создаёт новую модель безопасности или новый жизненный цикл. Если группы пользователей работают с действительно разными бизнес-объектами либо имеют различающиеся предметные правила, проблема шире одной раскладки.

---

## 5. List View

`List` естественен для поиска, фильтрации и массового просмотра записей.

Источник:

- https://docs.frappe.io/framework/user/en/api/list

`List` можно расширять JavaScript-настройкой, индикаторами и собственными действиями.

### Архитектурное правило

Если пользователю нужен обычный реестр документов, сначала проверить `List View`, а не строить отдельный одностраничный интерфейс (SPA) для реестра.

---

## 6. Kanban, Calendar, Gantt и другие представления

Разные представления подходят разным смыслам данных.

Пример:

```text
status/category → Kanban
start/end date  → Calendar/Gantt
hierarchy       → Tree
```

Но представление должно соответствовать уже существующему смыслу поля.

### Неправильно

Добавить искусственное поле только потому, что конкретному интерфейсу нужна колонка, хотя бизнес-смысла у поля нет.

Если поле существует только для компоновки экрана и не выражает состояние модели, нужно проверить, не смешались ли предметная модель и представление.

---

## 7. Workspace

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Workspace` предназначен для организации рабочей области Desk: ярлыков, ссылок, графиков и секций.

Источник:

- https://docs.frappe.io/framework/user/en/desk/workspace

`Workspace` отвечает на вопрос:

> Как пользователю собрать доступ к рабочим объектам и информации?

Он не должен становиться скрытым источником бизнес-логики.

---

## 8. Report Builder

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Report Builder` позволяет построить простой отчёт без программирования на основе `DocType` и связанных данных.

Источник:

- https://docs.frappe.io/framework/user/en/desk/reports/report-builder

Подходящий класс задач:

```text
выбрать поля;
отфильтровать;
сгруппировать;
получить простой рабочий отчёт.
```

---

## 9. Query Report

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Query Report` предназначен для отчёта на основе SQL-запроса.

Источник:

- https://docs.frappe.io/framework/user/en/guides/reports-and-printing/how-to-make-query-report

Он уместен, когда требование естественно выражается запросом и не нуждается в сложном программном расчёте.

### Предупреждение по безопасности

Отчёт должен учитывать, какие данные реально разрешено показывать пользователю. SQL сам по себе не делает запрос автоматически учитывающим права в том же смысле, что `Document API`.

При чувствительных данных права нужно проверять отдельно.

---

## 10. Script Report

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Script Report` использует Python для сложной логики отчёта.

Источник:

- https://docs.frappe.io/framework/user/en/guides/reports-and-printing/how-to-make-script-reports

Подходит, если отчёт требует:

- сложных расчётов;
- нескольких запросов;
- нестандартного формирования колонок и данных;
- графиков, сообщений или итогов.

### Не считать Script Report «хуже» Query Report

Это не лестница качества.

Выбор зависит от природы задачи:

```text
простая настройка       → Report Builder
естественный SQL-запрос → Query Report
программная логика      → Script Report
```

---

## 11. Prepared Report

Для тяжёлых отчётов Framework поддерживает подготовку в фоне.

Источник:

- https://docs.frappe.io/framework/user/en/guides/reports-and-printing/how-to-make-script-reports

Это связывает отчётность с фоновой обработкой, а не требует держать пользователя в долгом HTTP-запросе.

---

## 12. Web Form

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Web Form` позволяет создать веб-форму поверх `DocType`, включая создание и редактирование `Documents`, публичные сценарии и работу после входа.

Источник:

- https://docs.frappe.io/framework/user/en/web-form

Подходящий сценарий:

> Внешний пользователь должен отправить простую заявку через веб.

### Тревожный признак

Сразу строить отдельный фронтенд + API только ради одной формы, не проверив `Web Form`.

---

## 13. Portal и веб-страницы

Frappe имеет `Portal` и веб-механизмы для серверно формируемых страниц и пользовательских веб-сценариев.

Источник:

- https://docs.frappe.io/framework/user/en/portal-pages

Они подходят, когда `Web Form` уже слишком ограничен, но полноценный отдельный фронтенд ещё не требуется.

---

## 14. Собственный фронтенд совершенно допустим

Стандарт не утверждает:

```text
всё приложение обязано работать только через Desk
```

Собственный фронтенд оправдан, если требование действительно специализированное:

```text
массовая высокочастотная работа;
сложные жесты и взаимодействия;
специализированный пользовательский интерфейс;
интерфейс, прежде всего рассчитанный на мобильные устройства;
визуальный редактор;
панель в реальном времени;
нестандартная навигационная модель.
```

Frappe при этом может оставаться серверной прикладной платформой.

### Главная граница

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Собственный фронтенд не должен вынуждать нас без причины строить параллельную платформу данных и бизнес-логики.

---

## 15. Не хранить бизнес-правила только в интерфейсе

Если собственный фронтенд запрещает кнопку, но серверный API позволяет операцию, запрет является только удобством интерфейса.

Безопасность и инварианты должны оставаться на серверной стороне.

Связанные разделы:

- `03_DOCUMENT_LIFECYCLE.md`;
- `04_SECURITY.md`.

---

## 16. Печать и вывод документов

Frappe имеет встроенные возможности печати и вывода документов как часть платформы из коробки.

Перед созданием отдельного PDF-сервиса для обычного печатного `Document` нужно проверить стандартные `Print Format` и другие возможности печати Framework.

Но специализированный генератор оправдан, если требования к макету, способу формирования или выходному формату выходят за стандартные возможности.

---

## 17. Realtime — штатный путь для обновлений в реальном времени

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe поставляется с realtime API на базе Socket.IO. Серверный код может публиковать события через `frappe.publish_realtime`, а клиент — подписываться через `frappe.realtime.on`. Для отображения прогресса есть `frappe.publish_progress`.

Источник:

- https://docs.frappe.io/framework/user/en/api/realtime

Подходящий класс задач:

```text
обновить экран после серверного события;
показать прогресс фоновой задачи;
уведомить открытый интерфейс об изменении данных.
```

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Если требование буквально означает «сервер должен сообщить открытому интерфейсу об изменении», сначала проверить штатный realtime API, а не создавать опрос сервера каждые несколько секунд или отдельный WebSocket-сервер.

При этом экспериментальные собственные обработчики realtime-событий из nightly-документации нельзя считать стабильным контрактом v16 без отдельной проверки версии.

---

## 18. Архитектурная проверка интерфейса

```text
1. Это обычная карточка Document?
2. Подходит ли стандартная Form?
3. Нужны ли разные формы одного DocType — подходит ли DocType Layout?
4. Это обычный реестр — подходит ли List?
5. Представление Kanban/Calendar/Gantt отражает реальное поле модели?
6. Нужен ли Workspace или это бизнес-логика, спрятанная в навигации?
7. Какой тип отчёта соответствует природе расчёта?
8. Можно ли использовать Web Form/Portal вместо отдельного фронтенда?
9. Если собственный фронтенд нужен — почему?
10. Нужны ли realtime-события вместо собственного опроса сервера/WebSocket?
11. Где находятся реальные серверные правила?
12. Не диктует ли конкретный экран структуру предметной модели?
```
