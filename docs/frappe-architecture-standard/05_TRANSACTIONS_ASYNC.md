# 05. Транзакции, фоновые задачи и планировщик

## 1. Транзакции — часть архитектуры Frappe

Предыдущая версия стандарта почти не учитывала транзакции. Для production-приложения это критический пробел.

**[ДОКУМЕНТАЦИЯ FRAPPE]** Database API описывает модель транзакций Frappe:

- успешный записывающий web-request фиксируется в конце;
- необработанное исключение вызывает откат;
- фоновая или плановая задача фиксируется после успешного завершения;
- необработанное исключение в задаче вызывает откат;
- patches также выполняются в рамках модели транзакций.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Главный вывод для новичка:

> Обычно не нужно вручную управлять `commit` для каждой операции. Framework уже определяет границу транзакции.

---

## 2. Почему ручной frappe.db.commit() — тревожный признак

Если обычная бизнес-операция выполняется внутри запроса:

```text
создать документ A
обновить документ B
создать документ C
```

Framework способен зафиксировать изменения вместе после успешного завершения.

Если разработчик делает `commit` посередине:

```text
создали A
COMMIT
обновили B
ошибка при C
```

`rollback` уже не сможет вернуть A.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Поэтому ручной `commit` внутри обычного потока приложения требует конкретного обоснования.

Это не абсолютный запрет: существуют миграции, служебные инструменты или специальные долгие сценарии. Но «на всякий случай закоммитим» — неправильный мотив.

---

## 3. Исключение поймали сами — сами отвечаем за откат

**[ДОКУМЕНТАЦИЯ FRAPPE]** Документация Database API отдельно предупреждает: если код сам ловит исключение, слой базы данных уже не знает, что операция должна считаться неуспешной; разработчик отвечает за корректное поведение транзакции.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Пример риска:

```python
try:
    dangerous_operation()
except Exception:
    frappe.log_error()
    return "ok"
```

Если `dangerous_operation()` частично изменила БД, а исключение проглочено, стандартный путь отката может не сработать так, как ожидает разработчик.

---

## 4. Прямое обновление БД обходит часть жизненного цикла Document

**[ДОКУМЕНТАЦИЯ FRAPPE]** `frappe.db.set_value()` обновляет значение в базе и не вызывает ORM-события вроде `validate` и `on_update`.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Поэтому:

```text
Document API
    → обычное изменение бизнес-данных,
      где нужны проверки и жизненный цикл

Database API напрямую
    → намеренный обход жизненного цикла
```

### Типовая ошибка

Использовать `db_set`/`set_value` вместо `save()` просто потому, что так короче или быстрее.

Если бизнес-инварианты находятся в Controller, такое обновление может их обойти.

---

## 5. Когда прямой доступ к БД нормален

Он может быть оправдан, если:

- обновляется техническое или вычисляемое поле;
- миграция намеренно обходит жизненный цикл;
- массовая операция требует другого профиля производительности;
- разработчик сознательно управляет последствиями;
- нужно выполнить служебное внутреннее обновление.

Ключевое слово — **намеренно**.

---

## 6. Внешние эффекты и фиксация транзакции

Один из самых опасных классов ошибок:

```text
1. сохранить Frappe Document
2. отправить данные во внешнюю систему
3. позже в запросе возникает исключение
4. Frappe делает rollback
```

Получается:

```text
внешняя система считает операцию выполненной
Frappe считает, что операции не было
```

Frappe предоставляет callbacks транзакций и `enqueue_after_commit`.

Источники:

- https://docs.frappe.io/framework/user/en/api/database
- https://docs.frappe.io/framework/user/en/api/background_jobs
- https://github.com/frappe/frappe/blob/version-16/frappe/utils/background_jobs.py

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Внешний эффект, который должен происходить только после успешной фиксации данных, нужно привязывать к пути успешного `commit`.

---

## 7. after_commit

Database API предоставляет callbacks:

```text
before_commit
after_commit
before_rollback
after_rollback
```

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Это полезно, когда работа с внешним ресурсом должна соответствовать результату транзакции БД.

Но callback не отменяет необходимости думать об идемпотентности: процесс может упасть после внешнего эффекта, сетевой ответ может потеряться и т. д.

---

## 8. Background Jobs — штатная инфраструктура фоновых задач

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe поставляется с системой фоновых задач и `frappe.enqueue`.

Источник:

- https://docs.frappe.io/framework/user/en/api/background_jobs

**[ИСХОДНЫЙ КОД]** В `version-16` реализация поддерживает:

- очереди;
- таймауты;
- `enqueue_after_commit`;
- callbacks успеха/ошибки;
- идентификатор задачи;
- дедупликацию;
- `commit`/`rollback` в worker-процессе.

Источник:

- https://github.com/frappe/frappe/blob/version-16/frappe/utils/background_jobs.py

### Когда фоновая задача — естественный выбор

```text
долгий расчёт;
массовая обработка;
внешняя интеграция, которую не нужно держать в HTTP-запросе;
работа, которая может выполняться асинхронно.
```

---

## 9. Фоновая задача не означает «можно забыть о надёжности»

Перед `enqueue` нужно ответить:

```text
1. Можно ли безопасно выполнить задачу повторно?
2. Что будет, если worker упадёт посередине?
3. Нужен ли job_id / deduplicate?
4. Должна ли задача запускаться только после commit?
5. Как пользователь узнает результат?
6. Как обрабатывается ошибка?
7. Какой timeout действительно нужен?
```

### Идемпотентность

На бытовом языке:

> Если одну и ту же кнопку случайно нажали дважды или задача запустилась повторно, система не должна создать двойную оплату, двойную накладную или повторный внешний запрос без контроля.

---

## 10. enqueue_after_commit

**[ДОКУМЕНТАЦИЯ FRAPPE + ИСХОДНЫЙ КОД]** `frappe.enqueue` поддерживает `enqueue_after_commit=True`.

Источники:

- https://docs.frappe.io/framework/user/en/api/background_jobs
- https://github.com/frappe/frappe/blob/version-16/frappe/utils/background_jobs.py

Это важно для сценария:

```text
создали документ
    ↓
после успешного commit
    ↓
запустили тяжёлую обработку этого документа
```

Иначе worker теоретически может начать работать с состоянием, которое ещё не зафиксировано или позже будет откатано.

## 11. Scheduler Events

**[ДОКУМЕНТАЦИЯ FRAPPE]** Периодические задачи подключаются через hook `scheduler_events`.

Источник:

- https://docs.frappe.io/framework/user/en/api/background_jobs

Пример:

```text
каждый час проверить просроченные записи
каждую ночь пересчитать агрегаты
раз в неделю выполнить очистку
```

Для задач конкретного сайта планировщик Frappe — штатный выбор по умолчанию.

---

## 12. Когда внешний планировщик нормален

Внешний cron или корпоративный оркестратор не является автоматически костылём.

Он может быть правильным, если процесс:

- управляет несколькими независимыми системами;
- является инфраструктурным;
- должен существовать даже без доступного Frappe Site;
- централизованно управляется отдельной платформой оркестрации.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Тревожный признак — не внешний планировщик сам по себе, а параллельный планировщик без отдельной ответственности.

## 13. Notification — штатный механизм пользовательских уведомлений

Frappe имеет подсистему `Notification` для событий `Document`, условий и уведомлений по датам.

Источник:

- https://docs.frappe.io/framework/notifications

Подходящий сценарий:

```text
за 3 дня до срока отправить уведомление ответственному
после изменения status уведомить руководителя
```

### Не превращать Notification в шину событий интеграции

`Notification` не нужно автоматически использовать для:

```text
гарантированной доставки событий предметной области;
строго однократной внешней обработки;
сложных повторных попыток;
внешнего журнала событий.
```

Если требуется надёжная оркестрация интеграций, это другая ответственность.

---

## 14. Assignment / ToDo

Frappe имеет встроенный механизм назначения работы через `Assign To` / `ToDo`.

Источник:

- https://docs.frappe.io/framework/assignments-and-todos

Он подходит, когда смысл требования:

> назначить пользователю работу по конкретному Document.

Но это не означает, что любое предметное поле `account_manager`, `owner_employee` или `responsible_department` нужно заменить `Assignment`.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Отличаем рабочее назначение от устойчивого свойства бизнес-объекта.

---

## 15. Типовой неправильный сценарий

Задача:

> После submit документа отправить его в API, построить PDF и обновить 20 000 строк.

Плохой вариант:

```text
on_submit
  ├─ HTTP API call
  ├─ PDF generation
  └─ цикл 20 000 updates
```

всё синхронно в одном запросе.

Риски:

- большое время ответа;
- timeout;
- длинные блокировки;
- внешний API уже принял данные, а транзакция затем откатилась;
- пользователь не понимает, завершилась ли операция.

Более устойчивый вариант:

```text
submit-транзакция
      ↓
commit
      ↓
enqueue_after_commit
      ↓
фоновая обработка
```

Конкретная реализация зависит от требований к надёжности.

---

## 16. Архитектурная проверка транзакций и фоновой обработки

```text
1. Где начинается и заканчивается транзакция?
2. Есть ли ручной commit/rollback? Зачем?
3. Есть ли прямые записи в БД, обходящие жизненный цикл Document?
4. Есть ли внешние эффекты до commit?
5. Нужен ли after_commit/enqueue_after_commit?
6. Должна ли операция быть фоновой задачей?
7. Идемпотентна ли задача?
8. Как обрабатываются повторные попытки и ошибки?
9. Нужна ли дедупликация?
10. Планировщик относится к одному Site или это внешняя оркестрация?
```

Без ответов на эти вопросы сложную бизнес-операцию нельзя считать архитектурно завершённой.
