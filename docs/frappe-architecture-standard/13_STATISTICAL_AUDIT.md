# 13. Statistical Audit — количественный, корреляционный и регрессионный анализ

## 1. Что именно здесь анализируется

Этот раздел специально не пытается «доказать статистикой», что Frappe-native архитектура лучше любой другой. Для такого вывода понадобился бы реальный набор независимых Frappe-проектов с измеренными дефектами, стоимостью обновлений, временем разработки и другими outcome metrics.

Такого датасета у нас нет.

Поэтому корреляционно-регрессионный анализ применяется честно к тому, что действительно измерено: **структуре перестроенной документации**.

Цели:

1. проверить, нет ли сильного перекоса объёма между архитектурными областями;
2. проверить плотность первичных источников;
3. проверить, объясняется ли размер документов количеством содержательных разделов и пруфов, а не искусственным единообразием;
4. найти разделы, требующие дополнительного аудита;
5. не выдавать малую выборку за статистическое доказательство качества Framework.

Дата расчёта: **2 сентября 2026 года**.

## 3. Баланс объёма

Для девяти core chapters:

```text
общий объём:          117 826 bytes
средний размер:        13 092 bytes
медиана:               13 174 bytes
коэффициент вариации:   11.7 %
```

### Интерпретация

CV около 11.7% означает, что core chapters достаточно сбалансированы по размеру. Нет одного раздела, который в 3–5 раз больше остальных и фактически поглощает стандарт.

Минимум:

```text
08 UI/Reporting = 10 603 bytes
```

Максимум:

```text
03 Document Lifecycle = 15 234 bytes
```

Отношение max/min ≈ 1.44.

Это приемлемый разброс для тем разной сложности.

## 4. Плотность первичных источников

Рассчитано количество source references на 10 000 bytes текста.

| Документ | Sources / 10k bytes |
|---|---:|
| 01 Foundations | 11.45 |
| 02 Data Model | 8.27 |
| 03 Lifecycle | 7.88 |
| 04 Security | 8.41 |
| 05 Transactions | 10.63 |
| 06 API | 7.95 |
| 07 Extension | 11.63 |
| 08 UI | 9.43 |
| 09 Deployment | 8.64 |

Среднее:

```text
9.37 source references / 10k bytes
```

Диапазон:

```text
7.88 ... 11.63
```

### Вывод

Ни один core chapter не является полностью «мнением без пруфов».

Самая высокая source density у Extension и Foundations — ожидаемо, потому что эти разделы много раз разграничивают official seam и наш inference.

Самая низкая у Lifecycle и API. Это не автоматически дефект: оба раздела несколько раз опираются на одни и те же сильные upstream-файлы (`document.py`, `api/v2.py`) вместо множества разных поверхностных ссылок.

Тем не менее именно **03 Lifecycle** и **06 API** следует перепроверять особенно внимательно при будущих major-version обновлениях.

## 5. Pearson correlation matrix

Для метрик core chapters рассчитана линейная корреляция Pearson.

| Пара | r |
|---|---:|
| Размер ↔ число разделов | +0.211 |
| Размер ↔ source refs | +0.443 |
| Размер ↔ review items | +0.314 |
| Sections ↔ source refs | −0.065 |
| Sections ↔ review items | +0.707 |
| Source refs ↔ review items | −0.288 |

### Что это означает

#### Размер ↔ разделы: `r = +0.211`

Слабая связь.

Большое количество разделов не означает автоматически раздутый файл. Документ может быть хорошо декомпозирован на короткие части.

#### Размер ↔ source refs: `r = +0.443`

Умеренная положительная связь.

Более объёмные chapters в среднем имеют немного больше ссылок, но размер не объясняется только пруфами.

#### Sections ↔ review items: `r = +0.707`

Достаточно сильная положительная связь, но она частично конструктивна: более детально разбитые темы обычно имеют полноценный design checklist.

## 6. Корреляция «число разделов ↔ средний размер раздела»

Дополнительно рассчитано:

```text
r = −0.845
```

Это сильная отрицательная корреляция.

### Интерпретация

Чем больше отдельных архитектурных вопросов выделено в chapter, тем короче в среднем каждый вопрос.

Это хороший структурный признак для beginner-oriented документации:

```text
не одна длинная простыня
а много коротких законченных решений
```

Но корреляция сама по себе не доказывает читаемость. Она только показывает отсутствие паттерна «больше headings → ещё более раздутый текст».

---

## 7. Multiple linear regression

Проверена модель:

```text
file_size_bytes
    ~ sections
    + source_refs
    + review_items
```

Получено на обучающей выборке:

```text
R² = 0.426
```

Оценённые коэффициенты:

```text
intercept      ≈ 4 675 bytes
sections       ≈ −110 bytes на дополнительный section
source_refs    ≈ +430 bytes на source reference
review_items   ≈ +509 bytes на review item
```

### Почему коэффициенты нельзя трактовать буквально

Выборка всего `n = 9`.

Кроме того, metrics зависимы: например, почти все thematic chapters намеренно имеют около десяти review items.

Поэтому коэффициент `−110 bytes на section` **не означает**, что добавление heading физически уменьшает документ на 110 bytes. Это артефакт маленькой многомерной выборки и collinearity.

---

## 8. Проверка regression устойчивости

Чтобы не выдавать in-sample `R² = 0.426` за доказательство, выполнена Leave-One-Out Cross Validation.

Результат:

```text
LOOCV R² ≈ −0.508
MAE      ≈ 1 599 bytes
RMSE     ≈ 1 766 bytes
```

### Вывод

Регрессионная модель **не является устойчивой прогнозной моделью**.

Это важный отрицательный результат.

Он показывает, что нельзя по трём простым structural metrics предсказывать нужный размер architecture chapter. Иными словами, документация не должна выравниваться искусственно под формулу.

Правильная реакция — **не подгонять файлы под regression**, а сохранить тематически естественный объём.

---

## 9. Экспертная risk coding — только описательная проверка

Дополнительно chapters были размечены по максимальному потенциальному ущербу ошибки от 1 до 5:

```text
1 — в основном presentation inconvenience
2 — локальная архитектурная сложность
3 — заметный technical debt
4 — data/upgrade integrity risk
5 — security, transaction или major integrity risk
```

Разметка является **экспертной**, а не объективно измеренной переменной, поэтому её нельзя использовать как доказательство причинности.

Для проверки распределения внимания получено:

```text
risk score ↔ file size      r ≈ +0.515
risk score ↔ section count  r ≈ +0.596
```

### Интерпретация

Высокорисковые темы в среднем получили больше текста и больше отдельных вопросов.

Это хороший признак баланса документации, но не статистическое доказательство её правильности.

---

## 10. Что корреляция НЕ позволяет заключить

Нельзя писать:

```text
«Frappe-native решение на 43% безопаснее»
«каждый source снижает technical debt»
«больше sections повышает качество»
```

Для подобных утверждений нет эмпирической выборки проектов.

Статистический аудит здесь отвечает только на вопрос:

> Насколько сбалансирована и доказательно структурирована наша документация?

## 12. Redundancy audit

Осознанное повторение оставлено только в двух случаях:

### 1. Security boundary

`ignore_permissions`, Client Script и API упоминаются в нескольких chapters, потому что затрагивают разные decision tracks.

### 2. Transaction boundary

`enqueue_after_commit`, Webhook/API side effects и lifecycle также пересекаются намеренно.

Для уменьшения смыслового дублирования detailed explanation находится в owning chapter, а остальные chapters должны по возможности ссылаться на него.

### Правило дальнейшей редакции

Если одинаковое объяснение начинает занимать более одного абзаца в двух файлах, оставить полную версию у owner-topic, а во втором месте — короткий cross-reference.

## 13. LLM-noise audit

Проверялись характерные признаки машинной «воды»:

```text
повтор одного вывода разными словами;
ложные абсолюты;
симметричные списки ради симметрии;
термины без operational meaning;
выдуманная статистика вроде «90% проектов»;
необоснованные слова «best practice»;
ссылка, которая не доказывает весь абзац;
риторические лозунги вместо decision criterion.
```

В новой структуре намеренно применены меры:

- каждый chapter заканчивается конкретным design review;
- normative claims отделены от inference;
- исключения описываются рядом с правилом;
- нет выдуманной частоты встречаемости решений;
- service/repository/fork/custom UI не демонизируются по названию;
- negative regression result сохранён, а не «исправлен» ради красивого вывода.

### Остаточный риск

Главный риск теперь не структурный, а **version drift**.

Наиболее чувствительные к изменениям areas:

1. permissions/query engine;
2. REST API v2;
3. hooks/extension mechanisms;
4. background jobs/scheduler;
5. migration behaviour.

Поэтому стандарт должен проходить source-level re-audit при переходе на следующую major version Frappe.

---

## 15. Решение

После перестройки и статистического аудита документация может использоваться как **рабочий Frappe Architecture Standard для design review**.

Но её нельзя объявлять «официальной архитектурой Frappe».

Корректная формулировка:

> Это доказательно собранный design standard, выведенный из документированной философии, public primitives и upstream implementation Frappe v16, с явным отделением собственных архитектурных выводов от официальных контрактов Framework.
