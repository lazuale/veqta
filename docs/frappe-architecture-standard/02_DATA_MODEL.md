# 02. Модель данных — как выбирать DocType, поля и связи

## 1. Главный вопрос

Frappe — фреймворк, основанный на метаданных, поэтому качество приложения во многом определяется качеством модели `DocType`.

Перед созданием каждого нового `DocType` нужно спросить:

> Это действительно самостоятельный `Document` системы или всего лишь свойство, строка или ссылка другого `Document`?

Это не официальный «тест Frappe», а **[АРХИТЕКТУРНЫЙ ВЫВОД]**, основанный на том, что Framework предоставляет разные механизмы для разных форм данных.

Основные источники:

- https://docs.frappe.io/framework/user/en/basics/doctypes
- https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes

---

## 2. Когда нужен обычный DocType

**[ДОКУМЕНТАЦИЯ FRAPPE]** `DocType` — основной строительный блок и описание типа `Document`.

Обычный `DocType` естественен, если запись имеет собственную идентичность и хотя бы несколько из признаков ниже:

```text
имеет самостоятельный жизненный цикл;
имеет собственные права доступа;
на неё ссылаются другие Documents;
её открывают и ищут отдельно;
она может существовать независимо от одного родителя;
нужна собственная история изменений;
у неё есть собственные бизнес-правила.
```

Пример:

```text
Vehicle
Customer
Contract
Work Order
Inspection
```

### Ошибка новичка

Создавать `DocType` для каждого существительного:

```text
Task Color
Task Priority Value
Task Comment Row
Task Responsible Row
```

только потому, что «отдельная таблица выглядит чище».

Каждый лишний `DocType` добавляет собственную модель, права доступа, именование, поиск, списки, ссылки и поверхность для будущих изменений.

---

## 3. Когда достаточно DocField

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe предоставляет типы полей для описания свойств `Document`: `Data`, `Select`, `Int`, `Date`, `Link`, `Table` и другие.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes

Если значение является обычным свойством `Document` и не имеет самостоятельного поведения, отдельный `DocType` чаще всего не нужен.

Пример:

```text
Vehicle
  registration_number : Data
  manufacture_year    : Int
  active              : Check
```

### Select или отдельный справочник?

`Select` подходит, когда набор значений:

- мал;
- стабилен;
- не имеет дополнительных атрибутов;
- не требует собственных прав или отдельного управления.

Отдельный `DocType` лучше, когда элемент списка сам становится управляемым объектом.

Пример:

```text
Priority = Low / Normal / High
```

может быть `Select`.

Но если у каждой Priority имеются:

```text
name
response_time
color
escalation_rule
active
```

это уже хороший кандидат на отдельный `DocType`.

## 4. Link — живая ссылка на другой Document

**[ДОКУМЕНТАЦИЯ FRAPPE]** Тип поля `Link` ссылается на другой `DocType`.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes

Пример:

```text
Work Order
  vehicle -> Vehicle
```

Если `Vehicle` является самостоятельной справочной записью, `Link` сохраняет настоящую связь.

### Ошибка

Хранить вместо `Link`:

```text
vehicle_name = "Shacman A123"
```

когда система должна работать именно с записью `Vehicle`.

Так теряются ссылочная целостность Frappe, поиск по Link и возможность однозначно идентифицировать объект.

---

## 5. Снимок значения — важное исключение из правила Link

Не каждое повторение значения является ошибкой.

Иногда транзакционный документ должен сохранить состояние данных **на момент операции**.

Пример:

```text
Invoice
  customer -> Customer
  customer_name_snapshot
  billing_address_snapshot
```

Если завтра `Customer` поменяет адрес, старый `Invoice` не должен обязательно переписать исторический адрес.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Поэтому нужно различать:

```text
Link           = текущая связь с живой справочной записью
Снимок значения = историческое значение на момент события
```

Решение определяется бизнес-смыслом, а не борьбой с «дублированием данных» как таковым.

---

## 6. Child DocType — составная часть родительского Document

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Child DocType` предназначен для записей, прикреплённых к родительскому `DocType`. Дочерняя строка содержит `parent`, `parenttype`, `parentfield`, `idx`.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/child-doctype

Пример:

```text
Purchase Request
  applicant
  date
  items[]
      item
      qty
      uom
```

`Purchase Request Item` не является отдельной заявкой. Это состав документа.

### Лучший вопрос для новичка

Не только:

> «Переживёт ли строка удаление родителя?»

а:

> **«Эта запись является частью одного Document или отдельной бизнес-записью, которая просто связана с ним?»**

Если запись требует собственных прав, используется несколькими родителями или на неё должны ссылаться другие документы, отдельный `DocType` может быть правильнее.

---

## 7. Table MultiSelect

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Table MultiSelect` позволяет представить набор ссылок через механизм дочерней таблицы.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes

Это хороший вариант, когда родительский документ должен выбрать несколько записей одного типа и сама связь почти не несёт дополнительных бизнес-атрибутов.

Если связь имеет собственные данные:

```text
role
valid_from
valid_to
allocation_percent
```

может понадобиться обычная дочерняя строка или самостоятельный `DocType` связи.

---

## 8. Dynamic Link

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Dynamic Link` позволяет одному полю ссылаться на `Documents` разных `DocTypes`, а целевой `DocType` определяется другим полем.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes

Пример:

```text
reference_doctype = "Sales Invoice"
reference_name    = "SINV-0001"
```

или тот же объект может ссылаться на `Purchase Order`, `Issue` и т. д.

Использовать `Dynamic Link` только ради «универсальности на будущее» не следует. Обычный `Link` проще и точнее выражает модель, если тип связи известен заранее.

---

## 9. Когда нужен отдельный DocType связи

Frappe не запрещает моделировать связь отдельным `DocType`.

Это естественно, когда отношение само является бизнес-фактом.

Пример:

```text
Employee Project Membership
  employee
  project
  role
  valid_from
  valid_to
  allocation_percent
```

Здесь membership имеет собственный смысл, историю и поля. Он уже не просто «список выбранных сотрудников».

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Отдельный `DocType` связи оправдан не потому, что many-to-many «должен иметь join table», а потому что отношение имеет самостоятельный смысл.

---

## 10. Single DocType

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Single DocType` предназначен для данных, где на одном сайте имеет смысл только одна запись, например настройки.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/single-doctype

Пример:

```text
My App Settings
  default_priority
  integration_enabled
  api_base_url
```

### Неправильно

Создать обычный `DocType` `My App Settings`, а потом вручную запрещать вторую запись.

Framework уже имеет тип модели для этого случая.

---

## 11. Virtual DocType

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Virtual DocType` позволяет представить данные, которые физически хранятся не в обычной таблице Frappe, как `Documents` Framework.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/virtual-doctype

Внешний источник может быть API, другая база данных и т. п.

### Когда это хорошо

Если внешние данные действительно должны вести себя внутри Frappe как `Documents`:

- отображаться стандартными представлениями;
- участвовать в правах доступа;
- читаться через ресурсный API;
- иметь интерфейс, совместимый с `Document`.

### Когда не нужно

Если приложение делает два вызова внешнего API для расчёта курса валют, создавать `Virtual DocType` `External Exchange Rate Record` может быть лишним.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Внешний источник сам по себе не означает `Virtual DocType`. Нужен именно смысл `Document`.

---

## 12. Tree DocType

Frappe поддерживает древовидные `DocType` для иерархических данных.

Использовать дерево нужно, когда предметная область действительно иерархична:

```text
Department
Account
Territory
```

Не нужно превращать любую связь «родитель — потомок» в дерево только ради красивого интерфейса.

Источник для общей модели `DocType`:

- https://docs.frappe.io/framework/user/en/basics/doctypes

---

## 13. Naming — часть архитектуры, а не косметика

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe имеет системное поле `name` и несколько стратегий именования: поле, `Naming Series`, expression, UUID, controller `autoname` и другие.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/naming

При проектировании `DocType` нужно решить:

```text
name = технический ID?
или
name = бизнес-номер, который видит человек?
```

Это важно, потому что `name` участвует в ссылках и URL.

### Пример

Для `Vehicle` естественным `name` может быть UUID или внутренний ID, если госномер способен измениться.

Для официального документа может быть оправдан бизнес-номер через `Naming Series`.

### Тревожный признак

Использовать изменяемое отображаемое название как постоянный первичный ключ только потому, что оно сейчас уникально.

---

## 14. Не путать идентификатор и отображаемое имя

У `Document` есть идентификатор `name`, но пользователю часто нужен человекочитаемый заголовок.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Если отображаемое имя может изменяться, а ссылки должны оставаться стабильными, лучше разделить:

```text
name  = стабильный ID
title = изменяемое отображаемое значение
```

Это особенно важно для каталогов и справочных данных.

## 15. Архитектурная проверка модели данных

Перед утверждением нового `DocType` пройти вопросы:

```text
1. Это самостоятельный Document или свойство другого?
2. Нужен ли собственный жизненный цикл?
3. Нужны ли собственные права доступа?
4. Должны ли другие Documents ссылаться на эту запись?
5. Это состав родительского Document или самостоятельная запись?
6. Link нужен как живая связь или бизнесу нужен снимок значения?
7. Нужен ли Single вместо обычного DocType?
8. Нужен ли Dynamic Link или обычный Link точнее?
9. Должны ли внешние данные действительно иметь смысл Document?
10. Что является стабильным идентификатором и как работает naming?
11. Что произойдёт с существующими ссылками при rename?
12. Как модель будет мигрировать после появления производственных данных?
```

Если на эти вопросы нет ответа, `DocType` ещё рано создавать.
