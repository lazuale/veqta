# VEQTA — журнал решений

Этот файл фиксирует не все идеи обсуждения, а только текущее состояние решений: что принято, что отброшено и что ещё требует проверки.

---

## Принято

### D-001. Frappe Framework — техническая платформа

**Решение:** VEQTA строится как приложение на Frappe Framework.

**Следствие:** не переписываем штатные инфраструктурные возможности Frappe без доказанной необходимости.

---

### D-002. VEQTA не является framework поверх Frappe

**Решение:** проект не создаёт собственный ORM, RBAC, form builder, workflow platform, plugin system или другой технический слой только ради архитектурной чистоты.

**Причина:** это дублировало бы платформу и резко увеличивало сложность проекта.

---

### D-003. Основная идея — пользователь задаёт процесс

**Решение:** VEQTA не навязывает конкретную методологию управления работой.

Пользователь должен иметь возможность адаптировать типы работы, состояния, workflow, роли, формы и представления под себя преимущественно штатными средствами Frappe.

---

### D-004. Гибкость процесса не должна разрушать данные

**Решение:** модель проектируется analytics-ready с самого начала.

Основные ограничения:

- один факт — один источник истины;
- ключевые факты структурированы;
- не использовать JSON/EAV как основу Core;
- не хранить производные показатели как первичные данные без необходимости;
- история, важная для аналитики, должна быть машинно читаемой.

---

### D-005. OLTP является источником истины

**Решение:** VEQTA Core хранит транзакционные первичные данные. Отдельная OLAP/DWH-архитектура не является обязательной частью первой версии.

При развитии аналитический слой может строиться отдельно на основе OLTP.

---

### D-006. Начинаем с минимальной модели

**Решение:** до доказанной необходимости ядро начинается только с понятий:

- `Work Item`;
- `Work Type`;
- `State`.

Новые сущности не добавляются заранее.

---

### D-007. GitHub — источник истины проекта

**Решение:** согласованные решения, изменение курса и текущая модель фиксируются в репозитории `lazuale/veqta`.

Чат и другие обсуждения являются рабочей средой, но не заменяют проектную документацию.

---

### D-008. VEQTA проектируется только относительно актуального стабильного Frappe

**Решение:** все технические решения VEQTA проверяются относительно актуальной стабильной major-ветки и текущего стабильного релиза Frappe Framework.

На дату проверки **2026-08-29** целевая major-ветка — `version-16`, последняя проверенная стабильная v16-версия — `v16.32.0` от 2026-08-26.

Перед реализацией решения, зависящего от поведения Frappe, актуальность версии проверяется заново.

**Иерархия источников:**

1. официальная документация Frappe;
2. официальные исходники `frappe/frappe` актуальной ветки/стабильного тега;
3. официальные release notes и migration notes;
4. issues/PR официального репозитория для проверки ограничений и багов;
5. форум и сторонние материалы — только как вспомогательные источники.

Наличие функции в `develop` не считается достаточным основанием для зависимости VEQTA, пока функция не вошла в стабильный релиз.

Подробно: `FRAPPE_BASELINE.md`.

---

### D-009. Репозиторий содержит реальный воспроизводимый продукт, а не только проектные заметки

**Решение:** `lazuale/veqta` является репозиторием реального Frappe app VEQTA.

В Git должны попадать не только вручную написанные Python/JS-файлы и документация, но и все продуктовые метаданные и конфигурация, созданные на dev-стенде через Desk и являющиеся частью VEQTA.

Обязательный рабочий цикл:

```text
Desk / код
   ↓
изменение VEQTA на dev-site
   ↓
сохранение или штатный export в apps/veqta
   ↓
git diff
   ↓
commit
   ↓
push в lazuale/veqta
```

Если конкретная настройка Frappe хранится только в БД, она не считается частью воспроизводимого продукта, пока не экспортирована штатным способом в приложение — например как fixture/customization или другим поддерживаемым Frappe-механизмом.

Критерий воспроизводимости:

> **Чистый site + Frappe целевой версии + установка `veqta` из Git должны восстанавливать продуктовую конфигурацию VEQTA без повторного ручного накликивания уже принятых частей продукта.**

Локальный dev-site является средой разработки и проверки, а не единственным носителем состояния продукта.

Подробно: `CLICK_TO_GIT_RULE.md`.

## Отброшено / не считаем текущей архитектурой

### X-001. Большой заранее спроектированный VEQTA Kernel

Не фиксируем заранее как обязательные Core:

- Lifecycle Scheme;
- Responsibility Engine;
- Policy Layer;
- Capability Contract;
- универсальный Event Bus;
- собственный extension framework.

Причина: преждевременная архитектура для проекта, который должен максимально использовать Frappe.

---

### X-002. Собственный workflow engine как исходная архитектура

Не принимается без отдельного доказательства необходимости.

Сначала проверяются штатные Workflow, Conditions и другие возможности Frappe на реальных сценариях VEQTA.

---

### X-003. Микросервисы и множество Frappe apps с первого дня

Не используются.

Стартовая модель — один app `veqta` с простой внутренней структурой. Разделение на самостоятельные apps возможно позже, если появится реальная независимая функциональность.

---

### X-004. ERPNext как основа VEQTA

VEQTA строится на чистом Frappe Framework, а не как кастомизация ERPNext.

Причина: VEQTA должна иметь собственную предметную модель, а ERPNext добавляет ненужную для ядра ERP-семантику.

---

## Открытые вопросы

### Q-001. Минимальный состав `Work Item`

Текущая рабочая модель описана в `WORK_ITEM_V0_1.md` и ещё должна пройти проверку универсальности.

После проверки штатного Assignment поле `responsible/assigned_to` исключено из первого прототипа: сначала проверяется возможность вообще не дублировать назначения, используя связанные `ToDo` Frappe.

### Q-002. Как хранить и настраивать `State`

Проверка актуального Frappe показала:

- на один DocType может быть активен только один Workflow;
- Workflow Transition поддерживает Condition по полям документа;
- Frappe создаёт workflow-state поле целевого DocType как Link на штатный `Workflow State`;
- `Workflow State` является штатным master DocType с уникальным именем состояния.

Рабочая гипотеза v0.1: не создавать собственный `Work State` и lifecycle engine; использовать один штатный Workflow для `Work Item`, а разные ветки процесса ограничивать Conditions по `work_type`.

Ограничение: при большом числе типов один общий Workflow может стать трудно поддерживаемым. Это должно быть проверено реальным прототипом, а не решено заранее новой подсистемой.

Подробно: `WORK_TYPE_STATE_V0_1.md` и `PROTOTYPE_V0_1.md`.

Статус вопроса: **не закрыт до прототипа**.

### Q-003. Нужна ли отдельная структурированная история изменений состояния

Проверка Frappe показала:

- Workflow transition сохраняет новое состояние и добавляет Workflow comment;
- `Version` хранит технические изменения в сериализованном поле `data`, а не как отдельную аналитическую запись перехода.

Рабочая гипотеза: если VEQTA должна считать время в состояниях и восстанавливать последовательность lifecycle, нужен минимальный `Work State Change` со структурированными полями `work_item`, `from_state`, `to_state`, `changed_by`, `changed_at`.

Он не заменяет Version/Timeline и не является Event Store.

Подробно: `STATE_HISTORY_V0_1.md` и этапы A/B в `PROTOTYPE_V0_1.md`.

Статус: **сначала подтверждаем недостаточность штатного audit на прототипе; код до этого не добавляем**.

### Q-004. Нужен ли `Workstream`

Ранее рассматривался как контекст/контур работы, но после перезапуска архитектуры не входит в минимальный Core до доказанной необходимости.

### Q-005. Нужен ли `Outcome`

Разделение состояния и результата выглядит полезным для части сценариев, но пока не включается в базовый Core.

### Q-006. Assignment / ответственность

Проверка официальной документации и исходников Frappe v16 показала:

- штатный `Assign To` создаёт отдельный связанный `ToDo` для каждого назначенного пользователя;
- `ToDo` хранит структурированные поля `allocated_to`, `reference_type`, `reference_name`, `status`, `assigned_by`;
- системный `_assign` является JSON-представлением назначений для UI, но не единственным хранилищем;
- стандартный Desk UI поддерживает multiple assignment;
- специальное поле `assigned_to`, если оно существует в целевом DocType, небезопасно как единственный источник истины при multiple assignment: новое назначение его перезаписывает, а снятие assignment очищает.

Поэтому предыдущая гипотеза с `Work Item.assigned_to` ослаблена.

Рабочая гипотеза prototype v0.1:

- не создавать `responsible` / `assigned_to` в Work Item;
- использовать штатные `ToDo` как источник факта назначения;
- не создавать собственную модель ownership;
- отдельно решить после прототипа, нужен ли VEQTA именно один accountable owner или штатного assignment достаточно.

Подробно: `ASSIGNMENT_V0_1.md`.

### Q-007. Минимальная модель `Work Type`

Рабочая гипотеза: `Work Type` — собственный master DocType VEQTA со стабильным машинным `code`, пользовательским `label`, необязательным `description` и признаком `disabled`.

Предлагается сохранить стабильный машинный code отдельно от пользовательского отображения.

Статус: **требует подтверждения прототипом**.

### Q-008. Prototype v0.1

Следующий практический этап зафиксирован в `PROTOTYPE_V0_1.md`.

Он проверяет без преждевременной разработки:

- два Work Type на одном `Work Item`;
- один штатный Workflow с Conditions по `work_type`;
- штатный Assignment/ToDo;
- техническую и аналитическую историю State;
- переименование State/Work Type и целостность ссылок;
- штатные Form/List/Kanban/filters Desk.

До результатов этого прототипа новые Core-сущности не проектируются.

## Как обновлять журнал

При изменении архитектурного решения:

1. старое решение не стирается без следа;
2. фиксируется новое решение и причина изменения;
3. зависимые документы обновляются;
4. спорная идея остаётся в `Открытых вопросах`, а не выдаётся за принятую архитектуру.
