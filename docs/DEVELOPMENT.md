# VEQTA — правила разработки

Статус: **обязательные правила проекта**.

Этот документ определяет, как принимаются технические решения и как изменения со стенда становятся реальным кодом VEQTA.

## 1. Целевая платформа

VEQTA разрабатывается как самостоятельное приложение на **Frappe Framework**.

На дату последней проверки — **2026-08-29**:

- стабильная major-линия: `version-16`;
- последняя проверенная стабильная версия: `v16.32.0`.

Это текущая точка разработки, а не вечный pin. Перед новым развёртыванием и перед решением, зависящим от поведения Framework, актуальная stable-версия проверяется повторно.

## 2. Как проверяем возможности Frappe

Нельзя проектировать VEQTA по памяти, старым статьям или поведению прошлых major-версий.

Порядок проверки:

1. официальная документация Frappe;
2. официальный исходный код `frappe/frappe` текущей stable-ветки/тега;
3. официальные release notes и migration notes;
4. issues и PR официального репозитория — для известных ограничений и багов;
5. форум и сторонние материалы — только как указатель, что проверить официально.

Наличие функции в `develop` не означает, что на неё можно опираться в VEQTA, пока функция не вошла в используемую stable-линию.

Если документация неполна или решение влияет на модель данных, Workflow, permissions, Assignment, audit, API, hooks, Desk, Kanban, background jobs или совместимость БД — исходники Frappe проверяются обязательно.

Проверка официальных исходников — часть работы по разработке VEQTA; пользователь не обязан вручную приносить фрагменты Frappe-кода из локального стенда.

## 3. Не переписываем Frappe

Перед добавлением собственной подсистемы задаём вопросы по порядку:

1. Это уже умеет Frappe?
2. Это можно корректно настроить штатными средствами?
3. Это действительно часть универсальной модели VEQTA?
4. Без нового кода обязательное свойство продукта нарушается?

Собственный код появляется только после конкретного ответа «да» на последний вопрос.

## 4. Git — источник истины продукта

`lazuale/veqta` должен содержать **реальное воспроизводимое состояние приложения VEQTA**.

Локальный site — среда разработки и испытаний. Настройка, которая существует только в его базе данных, не считается частью продукта.

Обязательный цикл:

```text
изменение в Desk / изменение кода
        ↓
файлы или экспортированная конфигурация в apps/veqta
        ↓
git diff
        ↓
commit
        ↓
push в lazuale/veqta
```

Стандартные DocType приложения в Developer Mode сохраняются в дерево app. Настройки, которые Frappe хранит только как записи БД, должны попадать в app штатным механизмом Frappe — fixtures, export customizations или другим официальным способом, подходящим для конкретного типа конфигурации.

Не создаём собственный exporter VEQTA, пока штатных механизмов достаточно.

## 5. Критерий воспроизводимости

Контрольный тест продукта:

```text
чистый совместимый Frappe site
+ код lazuale/veqta
+ install-app / migrate / штатный импорт конфигурации
= согласованное состояние VEQTA
```

Если уже принятые продуктовые DocType, Workflow или другая конфигурация требуют повторного ручного накликивания, значит эта часть ещё не зафиксирована как код продукта.

## 6. Что коммитим

В repository должны попадать:

- исходники Frappe app `veqta`;
- стандартные DocType и другие app metadata;
- JS/Python и другой собственный код VEQTA;
- fixtures/exported customizations, которые являются частью продукта;
- migrations/patches при их появлении;
- тесты;
- документация проекта.

## 7. Что не коммитим

Не отправляются в repository:

- весь Bench;
- исходники самого Frappe;
- локальная MariaDB и её dumps с рабочими данными;
- `site_config.json` с секретами;
- Administrator/MariaDB passwords;
- private SSH keys;
- содержимое private folders site;
- локальные пользовательские тестовые данные, если они не являются специально подготовленными fixtures/tests.

## 8. Обычный Git-цикл

Перед работой:

```bash
cd ~/frappe/veqta-bench/apps/veqta
git status
git pull --ff-only origin main
```

После согласованного изменения:

```bash
git status
git diff
git add .
git diff --cached
git commit -m "Краткое описание изменения"
git push origin main
```

На стадии prototype допускается прямой `main`. Более строгий branch/PR workflow вводится тогда, когда он начнёт приносить реальную пользу.

## 9. Рабочая формула

> **Официальный Frappe → живой тест → код VEQTA → Git.**
