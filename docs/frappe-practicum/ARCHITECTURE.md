# Архитектура практикумов

Курс строится вокруг реальных проектов. Каждый следующий проект использует уже освоенные механизмы и добавляет новый слой Frappe.

Задача программы — не провести ученика по всем меню, а научить собирать приложения так, как это принято во Frappe.

## Общая последовательность

```text
Frappe / Bench / Site
        ↓
App / Module / Developer Mode
        ↓
DocType / Fields / Links / Naming
        ↓
Customize Form / site-specific customization
        ↓
Users / Roles / Permissions
        ↓
Assign To / ToDo / Collaboration
        ↓
DocStatus / Workflow
        ↓
Reports / Print / Workspace
        ↓
Automation
        ↓
Web Form
        ↓
Самостоятельное приложение
```

Эта последовательность важна. Нельзя нормально понять Workflow, пока не понятен документ. Нельзя оценить Assignment Rule, пока не понятно ручное назначение. Нельзя строить полезный Workspace, пока нет реальных документов и отчётов.

## P0. Учебное приложение

Первый практикум отвечает на вопрос: из чего вообще состоит Frappe-приложение.

Ученик создаёт:

```text
Bench
 └── site
      └── installed app
           └── Module
```

И видит связь между Desk и файловой структурой app.

Что важно понять:

- Bench управляет окружением и site;
- site — конкретный экземпляр Frappe;
- app — устанавливаемый пакет функциональности;
- Module группирует объекты приложения;
- Developer Mode позволяет создавать стандартные объекты приложения и сохранять их метаданные в кодовой базе app;
- Desk — рабочий интерфейс над этими объектами.

P0 не должен превращаться в курс Linux или внутренностей Python-пакета. Команды и файлы показываются только настолько, насколько это помогает понять устройство Frappe.

## P1. Реестр оборудования

Первый настоящий проект учит строить модель данных.

Минимальная модель:

```text
Тип оборудования
        │
        ▼
   Оборудование
        │
        ├──────► Место размещения
        │
        ▼
Передача оборудования
        │
        ▼
Строки передачи
```

Здесь естественно изучаются:

- обычные DocType;
- Child Table;
- Single DocType для простой настройки проекта;
- основные Field Types;
- Link и Dynamic Link;
- Naming;
- Title Field;
- Form Builder;
- Quick Entry;
- Search Fields;
- Track Changes;
- импорт/экспорт;
- List View.

В конце P1 ученик должен уметь объяснить не только «как создать поле», но и почему конкретная сущность стала отдельным DocType, а другая — дочерней таблицей.

## P2. Настройка существующих форм

После создания собственных DocType появляется второй важный сценарий Frappe: изменить уже существующий объект, не переписывая его исходное определение.

Здесь изучаются:

```text
Standard DocType app
        ≠
Custom DocType on site
        ≠
Customize Form of existing DocType
```

Для лабораторной задачи можно безопасно добавить учебное поле в стандартный `User` или другой подходящий системный DocType, изменить подпись/свойство и затем посмотреть созданные `Custom Field` и `Property Setter`.

Одновременно ученик приводит рабочий интерфейс в порядок:

- списки;
- saved filters;
- quick entry;
- preview;
- Workspace;
- shortcuts;
- quick lists.

Главная цель P2 — не дизайн. Ученик должен понять механизм расширения существующего Frappe без правки исходного DocType.

## P3. Внутренние заявки

Теперь в приложение входят несколько пользователей.

Модель:

```text
Категория заявки
       │
       ▼
Внутренняя заявка
       │
       ├── заявитель
       ├── исполнитель
       ├── приоритет
       ├── срок
       └── статус
```

Главное разделение этапа:

```text
Permissions
= что пользователь имеет право делать

Assignment
= за какую работу пользователь отвечает
```

Поэтому сначала настраиваются User, Role и Permissions, а уже затем Assign To и ToDo.

После этого добавляются Comments, Timeline, Tags и Kanban.

P3 считается освоенным только после проверки под несколькими реальными учебными пользователями, включая отрицательный сценарий доступа.

## P4. Согласование закупки

Здесь ученик впервые работает не просто со статусом, а с формальным жизненным циклом документа.

Сначала отдельно проверяется:

```text
Draft → Submit → Cancel → Amend
```

После этого добавляется Workflow.

Нужно жёстко различать:

| Понятие | Смысл |
|---|---|
| Status | предметное состояние, придуманное для задачи |
| Workflow State | состояние управляемого маршрута |
| DocStatus | системное состояние документа: 0 / 1 / 2 |

Внутри Workflow ученик видит:

- Workflow State;
- Workflow Action Master;
- Workflow Transition;
- allowed role;
- условие перехода;
- Workflow Action как фактическую запись действия пользователя.

Так Workflow изучается как система переходов, а не как набор кнопок «Согласовать / Отклонить».

## P5. Журнал проверок

К этому моменту приложение уже умеет хранить данные и проводить их по процессу. Теперь оно должно помогать работать с накопленной информацией.

Модель проверки:

```text
Объект проверки
       │
       ▼
    Проверка
       │
       ▼
Пункты проверки
```

На этих данных ученик строит:

- Calendar;
- Report Builder;
- группировки и агрегаты;
- Number Card;
- Dashboard Chart;
- Workspace;
- Print Format;
- PDF.

Главный критерий: рабочий экран должен отвечать на реальные вопросы пользователя, например «что проверить сегодня?» и «где есть проблемы?», а не быть набором декоративных карточек.

## P6. Регламентные работы и автоматизация

Автоматизация вводится только после ручного прохождения процесса.

Здесь не строится искусственная цепочка из всех механизмов сразу. Каждый инструмент решает свою задачу.

### Auto Repeat

Нужен, когда сам документ должен регулярно повторяться.

Изучаются:

- Allow Auto Repeat на DocType;
- периодичность;
- start/end date;
- assignee;
- создание отдельных документов для нескольких исполнителей.

### Assignment Rule

Нужен, когда входящий документ должен автоматически получить исполнителя.

Изучаются:

- Round Robin;
- Load Balancing;
- Based on Field;
- Weighted Distribution;
- Assign Condition;
- Unassign / Close condition на уровне понимания.

Важно прямо показать, что штатный `Assign Condition` использует простое PythonExpression. Это часть механизма Frappe, а не собственный Python-контроллер.

### Notification

Нужна для реакции на событие или дату.

Базовый сценарий строится через System Notification и Filters, чтобы не зависеть от SMTP и не заставлять ученика писать условие на Python без необходимости.

После этого можно дополнительно показать email при настроенной почте.

## P7. Web Form

Последний новый слой — внешний интерфейс к обычному Document.

Архитектура:

```text
Пользователь сайта
        ↓
     Web Form
        ↓
     Document
        ↓
       Desk
        ↓
Внутренний процесс
```

Ученик проходит несколько разных моделей доступа:

1. анонимная форма;
2. форма с Login Required;
3. форма с Apply document permissions;
4. список и редактирование собственных документов;
5. Web Form Request / Key required как отдельный расширенный сценарий.

P7 должен снять представление, что Web Form создаёт отдельную систему. Это просто другой интерфейс к Frappe Document.

## P8. Операционный центр

Финальный проект строится по техническому заданию, без инструкции по кликам.

Ученик сам решает:

- какие нужны DocType;
- где Child Table, а где Link;
- какие статусы достаточно хранить полем;
- где нужен Workflow;
- как разделить роли;
- где применить Assignment;
- что автоматизировать;
- какие отчёты полезны;
- что показать на Workspace;
- нужен ли Web Form.

Финальный проект не обязан использовать редкую функцию только потому, что она была в курсе. Но основные слои Frappe должны быть представлены осмысленно.

## Как устроен каждый практикум

У всех проектов одна простая структура.

### 1. Задача

Что нужно получить в терминах реальной работы.

### 2. Что будет работать в конце

Короткий список наблюдаемых результатов.

### 3. Модель

DocType, связи, ключевые поля, роли и жизненный цикл — до начала кликов.

### 4. Сборка

Пошаговые действия в том порядке, в котором их реально делает пользователь Frappe.

### 5. Проверка

Проект проверяется на реальных тестовых данных и под несколькими пользователями, если это важно для функции.

### 6. Самостоятельное изменение

Небольшое изменение требований без готовой инструкции. Оно показывает, понял ли ученик механизм.

## Правила программы

- Сначала ручной процесс, потом автоматизация.
- Сначала модель данных, потом интерфейс.
- Права всегда проверяются входом под другим пользователем.
- Новая функция должна решать понятную задачу проекта.
- Если механизм требует простого штатного выражения, это объясняется, а не маскируется.
- Не пишем собственную бизнес-логику, пока штатных средств достаточно.
- Не избегаем App, Developer Mode или других нативных частей Frappe только потому, что они технические.
- Если фактический v16 ведёт себя иначе, чем написано в уроке, исправляется урок, а не стенд подгоняется под инструкцию.

## Что считаем хорошим результатом

После курса ученик должен воспринимать Frappe не как набор форм и не как «конструктор без кода», а как платформу со своими нормальными строительными блоками:

```text
App
  └── Module
       ├── DocType
       ├── Permissions
       ├── Workflow
       ├── Reports
       ├── Workspace
       ├── Automation
       └── Web
```

И уметь выбирать эти блоки под новую задачу.
