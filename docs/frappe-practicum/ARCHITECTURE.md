# Архитектура практикумов

Курс идёт от устройства Frappe к самостоятельной сборке переносимого приложения.

Главный принцип простой: сначала ученик понимает строительный блок Frappe на реальной задаче, потом использует его в следующих проектах без повторного объяснения с нуля.

## Порядок

```text
Bench / Site / App
        ↓
DocType / Document / Fields / Naming
        ↓
Customize Form / Layout / переносимость
        ↓
Users / Roles / Permissions / Assignment
        ↓
DocStatus / Workflow / Audit Trail
        ↓
Reports / Workspace / Print
        ↓
Automation
        ↓
Web Form
        ↓
Чистый site → install app → проверка результата
```

Эта последовательность не случайна. Workflow бессмысленно изучать до жизненного цикла документа. Assignment Rule непонятен до ручного Assign To. Workspace бесполезен без накопленных документов и отчётов. А app нельзя считать готовым, пока он не установился на второй чистый site.

## Базовая модель Frappe

В P0–P1 нужно один раз закрепить четыре понятия:

```text
DocType
= описание типа документов

DocField
= описание поля DocType

Document
= конкретная запись этого DocType

name
= уникальный идентификатор Document
```

Это основа всего последующего курса. Если ученик воспринимает Frappe только как набор экранов, дальнейшая программа теряет смысл.

## Три способа получить объект или изменение

В курсе специально показываются три разных сценария.

### 1. Стандартный объект своего app

Создаётся в Developer Mode, относится к Module приложения и сохраняется в файлах app штатным способом.

Основная предметная модель курса строится именно так.

### 2. Site-specific customization

Нужно изменить существующий DocType на конкретном site — используем Customize Form. Появляются Custom Field, Property Setter и другие кастомизации.

Если эти изменения должны поставляться вместе с app, используем Export Customizations.

### 3. Нужная приложению запись базы данных

Некоторые настройки существуют как обычные записи БД. Если без них приложение не воспроизводится на новом site, их можно включить в fixtures и экспортировать через `bench export-fixtures`.

Эти три сценария нельзя смешивать. Один из главных результатов курса — понимать, где именно живёт конкретная настройка.

## P0. Учебное приложение

P0 отвечает на вопрос: из чего состоит Frappe-приложение и как с ним работать.

Ученик:

- создаёт site;
- создаёт app через `bench new-app`;
- устанавливает app на site;
- включает Developer Mode;
- находит default Module, созданный вместе с app;
- смотрит структуру app и `hooks.py`;
- проходит базовую навигацию Desk v16;
- проверяет scheduler, workers и PDF;
- создаёт пробный стандартный DocType и видит появившиеся файлы;
- проверяет изменения через Git.

P0 не превращается в курс Linux или Python packaging. Команды и файлы показываются только настолько, насколько нужны для понимания Frappe.

## P1. Реестр оборудования

Первый рабочий проект посвящён модели данных.

Модель:

```text
Тип оборудования
       │
       ▼
  Оборудование
       │
       ├────────► Место размещения (Tree)
       │
       ▼
Передача оборудования
       │
       ▼
Строки передачи (Child)
```

Здесь естественно появляются:

- обычный DocType;
- Tree DocType для иерархии мест;
- Child DocType;
- основные Field Types;
- Link;
- Naming;
- Title Field;
- Search Fields;
- Form Builder;
- Quick Entry;
- Track Changes;
- List View;
- import/export;
- attachments.

Single DocType и Dynamic Link не вставляются в основной сценарий искусственно. Они показываются дополнительными упражнениями, если для них нет настоящей задачи.

Naming изучается не одной галкой. Ученик сравнивает несколько штатных способов и выбирает подходящий: например `By fieldname` для справочника и Expression/series для рабочего документа.

## P2. Кастомизация и переносимость

Это второй фундаментальный проект.

Сначала ученик меняет существующий DocType через Customize Form:

```text
Customize Form
      ↓
Custom Field / Property Setter
      ↓
Export Customizations
      ↓
файлы app
      ↓
Git diff
```

Затем отдельно знакомится с DocType Layout: создаёт альтернативное представление формы без изменения базового DocType и понимает отличие Layout от Customize Form.

После этого вводятся fixtures:

```text
нужная конфигурационная запись
      ↓
hooks.py: fixtures
      ↓
bench export-fixtures
      ↓
JSON в app
```

P2 заканчивается первой проверкой переносимости:

```text
site-1 → Git → site-2 → install-app → migrate → проверка
```

На этом этапе не обязательно переносить уже весь будущий курс. Нужно доказать сам принцип: стандартный DocType, одна кастомизация и одна fixture должны корректно приехать на новый site.

## P3. Внутренние заявки

Теперь приложение становится многопользовательским.

Главное разделение:

```text
Permissions
= что пользователь имеет право делать

Assignment
= за какую работу он отвечает
```

Порядок:

1. System User / Website User и автоматические роли;
2. собственные Role;
3. Role Permission Manager;
4. основные права;
5. If Owner, Permission Level и User Permission;
6. Share;
7. Assign To и ToDo;
8. Comments, Timeline, Tags;
9. Kanban.

Права проверяются только реальным входом под разными пользователями. Проверка от Administrator не считается.

## P4. Согласование закупки

Здесь изучается жизненный цикл документа.

Сначала без Workflow:

```text
Draft → Submit → Cancel → Amend
```

Затем:

- Allow on Submit для безопасного поля;
- Audit Trail для сравнения amended-версий;
- обычный Status;
- Workflow State;
- Workflow Action Master;
- Workflow Transition;
- allowed role;
- Workflow Action.

Ученик должен различать:

| Понятие | Что это |
|---|---|
| Status | обычное предметное поле |
| Workflow State | состояние управляемого маршрута |
| DocStatus | системное состояние Draft / Submitted / Cancelled |

Workflow добавляется только после того, как обычный жизненный цикл уже понятен.

## P5. Журнал проверок

На накопленных документах изучаем представление и анализ данных:

- Calendar;
- Report Builder;
- Group By и агрегаты;
- Number Card;
- Dashboard Chart;
- Workspace;
- Print View;
- Print Format Builder;
- Letter Head;
- PDF.

Workspace должен отвечать на реальные вопросы пользователя, а не демонстрировать все доступные блоки.

Для каждого создаваемого объекта снова проверяется вопрос: хранится ли он в app сам, требует экспорта или остаётся персональной настройкой site.

## P6. Регламентные работы и автоматизация

Три механизма изучаются отдельно.

### Auto Repeat

Когда нужно регулярно создавать новый экземпляр документа.

### Assignment Rule

Когда входящий документ нужно автоматически назначить пользователю.

В основном сценарии используется один естественный алгоритм, например Round Robin или Load Balancing. Остальные режимы сравниваются короткой лабораторией, а не прогоняются ради галочки.

### Notification

Когда нужно отреагировать на событие или дату.

Базовый сценарий использует System Notification и Filters, чтобы не зависеть от SMTP. Email остаётся дополнительной проверкой.

## P7. Web Form

Web Form показывает внешний интерфейс к обычному Document:

```text
Website user / Guest
        ↓
     Web Form
        ↓
     Document
        ↓
       Desk
```

Ученик сравнивает:

- anonymous;
- Login Required;
- Apply document permissions;
- list/edit;
- private request key.

Отдельно создаётся Standard Web Form в Developer Mode, чтобы увидеть его файлы в app и проверить переносимость на второй site.

## P8. Операционный центр

Финальный проект строится по ТЗ без инструкции по кликам.

Ученик сам решает:

- какие нужны DocType;
- где Tree, Child Table или обычный Link;
- какой Naming подходит;
- какие роли и права нужны;
- где достаточно Status, а где нужен Workflow;
- что автоматизировать;
- какие отчёты и Workspace полезны;
- нужен ли Web Form;
- какие записи надо положить в fixtures;
- какие Customize Form изменения экспортировать.

Финальная проверка выполняется на новом чистом site. Если после `install-app` и `migrate` приложение неполно, P8 не принят.

## Формат каждого практикума

Каждый проект должен иметь одинаковую практичную структуру:

1. **Задача** — что нужно получить в рабочих терминах.
2. **Модель** — DocType, связи, роли и жизненный цикл до начала кликов.
3. **Сборка** — пошаговые действия.
4. **Что изменилось в app** — какие файлы или записи появились и почему.
5. **Проверка** — нормальные и отрицательные сценарии.
6. **Самостоятельное изменение** — небольшое новое требование без готовой инструкции.
7. **Перед следующим проектом** — короткий список того, что ученик должен уметь объяснить и показать.

## Правила курса

- Новая функция появляется только по задаче.
- Модель данных проектируется до формы.
- Права проверяются под реальными учебными пользователями.
- Автоматизация вводится после ручного сценария.
- Не делаем site-specific настройку и не называем её автоматически частью app.
- Не экспортируем всё подряд в fixtures.
- Штатные expression-поля не скрываем.
- Не пишем собственную бизнес-логику, если задачу нормально решает Frappe.
- Если стенд v16.32.0 ведёт себя иначе, чем написано в уроке, исправляется урок.

Хороший результат курса — человек видит Frappe как систему связанных строительных блоков и умеет собрать из них приложение, которое живёт не только на одном учебном site.
