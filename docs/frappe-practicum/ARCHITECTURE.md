# Архитектура практикумов

Статус: **обязательная методическая архитектура**  
Уровень: **Frappe Framework 16 / базовый / без программирования**

## 1. Зачем нужна архитектура

Практикумы должны учить не отдельным кнопкам, а способу проектирования систем на Frappe.

Поэтому курс строится слоями. Каждый следующий проект добавляет новый класс возможностей и повторно использует предыдущие. Ученик должен постоянно видеть связь между прикладной задачей и механизмом платформы.

## 2. Архитектура обучения

```text
СТЕНД
  │
  ▼
ДАННЫЕ
DocType → Fields → Naming → Links → Child Tables
  │
  ▼
ИНТЕРФЕЙС
Form → List → Filters → Views
  │
  ▼
ДОСТУП
Users → Roles → Permissions → User Permissions
  │
  ▼
СОВМЕСТНАЯ РАБОТА
Assignments → ToDo → Comments → Timeline
  │
  ▼
ПРОЦЕСС
Status → DocStatus → Workflow
  │
  ▼
АВТОМАТИЗАЦИЯ
Notification → Auto Repeat → Assignment Rule
  │
  ▼
АНАЛИТИКА
Report Builder → Number Cards → Charts
  │
  ▼
РАБОЧИЙ ИНТЕРФЕЙС
Workspace
  │
  ▼
ВНЕШНИЙ ИНТЕРФЕЙС
Web Form
  │
  ▼
ИТОГОВАЯ СИСТЕМА
```

Эта последовательность обязательна. Она не позволяет вводить автоматизацию до того, как ученик понял документы и пользователей, либо Workflow до понимания обычного жизненного цикла документа.

## 3. Архитектура линейки проектов

```text
P0  Учебный стенд
 │
 ▼

 │   данные и структура
 ▼
P2  Внутренние заявки
 │   пользователи, права, назначения

     самостоятельная интеграция
```

## 4. Связь проектов с уровнями платформы

### P0 — среда

Ученик получает рабочий site и понимает:

- что такое Bench на пользовательском уровне;
- что такое site;
- где находится Desk;
- как найти нужный DocType или настройку;
- где находятся пользователи и роли;
- что scheduler и background jobs существуют и обслуживают встроенные механизмы.

P0 не является курсом администрирования Linux или Bench. Инфраструктурные действия включаются только в объёме, необходимом для воспроизводимого учебного стенда.

### P1 — данные

Вводится фундаментальная модель Frappe:

```text
DocType
  ├─ Fields
  ├─ Naming
  ├─ Form
  ├─ List
  ├─ Link
  └─ Child Table
```

Главный результат — ученик начинает мыслить сущностями и связями, а не таблицами Excel или отдельными экранами.

### P2 — люди и доступ

Поверх документов добавляется многопользовательская работа:

```text
Document
   │
   ├─ Permissions
   ├─ User Permission
   ├─ Share
   └─ Assignment
           │
           ▼
          ToDo
```

Главный результат — понимание разницы между «кто может видеть документ» и «кто отвечает за работу по документу».

### P3 — процесс

Вводятся три независимых понятия:

```text
Status          прикладное состояние
Workflow State  состояние маршрута
DocStatus       системный жизненный цикл документа
```

Они должны изучаться отдельно, а затем соединяться в одном процессе согласования.

### P4 — контроль и представление

Система начинает не только хранить документы, но и отвечать на вопросы пользователя:

- что запланировано;
- что выполнено;
- где есть проблемы;
- сколько документов каждого типа;
- что нужно распечатать;
- что нужно вынести на рабочую панель.

Архитектура слоя:

```text
Documents
   │
   ├─ Calendar / Views
   ├─ Report Builder
   ├─ Print Format
   └─ Aggregates
          │
          ├─ Number Card
          ├─ Chart
          └─ Workspace
```

### P5 — автоматизация

Ученик передаёт платформе повторяющиеся действия:

```text
Шаблон / документ
       │
       ▼
   Auto Repeat
       │
       ▼
Новый документ
       │
       ▼
Assignment Rule
       │
       ▼
Исполнитель / ToDo
       │
       ▼
Notification
```

Главный результат — понимание того, что часть процессов можно автоматизировать без собственного скрипта.

### P6 — внешний интерфейс

Ввод данных отделяется от Desk:

```text
Пользователь сайта
       │
       ▼
    Web Form
       │
       ▼
    Document
       │
       ▼
      Desk
```

Главный результат — понимание границы между внутренним рабочим интерфейсом Desk и стандартным web-интерфейсом Frappe.

### P7 — интеграция

Ученик получает только требования и критерии приёмки. Архитектуру решения он строит самостоятельно из изученных блоков.

## 5. Стандартная структура каждого практикума

Каждый будущий файл практикума должен иметь одинаковую структуру.

### 5.1. Контекст

Коротко описывается реальная прикладная ситуация без терминов Frappe.

Пример:

> Нужно учитывать оборудование, его текущее место и факты передачи между ответственными.

### 5.2. Результат

Одним абзацем фиксируется, что должно работать после завершения.

### 5.3. Требования

Перечень проверяемых требований к системе. Требование формулируется как наблюдаемое поведение, а не как название кнопки.

Плохо:

> Настроить Link.

Хорошо:

> В карточке оборудования тип должен выбираться из отдельного справочника, а не вводиться произвольным текстом.

### 5.4. Модель данных

До сборки фиксируются:

- DocType;
- назначение каждого DocType;
- тип документа: основной / справочник / child / single;
- ключевые поля;
- связи;
- Naming;
- жизненный цикл.

### 5.5. Роли и доступ

Если в проекте участвуют несколько пользователей, до сборки сценариев фиксируются:

- роли;
- кто создаёт;
- кто читает;
- кто изменяет;
- кто назначается;
- кто утверждает;
- что пользователь не должен видеть или делать.

### 5.6. Пошаговая сборка

Инструкция должна давать действия в естественной последовательности.

Нельзя вводить настройку до объяснения задачи, которую она решает.

### 5.7. Тестовые данные

Каждый проект получает минимальный набор данных, достаточный для проверки всех механизмов.

Требования к данным:

- несколько записей каждого ключевого справочника;
- несколько документов в разных состояниях;
- минимум два пользователя там, где проверяются права;
- данные для положительных и отрицательных сценариев;
- данные для фильтров, отчётов и агрегатов.

### 5.8. Проверка

Ученик проходит контрольные сценарии.

Типовой набор:

1. штатный сценарий;
2. альтернативный сценарий;
3. попытка запрещённого действия;
4. проверка другим пользователем;
5. проверка списка/отчёта;
6. проверка фонового механизма, если он используется.

### 5.9. Приёмка

Практикум заканчивается чек-листом «готово / не готово».

Без прохождения чек-листа проект не считается завершённым.

### 5.10. Самостоятельное изменение

После основной инструкции ученик получает небольшое изменение требований, которое должен реализовать без копирования готовых шагов.

Пример:

> Добавьте новое место хранения и ограничьте пользователя так, чтобы он работал только с объектами этого места.

Этот блок проверяет понимание, а не способность повторять инструкцию.

## 6. Принцип наращивания сложности

Новый проект должен:

- вводить не более одного крупного нового слоя платформы;
- повторять ключевые механизмы предыдущего проекта;
- не требовать знаний из будущих проектов;
- оставаться полезной системой сам по себе.

Нельзя строить проект, в котором сразу впервые появляются DocType, права, Workflow, Auto Repeat и Web Form.

## 7. Разделение данных, процесса и представления

В практикумах нужно постоянно подчёркивать три слоя:

### Данные

Что хранится и как связано.

### Процесс

Кто и что делает с документами.

### Представление

Как пользователь находит, анализирует и вводит информацию.

Ошибки проектирования разбираются именно относительно этих слоёв.

          │           │           │

                      ▼
                 РАБОЧИЙ КОНТУР
                      │

       ▼              ▼              ▼
    Заявки         Проверки      Регламентные
                                   работы
       │              │              │
       └──────────────┼──────────────┘
                      ▼
                  УПРАВЛЕНИЕ
                      │
         ┌────────────┼────────────┐
         ▼            ▼            ▼

                      │
                      ▼
                     ToDo
                      │

Это не готовая физическая модель. Конкретные DocType и связи ученик должен выбрать сам.

## 9. Антипаттерны курса

Запрещены следующие методические решения:

- функции добавлены только ради покрытия матрицы;
- без объяснения создаются десятки полей;
- учебная система работает только при одном пользователе;
- права описаны, но не проверяются;
- Workflow используется там, где достаточно обычного статуса;
- Child Table используется как замена нормальному связанному DocType без причины;
- Select используется вместо справочника там, где значения являются самостоятельными данными;
- автоматизация скрывает от ученика фундаментальный процесс;
- инструкция требует вставить код, который ученик не понимает;
- итоговый проект повторяет предыдущий один в один;
- успех определяется по наличию экранов, а не по прохождению сценариев.

## 10. Архитектурный критерий завершения курса

Курс считается методически цельным, если ученик проходит путь:

```text
понимаю документ
      ↓
понимаю связи
      ↓
понимаю доступ
      ↓
понимаю ответственность
      ↓
понимаю процесс
      ↓
понимаю автоматизацию
      ↓
понимаю аналитику
      ↓
понимаю внешний ввод
      ↓
могу спроектировать систему сам
```
