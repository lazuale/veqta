# Архитектура практикумов

Курс строится вокруг одного учебного приложения — `facility_ops`.

Задача курса не в том, чтобы пройти список настроек Frappe. Задача — последовательно собрать небольшую рабочую систему службы эксплуатации и на каждом шаге понять, какой механизм Frappe решает конкретную задачу.

## 1. Техническая основа

На весь курс используется один стенд и один app:

```text
Bench:  facility-ops-bench
App:    facility_ops
Site:   facility-ops.localhost
Module: Facility Operations
Frappe: v16.32.0
```

P0 создаёт этот app. P1–P8 только развивают его.

Новый app ради очередной темы курса не создаётся.

## 2. Что мы строим

Учебный продукт — система небольшой службы эксплуатации.

Она должна уметь:

- хранить структуру мест эксплуатации;
- вести типы и единицы оборудования;
- фиксировать перемещение оборудования;
- принимать обращения о неисправностях и других проблемах;
- назначать обращения исполнителям;
- проводить обращения через управляемый процесс;
- планировать и фиксировать проверки;
- создавать регулярные работы;
- показывать состояние работы через Desk, Calendar, Reports и Workspace;
- принимать обращения через Web Form;
- полностью восстанавливаться на новом чистом site из app и штатно экспортированной конфигурации.

Это не ERP, не CMMS и не helpdesk общего назначения. Функциональность ограничена тем, что нужно для естественного изучения Frappe.

## 3. Предметная модель

### 3.1. Справочники

```text
Facility Location (Tree)
Equipment Type
Equipment
```

`Facility Location` показывает иерархию:

```text
Main Site
├── Building A
│   ├── Floor 1
│   └── Floor 2
└── Warehouse
```

`Equipment Type` описывает тип оборудования.

`Equipment` — конкретная единица оборудования, связанная с типом и текущим местом размещения.

### 3.2. Операционные документы

```text
Equipment Movement
└── Equipment Movement Item (Child)

Service Request

Inspection
```

`Equipment Movement` фиксирует факт перемещения одной или нескольких единиц оборудования. Это естественный документ для изучения Child Table и позже системного жизненного цикла Draft / Submit / Cancel / Amend.

`Service Request` — центральный рабочий документ приложения. На нём изучаются пользователи, permissions, Assign To, ToDo, Kanban, Workflow, Assignment Rule, Notification и Web Form.

`Inspection` фиксирует плановую или фактическую проверку оборудования. На нём естественно появляются Calendar, отчёты и печать.

### 3.3. Регламентная работа

```text
Maintenance Work
```

`Maintenance Work` — простой документ плановой работы по оборудованию. Он нужен для Auto Repeat и date-based автоматизации.

## 4. Связи

```text
Facility Location
   │
   ├─────────────► Equipment
   │                  │
   │                  ├────────► Equipment Movement Item
   │                  │              │
   │                  │              ▼
   │                  │        Equipment Movement
   │                  │
   │                  ├────────► Service Request
   │                  │
   │                  ├────────► Inspection
   │                  │
   │                  └────────► Maintenance Work
   │
Equipment Type ───────► Equipment
```

Связи намеренно простые. Если механизм Frappe можно изучить без нового DocType, новый DocType не вводится.

## 5. Почему механизмы распределены именно так

### DocType, Link, Tree и Child Table

Изучаются на реестре эксплуатации, потому что там они являются частью самой модели данных, а не учебным трюком.

### Customize Form и Export Customizations

Изучаются на уже существующем `Equipment`.

Сценарий: конкретному site понадобилось дополнительное локальное поле или изменение формы. Сначала оно создаётся как site-specific customization, затем ученик решает, должно ли изменение стать частью поставляемого app, и при необходимости выполняет Export Customizations.

### Permissions и Assignment

Изучаются на `Service Request`.

```text
Permissions
= что пользователь имеет право видеть и делать

Assignment
= за какую конкретную работу он отвечает
```

Эти механизмы нельзя смешивать.

### DocStatus

Изучается на `Equipment Movement`.

Перемещение после подтверждения становится зафиксированным фактом, поэтому здесь естественны:

```text
Draft → Submitted → Cancelled
             │
             └── Amend → новый Draft
```

### Workflow

Изучается отдельно на `Service Request`.

Пример маршрута:

```text
New
 ↓
Assigned
 ↓
In Progress
 ↓
Awaiting Review
 ↓
Closed
```

Workflow не используется вместо системного DocStatus и не заставляется решать задачу подтверждения транзакционного документа.

### Calendar, Reports, Workspace и Print

Изучаются после появления достаточного количества `Service Request`, `Inspection`, `Equipment` и `Equipment Movement`.

До этого Workspace и Dashboard Chart были бы декоративными.

### Automation

Вводится только после того, как соответствующие процессы уже выполнены вручную:

```text
ручная Maintenance Work → Auto Repeat
ручное Assign To        → Assignment Rule
ручная реакция          → Notification
```

### Web Form

Появляется в конце, когда `Service Request` уже имеет понятную модель, права и жизненный цикл. Web Form тогда является внешним входом в существующий процесс, а не отдельной демонстрационной формой.

## 6. Учебные роли

Минимальный набор:

```text
Requester
Technician
Facility Supervisor
```

### Requester

Создаёт обращения и работает только в пределах разрешённого сценария.

### Technician

Работает с назначенными обращениями, видит нужное оборудование и свои задачи.

### Facility Supervisor

Управляет операционной работой, Workflow, перемещениями, проверками, отчётами и рабочим столом.

`Administrator` используется только для администрирования и проверки конфигурации. Проверять обычные permissions под `Administrator` нельзя.

## 7. Три типа состояния

Курс специально разводит три разных понятия.

### Обычное предметное состояние

Например состояние оборудования:

```text
Active
Out of Service
Retired
```

Это обычное поле данных.

### Workflow State

Состояние управляемого процесса `Service Request`.

Его допустимые изменения контролирует Workflow.

### DocStatus

Системное состояние документа:

```text
0 = Draft
1 = Submitted
2 = Cancelled
```

На практике оно изучается на `Equipment Movement`.

Ученик должен закончить курс без смешивания этих трёх механизмов.

## 8. Что живёт в app, а что нет

На каждом этапе ученик классифицирует изменения.

### Standard metadata своего app

Например Standard DocType, созданный в Developer Mode.

Он хранится в файлах `facility_ops` и попадает в Git штатно.

### Site-specific customization

Например Custom Field или Property Setter через Customize Form.

Само наличие изменения на site ещё не означает, что оно входит в поставку app. Для переноса используется Export Customizations.

### Конфигурационная запись базы данных

Например Role, Workflow или другая запись, без которой приложение не воспроизводится.

Если она должна поставляться вместе с app, используется fixture только после доказанной необходимости.

### Рабочие данные

Конкретные Equipment, Service Request, Inspection и другие рабочие записи не являются исходным кодом приложения и не должны попадать в fixtures только ради переноса тестового содержимого.

## 9. Переносимость проверяется дважды

### Первый контроль — P4

После появления:

- Standard DocType;
- Export Customizations;
- Roles;
- Workflow;
- fixtures.

Создаётся второй чистый site и проверяется, что основная конфигурация действительно воспроизводится.

### Финальный контроль — P8

На новом чистом site устанавливается уже всё приложение целиком.

Контрольный принцип:

```text
clean Frappe site
+ facility_ops
+ install-app
+ migrate
= принятая конфигурация без ручного восстановления
```

## 10. Дополнительные лаборатории

Редкие возможности не добавляются в модель насильно.

Например:

- Single DocType;
- Dynamic Link;
- Table MultiSelect;
- Percent;
- Time / Duration;
- Attachment Gallery;
- Barcode;
- Signature;
- Geolocation;
- Gantt.

Они изучаются короткой лабораторией только после основной задачи соответствующего этапа.

Некоторые из них могут получить естественный сценарий: Barcode для Equipment, Signature для Inspection, Geolocation для Facility Location. Но отсутствие такого поля не должно ломать основную модель.

## 11. Последовательность обучения

```text
P0  платформа и настоящий app
 ↓
P1  модель эксплуатации
 ↓
P2  формы и site customization
 ↓
P3  многопользовательская работа и обращения
 ↓
P4  DocStatus + Workflow + переносимость конфигурации
 ↓
P5  проверки, аналитика, Workspace и печать
 ↓
P6  автоматизация
 ↓
P7  Web Form
 ↓
P8  чистая установка и приёмка
```

Каждый этап обязан оставлять `facility_ops` в рабочем состоянии.

## 12. Формат каждого этапа

1. **Рабочая задача** — что должно появиться в приложении.
2. **Модель** — сущности, поля, связи и роли до начала кликов.
3. **Сборка** — пошаговые действия.
4. **Что сделал Frappe** — metadata, database records, generated files.
5. **Git** — что изменилось в app и почему.
6. **Проверка** — нормальный и отрицательный сценарий.
7. **Самостоятельное изменение** — небольшое новое требование без готового рецепта.
8. **Контроль перед следующим этапом** — что ученик обязан уметь объяснить и показать.

## 13. Правила курса

- Один app развивается весь курс.
- Модель данных проектируется до формы.
- Новая сущность появляется только по реальной необходимости.
- Штатный механизм Frappe предпочтительнее собственного кода.
- Права проверяются под обычными учебными пользователями.
- Автоматизация вводится после ручного процесса.
- Не экспортируем рабочие данные как fixtures.
- Не превращаем `hooks.py` в урок Python.
- Не добавляем функцию ради галочки в матрице.
- Если фактический v16.32.0 ведёт себя иначе, исправляется курс.

Хороший результат курса — ученик понимает не только где находится нужная настройка, но и **почему именно этот строительный блок Frappe подходит для данной задачи и как он поставляется вместе с приложением**.
