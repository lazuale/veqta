# Дорожная карта практикумов

Программа идёт от устройства Frappe к самостоятельной сборке приложения.

```text
P0  Учебное приложение
 ↓
P1  Реестр оборудования
 ↓
P2  Настройка существующих форм
 ↓
P3  Внутренние заявки
 ↓
P4  Согласование закупки
 ↓
P5  Журнал проверок
 ↓
P6  Регламентные работы и автоматизация
 ↓
P7  Web Form обращений
 ↓
P8  Операционный центр
```

Каждый проект сначала собирается и проверяется на чистом учебном стенде. Только после этого на его механизмы можно опираться в следующем проекте.

## P0. Учебное приложение

### Что делаем

1. Разворачиваем Frappe Framework v16 по отдельной проверенной инструкции.
2. Фиксируем точную версию `bench version`.
3. Создаём учебный site.
4. Создаём app через `bench new-app`.
5. Устанавливаем app на site.
6. Включаем Developer Mode.
7. Создаём Module для практикумов.
8. Открываем Desk и находим свой Module.
9. Проверяем scheduler и background workers.
10. Проверяем генерацию PDF.
11. Смотрим файловую структуру app и Git-репозиторий.
12. Создаём пробный DocType, сохраняем его и смотрим, какие метаданные появились в app.
13. Удаляем пробный объект или оставляем его как учебный образец.

### Что нужно понять

- Bench, site и app — разные вещи;
- app устанавливается на site;
- Module организует функциональность внутри app;
- Developer Mode нужен для стандартных объектов приложения;
- UI Frappe и файлы app связаны;
- свой app не означает необходимость писать собственную бизнес-логику.

### Перед P1 проверьте

- app установлен;
- Module виден в Desk;
- Developer Mode работает;
- изменение стандартного DocType своего app сохраняется в app;
- Git видит изменения;
- PDF генерируется.

## P1. Реестр оборудования

### Что строим

Рабочий реестр оборудования с типами, местами размещения и документом передачи.

### Последовательность

1. Рисуем модель данных до создания форм.
2. Создаём справочники.
3. Создаём основной DocType `Оборудование`.
4. Создаём документ передачи.
5. Создаём Child DocType для строк передачи.
6. Добавляем Single DocType с настройками учебного приложения.
7. Проходим основные Field Types на реальной форме.
8. Добавляем Link и Dynamic Link в подходящем сценарии.
9. Настраиваем Section / Column / Tab Break.
10. Настраиваем Naming.
11. Настраиваем Title Field и Search Fields.
12. Включаем Track Changes.
13. Проверяем Quick Entry.
14. Создаём тестовые записи.
15. Импортируем набор оборудования.
16. Проверяем List View, фильтры и сортировку.
17. Экспортируем выборку.
18. Коротко знакомимся с дополнительными Field Types, которые не понадобились основной модели.

### Самостоятельная работа

Добавить новую характеристику оборудования так, чтобы модель осталась нормальной и существующие документы не пришлось пересоздавать.

### Перед P2 проверьте

Ученик может объяснить:

- почему сущность является отдельным DocType;
- когда использовать Link, а когда Select;
- когда нужна Child Table;
- чем Naming отличается от Title Field;
- зачем нужны Search Fields;
- где в app лежат метаданные созданных DocType.

## P2. Настройка существующих форм

### Что строим

Приводим учебное приложение и один существующий системный DocType к удобному рабочему виду.

### Последовательность

1. Берём безопасный существующий DocType учебного стенда, например `User` для учебного дополнительного поля.
2. Открываем Customize Form.
3. Добавляем Custom Field.
4. Меняем одно безопасное свойство существующего поля.
5. Находим созданный Custom Field.
6. Находим созданный Property Setter.
7. Сравниваем это с редактированием стандартного DocType своего app в Developer Mode.
8. Проверяем List View и saved filters.
9. Проверяем preview и Quick Entry там, где они уместны.
10. Создаём Workspace учебного приложения.
11. Добавляем Shortcuts.
12. Добавляем Quick Lists.
13. Добавляем полезную связь или действие DocType, если для модели есть естественный сценарий.

### Самостоятельная работа

Изменить ещё один существующий DocType на уровне site и объяснить, почему здесь нужен Customize Form, а не редактирование исходного DocType.

### Перед P3 проверьте

Ученик различает:

```text
Standard DocType своего app
Custom DocType на site
Customize Form существующего DocType
```

## P3. Внутренние заявки

### Что строим

Систему внутренних заявок для заявителя, координатора и исполнителя.

### Последовательность

1. Создаём DocType заявки и категории.
2. Создаём учебных пользователей.
3. Создаём роли.
4. Настраиваем CRUD permissions.
5. Проверяем доступ под каждым пользователем.
6. Настраиваем If Owner в подходящем сценарии.
7. Проверяем Permission Level.
8. Настраиваем User Permission.
9. Проверяем Share.
10. Назначаем заявку через Assign To.
11. Находим созданный ToDo.
12. Добавляем Due Date и Priority.
13. Используем Comments и Timeline.
14. Добавляем Tags.
15. Настраиваем Kanban по обычному статусу заявки.
16. Проверяем отрицательные сценарии доступа.

### Самостоятельная работа

Добавить вторую группу исполнителей и ограничить одному пользователю доступ к разрешённому набору данных штатными permissions.

### Перед P4 проверьте

Ученик без подсказки объясняет:

```text
Permission = доступ
Assignment = ответственность
```

И может доказать настройку входом под разными пользователями.

## P4. Согласование закупки

### Что строим

Заявку на закупку с позициями и управляемым согласованием.

### Последовательность

1. Создаём заявку и Child Table позиций.
2. Включаем Is Submittable.
3. Проходим Draft → Submit → Cancel → Amend без Workflow.
4. Добавляем обычное поле Status и понимаем его роль.
5. Создаём Workflow State.
6. Создаём Workflow Action Master.
7. Создаём Workflow Transitions.
8. Назначаем allowed roles.
9. Проверяем переходы под разными пользователями.
10. Смотрим реальные записи Workflow Action.
11. При необходимости добавляем простое условие перехода.
12. Проводим одну заявку до конца.
13. Вторую отклоняем.
14. Проверяем отмену submitted-документа и Amend.

### Самостоятельная работа

Добавить дополнительное согласование для отдельного сценария и объяснить, где достаточно состояния, а где действительно нужен новый переход Workflow.

### Перед P5 проверьте

Ученик различает:

- Status;
- Workflow State;
- DocStatus;
- Workflow Action Master;
- Workflow Action.

## P5. Журнал проверок

### Что строим

Систему проверок объектов с чек-листом, результатами и рабочим экраном.

### Последовательность

1. Создаём объект и тип проверки.
2. Создаём документ проверки.
3. Добавляем Child Table пунктов проверки.
4. Добавляем даты, результат, замечания и фотографии.
5. Создаём достаточно тестовых данных для отчётов.
6. Настраиваем Calendar.
7. Создаём Report Builder report.
8. Добавляем filters.
9. Используем Group By.
10. Проверяем Count / Sum / Average на подходящих полях.
11. Создаём Number Card.
12. Создаём Dashboard Chart.
13. Дорабатываем Workspace под реальные вопросы пользователя.
14. Проверяем Print View.
15. Создаём Print Format через визуальный builder.
16. Настраиваем Letter Head.
17. Получаем PDF.

### Самостоятельная работа

Переделать Workspace так, чтобы по нему можно было сразу понять:

- что проверить сегодня;
- где есть проблемы;
- что произошло за период.

### Перед P6 проверьте

Ученик умеет получить полезную сводку без SQL и собственного отчёта.

## P6. Регламентные работы и автоматизация

### Часть A. Auto Repeat

1. Создаём документ регламентной работы.
2. Проходим его вручную.
3. Включаем Allow Auto Repeat на DocType.
4. Создаём Auto Repeat.
5. Настраиваем периодичность.
6. Проверяем next schedule date.
7. Назначаем assignee штатной настройкой Auto Repeat.
8. Проверяем отдельные документы для нескольких assignee, если это подходит сценарию.
9. Ждём или безопасно моделируем ближайший запуск на учебном стенде и убеждаемся, что новый документ появился.

### Часть B. Assignment Rule

1. Берём поток входящих рабочих документов.
2. Создаём Assignment Rule.
3. Разбираем обязательный Assign Condition.
4. Используем минимальное понятное PythonExpression.
5. Проверяем Round Robin.
6. Проверяем Load Balancing.
7. Отдельно знакомимся с Based on Field.
8. Отдельно знакомимся с Weighted Distribution.
9. Проверяем созданные ToDo.
10. Смотрим Unassign / Close condition на простом сценарии.

### Часть C. Notification

1. Создаём System Notification.
2. Используем Filters condition.
3. Проверяем событие New / Save / Submit или подходящий вариант.
4. Проверяем notification у пользователя.
5. Проверяем date-based событие, если оно нужно проекту.
6. При настроенной почте дополнительно пробуем Email.

### Самостоятельная работа

Для трёх новых требований выбрать правильный механизм: Auto Repeat, Assignment Rule или Notification — и объяснить выбор.

### Перед P7 проверьте

Ученик не воспринимает «автоматизацию» как одну функцию и знает назначение каждого механизма.

## P7. Web Form обращений

### Что строим

Внешнюю форму обращения, которая создаёт обычный Document нашего app.

### Последовательность

1. Создаём DocType обращения.
2. Проверяем его в Desk.
3. Создаём Web Form.
4. Настраиваем Route.
5. Проверяем Anonymous responses.
6. Создаём вариант с Login Required.
7. Проверяем Apply document permissions.
8. Включаем Allow editing after submit там, где это соответствует сценарию.
9. Проверяем Allow multiple responses.
10. Включаем Show list.
11. Проверяем Attachments.
12. При необходимости проверяем Comments и Print.
13. Отдельным упражнением разбираем Web Form Request / Key required.
14. Открываем созданные документы в Desk и проводим их по внутреннему процессу.

### Самостоятельная работа

Сделать второй web-сценарий с другой моделью доступа и объяснить выбор.

### Перед P8 проверьте

Ученик понимает, что Web Form — это внешний интерфейс к Document, а не отдельная база данных.

## P8. Операционный центр

### Формат

Только техническое задание и критерии приёмки. Пошаговой инструкции нет.

### Минимум, который должен появиться в итоговом приложении

- собственный app и Module;
- несколько связанных стандартных DocType приложения;
- минимум один Child DocType;
- осмысленный Naming;
- подходящие Field Types;
- минимум три роли;
- проверяемые permissions;
- Assignment / ToDo;
- один submittable-процесс;
- Workflow;
- Report Builder;
- Number Card или Dashboard Chart;
- полезный Workspace;
- Print Format;
- хотя бы один оправданный механизм автоматизации;
- Web Form;
- тестовые данные;
- проверка под несколькими пользователями.

Не требуется механически вставлять в P8 каждую функцию из матрицы. Выбор должен быть обоснован задачей.

## Как разрабатываем сами файлы практикумов

После утверждения этой программы папка развивается так:

```text
frappe-practicum/
├── README.md
├── SCOPE.md
├── ARCHITECTURE.md
├── MATRIX.md
├── ROADMAP.md
└── projects/
    ├── 00-lab/
    ├── 01-equipment-registry/
    ├── 02-customization/
    ├── 03-internal-requests/
    ├── 04-purchase-approval/
    ├── 05-inspection-journal/
    ├── 06-automation/
    ├── 07-web-form/
    └── 08-final-project/
```

Каждый проект сначала пишется, затем проходится с нуля на фактическом v16 стенде, после чего исправляется инструкция. Только принятый проект становится основой следующего.

## Когда программа считается готовой

- P0–P7 можно пройти с чистого стенда;
- команды, названия полей и экранов соответствуют проверенной версии v16;
- каждая важная функция проверена по исходникам или официальной документации;
- нет скрытой обязательной зависимости от ERPNext;
- собственная программная логика не нужна для завершения базовых проектов;
- штатные expressions не скрыты и объяснены там, где Frappe их требует;
- P8 действительно можно выполнить без повторения пошаговой инструкции.
