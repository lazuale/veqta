# Дорожная карта практикумов

Статус: **обязательная последовательность прохождения**  
Платформа: **Frappe Framework 16**

## 1. Общий маршрут

```text
P0  Учебный стенд
 ↓
P1  Реестр оборудования
 ↓
P2  Внутренние заявки
 ↓
P3  Согласование закупки
 ↓
P4  Журнал проверок
 ↓
P5  Регламентные работы
 ↓
P6  Web Form обращений
 ↓
P7  Операционный центр
```

Проекты проходят последовательно. Переход к следующему этапу допускается только после выполнения контрольного сценария предыдущего.

## 2. Этап 0 — подготовить стенд

### Цель

Получить воспроизводимый учебный Frappe Framework 16 site.

### Необходимо выполнить

- развернуть Frappe Framework 16 по утверждённой инструкции стенда;
- создать учебный site;
- войти как Administrator;
- проверить Desk;
- проверить поиск/Awesomebar;
- создать минимум трёх учебных пользователей для будущих сценариев;
- создать базовые роли для проверки доступа;
- убедиться, что scheduler/background workers доступны встроенным механизмам, которые будут использоваться позже.

### Не входит в этап

- глубокое администрирование Bench;
- production hardening;
- reverse proxy как отдельная учебная тема;
- разработка приложения;
- Docker как обязательная тема курса, если сам стенд развёрнут другим штатным способом.

### Критерий перехода

Ученик может войти под разными пользователями, открыть Desk и самостоятельно найти системную сущность через поиск.

---

## 3. Этап 1 — научиться строить модель данных

### Проект

P1 «Реестр оборудования».

### Последовательность

1. Описать задачу человеческим языком.
2. Выделить сущности.
3. Отделить справочники от рабочих документов.
4. Создать DocType.
5. Добавить основные типы полей.
6. Настроить структуру формы.
7. Настроить Naming и Title Field.
8. Связать сущности через Link.
9. Добавить Child Table для строк передачи.
10. Добавить вложения и изображение.
11. Создать тестовые записи вручную.
12. Импортировать набор данных.
13. Проверить List View, фильтры и сортировку.
14. Экспортировать результат.

### Самостоятельное изменение

Добавить новую характеристику оборудования и изменить модель так, чтобы существующие данные продолжили использоваться без пересоздания документов.

### Критерий перехода

Ученик способен объяснить:

- почему конкретная сущность является отдельным DocType;
- чем Link отличается от Select;
- когда нужна Child Table;
- зачем Naming и Title Field;
- как найти и отфильтровать документы.

---

## 4. Этап 2 — добавить пользователей, доступ и ответственность

### Проект

P2 «Внутренние заявки».

### Последовательность

1. Создать модель заявки и категорий.
2. Определить роли: заявитель, исполнитель, координатор.
3. Создать/назначить роли учебным пользователям.
4. Настроить CRUD-права.
5. Проверить доступ под каждым пользователем.
6. Настроить ограничения владельца там, где это оправдано.
7. Настроить User Permission в отдельном сценарии.
8. Проверить Share.
9. Назначить заявку через Assign To.
10. Найти созданный ToDo.
11. Добавить срок и приоритет.
12. Провести работу через комментарии и Timeline.
13. Представить заявки в Kanban.
14. Проверить отрицательный сценарий доступа.

### Самостоятельное изменение

Добавить вторую группу исполнителей и ограничить одному пользователю доступ только к разрешённому набору данных штатными permissions.

### Критерий перехода

Ученик должен уверенно различать:

```text
Permissions = что пользователь имеет право делать
Assignment  = за что пользователь отвечает
```

Если ученик пытается решать назначения через права или права через назначения, этап не считается завершённым.

---

## 5. Этап 3 — построить жизненный цикл и Workflow

### Проект

P3 «Согласование закупки».

### Последовательность

1. Создать заявку и строки заявки.
2. Настроить документ как submittable.
3. Проверить Draft → Submit → Cancel → Amend без Workflow.
4. Отдельно создать прикладное поле статуса и понять его роль.
5. Создать Workflow States.
6. Определить роли участников согласования.
7. Создать Transitions.
8. Связать переходы с ролями.
9. Проверить допустимые и недопустимые переходы.
10. Проверить Workflow Actions.
11. Добавить штатное Notification для одного ключевого события.
12. Провести одну заявку до конца.
13. Отклонить вторую заявку.
14. Отменить подходящий submitted-документ и проверить дальнейшее поведение.

### Обязательная проверка понимания

Ученик должен своими словами объяснить:

| Понятие | Что означает |
|---|---|
| Status | прикладное состояние, определённое моделью задачи |
| Workflow State | текущее состояние управляемого маршрута |
| DocStatus | системный жизненный цикл Draft / Submitted / Cancelled |

### Самостоятельное изменение

Добавить дополнительный этап согласования для заявок определённой категории, если это можно сделать штатной настройкой Workflow без отдельного скрипта. Если для конкретной логики требуется код, ученик должен это распознать и не обходить ограничение костылём.

### Критерий перехода

Ученик способен построить простой Workflow и не использует его там, где достаточно обычного статуса.

---

## 6. Этап 4 — научиться контролировать и представлять данные

### Проект

P4 «Журнал проверок».

### Последовательность

1. Создать справочники объектов и типов проверок.
2. Создать документ проверки.
3. Создать Child Table чек-листа.
4. Добавить результаты, замечания, даты и фотографии.
5. Создать достаточный набор тестовых проверок.
6. Настроить Calendar View.
7. Построить Report Builder Report.
8. Добавить фильтры.
9. Использовать Group By.
10. Проверить Count/Sum/Average там, где соответствуют данным.
11. Создать Number Card.
12. Создать Dashboard Chart.
13. Собрать Workspace.
14. Добавить полезные Shortcut и Quick List.
15. Проверить стандартную печать.
16. Собрать отдельный Print Format через визуальный builder.
17. Получить PDF.
18. При необходимости настроить Letter Head.

### Самостоятельное изменение

Изменить Workspace так, чтобы он отвечал на три вопроса пользователя:

1. Что нужно проверить сегодня?
2. Где есть проблемы?
3. Что произошло за выбранный период?

Добавление декоративных блоков без ответа на эти вопросы не считается улучшением.

### Критерий перехода

Ученик умеет превратить накопленные документы в рабочее представление для конкретной роли без SQL и собственного отчёта.

---

## 7. Этап 5 — передать повторяющиеся действия Frappe

### Проект

P5 «Регламентные работы».

### Последовательность

1. Определить рабочий документ, который должен повторяться.
2. Проверить ручной сценарий его создания и выполнения.
3. Настроить Auto Repeat.
4. Проверить создание следующего экземпляра.
5. Создать Assignment Rule.
6. Проверить назначение документа пользователю.
7. Проверить связанный ToDo, если он создаётся выбранным штатным сценарием.
8. Создать Notification.
9. Проверить системное уведомление.
10. При наличии настроенной почты дополнительно проверить email.
11. Проверить Calendar.
12. При наличии естественной модели дат дополнительно исследовать Gantt.

### Ключевой принцип

Сначала ученик должен пройти процесс вручную и понять его. Только после этого он автоматизируется.

### Самостоятельное изменение

Создать второй регламент с другой периодичностью и другим правилом назначения без копирования пошаговой инструкции.

### Критерий перехода

Система самостоятельно создаёт требуемую работу и назначает её по штатному механизму. Ученик понимает, какой именно механизм выполнил каждое действие.

---

## 8. Этап 6 — выйти за пределы Desk

### Проект

P6 «Web Form обращений».

### Последовательность

1. Создать простой DocType обращения.
2. Проверить его работу в Desk.
3. Создать Web Form поверх DocType.
4. Настроить route.
5. Опубликовать форму.
6. Проверить создание документа через web.
7. Проверить вложения.
8. Проверить guest-сценарий, если он разрешён конфигурацией практикума.
9. Создать вариант с Login Required.
10. Проверить работу авторизованного пользователя.
11. Проверить редактирование/список документов, если соответствующие штатные опции доступны в актуальном Frappe 16 стенде.
12. Открыть созданный документ в Desk.
13. Назначить его внутреннему исполнителю.
14. Проверить ограничения доступа.

### Самостоятельное изменение

Сделать второй web-сценарий с другими правилами доступа и объяснить, почему для него выбран Guest или Login Required.

### Критерий перехода

Ученик понимает, что Web Form — это альтернативный интерфейс к документу, а не отдельная база или отдельное приложение.

---

## 9. Этап 7 — итоговый проект

### Проект

P7 «Операционный центр».

### Формат

Ученик получает техническое задание, а не последовательность кликов.

Минимальные требования:

- несколько связанных DocType;
- минимум один Child DocType;
- осмысленный Naming;
- минимум три пользовательские роли;
- проверяемые ограничения доступа;
- User Permission или другой оправданный штатный механизм ограничения;
- Assign To / ToDo;
- Kanban или другое полезное дополнительное представление;
- Calendar для сущности с реальной календарной семантикой;
- один submittable-процесс;
- Workflow;
- Notification;
- Auto Repeat;
- Assignment Rule;
- Report Builder;
- агрегирование данных;
- Number Card;
- Dashboard Chart;
- Workspace;
- Print Format;
- Web Form;
- тестовые данные;
- сценарии под несколькими пользователями.

### Запрещено

- копировать готовую модель одного из предыдущих проектов без адаптации;
- вставлять код;
- использовать стороннее приложение;
- обходить ограничения платформы неочевидными хаками;
- считать проект завершённым только потому, что формы визуально существуют.

### Итоговая приёмка

Ученик должен продемонстрировать:

1. модель данных;
2. связи;
3. Naming;
4. роли и права;
5. отрицательный сценарий доступа;
6. назначение работы;
7. Workflow;
8. автоматическое действие;
9. отчёт;
10. рабочий Workspace;
11. печать;
12. Web Form;
13. полный пользовательский сценарий от создания до завершения;
14. объяснение, какие требования можно было решить штатно, а какие потребовали бы следующего уровня Frappe.

## 10. Контрольные точки курса

### Gate A — после P1

Ученик умеет моделировать данные.

### Gate B — после P2

Ученик понимает многопользовательскую модель и ответственность.

### Gate C — после P3

Ученик понимает жизненный цикл и управляемый процесс.

### Gate D — после P4

Ученик умеет представить накопленные данные пользователю.

### Gate E — после P5

Ученик умеет применять штатную автоматизацию без кода.

### Gate F — после P6

Ученик понимает внутренний и внешний интерфейс Frappe.

### Gate G — после P7

Ученик способен самостоятельно собрать законченную систему из штатных блоков.

## 11. Правило разработки будущих файлов уроков

Конкретные уроки создаются только после этой базовой документации и должны ей соответствовать.

Рекомендуемая будущая структура папки:

```text
frappe-practicum/
├── README.md
├── SCOPE.md
├── ARCHITECTURE.md
├── MATRIX.md
├── ROADMAP.md
└── projects/
    ├── 00-lab/
    ├── 01-equipment-registry/
    ├── 02-internal-requests/
    ├── 03-purchase-approval/
    ├── 04-inspection-journal/
    ├── 05-recurring-work/
    ├── 06-web-form/
    └── 07-final-project/
```

Папка `projects/` создаётся по мере разработки конкретных практикумов. До утверждения урока в неё не должны попадать экспериментальные инструкции, противоречащие `SCOPE.md` или `MATRIX.md`.

## 12. Порядок дальнейшей разработки курса

После фиксации этой дорожной карты дальнейшая работа идёт строго в таком порядке:

1. подготовить и проверить P0 на чистом Frappe Framework 16;
2. написать P1 полностью;
3. пройти P1 с нуля как ученик;
4. исправить несоответствия;
5. только после приёмки P1 писать P2;
6. повторять цикл для каждого следующего проекта;
7. после P6 провести аудит матрицы покрытия;
8. только затем финализировать ТЗ и приёмку P7.

Не следует писать все подробные уроки одновременно: фактическое поведение конкретного механизма на стенде должно проверяться до того, как на него начнут опираться последующие практикумы.

## 13. Критерий готовности всей базовой программы

Базовая программа готова к использованию, когда:

- P0–P6 имеют воспроизводимые пошаговые инструкции;
- каждый проект был пройден с чистого состояния;
- все обязательные строки `MATRIX.md` подтверждены практикой;
- ни один обязательный шаг не требует собственного кода;
- отсутствует обязательная зависимость от ERPNext или стороннего приложения;
- каждый проект имеет контрольные данные и приёмочный сценарий;
- P7 проверяет самостоятельную работу, а не память на последовательность кликов.
