# Дорожная карта практикумов

Программа проходит последовательно: P0 → P8. Следующий проект начинается только после проверки предыдущего на фактическом стенде v16.32.0.

## P0. Учебное приложение

### Задача

Получить рабочий Bench с Frappe v16.32.0, собственный app и учебный site, а затем увидеть связь между объектами Desk и файлами приложения.

### Практика

1. Подготовить системное окружение и Bench с Frappe v16.32.0 по отдельной проверенной инструкции стенда.
2. Зафиксировать вывод `bench version` и точный tag Frappe.
3. Создать app через `bench new-app`.
4. Создать учебный site.
5. Установить app на site и проверить `list-apps`.
6. Включить Developer Mode.
7. Найти модуль, который `bench new-app` создал вместе с приложением, и посмотреть `modules.txt`.
8. Просмотреть структуру app: module, `hooks.py`, `public`, `templates`, `patches.txt` и другие созданные каталоги без ручного изменения лишних файлов.
9. Пройти актуальную навигацию Desk v16: Apps Page, Workspace Sidebar, public/my workspaces, Awesomebar/command palette, List и Form.
10. Проверить scheduler и workers.
11. Создать пробный стандартный DocType в Module приложения.
12. Найти созданные файлы DocType в app.
13. Посмотреть `git status` и `git diff`.

PDF в P0 не проверяется. Он впервые понадобится в P5, где печатный сценарий и его зависимость будут проверены отдельно.

### Перед P1 проверьте

Ученик может объяснить разницу между Bench, app, site и Module, а также показать, где лежат файлы стандартного DocType своего app.

## P1. Реестр оборудования

### Задача

Собрать связанную предметную модель, а не просто форму.

### Модель

```text
Тип оборудования
       │
       ▼
  Оборудование
       │
       ├────────► Место размещения (Tree)
       │
       ▼
Передача оборудования
       │
       ▼
Строки передачи (Child)
```

### Практика

1. До работы в Desk нарисовать сущности и связи.
2. Создать `Тип оборудования`.
3. Создать `Место размещения` как Tree DocType и построить небольшую иерархию.
4. Создать `Оборудование`.
5. Создать `Передача оборудования`.
6. Создать Child DocType строк передачи.
7. Разместить основные поля через Form Builder.
8. Использовать Data/Text, Select, Check, Int/Float/Currency, Date/Datetime, Link, Attach/Attach Image и layout breaks там, где они действительно нужны.
9. Настроить Naming: сравнить способы и выбрать подходящий для справочника и рабочего документа.
10. Настроить Title Field и Search Fields.
11. Включить Track Changes там, где история полезна.
12. Проверить Quick Entry на простом справочнике.
13. Настроить List View и стандартную сортировку.
14. Создать записи вручную.
15. Импортировать тестовый набор оборудования через Data Import.
16. Отфильтровать и экспортировать выборку.
17. Посмотреть изменения app через Git.
18. Короткой лабораторией познакомиться с возможностями, которые не понадобились основной модели: Single DocType, Dynamic Link, Table MultiSelect, Percent, Time/Duration, Attachment Gallery и другими актуальными для v16.32.0 типами полей.
19. Дополнительно выполнить одну безопасную массовую операцию в List View, если она естественна для созданных данных.

### Самостоятельная работа

Добавить новую характеристику оборудования и изменить форму так, чтобы существующие документы продолжили работать без пересоздания.

### Перед P2 проверьте

Ученик может объяснить:

- DocType, DocField, Document и `name`;
- Link против Select;
- Tree против обычного справочника;
- Child Table против отдельного связанного DocType;
- Naming против Title Field;
- какие изменения P1 появились в Git.

## P2. Кастомизация и переносимость

### Задача

Понять, чем изменение существующего DocType отличается от разработки своего DocType и как собрать переносимый app.

### Часть A. Customize Form

1. Выбрать безопасный существующий DocType учебного стенда.
2. Добавить Custom Field через Customize Form.
3. Изменить одно безопасное свойство стандартного поля.
4. Найти созданные Custom Field и Property Setter.
5. Сравнить это с редактированием стандартного DocType своего app в Developer Mode.
6. Выполнить Export Customizations в Module приложения.
7. Найти экспортированные файлы в app.
8. Посмотреть Git diff.

### Часть B. DocType Layout

1. Создать альтернативный DocType Layout для подходящего DocType.
2. Изменить порядок, видимость или подписи нескольких полей.
3. Проверить условное применение Layout, если для модели есть простой понятный сценарий.
4. Убедиться, что базовый DocType при этом не переписывается.
5. Проверить, как стандартный Layout хранится в app.

### Часть C. Fixtures

1. Создать одну конфигурационную запись, которая действительно нужна приложению на другом site, например учебную Role.
2. Добавить точечную fixture в `hooks.py`.
3. Выполнить `bench --site <site> export-fixtures`.
4. Найти JSON в app.
5. Проверить Git diff.

### Часть D. Первый перенос

1. Сохранить состояние app в Git.
2. Создать второй чистый site.
3. Установить учебный app.
4. Выполнить migrate.
5. Проверить стандартные DocType P1.
6. Проверить экспортированную кастомизацию.
7. Проверить fixture.
8. Зафиксировать, что осталось только на первом site и почему.

### Дополнительно

- Saved Filters;
- Preview;
- Custom DocType как отдельный site-specific сценарий;
- `add_to_apps_screen` в `hooks.py`, только если нужен отдельный сценарий Apps Page.

### Самостоятельная работа

Добавить ещё одну небольшую site-specific кастомизацию или конфигурационную запись, самостоятельно выбрать Export Customizations либо fixture и доказать выбор установкой app на второй site.

### Перед P3 проверьте

Ученик без подсказки различает:

```text
стандартный объект своего app
Custom DocType на конкретном site
кастомизация через Customize Form
запись БД, которую приложение поставляет как fixture
```

И может показать, каким способом каждый тип переносится на новый site.

## P3. Внутренние заявки

### Задача

Собрать многопользовательскую систему заявок, где доступ и ответственность решаются разными механизмами.

### Практика

1. Создать DocType заявки и категории.
2. Создать учебных System Users.
3. Показать отличие System User от Website User.
4. Разобрать автоматические роли Guest, All, Administrator и Desk User.
5. Создать роли заявителя, исполнителя и координатора.
6. Открыть полную строку DocType Permissions и сверить реальные поля v16.32.0: Select, Read, Write, Create, Delete, Submit, Cancel, Amend, Mask, Report, Export, Import, Share, Print и Email.
7. Настроить необходимые Select / Read / Write / Create / Delete.
8. Проверить Report / Export / Import / Print / Email там, где они применимы.
9. Настроить If Owner.
10. Проверить Permission Level на одном поле.
11. Создать User Permission для ограничения связанного справочника.
12. Проверить Share.
13. Дополнительным упражнением посмотреть Mask / Data Masking и отдельно отметить экспериментальный статус этой возможности в v16.
14. Войти под каждым учебным пользователем и проверить положительные и отрицательные сценарии.
15. Назначить заявку через Assign To.
16. Найти созданный ToDo.
17. Проверить Due Date и Priority.
18. Использовать Comments и Timeline.
19. Добавить Tags.
20. Настроить Kanban по обычному статусу.
21. Определить, какие роли и настройки этого проекта должны поставляться вместе с app, и при необходимости обновить fixtures.

### Самостоятельная работа

Добавить вторую группу исполнителей и ограничить одному пользователю видимость документов по связанному значению без изменения основной модели заявки.

### Перед P4 проверьте

Ученик может доказать входом под разными пользователями:

```text
Permission = доступ
Assignment = ответственность
```

## P4. Согласование закупки

### Задача

Собрать документ с системным жизненным циклом и управляемым согласованием.

### Практика

1. Создать заявку и Child Table позиций.
2. Включить Is Submittable.
3. Пройти Draft → Submit → Cancel → Amend без Workflow.
4. Настроить права Submit / Cancel / Amend для нужных ролей.
5. Добавить безопасное служебное поле и проверить Allow on Submit.
6. Отдельно изменить значимое поле через Cancel + Amend и сравнить подходы.
7. Открыть Audit Trail и сравнить amended-версии.
8. Добавить обычное поле Status и понять его назначение.
9. Создать Workflow States.
10. Создать Workflow Action Master.
11. Создать Workflow Transitions и allowed roles.
12. Проверить переходы под разными пользователями.
13. Посмотреть реальные Workflow Action records.
14. Добавить простое transition condition только если оно действительно нужно сценарию.
15. Провести одну заявку до конца и вторую отклонить.
16. Проверить, каким способом Workflow и связанные настройки должны переноситься вместе с app; при необходимости использовать fixtures.

### Самостоятельная работа

Добавить ещё один вариант согласования и самостоятельно решить, требуется новый Workflow Transition, достаточно обычного Status или изменение вообще должно проходить через Cancel + Amend.

### Перед P5 проверьте

Ученик различает Status, Workflow State и DocStatus и может объяснить, когда нужен Allow on Submit, а когда Cancel + Amend.

## P5. Журнал проверок

### Задача

Превратить накопленные документы в рабочий экран, отчёты и печатный результат.

### Практика

1. Создать объект, тип и документ проверки с Child Table чек-листа.
2. Добавить даты, результаты, замечания и фотографии.
3. Создать достаточный набор тестовых данных.
4. Настроить Calendar.
5. Создать Report Builder report.
6. Добавить фильтры и Group By.
7. Проверить Count / Sum / Average на подходящих полях.
8. Создать Number Card.
9. Создать Dashboard Chart.
10. Собрать Workspace через штатный builder.
11. Добавить полезные Shortcut и Quick List.
12. Проверить доступ Workspace под разными ролями.
13. Проверить Print View.
14. Создать Print Format через визуальный builder.
15. Настроить Letter Head.
16. Подготовить и проверить поддерживаемую для учебного стенда PDF-зависимость по отдельной проверенной инструкции печати.
17. Получить PDF.
18. Проверить, какие отчёты, Workspace и другие объекты действительно попали в app; нужные site-specific записи подготовить к переносу штатным способом.

PDF-зависимость не ставится в P0 «на будущее»: она появляется здесь, потому что именно здесь впервые есть реальный сценарий PDF-печати.

### Самостоятельная работа

Переделать Workspace так, чтобы он сразу отвечал на три вопроса:

- что нужно проверить сегодня;
- где есть проблемы;
- что произошло за выбранный период.

### Перед P6 проверьте

Ученик может собрать полезную сводку без SQL, Script Report и собственного frontend.

## P6. Регламентные работы и автоматизация

### Часть A. Auto Repeat

1. Создать документ регламентной работы.
2. Сначала пройти его вручную.
3. Включить Allow Auto Repeat.
4. Создать Auto Repeat.
5. Настроить периодичность и даты.
6. Проверить next schedule date.
7. Проверить Assignee и вариант отдельных документов для нескольких исполнителей, если это соответствует задаче.
8. После штатного запуска scheduler убедиться, что новый документ создан.

### Часть B. Assignment Rule

1. Взять поток входящих рабочих документов.
2. Создать Assignment Rule.
3. Разобрать обязательный Assign Condition.
4. Использовать минимальный понятный PythonExpression.
5. Выбрать **один** алгоритм, естественный для основной задачи: Round Robin или Load Balancing.
6. Проверить автоматическое назначение и созданный ToDo.
7. Короткой сравнительной лабораторией посмотреть остальные режимы: второй из Round Robin/Load Balancing, Based on Field и Weighted Distribution.
8. Показать назначение Unassign / Close condition без искусственного усложнения сценария.

### Часть C. Notification

1. Создать System Notification.
2. Использовать Filters condition.
3. Проверить событие документа.
4. Проверить date-based событие.
5. Проверить уведомление у получателя.
6. Email протестировать только при настроенной почте.

### Самостоятельная работа

Для нескольких новых требований выбрать Auto Repeat, Assignment Rule или Notification и объяснить, почему выбран именно этот механизм.

### Перед P7 проверьте

Ученик понимает разницу между повторением документа, назначением исполнителя и уведомлением.

## P7. Web Form обращений

### Задача

Дать внешнему пользователю штатный интерфейс к обычному Document приложения.

### Практика

1. Создать DocType обращения и проверить его в Desk.
2. Создать Web Form.
3. Настроить Route.
4. Проверить Anonymous responses.
5. Создать вариант с Login Required.
6. Проверить Website User.
7. Проверить Apply document permissions.
8. Проверить Allow editing after submit. Это настройка Web Form и она не имеет отношения к `Allow on Submit` поля DocType из P4.
9. Проверить Allow multiple responses и Show list.
10. Проверить Attachments.
11. Comments и Print включать только там, где это нужно сценарию.
12. Дополнительным упражнением разобрать Web Form Request / Key required.
13. Создать Standard Web Form в Developer Mode.
14. Найти файлы Standard Web Form в app.
15. Проверить его после установки app на второй site.
16. Открыть созданный через Web Form Document в Desk и провести по внутреннему процессу.

### Самостоятельная работа

Сделать второй Web Form для того же или другого DocType с другой моделью доступа и объяснить, почему выбран Guest, Website User либо document permissions.

### Перед P8 проверьте

Ученик понимает Guest, Website User и System User, а также разницу между site-specific Web Form и Standard Web Form приложения.

## P8. Операционный центр

### Формат

Только техническое задание и критерии приёмки. Пошаговой инструкции нет.

### Минимальные требования

Итоговое приложение должно содержать осмысленно выбранные:

- собственный app и Module;
- несколько связанных стандартных DocType;
- Child DocType;
- Tree или другой специальный тип только если он нужен модели;
- понятный Naming;
- минимум три пользовательские роли;
- проверяемые permissions;
- Assignment / ToDo;
- один submittable-процесс;
- Workflow;
- Report Builder;
- Number Card или Dashboard Chart;
- полезный Workspace;
- Print Format;
- хотя бы один оправданный механизм автоматизации;
- Web Form;
- тестовые данные.

Не требуется механически использовать каждую строку MATRIX.md.

### Финальная проверка

1. Зафиксировать app в Git.
2. Создать новый чистый site.
3. Установить app.
4. Выполнить migrate.
5. Проверить DocType и связи.
6. Проверить экспортированные кастомизации.
7. Проверить fixtures.
8. Проверить роли и права.
9. Проверить Workflow.
10. Проверить Workspace и отчёты.
11. Проверить автоматизацию после штатного запуска scheduler.
12. Проверить Standard Web Form.
13. Пройти полный пользовательский сценарий под несколькими пользователями.

Если для запуска итоговой системы требуется вручную повторить настройки со старого site, приложение не принято.
