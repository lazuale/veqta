# Дорожная карта учебного практикума Frappe

Статус: **черновик для согласования**.

Продолжает:

- [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md);
- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md);
- [`STAGE_DEPENDENCY_GRAPH.md`](STAGE_DEPENDENCY_GRAPH.md).

Дорожная карта не является каталогом возможностей Frappe и не фиксирует количество уроков. Она превращает граф зависимостей в последовательность законченных практических этапов.

Каждый этап описывается одинаково:

```text
входное состояние
→ реальное требование
→ действия ученика
→ штатный механизм Frappe
→ наблюдаемый результат
→ проверка
→ архитектурный вывод
```

Если результат предыдущего этапа не принят, следующий зависимый этап не начинается.

---

# 1. Обязательный маршрут

CORE строится только из узлов `P00–P12` графа зависимостей.

```text
Среда
  ↓
App / Site / Module
  ↓
Equipment + Customer
  ↓
Rental + Rental Item + Link
  ↓
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ status       │ Form / List  │ invariants   │ permissions  │
└──────┬───────┴──────────────┴──────┬───────┴──────────────┘
       │                              │
       └────→ cross-document rule ←───┘

cross-document rule + permissions
        ↓
   tests + delivery audit
        ↓
     clean install
```

Naming не является отдельной необязательной веткой: стратегия `name` выбирается при создании каждого самостоятельного DocType.

`NEXT`, `GATE` и `EXT` не включаются автоматически. Они описаны отдельно после CORE.

# 2. Этап 0 — подготовить учебную среду

**Опорный узел:** `P00`.

## Вход

Рабочая машина/WSL-среда без учебного приложения.

## Требование

Нужна совместимая среда Frappe v16, в которой изменения можно создавать как часть App и сохранять в Git.

## Ученик делает

1. Проверяет Bench и версию Frappe.
2. Создаёт или использует отдельный учебный Site.
3. Включает developer mode там, где он нужен для Standard DocType.
4. Проверяет Git.
5. Убеждается, что Site открывается и Bench-команды работают.

## Механизмы

```text
Bench
Site
developer mode
Git
```

## Результат

Среда готова к созданию настоящего Frappe App.

## Проверка

Ученик может показать:

- какой Bench используется;
- какой Site учебный;
- какая версия Frappe установлена;
- где будут находиться исходники App;
- что Site работает.

## Архитектурный вывод

`Bench` — среда управления, а не предметный слой приложения.

## Не включать

Production deployment, reverse proxy, TLS, резервное копирование, hardening и эксплуатацию сервера. Это отдельная дисциплина.

# 3. Этап 1 — создать границу учебного App

**Опорный узел:** `P01`.

**Зависит от:** этапа 0.

## Требование

Учебная модель должна принадлежать отдельному устанавливаемому App, а не быть набором случайных локальных настроек Site.

## Ученик делает

1. Создаёт нейтральный App практикума.
2. Устанавливает его на учебный Site.
3. Проверяет структуру App.
4. Создаёт/проверяет Module учебной предметной области.
5. Добавляет исходники App в Git.

## Результат

```text
App существует в исходниках
App установлен на Site
Module принадлежит App
```

## Проверка

Ученик объясняет:

```text
Bench  ≠ Site
Site   ≠ App
App    ≠ Module
Module ≠ отдельное приложение
```

## Архитектурный вывод

App — граница установки и исходного кода. Site — экземпляр. Module — группировка внутри App.

# 4. Этап 2 — смоделировать Equipment

**Опорный узел:** `P02`.

**Покрывает:** `R01`, `R06`, `D00` для Equipment.

**Зависит от:** этапа 1.

## Требование

Оборудование существует независимо от конкретной выдачи и переиспользуется в разных Rentals.

## Ученик делает

1. Создаёт Standard `DocType` `Equipment`.
2. Добавляет только свойства Equipment.
3. Для небольшого стабильного типа использует `Select`, а не отдельный справочник.
4. Выбирает стратегию `name` и объясняет её.
5. Создаёт несколько записей.

## Механизмы

```text
Standard DocType
DocField
Select
naming
Form
List
```

## Результат

Equipment существует как самостоятельный `Document`, а простые свойства не превращены в лишние DocTypes.

## Проверка

Ученик должен:

- создать запись;
- открыть её повторно;
- найти через List;
- изменить отображаемое поле и объяснить, почему идентичность остаётся корректной;
- объяснить, почему `Equipment Type` пока не отдельный DocType.

## Архитектурный вывод

Не каждое существительное предметной области является отдельным DocType.

# 5. Этап 3 — смоделировать Customer

**Опорный узел:** `P03`.

**Покрывает:** `R02`, `D00` для Customer.

**Зависит от:** этапа 1.

## Требование

Один Customer может участвовать во многих Rentals и должен существовать независимо от них.

## Ученик делает

1. Создаёт Standard `DocType` `Customer`.
2. Добавляет минимальные необходимые поля.
3. Выбирает naming.
4. Создаёт несколько клиентов.

## Результат

Customer существует как самостоятельный `Document`.

## Проверка

Ученик объясняет, почему имя клиента нельзя просто копировать текстом в каждый Rental вместо настоящей связи.

## Архитектурный вывод

`Equipment` и `Customer` независимы друг от друга. Их можно создавать в любом порядке.

# 6. Этап 4 — собрать Rental как композицию Documents

**Опорный узел:** `P04`.

**Покрывает:** `R03`, `R04`, `R05`, `D00` для Rental.

**Зависит от:** этапов 2 и 3.

## Требование

Одна операция проката должна:

- иметь собственную идентичность;
- ссылаться на одного существующего Customer;
- содержать несколько единиц Equipment;
- хранить строки как состав одной операции.

## Ученик делает

1. Создаёт Standard `DocType` `Rental`.
2. Создаёт `Rental Item` как `Child DocType`.
3. Добавляет в Rental `Link → Customer`.
4. Добавляет `Table → Rental Item`.
5. В `Rental Item` добавляет `Link → Equipment`.
6. Выбирает naming для Rental.
7. Создаёт первый реальный Rental.

## Механизмы

```text
DocType
Child DocType
Table
Link
naming
```

## Результат

```text
Rental
├── Customer [Link]
└── Rental Item [Table]
     └── Equipment [Link]
```

## Проверка

Создать Rental минимум с двумя Equipment и объяснить:

- почему Customer — `Link`;
- почему Equipment — `Link`;
- почему `Rental Item` — Child DocType;
- почему строка не является самостоятельной карточкой;
- какое требование заставило бы пересмотреть эту модель.

## Архитектурный вывод

Здесь собирается центральная модель Frappe: самостоятельные Documents, ссылки и состав родительского Document.

```text
business status ≠ Workflow ≠ docstatus
```

# 8. Этап 5B — пройти вертикальный сценарий через Desk

**Опорный узел:** `P06`.

**Покрывает:** `R16`.

**Зависит от:** этапа 4. После 5A проходить удобнее, но архитектурной зависимости нет.

## Требование

Оператор должен работать с приложением без собственного frontend.

## Ученик делает

Через стандартный Desk:

1. создаёт Equipment;
2. создаёт Customer;
3. создаёт Rental;
4. выбирает Customer через Link;
5. добавляет Equipment;
6. сохраняет Rental;
7. находит Rental в List;
8. открывает его повторно.

## Механизмы

```text
Desk
Form
List
Link control
Child Table UI
filters
```

## Результат

Первая вертикально рабочая версия приложения без собственного UI.

## Проверка

Сценарий проходит без ручного SQL, прямой работы с БД и собственного SPA.

## Архитектурный вывод

Стандартный Desk — нормальный UI по умолчанию для обычной административной работы.

# 9. Этап 5C — защитить инварианты одного Rental

**Опорный узел:** `P07`.

**Покрывает:** `R09`, `R10`.

**Зависит от:** этапа 4.

## Требования

Нельзя сохранить:

```text
end_date < start_date
одно Equipment дважды внутри одного Rental
```

## Ученик делает

1. Находит Python Controller Rental.
2. Реализует проверки в серверном lifecycle-пути `Document`.
3. Использует `validate()` там, где его семантика совпадает с требованием.
4. Клиентскую подсказку рассматривает только как дополнение UX.

## Механизмы

```text
Document Controller
validate()
серверная ошибка валидации
```

## Результат

Некорректный Rental невозможно сохранить обычным серверным путём.

## Проверка

Проверить оба ошибочных сценария через Form и затем через серверный тест/другой путь создания Document.

## Архитектурный вывод

```text
Client Script = удобство интерфейса
server path   = гарантия данных
```

# 10. Этап 5D — ввести базовые права

**Опорный узел:** `P09`.

**Покрывает:** `R13`.

**Зависит от:** этапа 4.

Это отдельная независимая ветка после появления реальных DocTypes.

## Требование

Оператор и менеджер должны иметь разные права.

## Ученик делает

1. Создаёт/использует роли `Rental Operator` и `Rental Manager`.
2. Настраивает `DocType Permissions` для Equipment, Customer и Rental.
3. Создаёт двух учебных пользователей.
4. Проверяет операции под каждой ролью.

## Механизмы

```text
User
Role
DocType Permissions
```

## Проверка

Под каждым пользователем проверить необходимые `Read/Create/Write/Delete` и другие реально используемые права.

## Не делать

- собственную ACL-таблицу;
- проверку роли только JavaScript-кодом;
- `ignore_permissions=True` как способ обойти неправильно настроенные permissions.

## Архитектурный вывод

Безопасность начинается со штатной permission model Frappe.

# 11. Этап 6 — проверить правило между несколькими Rentals

**Опорный узел:** `P08`.

**Покрывает:** `R11`.

**Зависит от:** этапов 5A и 5C.

## Требование

Одно Equipment нельзя выдать в двух Rentals на пересекающиеся активные периоды.

## Ученик делает

1. Формулирует правило пересечения периодов.
2. Определяет, какие статусы участвуют в проверке.
3. В серверной логике Rental читает другие Rentals через штатный Query/Database API.
4. Блокирует последовательное создание конфликтующей записи.

## Механизмы

```text
Controller
Database / Query API
Document lifecycle
```

## Проверка

Создать:

1. корректный активный Rental;
2. второй Rental с тем же Equipment и пересекающимся периодом;
3. второй Rental с непересекающимся периодом.

Второй сценарий должен блокироваться, третий — проходить.

## Обязательная граница

Этот этап **не объявляется полноценной concurrency-защитой**. Параллельные транзакции могут потребовать отдельной стратегии блокировок/изоляции/резервирования.

## Архитектурный вывод

Сложнее запрос не означает автоматически, что нужен Service. Сначала определяется владелец предметного правила.

# 12. Этап 7 — закрепить собственные контракты тестами

**Опорный узел:** `P10`.

**Покрывает:** `R23`.

**Зависит от:** этапов 6 и 5D.

## Требование

Изменения приложения не должны незаметно сломать собственные правила и permissions.

## Ученик делает

Создаёт минимальный набор автоматических тестов:

```text
валидный Rental сохраняется
невалидный период отвергается
дублирующее Equipment отвергается
пересекающийся Rental отвергается
роль без нужного права не выполняет запрещённую операцию
```

## Механизмы

```text
Frappe test runner
FrappeTestCase / штатная тестовая база
```

## Не тестировать ради количества

```text
Link вообще работает
frappe.get_doc вообще загружает Document
Form вообще существует
```

## Проверка

Намеренно сломать одно собственное правило и увидеть падение соответствующего теста.

## Архитектурный вывод

Тестируется добавленная нами ответственность, а не Framework как таковой.

# 13. Этап 8 — провести аудит доставки состояния App

**Опорный узел:** `P11`.

**Покрывает:** `R21`, `R22`.

**Зависит от:** этапов 6 и 5D.

## Требование

Обязательная модель не должна существовать только потому, что её однажды накликали на текущем dev-site.

## Ученик делает

Для каждого обязательного элемента определяет владельца состояния:

```text
Standard DocType → App source / JSON
Controller       → App source
обязательная Role/configuration → штатный переносимый механизм, если требуется
Site-local configuration → остаётся Site-local
изменение существующих данных → patch только при реальной необходимости
```

Проверяет изменения через `bench migrate` на существующем учебном Site.

## Проверка

В репозитории можно указать источник каждого обязательного элемента; нет обязательного ручного SQL и скрытого списка действий после установки.

## Архитектурный вывод

Работающий dev-site ещё не доказывает воспроизводимость App.

# 14. Этап 9 — чистая установка и финальная приёмка

**Опорный узел:** `P12`.

**Покрывает:** `R24`.

**Зависит от:** этапов 5B, 7 и 8.

## Вход

Есть:

```text
рабочий пользовательский сценарий
серверные правила
permissions
автоматические тесты
проверенная доставка состояния App
```

## Требование

Приложение должно восстанавливаться на новом совместимом Site из исходников и штатных механизмов Frappe.

## Ученик делает

1. Создаёт новый чистый Site.
2. Устанавливает учебный App.
3. Выполняет `migrate`.
4. Запускает тесты.
5. Создаёт минимальные пользовательские данные.
6. Проходит вертикальный сценарий проката.

## Финальный критерий

```text
чистый совместимый Frappe Site
+ учебный App из Git
+ install-app
+ migrate
+ tests
+ основной пользовательский сценарий
= практикум CORE пройден
```

## Приёмка провалена, если

- обязательный DocType отсутствует;
- требуются неизвестные ручные изменения БД;
- обязательная конфигурация осталась только на исходном dev-site;
- тесты не проходят;
- основной Rental нельзя оформить штатным путём;
- права отличаются от ожидаемых;
- для запуска требуется вручную править Frappe core.

## Архитектурный вывод

Воспроизводимость является частью архитектуры, а не финальной косметической операцией.

# 15. Результат CORE

После этапа 9 ученик не обязан «знать все функции Frappe».

Он должен уметь самостоятельно пройти базовую цепочку:

```text
требование
→ ответственность
→ DocType / Field / Link / Child / permissions / lifecycle
→ штатный UI
→ собственная серверная логика только для новой ответственности
→ tests
→ migrate
→ clean install
```

Это и является результатом базового практикума.

# 16. NEXT — естественные необязательные продолжения

Каждая ветка подключается только после CORE-модели и только при принятом требовании.

## N01. Rental Settings

**Основание:** `R07`.

```text
одна реальная конфигурация на Site
→ Single DocType
```

Single не добавляется только ради знакомства с механизмом.

## N02. История, комментарии и файлы

**Основание:** `R12`.

```text
Comment
File / Attach
Track Changes / Version
```

Собственные `Rental Comment`, `Rental Attachment`, `Rental History` не создаются без другой семантики.

## N03. Права на отдельные поля

**Основание:** `R14`.

При реальном чувствительном поле — `Permission Level`.

## N04. Назначение работы

**Основание:** `R15`.

При реальной очереди работы — `Assignment / ToDo`. Рабочее назначение и исторический предметный «ответственный» сначала различаются по смыслу.

## N05. Workspace

**Основание:** `R17`.

Добавляется только если обычной навигации недостаточно.

## N06. Calendar

**Основание:** `R18`.

Используется как представление существующих Rentals, а не повод создавать новую сущность.

## N07. Print Format

**Основание:** `R19`.

При необходимости акта выдачи сначала используется штатный `Print Format`.

## N08. Report Builder

**Основание:** `R20`.

Для простого реестра сначала проверяется `Report Builder`. Query/Script Report требуют отдельного требования.

# 17. GATE — условные архитектурные развилки

Каждый gate начинается с нового бизнес-требования.

## G01. Появилось подтверждение менеджером

**Основание:** `D01`.

```text
состояния + переходы + роли
→ кандидат на Workflow
```

## G02. Выдача стала фиксируемым транзакционным фактом

**Основание:** `D02`.

```text
Draft → Submitted → Cancelled
→ кандидат на Is Submittable / docstatus
```

`Returned` сам по себе не является основанием для submit.

## G03. Equipment Type стал самостоятельной сущностью

**Основание:** `D03`.

```text
Select
→ пересмотр модели
→ Equipment Type DocType + Link
```

При существующих данных отдельно решается миграция.

## G04. Появилась внешняя заявка

**Основание:** `D04`.

Сначала решается модель:

```text
это Rental?
или самостоятельный Rental Request?
```

Только затем проверяется `Web Form`.

## G05. Появилось уведомление о сроке

**Основание:** `D05`.

Сначала проверяется `Notification`. Scheduler/background job появляется только при более сложном требовании.

### Отдельная миграционная развилка: naming пришлось изменить

Первичный выбор `name` относится к CORE (`D00`). Если после появления ссылок стратегия идентичности должна измениться, это уже отдельная миграционная задача, а не обычная настройка формы.

# 18. EXT — интеграционные продолжения

## X01. Обычный внутренний CRUD

**Основание:** `E01`.

Сначала используется штатный Document REST API.

## X02. Команда «вернуть прокат»

**Основание:** `E02`.

При настоящей командной семантике используется метод Document или whitelisted method с явным контрактом.

## X03. Исходящее событие

**Основание:** `E03`.

Для простого HTTP-события сначала проверяется `Webhook`. Integration service появляется при требованиях повторов, сверки, идемпотентности и сложного преобразования.

# 20. Критерий качества этапа

Перед превращением этапа в подробную инструкцию проверяется:

```text
1. Есть ли реальное входное состояние?
2. Понятно ли требование обычным языком?
3. Названа ли ответственность?
4. Выбран ли первый штатный механизм Frappe?
5. Объяснено ли совпадение его смысла с задачей?
6. Указана ли граница решения?
7. Есть ли наблюдаемый результат?
8. Можно ли проверить результат руками?
9. Не появился ли новый DocType/Service/API ради демонстрации?
10. Не превращён ли удобный порядок в ложную архитектурную зависимость?
```

# 21. Следующий документ

После согласования дорожной карты готовится **спецификация практических этапов**.

Для каждого CORE-этапа она должна содержать:

- точное начальное состояние;
- действия в интерфейсе и консоли;
- конкретные поля и настройки;
- ожидаемые результаты;
- контрольные данные;
- команды проверки;
- типовые ошибки новичка;
- критерий `готово / не готово`.

Только после этой спецификации пишутся пошаговые инструкции для ученика.
