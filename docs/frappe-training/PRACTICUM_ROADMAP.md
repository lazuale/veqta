# Дорожная карта учебного практикума Frappe

Статус: **черновик для согласования**.

Продолжает:

- [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md);
- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md);
- [`STAGE_DEPENDENCY_GRAPH.md`](STAGE_DEPENDENCY_GRAPH.md).

Дорожная карта не является каталогом возможностей Frappe и не фиксирует количество уроков. Она превращает граф зависимостей в последовательность законченных практических этапов.

Каждый этап описывается одинаково:

```text
входное состояние
→ реальное требование
→ действия ученика
→ штатный механизм Frappe
→ наблюдаемый результат
→ проверка
→ архитектурный вывод
```

Если результат предыдущего этапа не принят, следующий зависимый этап не начинается.

---

# 1. Что является обязательным маршрутом

CORE-маршрут строится только из узлов `P00–P12` графа зависимостей.

```text
Среда
  ↓
App / Site / Module
  ↓
Equipment + Customer
  ↓
Rental + Rental Item + Link
  ↓
┌──────────────┬──────────────┬──────────────┐
│ status       │ Form / List  │ invariants   │
│              │              │              │
└──────┬───────┴──────────────┴──────┬───────┘
       │                              │
       └────→ cross-document rule ←───┘

Rental model ───────────────→ Roles / Permissions

cross-document rule + permissions
        ↓
   tests + delivery audit
        ↓
     clean install
```

`NEXT`, `GATE` и `EXT` не включаются автоматически. Они описаны отдельно после CORE.

# 2. Этап 0 — подготовить учебную среду

**Опорный узел:** `P00`.

## Вход

Чистая рабочая машина/WSL-среда, на которой ещё нет учебного приложения.

## Требование

Нужна совместимая среда Frappe v16, в которой изменения можно создавать как часть App и сохранять в Git.

## Ученик делает

1. Проверяет установленный Bench и версию Frappe.
2. Создаёт или использует отдельный учебный Site.
3. Включает developer mode там, где он необходим для Standard DocType.
4. Проверяет доступ к Git.
5. Убеждается, что Site открывается и Bench-команды работают.

## Механизмы

```text
Bench
Site
developer mode
Git
```

## Результат

Среда готова к созданию настоящего Frappe App.

## Проверка

Ученик должен уметь показать:

- какой Bench используется;
- какой Site учебный;
- какая версия Frappe установлена;
- где будут находиться исходники App;
- что Site работает.

## Архитектурный вывод

`Bench` — среда управления, а не предметный слой приложения.

## Не включать

Production deployment, reverse proxy, TLS, резервное копирование, hardening и эксплуатацию сервера. Это отдельная дисциплина.

# 3. Этап 1 — создать границу учебного App

**Опорный узел:** `P01`.

**Зависит от:** этапа 0.

## Вход

Рабочий Bench и учебный Site.

## Требование

Учебная предметная модель должна принадлежать отдельному устанавливаемому App, а не быть набором случайных локальных настроек Site.

## Ученик делает

1. Создаёт новый нейтральный App практикума.
2. Устанавливает его на учебный Site.
3. Проверяет структуру App.
4. Создаёт/проверяет Module для учебной предметной области.
5. Добавляет исходники App в Git.

## Механизмы

```text
App
Site
Module
Git
```

## Результат

```text
App существует в исходниках
App установлен на Site
Module принадлежит App
```

## Проверка

Ученик без подсказки объясняет разницу:

```text
Bench  ≠ Site
Site   ≠ App
App    ≠ Module
Module ≠ отдельное приложение
```

## Архитектурный вывод

Граница установки и исходного кода определяется App. Site является экземпляром, а Module — группировкой внутри App.

# 4. Этап 2 — смоделировать Equipment

**Опорный узел:** `P02`.

**Покрывает:** `R01`, `R06`, часть `D00`.

**Зависит от:** этапа 1.

## Вход

Пустой учебный App.

## Требование

Оборудование существует независимо от конкретной выдачи и должно переиспользоваться в разных Rentals.

## Ученик делает

1. Создаёт Standard `DocType` `Equipment` в учебном App.
2. Добавляет только свойства, которые действительно принадлежат Equipment.
3. Для небольшого стабильного типа оборудования использует `Select`, а не отдельный справочник.
4. Выбирает стратегию `name` и объясняет её.
5. Создаёт несколько реальных записей.

## Механизмы

```text
Standard DocType
DocField
Select
naming
Form
List
```

## Результат

Equipment существует как самостоятельный `Document`, а простые свойства не превращены в лишние DocTypes.

## Проверка

Ученик должен:

- создать запись;
- открыть её повторно;
- найти через List;
- изменить отображаемое поле и объяснить, почему идентичность записи остаётся корректной;
- объяснить, почему `Equipment Type` пока не отдельный DocType.

## Архитектурный вывод

Не каждое существительное предметной области является отдельным DocType.

# 5. Этап 3 — смоделировать Customer

**Опорный узел:** `P03`.

**Покрывает:** `R02`, часть `D00`.

**Зависит от:** этапа 1.

## Вход

Учебный App уже существует.

## Требование

Один Customer может участвовать во многих Rentals и должен существовать независимо от них.

## Ученик делает

1. Создаёт Standard `DocType` `Customer`.
2. Добавляет минимальные необходимые поля.
3. Выбирает стратегию naming.
4. Создаёт несколько клиентов.

## Результат

Customer существует как самостоятельный `Document`.

## Проверка

Ученик объясняет, почему имя клиента нельзя просто копировать текстом в каждый Rental вместо настоящей ссылки.

## Архитектурный вывод

`Equipment` и `Customer` независимы друг от друга. Их можно создавать в любом порядке; дорожная карта не превращает это в искусственную зависимость.

# 6. Этап 4 — собрать Rental как композицию Documents

**Опорный узел:** `P04`.

**Покрывает:** `R03`, `R04`, `R05`, часть `D00`.

**Зависит от:** этапов 2 и 3.

## Вход

Есть самостоятельные `Equipment` и `Customer`.

## Требование

Одна операция проката должна:

- иметь собственную идентичность;
- ссылаться на одного существующего Customer;
- содержать несколько единиц Equipment;
- хранить строки как состав одной операции.

## Ученик делает

1. Создаёт Standard `DocType` `Rental`.
2. Создаёт `Rental Item` как `Child DocType`.
3. Добавляет в Rental `Link → Customer`.
4. Добавляет в Rental поле `Table → Rental Item`.
5. В `Rental Item` добавляет `Link → Equipment`.
6. Выбирает naming для Rental.
7. Создаёт первый реальный Rental.

## Механизмы

```text
DocType
Child DocType
Table
Link
naming
```

## Результат

```text
Rental
├── Customer [Link]
└── Rental Item [Table]
     └── Equipment [Link]
```

Один Rental содержит несколько существующих Equipment и ссылается на существующего Customer.

## Проверка

Ученик должен создать Rental с минимум двумя Equipment и затем объяснить:

- почему Customer — `Link`;
- почему Equipment — `Link`;
- почему `Rental Item` — Child DocType;
- почему строка не является самостоятельной карточкой;
- в каком будущем требовании `Rental Item` пришлось бы пересмотреть как обычный DocType.

## Архитектурный вывод

Здесь впервые собирается центральная модель Frappe: самостоятельные Documents, ссылки и состав родительского Document.

# 7. Этап 5A — добавить предметное состояние

**Опорный узел:** `P05`.

**Покрывает:** `R08`.

**Зависит от:** этапа 4.

Этот этап является одной из независимых веток после появления Rental.

## Требование

Пользователю нужно различать рабочее состояние проката.

## Ученик делает

Добавляет обычное поле `status`, например:

```text
Planned
Active
Returned
```

## Механизм

`Select` как предметное поле.

## Что намеренно не используется

```text
Workflow
Is Submittable
отдельный Rental Status DocType
docstatus как рабочий status
```

## Результат

Rental имеет понятное бизнес-состояние.

## Проверка

Создать Rentals в разных состояниях и отфильтровать их в List.

## Архитектурный вывод

```text
business status ≠ Workflow ≠ docstatus
```

Наличие нескольких состояний не создаёт автоматически Workflow.

# 8. Этап 5B — пройти вертикальный сценарий через Desk

**Опорный узел:** `P06`.

**Покрывает:** `R16`.

**Зависит от:** этапа 4. Практически удобно проходить после 5A, но это не жёсткая архитектурная зависимость.

## Требование

Оператор должен работать с приложением без собственного frontend.

## Ученик делает

Выполняет полный сценарий только через стандартный Desk:

1. создаёт Equipment;
2. создаёт Customer;
3. создаёт Rental;
4. выбирает Customer через Link;
5. добавляет несколько строк Equipment;
6. сохраняет Rental;
7. находит Rental в List;
8. открывает его повторно.

## Механизмы

```text
Desk
Form
List
Link control
Child Table UI
filters
```

## Результат

Получена первая вертикально рабочая версия приложения без собственного UI.

## Проверка

Сценарий должен полностью проходить без ручного SQL, прямой работы с БД и собственного SPA.

## Архитектурный вывод

Стандартный Desk — нормальный UI по умолчанию для обычной административной работы. UI следует за моделью, а не определяет её.

# 9. Этап 5C — защитить инварианты одного Rental

**Опорный узел:** `P07`.

**Покрывает:** `R09`, `R10`.

**Зависит от:** этапа 4.

## Требования

Нельзя сохранить:

```text
end_date < start_date
один Equipment дважды внутри одного Rental
```

## Ученик делает

1. Находит Python Controller Rental.
2. Реализует проверки в серверном lifecycle-пути `Document`.
3. Использует `validate()` там, где семантика совпадает с требованием.
4. При желании добавляет раннюю клиентскую подсказку, но не переносит гарантию только в браузер.

## Механизмы

```text
Document Controller
validate()
frappe.throw / ValidationError-путь
```

## Результат

Некорректный Rental невозможно сохранить обычным серверным путём.

## Проверка

Проверить оба ошибочных сценария через Form и затем через серверный тест/другой путь создания Document.

## Архитектурный вывод

```text
Client Script = удобство интерфейса
Controller/server path = гарантия данных
```

# 10. Этап 5D — ввести базовые права

**Опорный узел:** `P09`.

**Покрывает:** `R13`.

**Зависит от:** этапа 4.

Это отдельная независимая ветка после появления реальных DocTypes.

## Требование

Оператор и менеджер должны иметь разные права на работу с приложением.

## Ученик делает

1. Создаёт/использует роли `Rental Operator` и `Rental Manager`.
2. Настраивает `DocType Permissions` для Equipment, Customer и Rental.
3. Создаёт двух учебных пользователей.
4. Проверяет действия под каждой ролью.

## Механизмы

```text
User
Role
DocType Permissions
```

## Результат

Разные пользователи действительно получают разные серверные права на Documents.

## Проверка

Под каждым пользователем проверить минимум:

```text
Read
Create
Write
Delete
Report (если используется)
```

## Не делать

- собственную ACL-таблицу;
- проверку роли только JavaScript-кодом;
- `ignore_permissions=True` как способ «починить» неправильную модель прав.

## Архитектурный вывод

Проектирование безопасности начинается со штатной permission model Frappe.

# 11. Этап 6 — проверить правило между несколькими Rentals

**Опорный узел:** `P08`.

**Покрывает:** `R11`.

**Зависит от:** этапов 5A и 5C.

## Вход

Rental имеет предметный status и серверные инварианты одного Document.

## Требование

Одно Equipment нельзя выдать в двух Rentals на пересекающиеся активные периоды.

## Ученик делает

1. Формулирует точное правило пересечения периодов.
2. Определяет, какие статусы участвуют в проверке.
3. В серверной логике Rental читает другие Rentals через штатный Query/Database API.
4. Блокирует последовательное создание конфликтующей записи.

## Механизмы

```text
Controller
Database / Query API
Document lifecycle
```

## Результат

В обычном последовательном сценарии конфликтующий Rental не сохраняется.

## Проверка

Создать:

1. корректный активный Rental;
2. второй Rental с тем же Equipment и пересекающимся периодом;
3. второй Rental с непересекающимся периодом.

Ожидается: второй сценарий блокируется, третий проходит.

## Обязательная граница

Этот этап **не объявляется полноценной concurrency-защитой**. Две параллельные транзакции могут потребовать отдельной стратегии блокировок/изоляции/резервирования.

## Архитектурный вывод

Сложнее запрос ≠ автоматически нужен Service. Сначала определяется владелец предметного правила.

# 12. Этап 7 — закрепить собственные контракты тестами

**Опорный узел:** `P10`.

**Покрывает:** `R23`.

**Зависит от:** этапов 6 и 5D.

## Требование

Изменения приложения не должны незаметно сломать собственные бизнес-правила и permissions.

## Ученик делает

Создаёт минимальный набор автоматических тестов для собственных контрактов:

```text
валидный Rental сохраняется
невалидный период отвергается
дублирующее Equipment отвергается
пересекающийся Rental отвергается
роль без нужного права не выполняет запрещённую операцию
```

## Механизмы

```text
Frappe test runner
FrappeTestCase / штатная тестовая база
```

## Не тестировать ради количества

```text
Link field вообще работает
frappe.get_doc вообще загружает Document
Frappe Form вообще существует
```

Это контракты Framework, а не учебного App.

## Результат

Критические собственные правила защищены воспроизводимыми тестами.

## Проверка

Намеренно сломать одну проверку и убедиться, что соответствующий тест падает.

## Архитектурный вывод

Тестируется добавленная нами ответственность, а не Framework как таковой.

---

# 13. Этап 8 — провести аудит доставки состояния App

**Опорный узел:** `P11`.

**Покрывает:** `R21`, `R22`.

**Зависит от:** этапов 6 и 5D.

## Требование

Обязательная модель не должна существовать только потому, что её однажды накликали на текущем dev-site.

## Ученик делает

Для каждого обязательного элемента определяет владельца состояния:

```text
Standard DocType → App source / JSON
Controller       → App source
обязательная Role/configuration → штатный переносимый механизм, если требуется
Site-local configuration → остаётся Site-local
изменение существующих данных → patch только при реальной необходимости
```

Проверяет изменения через `bench migrate` на уже существующем учебном Site.

## Результат

Есть явный ответ, что именно восстановится из App, а что является локальной конфигурацией Site.

## Проверка

В репозитории можно указать источник каждого обязательного элемента; нет обязательного ручного SQL и скрытого списка действий «после установки накликать ещё десять настроек».

## Архитектурный вывод

Работающий dev-site ещё не доказывает воспроизводимость приложения.

---

# 14. Этап 9 — чистая установка и финальная приёмка

**Опорный узел:** `P12`.

**Покрывает:** `R24`.

**Зависит от:** этапов 5B, 7 и 8.

## Вход

Есть:

```text
рабочий пользовательский сценарий
серверные правила\permissions
автоматические тесты
проверенная доставка состояния App
```

## Требование

Приложение должно восстанавливаться на новом совместимом Site из исходников и штатных механизмов Frappe.

## Ученик делает

1. Создаёт новый чистый Site.
2. Устанавливает учебный App.
3. Выполняет `migrate`.
4. Запускает тесты.
5. Создаёт минимальные пользовательские данные.
6. Проходит вертикальный сценарий проката.

## Финальный критерий

```text
чистый совместимый Frappe Site
+ учебный App из Git
+ install-app
+ migrate
+ tests
+ основной пользовательский сценарий
= практикум CORE пройден
```

## Приёмка провалена, если

- обязательный DocType отсутствует;
- требуются неизвестные ручные изменения БД;
- обязательная конфигурация осталась только на исходном dev-site;
- тесты не проходят;
- основной Rental нельзя оформить штатным путём;
- права отличаются от ожидаемых;
- для запуска требуется править Frappe core вручную.

## Архитектурный вывод

Воспроизводимость является частью архитектуры, а не финальной косметической операцией.

---

# 15. Что получается после CORE

После этапа 9 ученик не «знает все функции Frappe».

Он должен уметь самостоятельно пройти базовую архитектурную цепочку:

```text
требование
→ ответственность
→ DocType / Field / Link / Child / permissions / lifecycle
→ штатный UI
→ собственная серверная логика только там, где появилась новая ответственность
→ tests
→ migrate
→ clean install
```

Это и является результатом базового практикума.

# 16. NEXT — естественные необязательные продолжения

Эти ветки подключаются только после CORE-модели и только если принято соответствующее требование.

## N01. Rental Settings

**Основание:** `R07`.

Если появляется единая настройка для всего Site, например default rental duration:

```text
одна конфигурация на Site
→ Single DocType
```

Нельзя добавлять Single только ради знакомства с типом DocType.

## N02. История, комментарии и файлы

**Основание:** `R12`.

Если пользователю действительно нужны обсуждение, вложения и обычная история:

```text
Comment
File / Attach
Track Changes / Version
```

Не создаются собственные `Rental Comment`, `Rental Attachment`, `Rental History` без другого предметного смысла.

## N03. Права на отдельные поля

**Основание:** `R14`.

Если появляется чувствительное поле:

```text
Permission Level
```

Если такого поля нет, `permlevel` не изучается искусственно.

## N04. Назначение работы

**Основание:** `R15`.

Если конкретный Rental нужно назначать сотруднику как рабочую задачу:

```text
Assignment / ToDo
```

Перед добавлением отдельного поля «ответственный» нужно различить рабочее назначение и исторический предметный факт.

## N05. Workspace

**Основание:** `R17`.

Если обычной навигации недостаточно и нужна рабочая точка входа:

```text
Workspace
```

## N06. Calendar

**Основание:** `R18`.

Если календарное представление реально помогает работе с периодами Rental, используется представление существующих Documents. Новая сущность ради календаря не создаётся.

## N07. Print Format

**Основание:** `R19`.

Если нужен акт выдачи, сначала используется штатный `Print Format`.

## N08. Report Builder

**Основание:** `R20`.

Если нужен простой реестр/отчёт, сначала проверяется `Report Builder`. `Query Report` и `Script Report` требуют отдельного требования.

# 17. GATE — архитектурные развилки

Это не обязательные продолжения. Каждый gate начинается с нового бизнес-требования.

## G00. Naming изменился

Если первоначальная стратегия `name` перестала соответствовать модели, решение пересматривается осознанно. Смена идентичности после появления ссылок рассматривается как миграционная задача, а не косметика.

## G01. Появилось подтверждение менеджером

**Основание:** `D01`.

```text
состояния + переходы + роли
→ кандидат на Workflow
```

Сначала доказывается необходимость управляемого перехода; затем настраивается Workflow.

## G02. Выдача стала фиксируемым транзакционным фактом

**Основание:** `D02`.

```text
Draft → Submitted → Cancelled
→ кандидат на Is Submittable / docstatus
```

`Returned` сам по себе не является основанием для submit.

## G03. Equipment Type стал самостоятельной сущностью

**Основание:** `D03`.

Если у типа появились собственные атрибуты и управление:

```text
Select
→ пересмотр модели
→ Equipment Type DocType + Link
```

При наличии существующих данных отдельно решается миграция.

## G04. Появилась внешняя заявка

**Основание:** `D04`.

Сначала решается модель:

```text
это тот же Rental?
или самостоятельный Rental Request?
```

Только затем выбирается `Web Form` как способ ввода.

## G05. Появилось уведомление о сроке

**Основание:** `D05`.

Сначала проверяется `Notification`. Scheduler/background job появляется только если реальное требование сложнее штатной Notification.

# 18. EXT — интеграционные продолжения

## X01. Обычный внутренний CRUD

**Основание:** `E01`.

Сначала используется штатный Document REST API.

Не создаются собственные `/create`, `/read`, `/update`, `/delete`, если они только переименовывают встроенный CRUD.

## X02. Команда «вернуть прокат»

**Основание:** `E02`.

Если операция имеет собственную командную семантику и правила, используется метод Document или whitelisted method с явным контрактом.

## X03. Исходящее событие

**Основание:** `E03`.

Для простого HTTP-события сначала проверяется `Webhook`. Отдельный integration service появляется при требованиях повторов, сверки, идемпотентности и сложного преобразования.

# 19. Что не является этапом практикума само по себе

Следующие формулировки запрещены как самостоятельные этапы:

```text
«изучить DocType»
«изучить Link»
«изучить Child Table»
«изучить Workflow»
«изучить Server Script»
«изучить REST API»
«изучить Background Jobs»
```

Допустим только вариант, где механизм появляется как ответ на требование и заканчивается наблюдаемым работающим результатом.

# 20. Критерий качества дорожной карты

Перед превращением этапа в подробную практическую инструкцию проверяется:

```text
1. Есть ли реальное входное состояние?
2. Понятно ли требование обычным языком?
3. Названа ли ответственность?
4. Выбран ли первый штатный механизм Frappe?
5. Объяснено ли, почему его смысл совпадает с задачей?
6. Указана ли граница решения?
7. Есть ли наблюдаемый результат?
8. Можно ли проверить результат руками?
9. Не появился ли новый DocType/Service/API только ради демонстрации?
10. Не превращена ли удобная последовательность обучения в ложную архитектурную зависимость?
```

Если хотя бы на один из ключевых вопросов нет ответа, этап ещё не готов к написанию подробного практикума.
