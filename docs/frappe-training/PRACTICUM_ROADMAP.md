# Дорожная карта учебного практикума Frappe

Статус: **черновик для согласования**.

Продолжает:

- [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md);
- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md);
- [`STAGE_DEPENDENCY_GRAPH.md`](STAGE_DEPENDENCY_GRAPH.md).

Дорожная карта не является каталогом возможностей Frappe и не фиксирует количество уроков. Она превращает граф зависимостей в последовательность законченных практических этапов.

Каждый этап описывается одинаково:

```text
входное состояние
→ реальное требование
→ действия ученика
→ штатный механизм Frappe
→ наблюдаемый результат
→ проверка
→ архитектурный вывод
```

Если результат предыдущего этапа не принят, следующий зависимый этап не начинается.

Исполняемые инструкции CORE находятся в [`core/`](core/README.md).

---

# 1. Обязательный маршрут

CORE строится только из узлов `P00–P12` графа зависимостей.

```text
Среда
  ↓
App / Site / Module
  ↓
Equipment + Customer
  ↓
Rental + Rental Item + Link
  ↓
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ status       │ Form / List  │ invariants   │ permissions  │
└──────┬───────┴──────────────┴──────┬───────┴──────────────┘
       │                              │
       └────→ cross-document rule ←───┘

cross-document rule + permissions
        ↓
   tests + delivery audit
        ↓
     clean install
```

Naming не является отдельной необязательной веткой: стратегия `name` выбирается при создании каждого самостоятельного DocType.

`NEXT`, `GATE` и `EXT` не включаются автоматически. Они описаны отдельно после CORE.

# 2. Этап 0 — подготовить учебную среду

**Исполняемая инструкция:** [`core/S00_ENVIRONMENT.md`](core/S00_ENVIRONMENT.md).

**Опорный узел:** `P00`.

## Вход

Рабочая машина/WSL-среда без учебного приложения.

## Требование

Нужна совместимая среда Frappe v16, в которой изменения можно создавать как часть App и сохранять в Git.

## Ученик делает

1. Проверяет Bench и версию Frappe.
2. Создаёт или использует отдельный учебный Site.
3. Включает developer mode там, где он нужен для Standard DocType.
4. Проверяет Git.
5. Убеждается, что Site открывается и Bench-команды работают.

## Механизмы

```text
Bench
Site
developer mode
Git
```

## Результат

Среда готова к созданию настоящего Frappe App.

## Проверка

Ученик может показать:

- какой Bench используется;
- какой Site учебный;
- какая версия Frappe установлена;
- где будут находиться исходники App;
- что Site работает.

## Архитектурный вывод

`Bench` — среда управления, а не предметный слой приложения.

## Не включать

Production deployment, reverse proxy, TLS, резервное копирование, hardening и эксплуатацию сервера. Это отдельная дисциплина.

# 3. Этап 1 — создать границу учебного App

**Исполняемая инструкция:** [`core/S01_APP_AND_SITE.md`](core/S01_APP_AND_SITE.md).

**Опорный узел:** `P01`.

**Зависит от:** этапа 0.

## Требование

Учебная модель должна принадлежать отдельному устанавливаемому App, а не быть набором случайных локальных настроек Site.

## Ученик делает

1. Создаёт нейтральный App практикума.
2. Устанавливает его на учебный Site.
3. Проверяет структуру App.
4. Создаёт/проверяет Module учебной предметной области.
5. Добавляет исходники App в Git.

## Результат

```text
App существует в исходниках
App установлен на Site
Module принадлежит App
```

## Проверка

Ученик объясняет:

```text
Bench  ≠ Site
Site   ≠ App
App    ≠ Module
Module ≠ отдельное приложение
```

## Архитектурный вывод

App — граница установки и исходного кода. Site — экземпляр. Module — группировка внутри App.

# 4. Этап 2 — смоделировать Equipment

**Исполняемая инструкция:** [`core/S02_EQUIPMENT_DOCTYPE.md`](core/S02_EQUIPMENT_DOCTYPE.md).

**Опорный узел:** `P02`.

**Покрывает:** `R01`, `R06`, `D00` для Equipment.

**Зависит от:** этапа 1.

## Требование

Оборудование существует независимо от конкретной выдачи и переиспользуется в разных Rentals.

## Ученик делает

1. Создаёт Standard `DocType` `Equipment`.
2. Добавляет только свойства Equipment.
3. Для небольшого стабильного типа использует `Select`, а не отдельный справочник.
4. Выбирает стратегию `name` и объясняет её.
5. Создаёт несколько записей.

## Механизмы

```text
Standard DocType
DocField
Select
naming
Form
List
```

## Результат

Equipment существует как самостоятельный `Document`, а простые свойства не превращены в лишние DocTypes.

## Проверка

Ученик должен:

- создать запись;
- открыть её повторно;
- найти через List;
- изменить отображаемое поле и объяснить, почему идентичность остаётся корректной;
- объяснить, почему `Equipment Type` пока не отдельный DocType.

## Архитектурный вывод

Не каждое существительное предметной области является отдельным DocType.

# 5. Этап 3 — смоделировать Customer

**Опорный узел:** `P03`.

**Покрывает:** `R02`, `D00` для Customer.

**Зависит от:** этапа 1.

## Требование

Один Customer может участвовать во многих Rentals и должен существовать независимо от них.

## Ученик делает

1. Создаёт Standard `DocType` `Customer`.
2. Добавляет минимальные необходимые поля.
3. Выбирает naming.
4. Создаёт несколько клиентов.

## Результат

Customer существует как самостоятельный `Document`.

## Проверка

Ученик объясняет, почему имя клиента нельзя просто копировать текстом в каждый Rental вместо настоящей связи.

## Архитектурный вывод

`Equipment` и `Customer` независимы друг от друга. Их можно создавать в любом порядке.

# 6. Этап 4 — собрать Rental как композицию Documents

**Опорный узел:** `P04`.

**Покрывает:** `R03`, `R04`, `R05`, `D00` для Rental.

**Зависит от:** этапов 2 и 3.

## Требование

Одна операция проката должна:

- иметь собственную идентичность;
- ссылаться на одного существующего Customer;
- содержать несколько единиц Equipment;
- хранить строки как состав одной операции.

## Ученик делает

1. Создаёт Standard `DocType` `Rental`.
2. Создаёт `Rental Item` как `Child DocType`.
3. Добавляет в Rental `Link → Customer`.
4. Добавляет `Table → Rental Item`.
5. В `Rental Item` добавляет `Link → Equipment`.
6. Выбирает naming для Rental.
7. Создаёт первый реальный Rental.

## Механизмы

```text
DocType
Child DocType
Table
Link
naming
```

## Результат

```text
Rental
├── Customer [Link]
└── Rental Item [Table]
     └── Equipment [Link]
```

## Проверка

Создать Rental минимум с двумя Equipment и объяснить:

- почему Customer — `Link`;
- почему Equipment — `Link`;
- почему `Rental Item` — Child DocType;
- почему строка не является самостоятельной карточкой;
- какое требование заставило бы пересмотреть эту модель.

## Архитектурный вывод

Здесь собирается центральная модель Frappe: самостоятельные Documents, ссылки и состав родительского Document.

# 7. Этап 5A — добавить предметное состояние

**Опорный узел:** `P05`.

**Покрывает:** `R08`.

**Зависит от:** этапа 4.

Это одна из независимых веток после появления Rental.

## Требование

Пользователю нужно различать рабочее состояние проката.

## Ученик делает

Добавляет обычное поле `status`, например:

```text
Planned
Active
Returned
```

## Механизм

`Select` как предметное поле.

## Что намеренно не используется

```text
Workflow
Is Submittable
Rental Status DocType
docstatus как рабочий status
```

## Проверка

Создать Rentals в разных состояниях и отфильтровать их в List.

## Архитектурный вывод

```text
business status ≠ Workflow ≠ docstatus
```

# 8. Этап 5B — пройти вертикальный сценарий через Desk

**Опорный узел:** `P06`.

**Покрывает:** `R16`.

**Зависит от:** этапа 4. После 5A проходить удобнее, но архитектурной зависимости нет.

## Требование

Оператор должен работать с приложением без собственного frontend.

## Ученик делает

Через стандартный Desk:

1. создаёт Equipment;
2. создаёт Customer;
3. создаёт Rental;
4. выбирает Customer через Link;
5. добавляет Equipment;
6. сохраняет Rental;
7. находит Rental в List;
8. открывает его повторно.

## Механизмы

```text
Desk
Form
List
Link control
Child Table UI
filters
```

## Результат

Первая вертикально рабочая версия приложения без собственного UI.

## Проверка

Сценарий проходит без ручного SQL, прямой работы с БД и собственного SPA.

## Архитектурный вывод

Стандартный Desk — нормальный UI по умолчанию для обычной административной работы.

# 9. Этап 5C — защитить инварианты одного Rental

**Опорный узел:** `P07`.

**Покрывает:** `R09`, `R10`.

**Зависит от:** этапа 4.

## Требования

Нельзя сохранить:

```text
end_date < start_date
одно Equipment дважды внутри одного Rental
```

## Ученик делает

1. Находит Python Controller Rental.
2. Реализует проверки в серверном lifecycle-пути `Document`.
3. Использует `validate()` там, где его семантика совпадает с требованием.
4. Клиентскую подсказку рассматривает только как дополнение UX.

## Механизмы

```text
Document Controller
validate()
серверная ошибка валидации
```

## Результат

Некорректный Rental невозможно сохранить обычным серверным путём.

## Проверка

Проверить оба ошибочных сценария через Form и затем через серверный тест/другой путь создания Document.

## Архитектурный вывод

```text
Client Script = удобство интерфейса
server path   = гарантия данных
```

# 10. Этап 5D — ввести базовые права

**Опорный узел:** `P09`.

**Покрывает:** `R13`.

**Зависит от:** этапа 4.

Это отдельная независимая ветка после появления реальных DocTypes.

## Требование

Оператор и менеджер должны иметь разные права.

## Ученик делает

1. Создаёт/использует роли `Rental Operator` и `Rental Manager`.
2. Настраивает `DocType Permissions` для Equipment, Customer и Rental.
3. Создаёт двух учебных пользователей.
4. Проверяет операции под каждой ролью.

## Механизмы

```text
User
Role
DocType Permissions
```

## Проверка

Под каждой ролью проверяется реальная разрешённая и запрещённая операция, а не только видимость кнопки.

## Архитектурный вывод

UI не является границей безопасности; права принадлежат permission engine Frappe.

# 11. Этап 6 — защитить междокументный инвариант

**Опорный узел:** `P08`.

**Покрывает:** `R11`, `R12`.

**Зависит от:** этапов 5A и 5C.

## Требование

Одно Equipment не может одновременно находиться в двух пересекающихся Rentals в состоянии `Active`.

## Почему это новый класс задачи

Проверка уже не ограничивается текущим Document:

```text
текущий Rental
+
другие Rentals
+
их Rental Items
+
даты
+
status
```

## Ученик делает

1. Формулирует правило пересечения интервалов.
2. На сервере ищет конфликтующие Documents штатным DB/Document API.
3. Запрещает сохранение/активацию конфликта.
4. Не дублирует это как единственную Client Script проверку.

## Проверка

Минимум:

```text
Rental A Active: 01–05
Rental B Active: 04–07
одно Equipment
→ ошибка
```

И непересекающийся случай:

```text
Rental A Active: 01–05
Rental B Active: 06–07
→ допустимо
```

## Архитектурный вывод

Собственный код появляется потому, что появилась новая предметная ответственность, а не потому, что «после no-code должен идти code».

# 12. Этап 7 — зафиксировать контракты автоматическими тестами

**Опорный узел:** `P10`.

**Покрывает:** обязательные инварианты CORE.

**Зависит от:** этапов 5C, 5D и 6.

## Требование

Критические правила должны проверяться повторяемо без ручного прокликивания.

## Тестируем минимум

```text
валидный Rental сохраняется
end_date < start_date запрещён
дубликат Equipment в одном Rental запрещён
пересекающийся Active Rental запрещён
непересекающийся Rental разрешён
```

Permission-сценарии добавляются там, где они являются контрактом приложения и могут быть стабильно проверены.

## Механизм

Frappe test runner и Frappe-aware tests.

## Проверка

Тесты запускаются штатной командой Bench и проходят на учебном Site.

## Архитектурный вывод

Мы тестируем собственные контракты приложения, а не доказываем тестами, что Frappe вообще умеет сохранять Document.

---

# 13. Этап 8 — аудит владения и доставки состояния App

**Опорный узел:** `P11`.

**Зависит от:** сформированной модели и permissions.

## Требование

Всё обязательное состояние приложения должно быть понятно откуда берётся и как попадает на другой Site.

## Ученик классифицирует каждый элемент

```text
Standard metadata
source code
fixture/config
site-local customization
runtime/transaction data
```

## Проверка

Для каждого обязательного элемента ответить:

```text
кто владелец?
где source of truth?
как попадает на чистый Site?
```

Если ответ: «после установки надо ещё вручную накликать вот это обязательное поле», этап не принят.

## Архитектурный вывод

Воспроизводимость — часть архитектуры приложения, а не последняя DevOps-операция.

# 14. Этап 9 — чистая установка и финальная приёмка

**Опорный узел:** `P12`.

**Зависит от:** этапов 7 и 8.

## Требование

Нужно доказать, что приложение существует не только на том Site, где его разрабатывали.

## Ученик делает

1. Создаёт второй чистый совместимый Site.
2. Устанавливает `rental_training` из repository App.
3. Выполняет migrate.
4. Включает/подготавливает test environment штатным способом.
5. Запускает тесты.
6. Проходит основной пользовательский сценарий.

## Критерий

```text
чистый совместимый Frappe Site
+ repository rental_training
+ install-app
+ migrate
= обязательная структура приложения
```

После этого основные операции работают без ручного восстановления схемы через UI.

## Архитектурный вывод

Это главный доказательный тест архитектуры CORE.

---

# 15. Что CORE намеренно не добавляет автоматически

После CORE могут появляться дополнительные требования.

Они не являются продолжением курса по принципу «остались функции Frappe — надо их пройти».

Они подключаются отдельными ветками.

## NEXT

Практические продуктовые возможности:

```text
Notification
Report
Print Format
Web Form
REST
background job
scheduler
Single DocType
```

Каждая начинается с собственного требования и только после существования стабильного CORE.

## GATE

Механизмы, которые вводятся только при появлении соответствующей семантики:

```text
Workflow
Is Submittable / docstatus
User Permission
Share
Permission Type
```

## EXT

Специальные архитектурные расширения:

```text
foreign DocType customization
fixtures
exported customizations
doc_events
extend_doctype_class
override_doctype_class
custom API
```

Их нельзя тащить в базовый Rental без соответствующей задачи.

# 16. Финальный результат маршрута

После CORE ученик должен иметь не набор знакомых экранов, а работающую причинно-следственную модель:

```text
требование
    ↓
ответственность
    ↓
штатный механизм Frappe
    ↓
модель / правило / permission
    ↓
наблюдаемый сценарий
    ↓
автоматический контракт
    ↓
чистая установка
```

И уметь объяснить не только **как** сделать решение во Frappe, но и **почему** оно построено именно на этом штатном механизме.
