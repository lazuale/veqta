# Дорожная карта учебного практикума Frappe

Статус: **CORE-маршрут полностью написан; готов к финальному аудиту**.

Продолжает:

- [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md);
- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md);
- [`STAGE_DEPENDENCY_GRAPH.md`](STAGE_DEPENDENCY_GRAPH.md).

Дорожная карта не является каталогом возможностей Frappe и не фиксирует количество уроков. Она превращает граф зависимостей в последовательность законченных практических этапов.

Каждый этап описывается одинаково:

```text
входное состояние
→ реальное требование
→ действия ученика
→ штатный механизм Frappe
→ наблюдаемый результат
→ проверка
→ архитектурный вывод
```

Если результат предыдущего этапа не принят, следующий зависимый этап не начинается.

Исполняемые инструкции CORE находятся в [`core/`](core/README.md).

---

# 1. Обязательный маршрут

CORE строится только из узлов `P00–P12` графа зависимостей.

```text
Среда
  ↓
App / Site / Module
  ↓
Equipment + Customer
  ↓
Rental + Rental Item + Link + Table MultiSelect
  ↓
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ status       │ Form / List  │ invariants   │ permissions  │
└──────┬───────┴──────────────┴──────┬───────┴──────────────┘
       │                              │
       └────→ cross-document rule ←───┘

cross-document rule + permissions
        ↓
   tests + delivery audit
        ↓
     clean install
```

Naming не является отдельной необязательной веткой: стратегия `name` выбирается при создании каждого самостоятельного DocType.

`NEXT`, `GATE` и `EXT` не включаются автоматически. Они описаны отдельно после CORE.

# 2. Этап 0 — подготовить учебную среду

**Исполняемая инструкция:** [`core/S00_ENVIRONMENT.md`](core/S00_ENVIRONMENT.md).

**Опорный узел:** `P00`.

## Вход

Рабочая машина/WSL-среда без учебного приложения.

## Требование

Нужна совместимая среда Frappe v16, в которой изменения можно создавать как часть App и сохранять в Git.

## Ученик делает

1. Проверяет Bench и версию Frappe.
2. Создаёт или использует отдельный учебный Site.
3. Включает developer mode там, где он нужен для Standard DocType.
4. Проверяет Git.
5. Убеждается, что Site открывается и Bench-команды работают.

## Механизмы

```text
Bench
Site
developer mode
Git
```

## Результат

Среда готова к созданию настоящего Frappe App.

## Проверка

Ученик может показать:

- какой Bench используется;
- какой Site учебный;
- какая версия Frappe установлена;
- где будут находиться исходники App;
- что Site работает.

## Архитектурный вывод

`Bench` — среда управления, а не предметный слой приложения.

## Не включать

Production deployment, reverse proxy, TLS, резервное копирование, hardening и эксплуатацию сервера. Это отдельная дисциплина.

# 6. Этап 4 — собрать Rental как композицию Documents

**Исполняемая инструкция:** [`core/S04_RENTAL_COMPOSITION.md`](core/S04_RENTAL_COMPOSITION.md).

**Опорный узел:** `P04`.

**Покрывает:** `R03`, `R04`, `R05`, `D00` для Rental.

**Зависит от:** этапов 2 и 3.

## Требование

Одна операция проката должна:

- иметь собственную идентичность;
- ссылаться на одного существующего Customer;
- выбирать несколько существующих Equipment;
- хранить выбранный набор как часть одного Rental.

У строки связи пока нет собственных бизнес-атрибутов: она содержит только ссылку на Equipment.

## Ученик делает

1. Создаёт `Rental Item` как минимальный `Child DocType`.
2. Добавляет в `Rental Item` `Link → Equipment` и отмечает это Link-поле `In List View`.
3. Создаёт Standard `DocType` `Rental`.
4. Добавляет в Rental `Link → Customer`.
5. Добавляет даты периода.
6. Добавляет `Table MultiSelect → Rental Item`.
7. Выбирает naming для Rental.
8. Создаёт первый реальный Rental минимум с двумя Equipment.

## Механизмы

```text
DocType
Child DocType
Link
Table MultiSelect
Date
naming
```

## Почему не обычный Table

Текущее требование звучит как:

```text
выбрать несколько существующих Equipment
```

а `Rental Item` содержит только:

```text
equipment → Link → Equipment
```

Frappe предоставляет `Table MultiSelect` именно как комбинацию Link и child-table механизма для такого набора. Обычный `Table` станет естественнее, когда у строки появятся собственные атрибуты отношения — например цена, состояние при выдаче или дата фактического возврата конкретной позиции.

## Результат

```text
Rental
├── customer → Link → Customer
└── items    → Table MultiSelect → Rental Item
                                  └── equipment → Link → Equipment
```

## Проверка

Создать Rental минимум с двумя Equipment и объяснить:

- почему Customer — `Link`;
- почему Equipment — `Link`;
- зачем `Table MultiSelect` всё равно использует Child DocType;
- почему `Rental Item` не самостоятельная карточка;
- почему обычный `Table` пока был бы менее точным механизмом;
- какое новое требование заставит пересмотреть выбор.

## Архитектурный вывод

Здесь собирается центральная модель Frappe: самостоятельные Documents, живые Links и принадлежащий родителю набор связанных Documents без преждевременного усложнения строки отношения.

# 11. Этап 6 — защитить междокументный инвариант

**Исполняемая инструкция:** [`core/S06_ACTIVE_RENTAL_CONFLICT.md`](core/S06_ACTIVE_RENTAL_CONFLICT.md).

**Опорный узел:** `P08`.

**Покрывает:** `R11`.

**Зависит от:** этапов 5A и 5C.

## Требование

Одно Equipment не может одновременно находиться в двух пересекающихся Rentals в состоянии `Active`.

## Почему это новый класс задачи

Проверка уже не ограничивается текущим Document:

```text
текущий Rental
+
другие Rentals
+
их Rental Items
+
даты
+
status
```

## Ученик делает

1. Фиксирует включительную формулу пересечения дат.
2. На сервере находит другие Rentals с теми же Equipment штатным Database API.
3. Использует внутреннее чтение, которое не позволяет permission-filtering пользовательского List скрыть реальный конфликт.
4. Исключает текущий Rental при редактировании.
5. Запрещает сохранение/активацию конфликтующего Active Rental.
6. Проверяет правило через Desk и обычный `Document.insert()`.
7. Отдельно фиксирует, что последовательная `validate()`-проверка не равна полной concurrency/locking strategy.

## CORE-семантика

```text
Planned  → не блокирует
Active   → блокирует
Returned → не блокирует
```

Периоды конфликтуют, если:

```text
existing.start_date <= current.end_date
AND
existing.end_date >= current.start_date
```

## Проверка

Минимум:

```text
Active 10–12 + Active 11–13, same Equipment → ошибка
Active 10–12 + Active 12–14, same Equipment → ошибка
Active 10–12 + Active 13–14, same Equipment → допустимо
Planned overlap                             → допустимо
Planned → Active при конфликте              → ошибка
повторный save самого Active Rental         → допустимо
```

## Архитектурный вывод

`get_all()` внутри системного инварианта может быть осознанным выбором, но это не превращает его в замену permission-aware пользовательским запросам. И обычная cross-document validation не должна выдавать себя за доказанную стратегию конкурентного резервирования.

# 12. Этап 7 — зафиксировать контракты автоматическими тестами

**Исполняемая инструкция:** [`core/S07_AUTOMATED_CONTRACT_TESTS.md`](core/S07_AUTOMATED_CONTRACT_TESTS.md).

**Опорный узел:** `P10`.

**Покрывает:** `R23` и обязательные инварианты/permissions CORE.

**Зависит от:** этапов 5C, 5D и 6.

## Требование

Критические правила должны проверяться повторяемо без ручного прокликивания.

## Механизм

Для DB/Document/permission сценариев актуального Frappe v16 используется Frappe-aware integration test:

```python
from frappe.tests import IntegrationTestCase
```

и штатный Bench test runner.

## Тестируем минимум

```text
валидный Rental сохраняется
end_date < start_date запрещён
дубликат Equipment в одном Rental запрещён
пересекающийся Active Rental запрещён
общая граничная дата считается конфликтом
непересекающийся Active Rental разрешён
Planned overlap разрешён
self-save Active Rental разрешён
Operator не может создавать Equipment
Operator может create/write Rental и не может delete
Manager может CRUD Equipment
```

Тестовые Customer/Equipment/Users создаются самим test case и не зависят от вручную заполненного dev-site.

## Проверка

1. Полный App suite проходит через `bench --site ... run-tests --app rental_training`.
2. Ученик намеренно ломает одно собственное правило и получает красный test.
3. После восстановления правила suite снова зелёный.

## Архитектурный вывод

Мы тестируем собственные контракты приложения, а не доказываем тестами, что Frappe вообще умеет сохранять Document.

# 13. Этап 8 — аудит владения и доставки состояния App

**Исполняемая инструкция:** [`core/S08_APP_STATE_DELIVERY_AUDIT.md`](core/S08_APP_STATE_DELIVERY_AUDIT.md).

**Опорный узел:** `P11`.

**Покрывает:** `R21`, `R22`.

**Зависит от:** сформированной CORE-модели, permissions и этапа 7 как контрольной проверки поведения.

## Требование

Всё обязательное состояние приложения должно иметь понятного владельца, source of truth и штатный путь доставки на другой Site.

## Ученик строит delivery manifest

```text
Module                    → modules.txt
Standard DocTypes         → DocType JSON
fields/naming/default ACL → Standard metadata
V01/V02/V03               → rental.py
Role                      → hooks.py + fixtures/role.json
tests                     → test_rental.py

Users/business records    → Site database
developer_mode/allow_tests→ Site config
```

## Проверки

1. Все обязательные App-owned файлы находятся в Git.
2. Для CORE DocTypes отсутствует скрытая обязательная зависимость от `Custom Field`, `Property Setter` и `Custom DocPerm`.
3. `export-fixtures` повторно даёт тот же committed Role fixture и не оставляет необъяснённый Git diff.
4. Users и business Documents не экспортированы fixtures.
5. `bench migrate` проходит без ручного SQL и повторного накликивания обязательной модели.
6. После migrate автоматические tests остаются зелёными.
7. App Git снова clean.

## Почему patch пока не нужен

CORE формирует первый baseline приложения. Dev/test Site, на котором модель менялась во время обучения, не объявлен поддерживаемой предыдущей production-версией. Поэтому patch не создаётся только ради демонстрации механизма.

Patch становится обязательным, когда реальная новая версия требует одноразово преобразовать существующие данные поддерживаемой старой версии.

## Архитектурный вывод

Воспроизводимость — часть архитектуры App. `migrate`, fixtures и patches имеют разные ответственности и не заменяют друг друга.

# 14. Этап 9 — чистая установка и финальная приёмка

**Опорный узел:** `P12`.

**Покрывает:** `R24`.

**Зависит от:** этапов 7 и 8.

## Требование

Нужно доказать, что приложение существует не только на dev-site, где его разрабатывали.

## Ученик делает

1. Фиксирует clean Git и commit SHA текущего `rental_training`.
2. Убеждается, что `developer_mode` не включён глобально для всего Bench.
3. Создаёт новый `rental-acceptance.localhost` без `--install-app`.
4. Доказывает, что до установки на Site есть только `frappe`, а CORE DocTypes/Role отсутствуют.
5. Устанавливает `rental_training` штатным `install-app` без developer mode.
6. Проверяет Module, четыре Standard DocTypes, Role fixtures, default permissions и отсутствие скрытых Site-customizations.
7. Выполняет `migrate` как обычный update-path.
8. Включает только Site-local `allow_tests` и запускает полный App suite.
9. Создаёт Site-local Operator/Manager Users после установки.
10. Под Manager проходит `Equipment → Customer → Rental`.
11. Под Operator проверяет разрешённые/запрещённые действия и реальный V03 через Desk.
12. Повторно запускает tests после появления обычных business Documents.
13. Проверяет, что App Git остался clean.

## Критерий

```text
чистый совместимый Frappe Site
+ committed rental_training
+ install-app без developer_mode
+ migrate
+ tests
+ реальный Desk/permission scenario
+ Git clean
= воспроизводимый CORE
```

## Что этот этап не доказывает

S09 проверяет воспроизводимость App на новом Site того же совместимого Bench. Это не production deployment test и не проверка reverse proxy, TLS, backup, HA, container image или отдельной машины.

## Архитектурный вывод

Clean Site acceptance является финальным доказательством того, что обязательная модель действительно принадлежит App, а не истории ручных действий на dev-site.

# 15. Что CORE намеренно не добавляет автоматически

После CORE могут появляться дополнительные требования.

Они не являются продолжением курса по принципу «остались функции Frappe — надо их пройти».

Они подключаются отдельными ветками.

# 16. Финальный результат маршрута

После CORE ученик должен иметь не набор знакомых экранов, а работающую причинно-следственную модель:

```text
требование
    ↓
ответственность
    ↓
штатный механизм Frappe
    ↓
модель / правило / permission
    ↓
наблюдаемый сценарий
    ↓
автоматический контракт
    ↓
чистая установка
```

И уметь объяснить не только **как** сделать решение во Frappe, но и **почему** оно построено именно на этом штатном механизме.
