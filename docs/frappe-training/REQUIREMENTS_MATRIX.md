# Матрица требований учебного практикума Frappe

Статус: **черновик для архитектурной проверки**.

Этот документ продолжает [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md).

Следующие слои:

- [`STAGE_DEPENDENCY_GRAPH.md`](STAGE_DEPENDENCY_GRAPH.md) — реальные зависимости между результатами;
- [`PRACTICUM_ROADMAP.md`](PRACTICUM_ROADMAP.md) — практические этапы, полученные из графа.

Матрица не задаёт программу занятий и не является списком функций, которые надо обязательно «пройти». Она проверяет, что каждый механизм Frappe появляется из понятного требования:

```text
требование
    ↓
ответственность
    ↓
первый штатный механизм Frappe
    ↓
почему его семантика подходит
    ↓
где проходит граница
    ↓
что проверить руками
```

Нормативная база — [`docs/frappe-architecture-standard`](../frappe-architecture-standard/README.md).

---

## 1. Уровни требований

### CORE — обязательная основа

```text
R01–R06
R08–R11
R13
R16
R21–R24
```

Кроме этих требований, при создании каждого самостоятельного DocType обязательно принимается архитектурное решение `D00` о стратегии `name`. Это не дополнительная функция и не условная ветка: системный `name` существует у Document в любом случае, поэтому его семантика должна быть выбрана осознанно.

### NEXT — естественный второй контур

```text
R07
R12
R14–R15
R17–R20
```

Каждый NEXT включается только если он действительно нужен принятому учебному сценарию.

### GATE — архитектурные развилки

```text
D01–D05
```

Механизм появляется только после нового требования с соответствующей семантикой.

### EXT — расширения

```text
E01–E03
```

API и интеграции не входят в минимальный маршрут автоматически.

# 2. CORE — основная модель

## R01. Реестр оборудования

**Требование:** каждая единица оборудования существует независимо от конкретной выдачи и используется многими Rentals.

**Ответственность:** самостоятельная запись.

**Первый механизм:** Standard `DocType` `Equipment`.

**Граница:** простые свойства не превращаются в отдельные DocTypes без собственного смысла.

**Проверка:** создать несколько Equipment, открыть через Form/List, найти и использовать в Link.

---

## R02. Реестр клиентов

**Требование:** один клиент участвует в нескольких Rentals.

**Ответственность:** самостоятельная запись.

**Первый механизм:** Standard `DocType` `Customer`.

**Граница:** текстовое имя не заменяет настоящую связь; исторический snapshot — отдельное требование.

**Проверка:** использовать одного Customer в нескольких Rentals.

---

## R03. Rental как отдельный рабочий Document

**Требование:** хранить клиента, период, состав оборудования и текущее состояние одной операции.

**Первый механизм:** Standard `DocType` `Rental`.

**Граница:** наличие состояний не делает Rental автоматически Workflow или Submittable.

---

## R04. Несколько единиц Equipment в одном Rental

**Ответственность:** принадлежащий Rental набор ссылок на существующие Equipment.

**Первый механизм:** `Table MultiSelect` через `Rental Item` как минимальный `Child DocType` с одним `Link → Equipment`.

**Почему не обычный Table:** у строки отношения сейчас нет собственных бизнес-атрибутов кроме ссылки. Если появятся цена, состояние при выдаче, фактический возврат конкретной позиции и т. п., обычный `Table` станет естественным кандидатом.

**Граница:** самостоятельный lifecycle/permissions/ссылки строки могут потребовать уже отдельного DocType отношения.

---

## R05. Живые связи

```text
Rental.customer       → Link → Customer
Rental Item.equipment → Link → Equipment
```

**Первый механизм:** `Link`; для набора Equipment — `Table MultiSelect` поверх Child DocType.

**Граница:** `Dynamic Link` не используется ради абстрактной универсальности; текст не заменяет связь без требования snapshot.

---

## R06. Небольшой стабильный тип Equipment

**Требование:** тип имеет только несколько стабильных значений и не имеет собственных атрибутов.

**Первый механизм:** `Select`.

**Граница:** при появлении собственных атрибутов/управления тип может стать отдельным `Equipment Type` DocType (`D03`).

---

## R08. Предметное состояние Rental

**Требование:** различать `Planned`, `Active`, `Returned`.

**Первый механизм:** обычное поле `status` (`Select`).

**Граница:** status не равен `Workflow` и не равен `docstatus`.

---

# 3. CORE — серверные правила

## R09. Корректный период

**Требование:** `end_date` не раньше `start_date` независимо от способа создания Document.

**Первый механизм:** `Controller.validate()`.

**Граница:** Client Script может улучшить UX, но не является серверной гарантией.

**Проверка:** неправильный период должен быть отклонён не только через Form, но и через обычный серверный `Document.insert()`.

---

## R10. Нет дублей Equipment внутри одного Rental

**Требование:** один и тот же Equipment не может присутствовать в `Rental.items` дважды.

**Первый механизм:** проверка Controller Rental в серверном lifecycle-пути.

**Почему:** `Table MultiSelect` — подходящий UI/control для набора, но browser control не является гарантией данных для других путей создания Document.

**Граница:** отдельный движок правил ради одной проверки не нужен.

**Проверка:** программно сформировать Rental с двумя одинаковыми child rows и убедиться, что обычный `Document.insert()` отклонён.

---

## R11. Нет пересекающихся активных Rentals одного Equipment

**Ответственность:** междокументный инвариант Rental, использующий другие Documents.

**Первый механизм:** `Rental Controller.validate()` + штатный Database API.

CORE-семантика:

```text
Planned  → не блокирует
Active   → блокирует
Returned → не блокирует
```

Периоды включительны и конфликтуют, если:

```text
existing.start_date <= current.end_date
AND
existing.end_date >= current.start_date
```

Внутренний validator должен учитывать реальный конфликт независимо от permission-filtering пользовательского List. Поэтому системное чтение через `frappe.get_all()` здесь используется намеренно; пользовательские выборки от этого не перестают быть permission-aware.

При редактировании текущий Rental исключается из поиска по `name`, чтобы не возникал self-conflict.

**Граница:** обычная `validate()`-проверка гарантирует обнаружение уже существующего конфликта при последовательном сохранении, но не является полной стратегией конкурентного бронирования. Параллельные транзакции, locking/reservation strategy — отдельная production-задача.

---

# 4. CORE — безопасность и UI

## R13. Оператор и менеджер имеют разные права

**Первый механизм:** `Role` + `DocType Permissions`.

**Граница:** собственная ACL не вводится, пока штатной модели достаточно.

**Проверка:** войти под разными пользователями и проверить фактические операции.

---

## R16. Базовый сценарий работает без собственного frontend

**Первый механизм:** Desk `Form` + `List`.

**Граница:** custom frontend появляется только под отдельное UX-требование.

**Проверка:** полностью пройти создание Equipment → Customer → Rental через стандартный Desk.

---

# 5. NEXT — второй контур

## R07. Одна настройка уровня Site

Если появляется реальное глобальное значение приложения, первый кандидат — `Single DocType` `Rental Settings`.

Без такого требования Single не добавляется ради покрытия.

## R12. История, комментарии, файлы

Первый кандидат — `Version`/Timeline, `Comment`, `File`/Attach.

Не создавать собственные `Rental History`, `Rental Comment`, `Rental Attachment` без другой семантики.

## R14. Поля только менеджеру

Первый кандидат — `Permission Level`.

Без реального чувствительного поля механизм не включается.

## R15. Назначить Rental сотруднику

Первый кандидат — `Assignment` / `ToDo`.

Если ответственный является историческим бизнес-фактом, может понадобиться обычное Link-поле; это другой смысл.

## R17. Единая точка входа

Первый кандидат — `Workspace`.

## R18. Rentals по датам

Первый кандидат — Calendar view. Новая сущность ради календаря не создаётся.

## R19. Акт выдачи

Первый кандидат — `Print Format`.

## R20. Простой рабочий отчёт

Первый кандидат — `Report Builder`. Query/Script Report появляются только после конкретного требования, которое Report Builder не выражает.

---

# 6. Обязательное архитектурное решение — naming

## D00. Naming — CORE decision

Для каждого самостоятельного DocType нужно осознанно выбрать стратегию `name`.

Первый механизм: штатные naming strategies (`Naming Series`, field/expression, `autoname`, UUID и т. д.).

Граница: изменяемое бизнес-поле не выбирается вечным ID только потому, что сегодня оно уникально.

Это решение принимается при создании `Equipment`, `Customer` и `Rental`, до того как на их `name` начнут опираться ссылки и пользовательские сценарии.

# 7. GATE — архитектурные развилки

## D01. Менеджер подтверждает выдачу

Появились состояния + переходы + роли.

Первый кандидат: `Workflow`.

Граница: обычный status сам по себе не требует Workflow.

---

## D02. Выдача становится зафиксированным фактом

После фактической выдачи ключевые данные нельзя свободно переписывать, ошибочную операцию нужно отменять.

Первый кандидат: `Is Submittable` / `docstatus`.

Граница: `Returned` не означает Submitted. Workflow и docstatus отвечают на разные вопросы.

---

## D03. Equipment Type стал самостоятельной сущностью

Если у типа появились свойства, активность и управление, `Select` пересматривается в отдельный `Equipment Type` + Link.

При существующих данных отдельно решается миграция.

---

## D04. Внешний посетитель оставляет заявку

Сначала решается предметная модель: это Rental или отдельный `Rental Request`?

Только после этого первый UI-кандидат — `Web Form`.

---

## D05. Напоминание о возврате

Первый кандидат — `Notification`.

Scheduler/background job появляется только если конкретное требование выходит за семантику Notification.

---

# 8. EXT — API и интеграции

## E01. Внутренний клиент делает обычный CRUD

Первый механизм: Document REST API.

Не создавать собственные `/create_rental`/`read`/`update`/`delete`, если они только переименовывают штатный CRUD.

## E02. Предметная команда `return_rental`

Первый кандидат: Document method или whitelisted method — если операция действительно имеет командную семантику и правила.

## E03. Исходящее HTTP-событие

Первый кандидат: `Webhook`.

Сложные гарантированные повторы, сверка и идемпотентность создают уже отдельную интеграционную ответственность.

---

# 9. CORE — доставка и тестирование

## R21. Обязательное состояние принадлежит App

Другой Site после установки должен получить те же обязательные элементы.

Source of truth CORE разделён по штатной семантике:

```text
Module                        → modules.txt
Standard DocTypes             → DocType JSON
fields/naming/default DocPerm → Standard metadata
Controller                    → Python source
Role                          → filtered fixture
Users/business data           → Site-local, не fixtures
```

**Проверка:** у обязательного элемента должен быть понятный owner/source/delivery path; скрытый ручной шаг dev-site не принимается.

---

## R22. Изменение модели не требует ручного SQL

Schema sync выполняется через `migrate`; fixture/config синхронизируются штатными механизмами App. `patch` применяется, когда существующие данные поддерживаемой предыдущей версии действительно надо преобразовать.

**Граница:** patch не создаётся ради знакомства с механизмом и не нужен только потому, что на dev-site во время разработки уже были тестовые записи.

---

## R23. Критические правила защищены тестами

Тестируются собственные инварианты и permissions, а не Framework ради coverage.

Для DB/Document/permission сценариев v16 используется актуальный `IntegrationTestCase`.

---

## R24. Финальная установка чистая и воспроизводимая

```text
чистый Frappe Site
+ App из Git
+ install-app
+ migrate
+ tests
= рабочее обязательное состояние
```

После установки повторяется основной пользовательский сценарий.

---

# 10. Необязательность механизмов — явное правило

В CORE сейчас **не входят автоматически**:

```text
Single DocType
Permission Level
Assignment
Workspace
Calendar
Print Format
Report Builder
Workflow
docstatus
Web Form
Notification
REST integration
Virtual/Dynamic/Tree DocType
Server Script
User Permission / Share / permission hooks
Realtime / Background Jobs
custom frontend
extend/override hooks
fork Frappe
```

Это не оценка полезности механизмов. Просто CORE-предметная область пока не предъявила соответствующих требований.

# 11. Контроль перед дорожной картой

```text
1. CORE состоит только из реальных обязательных требований?
2. Каждый DocType имеет самостоятельный смысл?
3. Naming выбран осознанно до появления зависимых ссылок?
4. Workflow не введён ради количества статусов?
5. docstatus не используется как бизнес-статус?
6. Инварианты гарантируются серверным Document-путём?
7. Междокументный invariant не зависит случайно от permission-filtering пользовательского List?
8. Concurrency boundary V03 названа честно?
9. Права начинаются со штатных permissions?
10. UI следует за моделью?
11. Обязательное App-owned состояние имеет source of truth и delivery path?
12. Runtime Users/business data не выданы за fixtures продукта?
13. Patch появляется только из реальной data migration?
14. API не дублирует стандартный CRUD без причины?
15. App и Site не смешаны?
16. Финал проверяется на чистом Site?
```

Если какой-то ответ отрицательный, исправляется архитектура, а не дорожная карта.
