# Матрица требований учебного практикума Frappe

Статус: **черновик для архитектурной проверки**.

Этот документ продолжает [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md). Он не задаёт программу занятий и не является списком функций, которые необходимо обязательно «пройти».

Его задача — проверить, что каждый механизм Frappe появляется из понятного требования предметной области:

```text
требование
    ↓
ответственность
    ↓
первый штатный механизм Frappe
    ↓
почему его семантика подходит
    ↓
где проходит его граница
    ↓
что ученик должен проверить руками
```

Нормативная база — [`docs/frappe-architecture-standard`](../frappe-architecture-standard/README.md), в первую очередь:

- [`02_DATA_MODEL.md`](../frappe-architecture-standard/02_DATA_MODEL.md);
- [`03_DOCUMENT_LIFECYCLE.md`](../frappe-architecture-standard/03_DOCUMENT_LIFECYCLE.md);
- [`04_SECURITY.md`](../frappe-architecture-standard/04_SECURITY.md);
- [`06_API_INTEGRATION.md`](../frappe-architecture-standard/06_API_INTEGRATION.md);

## 1. Уровни требований

Матрица специально **не считает все перечисленные механизмы обязательными**.

### CORE — обязательная основа

Без этих требований нельзя считать, что ученик построил и архитектурно проверил минимальное приложение:

```text
R01–R06
R08–R11
R13
R16
R21–R24
```

### NEXT — естественный второй контур

Это нормальные требования реального приложения, но они не должны включаться только ради покрытия функций:

```text
R07
R12
R14–R15
R17–R20
```

Перед составлением дорожной карты для каждого из них ещё раз проверяется, действительно ли он нужен учебному сценарию.

### GATE — точки архитектурного выбора

```text
D00–D05
```

Они специально формулируются как новые требования. Механизм появляется только если требование принимается.

### EXT — расширения

```text
E01–E03
```

API и интеграции не входят в минимальный маршрут автоматически.

Наличие механизма в архитектурном стандарте **не означает**, что он обязан попасть в практикум.

# 2. Основная модель и правила

## R01. Вести отдельный реестр оборудования — CORE

**Требование**  
Каждая единица оборудования существует независимо от выдачи: её нужно создать один раз, находить, открывать и использовать во многих операциях проката.

**Ответственность**  
Самостоятельная предметная запись с собственной идентичностью.

**Первый штатный механизм Frappe**  
Standard `DocType` `Equipment`.

**Почему подходит**  
Оборудование является самостоятельным `Document`, а не свойством конкретного Rental.

**Граница**  
Не создавать отдельные `DocType` для каждого простого свойства оборудования. Марка, серийный номер, состояние и подобные значения сначала являются полями.

**Что проверить руками**  
Создать несколько Equipment, открыть их через стандартные `Form` и `List`, найти запись поиском и сослаться на неё из другого `Document`.

---

## R02. Вести отдельный реестр клиентов — CORE

**Требование**  
Один клиент может брать оборудование много раз.

**Ответственность**  
Самостоятельная справочная запись.

**Первый штатный механизм Frappe**  
Standard `DocType` `Customer`.

**Почему подходит**  
Customer существует независимо от Rental и используется многими Rentals.

**Граница**  
Имя клиента в Rental не должно становиться заменой настоящей связи. Если позднее понадобится исторический снимок имени или реквизитов, это отдельное требование, а не повод отказаться от `Link`.

**Что проверить руками**  
Создать Customer и затем использовать одну запись клиента в нескольких Rentals.

---

## R03. Оформлять прокат как отдельный рабочий документ — CORE

**Требование**  
Нужно хранить клиента, даты проката, состав оборудования и текущее состояние операции.

**Ответственность**  
Самостоятельный рабочий `Document`.

**Первый штатный механизм Frappe**  
Standard `DocType` `Rental`.

**Почему подходит**  
Rental имеет собственную идентичность, открывается отдельно и объединяет данные одной операции.

**Граница**  
На этом этапе Rental не объявляется автоматически `Is Submittable` и не получает `Workflow` только потому, что у него есть состояния.

**Что проверить руками**  
Создать, сохранить, открыть и изменить Rental через стандартную форму.

---

## R04. В одной выдаче может быть несколько единиц оборудования — CORE

**Требование**  
Один Rental содержит несколько строк оборудования.

**Ответственность**  
Состав одного родительского `Document`.

**Первый штатный механизм Frappe**  
`Rental Item` как `Child DocType` + поле `Table` в Rental.

**Почему подходит**  
Строка не существует как отдельная операция проката и принадлежит одному Rental.

**Граница**  
Если строке понадобится самостоятельный жизненный цикл, собственные права или ссылки из других Documents, решение пересматривается.

**Что проверить руками**  
Добавить несколько строк, изменить порядок, сохранить Rental и убедиться, что строки остаются частью родителя.

---

## R05. Выбирать клиента и оборудование из существующих записей — CORE

**Требование**  
Rental должен ссылаться на конкретного Customer, а Rental Item — на конкретное Equipment.

**Ответственность**  
Живая связь между Documents.

**Первый штатный механизм Frappe**  
`Link`.

**Почему подходит**  
Тип целевого `DocType` известен заранее, а бизнесу нужна именно связь с существующей записью.

**Граница**  
Не использовать `Dynamic Link` ради абстрактной «универсальности». Не копировать текст вместо ссылки, если исторический снимок не требуется.

**Что проверить руками**  
Выбрать существующие записи через Link, открыть связанную запись и проверить стандартный поиск Link.

---

## R06. Хранить небольшой стабильный тип оборудования — CORE

**Требование**  
Для Equipment нужен тип вроде `Tool`, `Camera`, `Computer`, при этом у типа пока нет собственных атрибутов и жизненного цикла.

**Ответственность**  
Простое свойство Equipment.

**Первый штатный механизм Frappe**  
Поле `Select`.

**Почему подходит**  
Малый стабильный набор значений не является самостоятельным бизнес-объектом.

**Граница**  
Если у типа появятся свои свойства, права, активность, нормативы или независимое управление, появляется основание для `Equipment Type` как отдельного `DocType`.

**Что проверить руками**  
Создать поле Select, отфильтровать Equipment по типу и объяснить, почему отдельный справочник пока не нужен.

---

## R07. Иметь один набор настроек приложения на Site — NEXT

**Требование**  
Например, нужно хранить стандартную длительность проката или значение по умолчанию, одинаковое для всего Site.

**Ответственность**  
Один набор конфигурации.

**Первый штатный механизм Frappe**  
`Rental Settings` как `Single DocType`.

**Почему подходит**  
На одном Site должна существовать ровно одна такая конфигурация.

**Граница**  
Если настройка должна отличаться по филиалу, компании или другому объекту, модель одной глобальной записи перестаёт соответствовать требованию.

**Что проверить руками**  
Открыть Single, изменить значение и использовать его из Rental.

---

## R08. Хранить рабочее состояние проката — CORE

**Требование**  
Пользователь должен различать, например, `Planned`, `Active`, `Returned`.

**Ответственность**  
Предметное состояние Rental.

**Первый штатный механизм Frappe**  
Обычное поле `status` (`Select`).

**Почему подходит**  
Требование пока говорит только о состоянии, а не о ролевой политике переходов или транзакционной фиксации.

**Граница**  
Несколько значений статуса сами по себе не являются основанием ни для `Workflow`, ни для `docstatus`. Предметный статус не должен без причины копировать системные значения `Draft / Submitted / Cancelled`.

**Что проверить руками**  
Изменить status, отфильтровать Rental в List и увидеть состояние в стандартном интерфейсе.

---

## R09. Нельзя сохранить период, где дата окончания раньше даты начала — CORE

**Требование**  
Некорректный Rental не должен появиться независимо от способа его создания.

**Ответственность**  
Инвариант данных.

**Первый штатный механизм Frappe**  
Серверная проверка в `Controller.validate()`.

**Почему подходит**  
Правило должно работать не только в браузерной форме, но и через REST API, импорт и серверный код.

**Граница**  
Client Script может дополнительно дать раннюю подсказку, но не является единственной гарантией.

**Что проверить руками**  
Попробовать сохранить неправильные даты через форму и затем проверить тот же инвариант серверным тестом или другим путём создания Document.

---

## R10. Одно Equipment нельзя указать в одном Rental дважды — CORE

**Требование**  
В составе одной выдачи не должно быть дублирующихся строк одного оборудования.

**Ответственность**  
Инвариант одного Rental.

**Первый штатный механизм Frappe**  
Проверка в Controller Rental.

**Почему подходит**  
Правило относится к состоянию одного `Document` и его Child Table.

**Граница**  
Не создавать отдельный «движок правил» ради одной проверки.

**Что проверить руками**  
Попробовать сохранить Rental с двумя одинаковыми Equipment и получить понятную ошибку.

---

## R11. Одно Equipment нельзя одновременно выдать двум клиентам на пересекающиеся периоды — CORE

**Требование**  
Новая выдача не должна конфликтовать с существующей активной выдачей того же Equipment.

**Ответственность**  
Бизнес-проверка, использующая данные нескольких Documents.

**Первый штатный механизм Frappe**  
Серверная логика Rental + запрос через штатный Database/Query API с учётом нужной семантики.

**Почему подходит**  
Правило является инвариантом Rental, но для проверки требуется посмотреть другие Rentals.

**Граница**  
Обычная проверка в `validate()` демонстрирует правильное размещение правила, но сама по себе не является полной стратегией конкурентного бронирования. Если приложение допускает одновременные конкурирующие операции, потребуется отдельно проектировать блокировки/транзакционную стратегию. Если доступность вырастет в подсистему с резервами, очередями и несколькими типами ресурсов, может появиться отдельный service или новая предметная модель.

**Что проверить руками**  
В обычном учебном сценарии создать первый Rental, затем попытаться создать пересекающийся второй и убедиться, что сохранение блокируется сервером; отдельно зафиксировать границу этого решения для конкурентных запросов.

---

## R12. Видеть обычную историю изменений, комментарии и файлы — NEXT

**Требование**  
Пользователь должен понимать, кто менял Rental, обсуждать его и прикладывать документы.

**Ответственность**  
Стандартная история Document, обсуждение и вложения.

**Первый штатный механизм Frappe**  
`Track Changes` / `Version`, `Comment`, `File` / Attach.

**Почему подходит**  
Frappe уже владеет этими общими прикладными ответственностями.

**Граница**  
Если понадобится юридически значимый неизменяемый журнал с другой семантикой, штатной истории может быть недостаточно.

**Что проверить руками**  
Изменить Rental, просмотреть Timeline/историю, добавить комментарий и файл без создания собственных `Rental History`, `Rental Comment`, `Rental Attachment`.

# 3. Права и работа пользователей

## R13. Оператор и менеджер имеют разные права — CORE

**Требование**  
Оператор должен работать с Rentals, а менеджер — иметь более широкие возможности управления.

**Ответственность**  
Доступ к `DocType` по роли.

**Первый штатный механизм Frappe**  
`Role` + `DocType Permissions`.

**Почему подходит**  
Это базовая декларативная модель авторизации Frappe.

**Граница**  
Не переходить к собственному ACL и не разбрасывать проверки имени роли по коду, пока штатных permissions достаточно.

**Что проверить руками**  
Создать двух пользователей с разными Roles, войти под каждым и проверить реальные Create/Read/Write/Delete/Report-права.

---

## R14. Некоторые поля Rental доступны только менеджеру — NEXT

**Требование**  
Например, внутренний финансовый комментарий или залог не должен быть доступен обычному оператору.

**Ответственность**  
Права на поля внутри одного DocType.

**Первый штатный механизм Frappe**  
`Permission Level` (`permlevel`).

**Почему подходит**  
Требование относится не к отдельной сущности, а к доступу к конкретным полям существующего Document.

**Граница**  
Скрытие JavaScript не считается защитой данных. Если такого чувствительного поля в учебной модели не будет, `permlevel` не добавляется ради демонстрации.

**Что проверить руками**  
Если требование принято, сравнить форму Rental под двумя ролями и проверить, что ограничение действует серверно, а не только визуально.

---

## R15. За конкретный Rental отвечает сотрудник — NEXT

**Требование**  
Нужно назначить человеку работу по конкретному Rental и видеть её в его очереди.

**Ответственность**  
Рабочее назначение.

**Первый штатный механизм Frappe**  
`Assignment` / `ToDo`.

**Почему подходит**  
Frappe уже имеет механизм назначения работы на Document.

**Граница**  
Если «ответственный оператор» является самостоятельным историческим бизнес-фактом Rental, который должен сохраняться в отчётности независимо от текущего Assignment, может понадобиться обычное поле Link на User/Employee. Если назначения в учебном процессе нет, Assignment не включается ради покрытия.

**Что проверить руками**  
Если требование принято, назначить Rental пользователю и увидеть задачу в штатной рабочей очереди.

# 4. Интерфейс и вывод

## R16. Работать с карточками и реестрами без собственного фронтенда — CORE

**Требование**  
Оператору нужны карточки Equipment, Customer, Rental и списки записей с фильтрами.

**Ответственность**  
Обычный административный CRUD UI.

**Первый штатный механизм Frappe**  
Desk `Form` + `List`.

**Почему подходит**  
Framework автоматически предоставляет эти представления вокруг DocType.

**Граница**  
Собственный frontend рассматривается только при отдельном UX-требовании, которое стандартный Desk действительно не выражает.

**Что проверить руками**  
Полностью выполнить базовый сценарий проката через стандартный Desk без создания SPA.

---

## R17. Дать пользователю одну рабочую точку входа — NEXT

**Требование**  
Оператору нужен экран с быстрыми ссылками на прокаты, оборудование и основные показатели.

**Ответственность**  
Организация навигации Desk.

**Первый штатный механизм Frappe**  
`Workspace`.

**Почему подходит**  
Workspace предназначен для организации рабочих объектов, ссылок и информационных блоков.

**Граница**  
Workspace не должен становиться источником бизнес-логики. Если обычной навигации Module достаточно, отдельный учебный шаг не нужен.

**Что проверить руками**  
Если требование принято, открыть рабочую область и перейти из неё к основным Documents и отчётам.

---

## R18. Видеть прокаты по датам — NEXT

**Требование**  
Пользователю важно понимать, какие Rentals приходятся на конкретные даты.

**Ответственность**  
Представление уже существующих данных во времени.

**Первый штатный механизм Frappe**  
Проверить штатное календарное представление для модели с датами.

**Почему подходит**  
Требование меняет представление, а не предметную модель.

**Граница**  
Не вводить новую сущность `Rental Calendar Entry` только ради календаря. Если календарь не улучшает учебный сценарий, его можно исключить.

**Что проверить руками**  
Если требование принято, открыть Rentals в календарном представлении и сопоставить их с теми же Documents в List/Form.

---

## R19. Печатать акт выдачи — NEXT

**Требование**  
По Rental нужен человекочитаемый документ с клиентом, периодом и перечнем оборудования.

**Ответственность**  
Печатное представление Document.

**Первый штатный механизм Frappe**  
`Print Format`.

**Почему подходит**  
Это штатная ответственность платформы для обычной печати Document.

**Граница**  
Отдельный PDF-сервис появляется только при действительно специальных требованиях к генерации. Если печатный документ не нужен принятому сценарию, Print Format не включается ради покрытия.

**Что проверить руками**  
Если требование принято, сформировать печатную форму для реального Rental.

---

## R20. Получить простой реестр активных Rentals — NEXT

**Требование**  
Пользователь хочет выбрать поля, отфильтровать активные Rentals и получить рабочий список без сложных вычислений.

**Ответственность**  
Простая отчётность по существующим данным.

**Первый штатный механизм Frappe**  
Сначала `Report Builder`.

**Почему подходит**  
Требование сводится к выбору полей, фильтрации и группировке.

**Граница**  
`Query Report` или `Script Report` появляется только если конкретное требование нельзя корректно выразить Report Builder. Не придумывать сложный отчёт только ради Python/SQL.

**Что проверить руками**  
Если требование принято, собрать рабочий отчёт без Python и объяснить границу Report Builder на конкретной задаче.

# 5. Точки архитектурного выбора

## D00. Выбрать стратегию `name` для Documents — GATE

**Требование**  
У каждой записи Frappe всё равно существует системный `name`; нужно осознанно решить, является ли он техническим идентификатором или бизнес-номером.

**Ответственность**  
Стабильная идентичность Documents и человекочитаемое именование.

**Первый штатный механизм Frappe**  
Штатные стратегии naming (`Naming Series`, field/expression, controller `autoname`, UUID и другие в зависимости от модели).

**Почему это точка выбора**  
Для Equipment изменяемое отображаемое значение или серийный номер не обязательно должно становиться вечным ID. Для Rental, наоборот, может быть полезен человекочитаемый номер операции.

**Граница**  
Не выбирать бизнес-поле как `name` только потому, что сегодня оно уникально. Не добавлять сложную собственную генерацию ID, пока штатная стратегия выражает требование.

**Что проверить руками**  
Для каждого самостоятельного DocType объяснить выбранную стратегию `name`, создать записи и проверить стабильность ссылок после изменения отображаемых данных.

---

## D01. Менеджер должен подтверждать выдачу — GATE

**Требование**  
Оператор готовит Rental, но перевод в подтверждённое состояние разрешён только менеджеру.

**Ответственность**  
Управляемые переходы между состояниями по ролям.

**Первый штатный механизм Frappe**  
Рассмотреть `Workflow`.

**Почему подходит**  
В требовании появились состояния, переходы и роли — именно семантика Workflow.

**Граница**  
Если процесс станет динамическим и не выражается штатными состояниями/условиями, может понадобиться предметная координация. Само наличие status не является причиной Workflow.

**Что проверить руками**  
Если требование принято, под оператором попытаться выполнить переход, доступный только менеджеру; под менеджером выполнить его штатно.

---

## D02. Подтверждённая выдача становится зафиксированным фактом — GATE

**Требование**  
После фактической выдачи ключевые данные операции нельзя свободно переписывать; ошибочную операцию нужно отменять отдельным действием.

**Ответственность**  
Транзакционная фиксация Document.

**Первый штатный механизм Frappe**  
Рассмотреть `Is Submittable` / `docstatus`.

**Почему подходит**  
Теперь появляется именно смысл `Draft → Submitted → Cancelled`, а не просто предметный статус `Returned`.

**Граница**  
Если бизнесу нужна только рабочая стадия `Returned`, `docstatus` для этого не применяется. Workflow и docstatus могут взаимодействовать, но отвечают на разные вопросы.

**Что проверить руками**  
Если требование принято, сравнить поведение Draft, Submitted и Cancelled Rental и увидеть ограничения изменения после submit.

---

## D03. Тип оборудования перестал быть простым списком — GATE

**Требование**  
Для типа оборудования появились, например, срок обслуживания, размер залога, активность и собственное управление.

**Ответственность**  
Самостоятельная справочная сущность.

**Первый штатный механизм Frappe**  
Пересмотреть `Select` и создать `Equipment Type` как обычный DocType, если признаки самостоятельной записи подтверждены.

**Почему подходит**  
Требование изменило бизнес-смысл типа: теперь это уже не просто значение поля.

**Граница**  
Нельзя создавать справочник заранее, пока этих требований нет.

**Что проверить руками**  
Если требование принято, изменить модель осознанно и объяснить, почему Link теперь точнее Select; если существуют старые данные — отдельно решить вопрос их миграции.

---

## D04. Внешний посетитель должен оставить заявку на прокат — GATE

**Требование**  
Человек без Desk-доступа отправляет данные через веб.

**Ответственность**  
Внешний ввод данных.

**Первый штатный механизм Frappe**  
Сначала решить предметный вопрос, затем проверить `Web Form`.

**Архитектурный вопрос до UI**  
Заявка посетителя — это уже Rental в начальном состоянии или другой самостоятельный бизнес-объект `Rental Request`?

- если смысл тот же — Web Form может работать поверх Rental;
- если заявка должна отдельно рассматриваться, отклоняться и только потом превращаться в Rental — появляется основание для нового DocType `Rental Request`.

**Почему это важно**  
`Web Form` является способом представления и ввода, а не ответом на вопрос о предметной модели.

**Что проверить руками**  
Если требование принято, сначала письменно обосновать модель, затем отправить реальную запись через Web Form и увидеть её в Desk.

---

## D05. Нужно отправлять напоминание о сроке возврата — GATE

**Требование**  
Пользователь должен получить уведомление, когда Rental подходит к сроку возврата или просрочен.

**Ответственность**  
Уведомление по условию/дате.

**Первый штатный механизм Frappe**  
Сначала проверить `Notification`.

**Почему подходит**  
Это общая прикладная ответственность, которой Framework уже владеет.

**Граница**  
Если требуется сложная периодическая обработка множества условий, повторов и внешних действий, может появиться `scheduler_events`/background job. Не строить планировщик ради одного обычного уведомления.

**Что проверить руками**  
Если требование принято, создать тестовый Rental с подходящей датой и получить штатное уведомление.

# 6. Интеграции и API

## E01. Внутренняя автоматизация должна читать и создавать Rentals — EXT

**Требование**  
Другой внутренний клиент понимает модель Frappe и выполняет обычный CRUD.

**Ответственность**  
Ресурсный API Document.

**Первый штатный механизм Frappe**  
Document REST API.

**Почему подходит**  
Frappe уже генерирует CRUD API для DocType и проводит операции через Document-модель и permissions.

**Граница**  
Не создавать `/create_rental`, `/read_rental`, `/update_rental`, `/delete_rental`, если они только переименовывают штатный CRUD.

**Что проверить руками**  
Если расширение принято, создать или прочитать Rental через REST от имени пользователя с ограниченными правами.

---

## E02. Внешнему клиенту нужна команда «вернуть прокат» — EXT

**Требование**  
Операция должна проверить бизнес-правила и выполнить предметное действие, а не просто изменить произвольное поле.

**Ответственность**  
Команда над Document.

**Первый штатный механизм Frappe**  
Метод Document или whitelisted method — в зависимости от выбранного контракта.

**Почему подходит**  
Появилась командная семантика, которой нет у простого CRUD.

**Граница**  
Не превращать каждое изменение одного поля в собственный endpoint.

**Что проверить руками**  
Если расширение принято, вызвать команду через API, проверить permissions и увидеть, что недопустимое состояние отвергается сервером.

---

## E03. Внешняя система должна получить событие о подтверждённой выдаче — EXT

**Требование**  
После определённого события Rental внешний HTTP-получатель должен получить сообщение.

**Ответственность**  
Исходящее HTTP-событие Document.

**Первый штатный механизм Frappe**  
`Webhook`.

**Почему подходит**  
Для простого исходящего события Framework уже имеет штатный механизм.

**Граница**  
Если интеграция требует гарантированных повторов, сложного преобразования, сверки состояния и идемпотентности, понадобится отдельный интеграционный service/background processing.

**Что проверить руками**  
Если расширение принято, отправить событие на тестовый HTTP endpoint и увидеть фактический payload.

# 7. Доставка, миграции и приёмка

## R21. Обязательная модель должна храниться в App, а не только на dev-site — CORE

**Требование**  
Другой Site после установки App должен получить те же Standard DocTypes и обязательные элементы приложения.

**Ответственность**  
Воспроизводимая доставка схемы и конфигурации.

**Первый штатный механизм Frappe**  
Standard DocType JSON, fixtures/exported configuration там, где это соответствует типу объекта, и `bench migrate`.

**Почему подходит**  
Это штатная модель доставки приложения Frappe.

**Граница**  
Локальная Site-настройка не должна случайно объявляться обязательной частью App, и наоборот.

**Что проверить руками**  
Показать соответствующие файлы в Git и объяснить, какие элементы принадлежат App, а какие конкретному Site.

---

## R22. Изменение модели не должно требовать ручного SQL — CORE

**Требование**  
При развитии приложения схема и обязательные изменения данных должны переноситься штатным обновлением.

**Ответственность**  
Миграция схемы и данных.

**Первый штатный механизм Frappe**  
DocType schema sync через `migrate`; `patch` только когда существующие данные действительно нужно преобразовать.

**Почему подходит**  
Framework уже имеет жизненный цикл миграций App.

**Граница**  
Не писать patch для каждого обычного добавления поля и не выполнять production SQL вручную без отдельной причины.

**Что проверить руками**  
Изменить модель, выполнить migrate и проверить результат на Site с уже существующими данными.

---

## R23. Критические правила должны быть защищены тестами — CORE

**Требование**  
После изменений нельзя случайно разрешить неправильные даты, двойную выдачу оборудования или обход прав.

**Ответственность**  
Проверка собственных контрактов приложения.

**Первый штатный механизм Frappe**  
Frappe test runner / `FrappeTestCase`.

**Почему подходит**  
Тестируются наши инварианты и права, а не сам факт работы стандартного Link или `frappe.get_doc()`.

**Граница**  
Не писать бессмысленные тесты стандартного Framework ради количества coverage.

**Что проверить руками**  
Запустить набор тестов, намеренно сломать одно правило и увидеть падение соответствующего теста.

---

## R24. Финальная установка должна быть чистой и воспроизводимой — CORE

**Требование**  
Практикум считается завершённым только если учебное App можно поставить на новый совместимый Frappe Site без скрытого ручного восстановления модели.

**Ответственность**  
Приёмка архитектуры App.

**Первый штатный путь**

```text
чистый Frappe Site
+ репозиторий App
+ install-app
+ migrate
+ tests
= рабочее обязательное состояние приложения
```

**Что проверить руками**  
Создать новый Site, установить учебное App, выполнить migrate, запустить тесты и пройти основной пользовательский сценарий от создания Equipment до оформления Rental.

# 8. Что сознательно не входит в обязательное ядро

На текущем наборе требований **нет основания обязательно включать**:

```text
Virtual DocType
Dynamic Link
Tree DocType
Packages
Server Script
permission_query_conditions
has_permission
Share
User Permission
Realtime API
Background Jobs
собственный WebSocket
Prepared Report
собственный frontend
extend_doctype_class
override_doctype_class
fork Frappe
```

Это не список «ненужных функций».

Это механизмы, для которых текущая предметная область пока не предъявила требование с совпадающей семантикой.

Если мы искусственно добавим их только потому, что они существуют во Framework, практикум снова превратится в каталог возможностей — именно от этого подхода архитектурный паспорт отказывается.

# 9. Контроль полноты матрицы

Перед превращением этой матрицы в последовательность практических этапов нужно проверить:

```text
1. Каждое обязательное требование имеет реальный предметный смысл?
2. Каждый новый DocType доказал самостоятельную ответственность?
3. Для каждого DocType осознанно выбрана стратегия name?
4. Не введён ли Workflow только ради статусов?
5. Не введён ли docstatus только ради финального значения status?
6. Все критические инварианты имеют серверную гарантию?
7. Не выдаётся ли простая validate-проверка за полную гарантию конкурентного бронирования?
8. Права начинаются со штатной модели Role/Permissions?
9. UI следует за моделью, а не определяет её?
10. Не появился ли собственный API, дублирующий Document REST API?
11. Обязательное состояние App воспроизводимо из Git?
12. Есть ли механизмы, включённые только ради «покрытия Frappe»?
```

Если ответ на пункт 12 — да, такие элементы удаляются до составления программы.

# 10. Что делать после согласования матрицы

Только после утверждения требований строится **граф зависимостей практических этапов**.

Не задаём заранее количество уроков. Последовательность должна следовать зависимостям самой системы, например:

```text
нельзя проверять Link до появления связанных DocTypes;
нельзя проверять permissions до появления Documents;
нельзя проверять Workflow до появления реального требования согласования;
нельзя проверять чистую установку до появления состояния App, которое нужно воспроизводить.
```

Из этого графа уже выводятся этапы, критерии готовности и финальная дорожная карта практикума.
