# 2. CORE — модель данных

## R01. Equipment существует независимо от Rental

**Ответственность:** самостоятельная сущность с собственной идентичностью.

**Первый механизм:** Standard DocType `Equipment`.

**Почему:** Equipment переиспользуется в разных Rentals и имеет собственные свойства.

**Граница:** не создавать отдельные DocTypes для каждого простого свойства.

---

## R02. Customer существует независимо от Rental

**Ответственность:** самостоятельная сущность клиента.

**Первый механизм:** Standard DocType `Customer`.

**Почему:** один Customer участвует во многих Rentals.

**Граница:** Rental не хранит имя Customer как текстовую копию вместо связи.

---

## R03. Rental — основной рабочий Document

**Ответственность:** самостоятельная операция проката.

**Первый механизм:** Standard DocType `Rental`.

**Граница:** Workflow и Is Submittable не включаются без отдельного требования.

---

## R04. Rental содержит несколько Equipment

**Ответственность:** принадлежащий Rental набор ссылок на Equipment.

**Первый механизм:** минимальный Child DocType `Rental Item` + `Table MultiSelect` в Rental.

**Почему:** текущая строка отношения содержит только `Link → Equipment`; отдельного самостоятельного lifecycle у неё нет.

**Граница:** обычный `Table` становится естественнее, если у строки появляются собственные бизнес-атрибуты отношения.

---

## R05. Rental ссылается на существующие Customer и Equipment

```text
Rental.customer       → Link → Customer
Rental Item.equipment → Link → Equipment
```

**Первый механизм:** `Link`.

**Граница:** Dynamic Link не используется ради абстрактной «универсальности»; текстовая копия допустима только при отдельном snapshot-требовании.

---

## R06. Тип Equipment — маленький стабильный список

**Первый механизм:** `Select`.

**Граница:** отдельный `Equipment Type` появится только когда тип получит собственные свойства/управление.

---

# 3. CORE — состояние и серверные правила

## R08. Rental имеет рабочее состояние

Значения CORE:

```text
Planned
Active
Returned
```

**Первый механизм:** обычное поле `Select`.

**Граница:** business status ≠ Workflow ≠ docstatus.

---

## R09. End Date не может быть раньше Start Date

**Ответственность:** инвариант данных Rental.

**Первый механизм:** серверный `Rental Controller.validate()`.

**Граница:** Client Script может быть UX-подсказкой, но не единственной гарантией.

**Проверка:** обычный `Document.insert()` отклоняет неправильный период без Form.

---

## R10. Equipment не повторяется внутри одного Rental

**Ответственность:** локальный инвариант Rental.

**Первый механизм:** серверный `Rental Controller.validate()`.

**Почему:** `Table MultiSelect` — подходящий UI/control для набора, но browser control не является гарантией данных для других путей создания Document.

**Граница:** отдельный движок правил ради одной проверки не нужен.

**Проверка:** программно сформировать Rental с двумя одинаковыми child rows и убедиться, что обычный `Document.insert()` отклонён.

---

## R11. Нет пересекающихся Active Rentals одного Equipment

**Ответственность:** междокументный инвариант Rental.

**Первый механизм:** `Rental Controller.validate()` + штатный Database API.

CORE-семантика:

```text
Planned  → не блокирует
Active   → блокирует
Returned → не блокирует
```

Периоды включительны и конфликтуют, если:

```text
existing.start_date <= current.end_date
AND
existing.end_date >= current.start_date
```

Внутренний validator должен учитывать реальный конфликт независимо от permission-filtering пользовательского List. Поэтому системное чтение через `frappe.get_all()` здесь допустимо намеренно; пользовательские выборки от этого не перестают быть permission-aware.

При редактировании текущий Rental исключается из поиска по `name`, чтобы не возникал self-conflict.

**Граница:** обычная `validate()`-проверка гарантирует обнаружение уже существующего конфликта при последовательном сохранении, но не является полной стратегией конкурентного бронирования. Параллельные транзакции, locking/reservation strategy — отдельная production-задача.

# 4. CORE — безопасность и UI

## R13. Оператор и менеджер имеют разные права

**Первый механизм:** `Role` + `DocType Permissions`.

**Граница:** собственная ACL не вводится, пока штатной модели достаточно.

**Проверка:** войти под разными пользователями и проверить фактические операции.

---

## R16. Базовый сценарий работает без собственного frontend

**Первый механизм:** Desk `Form` + `List`.

**Граница:** custom frontend появляется только под отдельное UX-требование.

**Проверка:** полностью пройти создание Equipment → Customer → Rental через стандартный Desk.

---

# 5. NEXT — второй контур

## R07. Одна настройка уровня Site

Если появляется реальное глобальное значение приложения, первый кандидат — `Single DocType` `Rental Settings`.

Без такого требования Single не добавляется ради покрытия.

## R12. История, комментарии, файлы

Первый кандидат — `Version`/Timeline, `Comment`, `File`/Attach.

Не создавать собственные `Rental History`, `Rental Comment`, `Rental Attachment` без другой семантики.

## R14. Поля только менеджеру

Первый кандидат — `Permission Level`.

Без реального чувствительного поля механизм не включается.

## R15. Назначить Rental сотруднику

Первый кандидат — `Assignment` / `ToDo`.

Если ответственный является историческим бизнес-фактом, может понадобиться обычное Link-поле; это другой смысл.

## R17. Единая точка входа

Первый кандидат — `Workspace`.

## R18. Rentals по датам

Первый кандидат — Calendar view. Новая сущность ради календаря не создаётся.

## R19. Акт выдачи

Первый кандидат — `Print Format`.

## R20. Простой рабочий отчёт

Первый кандидат — `Report Builder`. Query/Script Report появляются только после конкретного требования, которое Report Builder не выражает.

# 6. Обязательное архитектурное решение — naming

## D00. Naming — CORE decision

Для каждого самостоятельного DocType нужно осознанно выбрать стратегию `name`.

Первый механизм: штатные naming strategies (`Naming Series`, field/expression, `autoname`, UUID и т. д.).

Граница: изменяемое бизнес-поле не выбирается вечным ID только потому, что сегодня оно уникально.

Это решение принимается при создании `Equipment`, `Customer` и `Rental`, до того как на их `name` начнут опираться ссылки и пользовательские сценарии.

# 7. GATE — архитектурные развилки

## D01. Менеджер подтверждает выдачу

Появились состояния + переходы + роли.

Первый кандидат: `Workflow`.

Граница: обычный status сам по себе не требует Workflow.

---

## D02. Выдача становится зафиксированным фактом

После фактической выдачи ключевые данные нельзя свободно переписывать, ошибочную операцию нужно отменять.

Первый кандидат: `Is Submittable` / `docstatus`.

Граница: `Returned` не означает Submitted. Workflow и docstatus отвечают на разные вопросы.

---

## D03. Equipment Type стал самостоятельной сущностью

Если у типа появились свойства, активность и управление, `Select` пересматривается в отдельный `Equipment Type` + Link.

При существующих данных отдельно решается миграция.

---

## D04. Внешний посетитель оставляет заявку

Сначала решается предметная модель: это Rental или отдельный `Rental Request`?

Только после этого первый UI-кандидат — `Web Form`.

---

## D05. Напоминание о возврате

Первый кандидат — `Notification`.

Scheduler/background job появляется только если конкретное требование выходит за семантику Notification.

---

# 8. EXT — API и интеграции

## E01. Внутренний клиент делает обычный CRUD

Первый механизм: Document REST API.

Не создавать собственные `/create_rental`/`read`/`update`/`delete`, если они только переименовывают штатный CRUD.

## E02. Предметная команда `return_rental`

Первый кандидат: Document method или whitelisted method — если операция действительно имеет командную семантику и правила.

## E03. Исходящее HTTP-событие

Первый кандидат: `Webhook`.

Сложные гарантированные повторы, сверка и идемпотентность создают уже отдельную интеграционную ответственность.

# 10. Контроль перед следующим документом

1. CORE содержит только реальные требования?
2. Каждый DocType имеет самостоятельный смысл?
3. Naming выбран до появления зависимых Links?
4. Workflow не используется только из-за нескольких статусов?
5. docstatus не подменяет business status?
6. Инварианты гарантируются серверным Document-путём?
7. Междокументный invariant не зависит случайно от permission-filtering пользовательского List?
8. Concurrency boundary V03 названа честно?
9. Права начинаются с Role + DocPerm?
10. UI следует за моделью?
11. API не дублирует обычный CRUD?
12. App state и Site data разделены?
13. Финальный критерий проверяется на clean Site?
