# Матрица требований учебного практикума Frappe

Статус: **черновик для архитектурной проверки**.

Этот документ продолжает [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md). Следующий слой — [`STAGE_DEPENDENCY_GRAPH.md`](STAGE_DEPENDENCY_GRAPH.md).

Матрица не задаёт программу занятий и не является списком функций, которые надо обязательно «пройти». Она проверяет, что каждый механизм Frappe появляется из понятного требования:

```text
требование
    ↓
ответственность
    ↓
первый штатный механизм Frappe
    ↓
почему его семантика подходит
    ↓
где проходит граница
    ↓
что проверить руками
```

Нормативная база — [`docs/frappe-architecture-standard`](../frappe-architecture-standard/README.md), в первую очередь разделы о модели данных, lifecycle, security, API, UI/reporting, deployment/testing и decision standard.


# 2. Основная модель и правила

## R01. Вести отдельный реестр оборудования — CORE

**Требование**  
Каждая единица оборудования существует независимо от выдачи: её нужно создать один раз, находить, открывать и использовать во многих операциях проката.

**Ответственность**  
Самостоятельная предметная запись с собственной идентичностью.

**Первый штатный механизм Frappe**  
Standard `DocType` `Equipment`.

**Почему подходит**  
Оборудование является самостоятельным `Document`, а не свойством конкретного Rental.

**Граница**  
Не создавать отдельные `DocType` для каждого простого свойства оборудования.

**Что проверить руками**  
Создать несколько Equipment, открыть их через `Form`/`List`, найти запись и сослаться на неё из другого Document.

---

## R02. Вести отдельный реестр клиентов — CORE

**Требование**  
Один клиент может брать оборудование много раз.

**Ответственность**  
Самостоятельная справочная запись.

**Первый штатный механизм Frappe**  
Standard `DocType` `Customer`.

**Почему подходит**  
Customer существует независимо от Rental и используется многими Rentals.

**Граница**  
Имя клиента в Rental не должно заменять настоящую связь. Исторический снимок реквизитов, если понадобится, является отдельным требованием.

**Что проверить руками**  
Создать Customer и использовать одну запись в нескольких Rentals.

---

## R03. Оформлять прокат как отдельный рабочий документ — CORE

**Требование**  
Нужно хранить клиента, даты проката, состав оборудования и текущее состояние операции.

**Ответственность**  
Самостоятельный рабочий `Document`.

**Первый штатный механизм Frappe**  
Standard `DocType` `Rental`.

**Почему подходит**  
Rental имеет идентичность, открывается отдельно и объединяет одну операцию.

**Граница**  
На этом этапе Rental не объявляется автоматически `Is Submittable` и не получает `Workflow` только из-за наличия состояний.

**Что проверить руками**  
Создать, сохранить, открыть и изменить Rental через стандартную форму.

---

## R04. В одной выдаче несколько единиц оборудования — CORE

**Требование**  
Один Rental содержит несколько строк оборудования.

**Ответственность**  
Состав одного родительского Document.

**Первый штатный механизм Frappe**  
`Rental Item` как `Child DocType` + поле `Table` в Rental.

**Почему подходит**  
Строка принадлежит одному Rental и не является отдельной операцией.

**Граница**  
Если строке понадобится самостоятельный lifecycle, права или независимые ссылки, решение пересматривается.

**Что проверить руками**  
Добавить несколько строк, сохранить Rental и убедиться, что строки остаются частью родителя.

---

## R05. Выбирать клиента и оборудование из существующих записей — CORE

**Требование**  
Rental ссылается на конкретного Customer, Rental Item — на конкретное Equipment.

**Ответственность**  
Живая связь между Documents.

**Первый штатный механизм Frappe**  
`Link`.

**Почему подходит**  
Тип цели известен заранее и нужна настоящая связь с существующей записью.

**Граница**  
Не использовать `Dynamic Link` ради абстрактной универсальности и не копировать текст вместо ссылки без требования снимка.

**Что проверить руками**  
Выбрать существующие записи через Link и открыть связанные Documents.

---

## R06. Небольшой стабильный тип оборудования — CORE

**Требование**  
Для Equipment нужен тип вроде `Tool`, `Camera`, `Computer`, но у типа нет собственных атрибутов или lifecycle.

**Ответственность**  
Простое свойство Equipment.

**Первый штатный механизм Frappe**  
`Select`.

**Почему подходит**  
Малый стабильный набор значений пока не является самостоятельным бизнес-объектом.

**Граница**  
Если у типа появятся собственные свойства, права, активность или управление, появляется основание для отдельного `Equipment Type` DocType.

**Что проверить руками**  
Фильтровать Equipment по Select и объяснить, почему отдельный справочник пока не нужен.

---

## R07. Один набор настроек приложения на Site — NEXT

**Требование**  
Появилось значение уровня всего Site, например стандартная длительность проката.

**Ответственность**  
Один набор конфигурации.

**Первый штатный механизм Frappe**  
`Rental Settings` как `Single DocType`.

**Почему подходит**  
На одном Site должна существовать ровно одна такая конфигурация.

**Граница**  
Если общей настройки в принятом сценарии нет, `Single` не добавляется ради покрытия. Если настройка различается по филиалам/компаниям, Single перестаёт соответствовать модели.

**Что проверить руками**  
Если требование принято, изменить Single и использовать значение из Rental.

---

## R08. Рабочее состояние проката — CORE

**Требование**  
Нужно различать, например, `Planned`, `Active`, `Returned`.

**Ответственность**  
Предметное состояние Rental.

**Первый штатный механизм Frappe**  
Обычное поле `status` (`Select`).

**Почему подходит**  
Пока требуется только хранить состояние, а не управлять переходами по ролям или фиксировать транзакционный факт.

**Граница**  
Несколько значений сами по себе не требуют `Workflow` или `docstatus`. Предметный status без причины не копирует `Draft / Submitted / Cancelled`.

**Что проверить руками**  
Изменить status и отфильтровать Rentals в List.

---

## R09. Дата окончания не раньше даты начала — CORE

**Требование**  
Некорректный Rental не должен появиться независимо от способа создания.

**Ответственность**  
Инвариант данных.

**Первый штатный механизм Frappe**  
Серверная проверка в `Controller.validate()`.

**Почему подходит**  
Правило должно работать не только в браузерной форме, но и через API, импорт и серверный код.

**Граница**  
Client Script может дополнить UX, но не является единственной гарантией.

**Что проверить руками**  
Попробовать сохранить неправильные даты и проверить то же правило серверным тестом.

---

## R10. Одно Equipment не повторяется в одном Rental — CORE

**Требование**  
В составе одной выдачи нельзя дважды указать одно оборудование.

**Ответственность**  
Инвариант одного Rental.

**Первый штатный механизм Frappe**  
Проверка в Controller Rental.

**Граница**  
Не создавать отдельный движок правил ради одной проверки.

**Что проверить руками**  
Попробовать сохранить Rental с дублем и получить понятную ошибку.

---

## R11. Equipment нельзя выдать на пересекающиеся активные периоды — CORE

**Требование**  
Новый Rental не должен конфликтовать с существующей активной выдачей того же Equipment.

**Ответственность**  
Бизнес-проверка, использующая несколько Documents.

**Первый штатный механизм Frappe**  
Серверная логика Rental + штатный Query/Database API.

**Почему подходит**  
Это всё ещё инвариант Rental, хотя для проверки нужно читать другие Rentals.

**Граница**  
Обычный `validate()` демонстрирует правильное размещение правила, но не является полной стратегией конкурентного бронирования. Параллельные транзакции и блокировки — отдельная production-задача.

**Что проверить руками**  
Последовательно создать конфликтующий Rental и увидеть серверный запрет; отдельно зафиксировать границу для конкурентных запросов.

---

## R12. История изменений, комментарии и файлы — NEXT

**Требование**  
Пользователь должен видеть обычную историю Document, обсуждать Rental и прикладывать файлы.

**Первый штатный механизм Frappe**  
`Track Changes` / `Version`, `Comment`, `File` / Attach.

**Граница**  
Юридически значимый неизменяемый журнал может иметь другую семантику. Если история/обсуждение не нужны учебному сценарию, отдельный шаг не создаётся.

**Что проверить руками**  
Если требование принято, использовать Timeline/Comment/File без собственных `Rental History`, `Rental Comment`, `Rental Attachment`.

---

# 3. Права и работа пользователей

## R13. Оператор и менеджер имеют разные права — CORE

**Требование**  
Оператор работает с Rentals, менеджер имеет более широкие возможности.

**Ответственность**  
Доступ к DocType по роли.

**Первый штатный механизм Frappe**  
`Role` + `DocType Permissions`.

**Граница**  
Не переходить к собственной ACL, пока штатных permissions достаточно.

**Что проверить руками**  
Войти под двумя пользователями и проверить реальные Create/Read/Write/Delete/Report-права.

---

## R14. Некоторые поля доступны только менеджеру — NEXT

**Требование**  
Появилось реально чувствительное поле Rental.

**Первый штатный механизм Frappe**  
`Permission Level` (`permlevel`).

**Граница**  
JavaScript-скрытие не является защитой. Без реального чувствительного поля `permlevel` не добавляется ради демонстрации.

---

## R15. За Rental отвечает сотрудник — NEXT

**Требование**  
Нужно назначить работу конкретному человеку и видеть её в его очереди.

**Первый штатный механизм Frappe**  
`Assignment` / `ToDo`.

**Граница**  
Если ответственный — исторический бизнес-факт Rental, это может быть отдельное поле Link. Если назначения в процессе нет, Assignment не включается ради покрытия.

---

# 4. Интерфейс и вывод

## R16. Работать без собственного frontend — CORE

**Требование**  
Нужны карточки и реестры Equipment, Customer, Rental.

**Первый штатный механизм Frappe**  
Desk `Form` + `List`.

**Граница**  
Собственный frontend рассматривается только при отдельном UX-требовании, которого Desk не выражает.

**Что проверить руками**  
Полностью пройти базовый сценарий через стандартный Desk.

---

## R17. Единая рабочая точка входа — NEXT

Механизм: `Workspace`. Если обычной навигации достаточно, отдельный шаг не нужен.

## R18. Видеть Rentals по датам — NEXT

Механизм: Calendar view. Новая сущность ради календаря не создаётся.

## R19. Печатать акт выдачи — NEXT

Механизм: `Print Format`. Отдельный PDF-сервис появляется только под специальные требования.

## R20. Простой реестр активных Rentals — NEXT

Первый механизм: `Report Builder`. `Query Report`/`Script Report` появляются только после конкретной границы Report Builder.

# 5. GATE — архитектурные развилки

## D00. Выбрать стратегию `name`

Для каждого самостоятельного DocType нужно осознанно решить, является `name` техническим ID или бизнес-номером.

Первый механизм: штатные naming strategies (`Naming Series`, field/expression, `autoname`, UUID и т. д.).

Граница: не выбирать изменяемое поле вечным ID только потому, что сегодня оно уникально.

---

## D01. Менеджер подтверждает выдачу

Требование добавляет состояния, переходы и роли.

Первый кандидат: `Workflow`.

Граница: наличие status само по себе не доказывает необходимость Workflow.

---

## D02. Выдача становится зафиксированным фактом

После фактической выдачи ключевые данные нельзя свободно переписывать, ошибочную операцию нужно отменять.

Первый кандидат: `Is Submittable` / `docstatus`.

Граница: рабочий status `Returned` не означает Submitted. Workflow и docstatus решают разные задачи.

---

## D03. Equipment Type перестал быть простым списком

Если у типа появляются свои атрибуты и управление, `Select` пересматривается в пользу отдельного `Equipment Type` + Link.

При существующих данных отдельно проектируется миграция.

---

## D04. Внешний посетитель оставляет заявку

Сначала решается предметный вопрос: это уже Rental или отдельный `Rental Request`? Только после этого проверяется `Web Form`.

Web Form — представление/ввод, а не ответ на вопрос о модели.

---

## D05. Напоминание о возврате

Первый кандидат: `Notification`.

Scheduler/background job появляется только если реальное требование перерастает семантику Notification.

---

# 6. EXT — API и интеграции

## E01. Внутренний клиент читает/создаёт Rentals

Первый механизм: Document REST API.

Не создавать собственный CRUD API, если он только переименовывает стандартные операции.

## E02. Команда `return_rental`

Если операция имеет предметный смысл и правила, рассматривается метод Document или whitelisted method, а не произвольное изменение поля.

## E03. Внешняя система получает событие

Первый механизм для простого исходящего события: `Webhook`.

Если нужны гарантированные повторы, сверка, идемпотентность и сложное преобразование, появляется отдельная интеграционная ответственность.

# 7. Доставка, миграции и тесты

## R21. Обязательная модель принадлежит App — CORE

Другой Site после установки должен получить те же обязательные элементы.

Механизмы: Standard DocType JSON, fixtures/exported configuration по смыслу, `bench migrate`.

---

## R22. Изменение модели не требует ручного SQL — CORE

Schema sync выполняется через migrate; `patch` используется только когда существующие данные реально нужно преобразовать.

---

## R23. Критические правила защищены тестами — CORE

Тестируются наши инварианты и permissions, а не сам факт работы Framework.

Нужно намеренно сломать одно правило и увидеть падение соответствующего теста.

---

## R24. Финальная установка чистая и воспроизводимая — CORE

```text
чистый Frappe Site
+ App из Git
+ install-app
+ migrate
+ tests
= рабочее обязательное состояние
```

После этого повторяется основной пользовательский сценарий.

---

# 8. Что сознательно не является обязательным

На текущем CORE нет основания обязательно включать:

```text
Single DocType
Virtual DocType
Dynamic Link
Tree DocType
Packages
Server Script
Permission Level
User Permission
Share
permission hooks
Assignment
Workspace
Calendar
Print Format
Report Builder
Workflow
docstatus/Web Form
Notification
Realtime API
Background Jobs
REST integration
custom frontend
override/extend hooks
fork Frappe
```

Это не список ненужных функций. Это механизмы, для которых обязательная предметная область пока не предъявила требования с совпадающей семантикой.

# 9. Контроль перед дорожной картой

```text
1. Каждое CORE-требование имеет реальный предметный смысл?
2. Каждый DocType доказал самостоятельную ответственность?
3. Workflow не введён только ради статусов?
4. docstatus не введён только ради финального status?
5. Критические инварианты имеют серверную гарантию?
6. Права начинаются со штатной Role/Permissions-модели?
7. UI следует за моделью?
8. API не дублирует Document REST без причины?
9. App-состояние отделено от Site-настройки?
10. Финал проверяется на чистом Site?
```

Если ответ на любой вопрос отрицательный, сначала исправляется матрица/граф, а не дорожная карта.
