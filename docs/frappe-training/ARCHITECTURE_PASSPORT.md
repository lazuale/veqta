# Архитектурный паспорт учебного практикума Frappe

Статус: **черновик архитектуры для согласования**.

Этот документ фиксирует основу нового учебного практикума по Frappe Framework 16. Практикум не связан с VEQTA, не использует её предметную область и не наследует решения предыдущих версий.

Нормативная база — [`docs/frappe-architecture-standard`](../frappe-architecture-standard/README.md). Если учебное решение противоречит стандарту, исправляется практикум, а не стандарт подгоняется под занятие.

Связанные документы:

- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md) — требования и выбор механизмов;
- [`STAGE_DEPENDENCY_GRAPH.md`](STAGE_DEPENDENCY_GRAPH.md) — реальные зависимости между практическими результатами.

---

## 1. Цель

Практикум должен научить **строить небольшое приложение так, как предполагает сам Frappe**, а не проходить каталог функций Framework.

Для каждого требования ученик должен уметь ответить:

```text
1. Какая ответственность появилась?
2. Какой штатный механизм Frappe уже отвечает за неё?
3. Совпадает ли его смысл с требованием?
4. Если нет — какая официальная точка расширения подходит?
5. Какую новую ответственность действительно добавляет собственный код?
```

Основание:

- [`01_FOUNDATIONS.md`](../frappe-architecture-standard/01_FOUNDATIONS.md);
- [`10_DECISION_STANDARD.md`](../frappe-architecture-standard/10_DECISION_STANDARD.md);
- [`12_EVIDENCE_REGISTER.md`](../frappe-architecture-standard/12_EVIDENCE_REGISTER.md).

---

## 2. Чем практикум не является

Это не:

- энциклопедия всех возможностей Frappe;
- последовательность «урок DocType → урок Workflow → урок Report»;
- курс no-code;
- курс Python;
- демонстрация VEQTA;
- попытка обязательно использовать каждый механизм Framework;
- набор искусственных требований ради очередной функции.

Наличие кода само по себе не считается плохой архитектурой. Плохой признак — собственный механизм, который без причины дублирует уже существующую ответственность Frappe.

---

## 3. Учебная предметная область

Практикум строится вокруг **небольшого сервиса проката оборудования**.

Предметная область удобна тем, что без искусственного усложнения даёт:

- самостоятельные записи;
- документ с несколькими строками;
- связи между Documents;
- рабочее состояние;
- серверные инварианты;
- роли и права;
- возможность позже добавить реальные ветки настроек, печати, отчётов, уведомлений, внешнего ввода и API.

Но ни одна такая ветка не становится обязательной только потому, что она существует во Frappe.

## 4. Минимальная CORE-модель

На старте обязательны только:

```text
Equipment
Customer
Rental
└── Rental Item [Child DocType]
```

### Equipment

Самостоятельный объект проката:

- имеет идентичность;
- существует независимо от одной выдачи;
- участвует во многих Rentals;
- открывается и ищется отдельно.

### Customer

Самостоятельный клиент:

- существует независимо от Rental;
- участвует во многих Rentals;
- Rental ссылается на него через `Link`.

### Rental

Главный рабочий Document, объединяющий клиента, период, состав оборудования и предметное состояние.

`Rental` заранее **не** объявляется `Is Submittable` и не получает `Workflow`. Эти решения появляются только после требований с соответствующей семантикой.

### Rental Item

Часть одного Rental, поэтому начальное решение — `Child DocType`.

Если позднее строка получит самостоятельную идентичность, права, жизненный цикл или независимые ссылки, модель пересматривается по [`02_DATA_MODEL.md`](../frappe-architecture-standard/02_DATA_MODEL.md).

## 5. Что не создаётся заранее

В CORE заранее нет отдельных:

```text
Equipment Type
Rental Settings
Rental Status
Priority
Rental History
Rental Comment
Rental Assignee
Approval
Notification Log
Attachment
Rental Request
```

Причины должны появляться из требований:

- небольшой стабильный тип оборудования → сначала `Select`;
- один набор настроек всего Site → тогда кандидат `Single DocType`;
- история → сначала штатные `Version`/Timeline;
- комментарии → штатный `Comment`;
- файлы → штатный `File`/Attach;
- назначение работы → сначала `Assignment`/`ToDo`;
- обычный status не требует отдельного справочника;
- несколько состояний сами по себе не требуют `Workflow`;
- публичная форма сама по себе не доказывает необходимость отдельного `Rental Request`.

Это не запрет на эти решения. Это запрет вводить их **до появления их собственной ответственности**.

## 6. Архитектурная карта среды

```text
Bench
├── доступные Apps
└── Sites
     └── учебный Site
          └── установлен учебный App

Учебный App
└── Module
     ├── Standard DocTypes
     ├── Controllers
     ├── Reports при необходимости
     ├── Workspace при необходимости
     ├── fixtures / patches при необходимости
     └── другие штатные компоненты App
```

`Bench` — среда управления, не слой предметной архитектуры.

`Site` — конкретный экземпляр со своей БД и конфигурацией.

`App` — устанавливаемый пакет исходного кода и метаданных.

`Module` — штатная группировка внутри App, а не автоматически bounded context или отдельное приложение.

`DocType`/`Document` — центральная прикладная модель.

## 7. Правило появления механизма

```text
реальное требование
    ↓
ответственность
    ↓
штатный механизм Frappe
    ↓
совпадает ли семантика?
    ├─ да → использовать
    └─ нет → официальная точка расширения
                   ↓
              собственная новая ответственность
```

Нельзя вводить шаг формулировкой:

> Теперь изучим Workflow.

Нормальная формулировка:

> Менеджер должен подтверждать выдачу, а оператор не имеет права выполнить этот переход. Проверяем, выражается ли это штатным Workflow.

Это правило действует одинаково для `Workflow`, `docstatus`, `Notification`, `Assignment`, `Web Form`, Reports, hooks, Controller-кода и API.

---

## 8. Правило модели данных

```text
обычное свойство             → DocField
самостоятельный Document     → обычный DocType
состав одного Document       → Child DocType
ссылка на существующий Doc   → Link
одна конфигурация на Site    → Single DocType
```

`Dynamic Link`, `Virtual DocType`, отдельный DocType связи и другие варианты появляются только после соответствующего требования.

Нормативная база: [`02_DATA_MODEL.md`](../frappe-architecture-standard/02_DATA_MODEL.md).

---

## 9. Состояние и жизненный цикл

Практикум обязан различать:

```text
бизнес-статус = что происходит с объектом
Workflow      = кто и при каких условиях может выполнить переход
docstatus     = Draft / Submitted / Cancelled транзакционного Document
```

`Rental = Returned` не является автоматическим основанием делать Rental Submitted.

`Is Submittable` появляется только если возникает смысл зафиксированного факта, который нельзя свободно переписывать.

Нормативная база: [`03_DOCUMENT_LIFECYCLE.md`](../frappe-architecture-standard/03_DOCUMENT_LIFECYCLE.md).

## 10. Размещение логики

Не используется лестница «no-code → low-code → Python».

Используется ответственность:

```text
удобство формы                  → клиентский механизм
инвариант данных                → серверный путь
поведение собственного DocType  → Controller
реакция на чужой DocType        → официальная точка расширения
сложная операция нескольких Docs → service, если появилась отдельная ответственность
```

Критическое правило не считается реализованным, если оно существует только в Client Script или скрытой кнопке.

---

## 11. Права

Стартовая модель:

```text
User
Role
DocType Permissions
```

`Permission Level`, `Permission Type`, `If Owner`, `User Permission`, `Share`, permission hooks и собственная политика появляются только после требования, которое базовая модель не выражает.

UI-скрытие не является защитой данных.

Нормативная база: [`04_SECURITY.md`](../frappe-architecture-standard/04_SECURITY.md).

---

## 12. UI следует за моделью

```text
бизнес-объект
    ↓
DocType + fields + lifecycle + permissions
    ↓
подходящее представление
```

`Form` и `List` — нормальный интерфейс по умолчанию для обычной административной работы.

`Calendar`, `Report`, `Workspace`, `Web Form`, Portal или собственный frontend подключаются под реальное пользовательское требование.

Новая сущность не создаётся только ради нового экрана.

Нормативная база: [`08_UI_REPORTING.md`](../frappe-architecture-standard/08_UI_REPORTING.md).

---

## 13. Site и App — разные владельцы состояния

Нужно различать:

```text
локальную настройку конкретного Site
```

и

```text
обязательное состояние устанавливаемого App
```

Если Role, поле, DocType или другая конфигурация объявлена частью App, она не должна существовать только благодаря ручному действию на одном dev-site.

Для доставки используются штатные механизмы по смыслу: Standard DocType JSON, fixtures, exported customizations, patches и т. д.

Нормативная база:

- [`07_EXTENSION_CUSTOMIZATION.md`](../frappe-architecture-standard/07_EXTENSION_CUSTOMIZATION.md);
- [`09_DEPLOYMENT_TESTING.md`](../frappe-architecture-standard/09_DEPLOYMENT_TESTING.md).

## 14. Финальный критерий

Практикум завершён не тогда, когда dev-site «как-то работает».

```text
чистый совместимый Frappe Site
+ учебный App из Git
+ install-app
+ migrate
+ tests
= рабочее обязательное состояние приложения
```

Все обязательные элементы App восстанавливаются без скрытого списка ручных действий в БД или интерфейсе.

Тестируются наши критические контракты, а не сам Framework без причины.

---

## 15. Критерий качества учебного шага

Каждый шаг обязан отвечать:

```text
Требование: что понадобилось пользователю?
Ответственность: что должна обеспечивать система?
Штатный механизм: что для этого предусмотрел Frappe?
Почему подходит: какая семантика совпала?
Граница: когда механизма станет недостаточно?
Результат: что ученик реально увидит работающим?
```

Если нельзя объяснить, зачем механизм появился, шаг не включается.
