# Архитектурный паспорт учебного практикума Frappe

Статус: **черновик архитектуры для согласования**.

Этот документ фиксирует основу нового учебного практикума по Frappe Framework 16. Практикум не связан с VEQTA, не использует её предметную область и не наследует решения предыдущих версий практикума.

Нормативная архитектурная база практикума — [`docs/frappe-architecture-standard`](../frappe-architecture-standard/README.md). Если учебное решение противоречит этому стандарту, исправляется практикум, а не стандарт подгоняется под занятие.

---

## 1. Зачем нужен практикум

Цель — научиться **строить небольшое приложение так, как предполагает сам Frappe**, а не пройти каталог его функций.

После практикума ученик должен уметь для обычного требования ответить на четыре вопроса:

1. Какая ответственность появилась в приложении?
2. Какой штатный механизм Frappe отвечает за эту ответственность?
3. Совпадает ли смысл этого механизма с требованием?
4. Если штатного механизма недостаточно, какая официальная точка расширения подходит и какую новую ответственность добавляет собственный код?

Это напрямую следует из архитектурного стандарта:

- [`01_FOUNDATIONS.md`](../frappe-architecture-standard/01_FOUNDATIONS.md) — устройство Framework, App, Site, DocType/Document и принцип configuration over code;
- [`10_DECISION_STANDARD.md`](../frappe-architecture-standard/10_DECISION_STANDARD.md) — процедура выбора штатного механизма;
- [`12_EVIDENCE_REGISTER.md`](../frappe-architecture-standard/12_EVIDENCE_REGISTER.md) — первичные основания архитектурных утверждений.

---

## 2. Чего практикум не делает

Практикум **не является**:

- энциклопедией всех функций Frappe;
- последовательностью «урок DocType → урок Workflow → урок Report → урок Web Form»;
- курсом no-code;
- курсом Python-разработки;
- демонстрацией VEQTA;
- попыткой обязательно использовать каждый механизм Framework;
- набором искусственных задач, придуманных только ради показа очередной функции.

Наличие кода само по себе не считается усложнением. Ошибкой считается собственный механизм, который без необходимости дублирует уже существующую ответственность Frappe.

---

## 3. Учебная предметная область

Практикум строится вокруг **небольшого сервиса проката оборудования**.

Предметная область выбрана не как готовая архитектура, а как нейтральная задача, в которой естественно возникают:

- самостоятельные справочные записи;
- документ с несколькими строками;
- связи между Documents;
- настройки сайта;
- рабочее состояние;
- ограничения и проверки;
- роли и права;
- печатное представление;
- отчётность;
- уведомления;
- внешний ввод данных;
- необходимость воспроизводимой установки приложения.

Предметная область не должна усложняться только для того, чтобы «показать больше Frappe».

## 4. Минимальная модель

На старте допускаются только четыре самостоятельных решения и одна дочерняя модель.

```text
Equipment
Customer
Rental
└── Rental Item [Child DocType]

Rental Settings [Single DocType]
```

### Equipment

Самостоятельный объект проката.

Причина отдельного `DocType`:

- имеет собственную идентичность;
- существует независимо от одной конкретной выдачи;
- используется во многих Rentals;
- должен находиться и открываться отдельно.

### Customer

Самостоятельный клиент.

Причина отдельного `DocType`:

- существует независимо от конкретного Rental;
- один Customer может участвовать в нескольких Rentals;
- Rental должен ссылаться на конкретную запись клиента через `Link`.

### Rental

Главный рабочий документ практикума.

Он связывает клиента, период проката и состав выданного оборудования.

`Rental` не объявляется заранее `Is Submittable`, не получает `Workflow` и не обрастает дополнительными сущностями. Эти решения допускаются только после появления требования, семантика которого действительно совпадает с соответствующим механизмом Frappe.

### Rental Item

Строка состава одного Rental.

Начальное решение — `Child DocType`, потому что строка является частью одного родительского документа, а не самостоятельным бизнес-объектом.

Если позднее появится требование, которое придаёт строке собственную идентичность, жизненный цикл или независимые ссылки, решение пересматривается по правилам [`02_DATA_MODEL.md`](../frappe-architecture-standard/02_DATA_MODEL.md).

### Rental Settings

Один набор настроек для сайта.

Начальное решение — `Single DocType`, потому что для одного Site предполагается ровно одна конфигурация этого приложения.

## 5. Что намеренно не создаём заранее

На старте **нет** отдельных `DocType` для:

```text
Equipment Type
Rental Status
Priority
Rental History
Rental Comment
Rental Assignee
Approval
Notification Log
Attachment
```

Каждый такой объект сначала обязан доказать самостоятельный бизнес-смысл.

Например:

- небольшой стабильный набор типов оборудования может быть `Select`;
- обычная история изменений уже поддерживается Frappe;
- комментарии уже существуют в модели `Document`;
- файлы уже имеют штатный механизм;
- рабочее назначение сначала проверяется через Assignment/ToDo;
- простое поле состояния не требует отдельного справочника статусов;
- наличие нескольких состояний само по себе не требует `Workflow`.

Это не запрет на перечисленные решения. Это запрет вводить их **до появления ответственности, которую они реально выражают**.

## 6. Архитектурная модель, которую должен увидеть ученик

Учебная схема должна объясняться так:

```text
Bench
├── доступные Apps
└── Sites
     └── учебный Site
          └── установлен учебный App

Учебный App
└── Module
     ├── Standard DocTypes
     ├── Controllers
     ├── Reports
     ├── Workspace
     ├── fixtures / patches при необходимости
     └── другие штатные компоненты App
```

`Bench` — среда управления, а не слой предметной архитектуры приложения.

`Site` — конкретный экземпляр системы с собственной БД и конфигурацией.

`App` — устанавливаемый пакет исходного кода и метаданных.

`Module` — штатная группировка связанных объектов внутри App; он не объявляется автоматически отдельным bounded context или самостоятельным приложением.

`DocType`/`Document` — центральная прикладная модель Frappe.

Подробное основание: [`01_FOUNDATIONS.md`](../frappe-architecture-standard/01_FOUNDATIONS.md).

## 7. Правило появления нового механизма

Любой новый механизм в практикуме появляется только через цепочку:

```text
реальное требование
    ↓
ответственность
    ↓
штатный механизм Frappe
    ↓
проверка совпадения смысла
    ↓
использование механизма
```

Если смысл не совпадает:

```text
штатная точка расширения
    ↓
новая ответственность собственного кода
```

Нельзя вводить механизм формулировкой:

> «Теперь изучим Workflow».

Допустимая формулировка:

> «Менеджер должен подтверждать выдачу, оператор не должен иметь права самостоятельно переводить документ в подтверждённое состояние. Проверяем, выражается ли это штатным Workflow».

Такой порядок обязателен и для `Workflow`, `docstatus`, `Notification`, `Assignment`, `Web Form`, Reports, hooks, Controller-кода и остальных механизмов.

## 8. Правило модели данных

Перед каждым новым `DocType` ученик обязан определить, что именно моделируется.

```text
обычное свойство
    → DocField

самостоятельный Document
    → обычный DocType

состав одного Document
    → Child DocType

ссылка на существующий Document
    → Link

одна конфигурация на Site
    → Single DocType
```

Более сложные варианты (`Dynamic Link`, `Virtual DocType`, отдельный DocType связи и т. п.) вводятся только при реальном требовании.

Нормативная база: [`02_DATA_MODEL.md`](../frappe-architecture-standard/02_DATA_MODEL.md).

---

## 9. Правило состояния и жизненного цикла

Практикум обязан различать три понятия:

```text
бизнес-статус
Workflow
docstatus
```

Бизнес-статус отвечает на вопрос: **что сейчас происходит с объектом?**

`Workflow` отвечает на вопрос: **кто и при каких условиях может выполнить переход?**

`docstatus` отвечает на вопрос: **находится ли транзакционный Document в Draft, Submitted или Cancelled?**

`Rental = Returned` не является автоматическим основанием делать `Rental` Submitted.

Решение `Is Submittable` допускается только если в учебной предметной области появляется смысл окончательно зафиксированного транзакционного факта.

Нормативная база: [`03_DOCUMENT_LIFECYCLE.md`](../frappe-architecture-standard/03_DOCUMENT_LIFECYCLE.md).

---

## 10. Правило размещения логики

Практикум не использует схему «сначала no-code, потом low-code, потом Python».

Используется смысл ответственности:

```text
удобство формы
    → клиентский механизм

инвариант данных
    → серверный путь

поведение собственного DocType
    → Controller

реакция на чужой DocType
    → предусмотренная точка расширения

сложная операция нескольких Documents
    → отдельный service / предметный модуль, если он действительно нужен
```

Критическое правило нельзя считать реализованным только потому, что кнопка скрыта или Client Script не позволяет пользователю ввести значение через стандартную форму.

---

## 11. Права доступа

Права проектируются от штатной модели Frappe, а не от собственной таблицы ACL.

Первый уровень учебной модели:

```text
User
Role
DocType Permissions
```

Дополнительные механизмы (`Permission Level`, `Permission Type`, `If Owner`, `User Permission`, `Share`, permission hooks) вводятся только когда требование нельзя корректно выразить базовой моделью.

UI-скрытие не считается защитой данных.

Нормативная база: [`04_SECURITY.md`](../frappe-architecture-standard/04_SECURITY.md).

---

## 12. Интерфейс следует за моделью

Порядок проектирования:

```text
бизнес-объект
    ↓
DocType + поля + lifecycle + permissions
    ↓
подходящее представление
```

Стандартные `Form` и `List` считаются нормальным интерфейсом по умолчанию.

`Kanban`, `Calendar`, `Report`, `Workspace`, `Web Form`, Portal или собственный frontend подключаются только под возникшее пользовательское требование.

Нельзя создавать новую сущность только потому, что её удобно нарисовать отдельным экраном.

Нормативная база: [`08_UI_REPORTING.md`](../frappe-architecture-standard/08_UI_REPORTING.md).

---

## 13. Site-настройка и состояние App — разные вещи

Ученик должен различать:

```text
локальную настройку конкретного Site
```

и

```text
обязательное состояние устанавливаемого App
```

Если поле, Role, настройка или другой объект является обязательной частью учебного приложения, он не должен существовать только потому, что однажды был вручную создан на dev-site.

Для обязательного состояния используются штатные механизмы Frappe: Standard DocType JSON, fixtures, exported customizations, patches и другие предусмотренные способы в зависимости от смысла объекта.

Нормативная база:

- [`07_EXTENSION_CUSTOMIZATION.md`](../frappe-architecture-standard/07_EXTENSION_CUSTOMIZATION.md);
- [`09_DEPLOYMENT_TESTING.md`](../frappe-architecture-standard/09_DEPLOYMENT_TESTING.md).

## 14. Критерий завершённости практикума

Практикум считается завершённым не тогда, когда приложение работает на учебном dev-site.

Финальная проверка:

```text
чистый совместимый Frappe Site
+ репозиторий учебного App
+ install-app / migrate
= рабочее обязательное состояние приложения
```

После установки на чистый Site должны восстановиться все элементы, которые объявлены частью App, без скрытого списка ручных действий в БД или интерфейсе.

Дополнительно должны проходить тесты собственных критичных правил приложения. Стандартные механизмы Frappe не тестируются заново без причины; тестируются наши контракты поверх них.

---

## 15. Критерий качества каждого учебного шага

Учебный шаг принимается только если можно коротко заполнить карточку:

```text
Требование:
что понадобилось пользователю?

Ответственность:
что именно должна обеспечивать система?

Штатный механизм Frappe:
какой механизм предназначен для этого?

Почему подходит:
какая его семантика совпадает с требованием?

Граница:
в каком случае этого механизма станет недостаточно?

Результат:
что ученик должен увидеть работающим в системе?
```

Если невозможно объяснить, зачем механизм появился в приложении, такой шаг не включается в практикум.

---

## 16. Что проектируем после согласования паспорта

Только после утверждения этого документа подготавливаются:

1. требования учебной предметной области в порядке их появления;
2. матрица «требование → ответственность → механизм Frappe → доказательство»;
3. последовательность практических этапов;
4. критерии проверки каждого этапа;
5. финальный сценарий чистой установки и проверки приложения.

До этого момента количество занятий, названия лабораторных работ и обязательный список возможностей Frappe **не фиксируются**.
