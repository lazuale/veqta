# Архитектурный паспорт учебного практикума Frappe

Статус: **черновик архитектуры для согласования**.

Этот практикум проектируется с нуля и не связан с предметной областью VEQTA или предыдущими версиями практикума.

Нормативная база — [`docs/frappe-architecture-standard`](../frappe-architecture-standard/README.md). Если учебное решение конфликтует с этим стандартом, исправляется практикум, а не подгоняется стандарт под удобство урока.

---

# 1. Цель практикума

Научиться собирать небольшое приложение так, как это естественно для Frappe, а не проходить каталог функций Framework.

На каждом шаге ученик должен уметь ответить:

```text
1. Какая новая ответственность появилась?
2. Какой штатный механизм Frappe ей уже владеет?
3. Совпадает ли его семантика с требованием?
4. Если нет — какая официальная точка расширения подходит?
5. Какую новую ответственность добавляет собственный код?
```

Практикум не строится как лестница:

```text
no-code → low-code → Python
```

Правило другое:

> Не писать собственный механизм, пока штатный механизм Frappe уже правильно выражает эту ответственность.

---

# 2. Что практикум не пытается сделать

Это не:

- энциклопедия Frappe;
- последовательность «DocType → Workflow → Report → Web Form» ради знакомства с функциями;
- no-code курс;
- Python-курс;
- демонстрация VEQTA;
- обязательное использование каждого механизма Framework;
- искусственная предметная область для показа заранее выбранных технологий.

Собственный код не считается ошибкой сам по себе.

Ошибка — написать свой механизм там, где Frappe уже предоставляет механизм с правильной семантикой.

---

# 3. Нейтральная предметная область

Практикум строится вокруг маленького сервиса проката оборудования.

Нужны:

- самостоятельные записи;
- Document с несколькими связанными позициями;
- связи между Documents;
- рабочее состояние;
- серверные инварианты;
- роли и права;
- возможность позже добавить реальные ветки настроек, печати, отчётов, уведомлений, внешнего ввода и API.

Ни одна дополнительная ветка не становится обязательной только потому, что соответствующий механизм существует во Frappe.

## 4. Минимальная CORE-модель

```text
Equipment
Customer
Rental
└── Rental Item [Child DocType]
```

### Equipment

Самостоятельный объект: имеет идентичность, существует независимо от одной выдачи, используется многими Rentals и открывается отдельно.

### Customer

Самостоятельный клиент: существует независимо от Rental, участвует во многих Rentals, а Rental ссылается на него через `Link`.

### Rental

Главный рабочий Document, объединяющий клиента, период, набор Equipment и предметное состояние.

`Rental` заранее **не** объявляется `Is Submittable` и не получает `Workflow`.

### Rental Item

Часть одного Rental и техническая child-модель набора Equipment.

Пока строка содержит только:

```text
equipment → Link → Equipment
```

родитель использует `Table MultiSelect`, потому что требование — выбрать несколько существующих Equipment без собственных атрибутов строки отношения.

Если позднее строка получит, например, цену, состояние при выдаче или фактический возврат, обычный `Table` станет естественным кандидатом. Если строка получит самостоятельную идентичность, permissions, lifecycle или независимые ссылки, модель пересматривается по [`02_DATA_MODEL.md`](../frappe-architecture-standard/02_DATA_MODEL.md).

## 5. Что не создаётся заранее

В CORE заранее нет:

```text
Equipment Type
Rental Settings
Rental Status
Priority
Rental History
Rental Comment
Rental Assignee
Approval
Notification Log
Attachment
Rental Request
```

Принцип:

- маленький стабильный тип → сначала `Select`;
- одна настройка всего Site → тогда кандидат `Single DocType`;
- обычная история → штатный `Version`/Timeline;
- комментарии → `Comment`;
- файлы → `File`/Attach;
- назначение → сначала `Assignment`/`ToDo`;
- status не требует отдельного справочника;
- несколько состояний не требуют автоматически `Workflow`;
- публичная форма не доказывает необходимость отдельного `Rental Request`.

Это не запрет. Это запрет вводить механизм **до появления его ответственности**.

## 6. Архитектурная карта среды

```text
Bench
├── Apps
└── Sites
     └── учебный Site
          └── установлен учебный App

Учебный App
└── Module
     ├── Standard DocTypes
     ├── Controllers
     ├── Reports при необходимости
     ├── Workspace при необходимости
     ├── fixtures / patches при необходимости
     └── другие штатные компоненты
```

`Bench` — среда управления.

`Site` — конкретный экземпляр с БД и конфигурацией.

`App` — устанавливаемый пакет кода и метаданных.

`Module` — штатная группировка внутри App, а не автоматически bounded context.

`DocType`/`Document` — центральная прикладная модель.

## 7. Как появляется новый механизм

```text
реальное требование
    ↓
ответственность
    ↓
штатный механизм Frappe
    ↓
совпадает ли семантика?
    ├─ да → использовать
    └─ нет → официальная точка расширения
                   ↓
              собственная новая ответственность
```

Нельзя вводить шаг формулировкой «теперь изучим Workflow».

Нормальная формулировка: «менеджер должен подтверждать выдачу, оператор не может выполнить этот переход; проверяем Workflow».

---

## 8. Модель данных

```text
обычное свойство                   → DocField
самостоятельный Document           → обычный DocType
ссылка на существующий Document    → Link
набор Links без данных отношения   → Table MultiSelect + Child DocType
состав с данными строки            → Child DocType + Table
одна конфигурация на Site          → Single DocType
```

Более сложные варианты появляются только после соответствующего требования.

---

## 9. Состояние и lifecycle

```text
бизнес-статус = что происходит с объектом
Workflow      = кто и при каких условиях может выполнить переход
docstatus     = Draft / Submitted / Cancelled транзакционного Document
```

`Rental = Returned` не означает автоматически Submitted.

`Is Submittable` появляется только при смысле зафиксированного факта, который нельзя свободно переписывать.

## 10. Размещение логики

Нет лестницы `metadata → scripts → Python`.

Используется распределение по ответственности:

```text
UI convenience
→ client mechanism

инвариант данных одного собственного DocType
→ серверный Document path
→ Controller.validate() когда его lifecycle-семантика подходит

поведение собственного DocType
→ Controller

реакция на чужой DocType
→ официальный extension mechanism

сложная отдельная multi-document ответственность
→ service/domain module, только если она действительно появилась
```

S05C специально фиксирует первый собственный Python-код практикума именно по этому правилу:

```text
end_date >= start_date
Equipment не повторяется внутри одного Rental
        ↓
Rental Controller.validate()
```

Оба правила должны блокировать не только Form, но и обычный серверный `Document.insert()`.

---

## 11. Permissions

Начальный уровень:

```text
User
Role
DocType Permissions
```

Продвинутые механизмы добавляются только по необходимости.

Скрытие кнопки или поля на клиенте не считается защитой данных.

---

## 12. UI следует за моделью

```text
business object
→ DocType + fields + lifecycle + permissions
→ подходящее view
```

Form/List — нормальный базовый UI.

Kanban/Calendar/Report/Workspace/Web Form/Portal/custom frontend появляются под отдельные требования, а не ради покрытия возможностей Frappe.

---

## 13. Site state и App state

Обязательное состояние приложения не может существовать только потому, что его один раз накликали на dev-site.

Используются по смыслу:

- Standard DocType JSON;
- Controller source;
- fixtures;
- exported customizations;
- patches.

Runtime Documents конкретного Site не превращаются в fixtures только ради удобства демонстрации.

---

## 14. Критерий воспроизводимости

```text
clean compatible Frappe Site
+ training App repo
+ install-app / migrate
= working mandatory app state
```

Критические собственные контракты тестируются.

Не нужно повторно тестировать внутренности Frappe только ради coverage.

---

## 15. Quality gate каждого практического этапа

Каждый шаг должен иметь:

```text
Requirement
Responsibility
Native Frappe mechanism
Why it fits
Boundary
Visible working result
```

И заканчиваться проверяемым `ГОТОВО / НЕ ГОТОВО`.

---

## 16. Как строится программа после паспорта

```text
requirements
→ matrix
→ dependency graph
→ practical roadmap
→ exact stage specification
→ executable exercises
→ clean-install acceptance
```

Количество занятий заранее не фиксируется.

Последовательность определяется реальными зависимостями, а не желанием распределить функции Frappe по урокам.
