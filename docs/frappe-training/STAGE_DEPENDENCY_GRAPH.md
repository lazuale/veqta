# Граф зависимостей практических этапов Frappe

Статус: **черновик для архитектурной проверки**.

Этот документ продолжает:

- [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md);
- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md).

Он ещё **не является программой занятий** и не фиксирует количество уроков. Его задача — определить только реальные зависимости между законченными практическими результатами.

```text
что уже должно существовать
        ↓
какое новое требование теперь можно осмысленно решить
        ↓
какой механизм Frappe проверяется
        ↓
какой рабочий результат становится новой опорной точкой
```

---

## 1. Правила графа

### Узел — рабочий результат, а не тема

Правильно:

> Rental ссылается на существующего Customer и содержит несколько строк существующего Equipment.

Неправильно:

> Изучить Link и Child Table.

### Стрелка означает настоящую зависимость

```text
A → B
```

означает, что без результата A этап B нельзя корректно выполнить или архитектурно проверить.

Стрелка не используется только потому, что так удобнее преподавать.

### CORE — обязательный маршрут

В обязательный граф входят только `CORE`-требования из `REQUIREMENTS_MATRIX.md` и необходимые технические предпосылки.

`NEXT`, `GATE` и `EXT` остаются отдельными ветками.

```text
          ▼

  │

  │                    │
  │                    └──────────────┐
  │                                   │
  ├──────────────► P06. Form/List     │
  │                                   │
  ├──────────────► P07. Инварианты    │
  │                    │              │

  │                           ▼

  │                           │
```

Ключевой момент: после `P04` несколько веток развиваются **независимо**. Например, permissions не зависят от проверки пересекающихся прокатов, а стандартный Desk не зависит от наличия тестов.

# 3. P00 — готовая совместимая среда

**Тип:** техническая предпосылка.

Нужны:

```text
совместимый Bench
Frappe v16
рабочий Site
developer mode
Git
```

Цель этого узла — не обучение администрированию, а создание среды, где Standard DocType и другие обязательные элементы сразу могут принадлежать App.

**Результат:** ученик может работать с Bench, открыть Site и сохранять изменения приложения под Git.

---

# 4. P01 — создать и установить учебный App

**Зависит от:** `P00`.

Создаётся отдельный нейтральный App практикума и его Module. App устанавливается на учебный Site.

Ученик должен различать:

```text
Bench  = среда управления
Site   = конкретный экземпляр
App    = устанавливаемый пакет
Module = организация объектов внутри App
```

**Результат:** учебный App существует в Git и установлен на Site.

---

# 5. P02 — Equipment как самостоятельный Document

**Требования:** `R01`, `R06`, часть `D00`.

**Зависит от:** `P01`.

Создаётся Standard `DocType` `Equipment`.

На нём впервые проверяются решения:

```text
самостоятельный объект → DocType
простое свойство        → DocField
небольшой стабильный набор → Select
```

Одновременно выбирается осознанная стратегия `name`.

**Результат:** Equipment существует как самостоятельный Document без лишних справочников вокруг простых полей.

---

# 6. P03 — Customer как самостоятельный Document

**Требования:** `R02`, часть `D00`.

**Зависит от:** `P01`.

Создаётся Standard `DocType` `Customer` и выбирается его naming.

`P02` и `P03` друг от друга не зависят.

**Результат:** есть две независимые сущности, которые далее можно связать через Rental.

---

# 7. P04 — Rental как Document-композиция

**Требования:** `R03`, `R04`, `R05`, часть `D00`.

**Зависит от:** `P02` + `P03`.

Создаются:

```text
Rental
└── Rental Item [Child DocType]
```

Связи:

```text
Rental.customer       → Link → Customer
Rental.items          → Table → Rental Item
Rental Item.equipment → Link → Equipment
```

Здесь ученик соединяет в одном реальном сценарии:

```text
обычный DocType
Child DocType
Table
Link
```

**Результат:** один Rental связывает существующего Customer с несколькими существующими Equipment.

---

# 8. P05 — предметное состояние Rental

**Требование:** `R08`.

**Зависит от:** `P04`.

Добавляется обычное поле `status`, например:

```text
Planned
Active
Returned
```

На этом этапе **не появляются автоматически**:

```text
Workflow
Is Submittable
Rental Status DocType
```

**Результат:** предметное состояние хранится и фильтруется без подмены его `docstatus`.

---

# 9. P06 — рабочий сценарий через Desk

**Требование:** `R16`.

**Зависит от:** `P04`.

Проверяются штатные:

```text
Form
List
Link controls
Child Table UI
filters
```

Пользователь должен суметь без собственного frontend:

1. создать Equipment;
2. создать Customer;
3. создать Rental;
4. выбрать Customer;
5. добавить Equipment;
6. сохранить и найти Rental.

**Результат:** первая вертикальная рабочая версия приложения.

---

# 10. P07 — инварианты одного Rental

**Требования:** `R09`, `R10`.

**Зависит от:** `P04`.

В Controller появляются серверные проверки:

```text
end_date >= start_date
одно Equipment не повторяется дважды в одном Rental
```

Главное различие:

```text
Client Script       = удобство формы
Controller.validate = гарантия модели
```

**Результат:** неправильный Rental нельзя сохранить обычным серверным путём Document.

---

# 11. P08 — правило между несколькими Rentals

**Требование:** `R11`.

**Зависит от:** `P05` + `P07`.

Появляется правило:

> одно Equipment нельзя выдать двум клиентам на пересекающиеся активные периоды.

Это первый инвариант Rental, для которого нужно читать другие Documents.

**Результат:** последовательное создание конфликтующего Rental блокируется сервером.

**Граница:** учебная проверка в Controller не выдаётся за полную стратегию конкурентного бронирования. Параллельные транзакции и блокировки — отдельная production-задача.

---

# 12. P09 — базовые Roles и Permissions

**Требование:** `R13`.

**Зависит от:** `P04`.

Создаются реальные роли, например:

```text
Rental Operator
Rental Manager
```

Права задаются через `Role` + `DocType Permissions`.

Этот узел **не зависит от P07/P08**. Права можно проектировать сразу после появления реальных DocTypes и действий.

**Результат:** под разными пользователями реально различаются разрешённые операции.

---

# 13. P10 — тесты собственных контрактов

**Требование:** `R23`.

**Зависит от:** `P08` + `P09`.

К этому моменту у App появились собственные гарантии, которые имеет смысл тестировать:

```text
неправильный период отвергается
дублирование Equipment отвергается
конфликт прокатов обнаруживается в учебном сценарии
права реально ограничивают действия
```

Не тестируется ради количества сам факт, что стандартный Link работает.

**Результат:** `bench run-tests` защищает контракты учебного App.

---

# 14. P11 — аудит доставки состояния App

**Требования:** `R21`, `R22`.

**Зависит от:** `P08` + `P09` и завершённой обязательной модели.

Дисциплина воспроизводимости начинается ещё с `P01`, но здесь проводится отдельная приёмка:

```text
Standard DocTypes находятся в App
обязательные метаданные под Git
обязательная конфигурация доставляется штатно
нет скрытых ручных изменений dev-site
нет ручного SQL как обычного шага релиза
migrate синхронизирует схему
patch появляется только при реальном преобразовании данных
```

**Результат:** для каждого обязательного элемента понятно, принадлежит он App или конкретному Site.

---

# 15. P12 — чистая установка

**Требование:** `R24`.

**Зависит от:** `P06` + `P10` + `P11`.

Финальная приёмка выполняется на новом Site:

```text
чистый совместимый Frappe Site
+ учебный App из Git
+ install-app
+ migrate
+ tests
= рабочее обязательное состояние приложения
```

Затем повторяется основной пользовательский сценарий через Desk.

**Практикум архитектурно завершён только после этого узла.**

# 16. NEXT — необязательный второй контур

Эти ветки подключаются только при реальном учебном требовании.

| Узел | Требование | Реальная зависимость | Первый механизм |
|---|---|---|---|
| `N01` | `R07` — один набор настроек Site | `P04` | `Single DocType` |
| `N02` | `R12` — история, обсуждение, файлы | `P04` | `Version` / `Comment` / `File` |
| `N03` | `R14` — отдельные поля только менеджеру | `P09` | `Permission Level` |

# 17. GATE — архитектурные развилки

## G00 — naming (`D00`)

Naming не является поздним отдельным уроком. Каждый самостоятельный DocType проходит решение при создании:

```text
P02 → naming Equipment
P03 → naming Customer
P04 → naming Rental
```

---

## G01 — ролевое подтверждение (`D01`)

```text
P05 + P09 + требование ограничить переход по роли
                     ↓
                 Workflow?
```

`Workflow` появляется только после сочетания предметных состояний, ролей и требования управлять переходами.

---

## G02 — транзакционная фиксация (`D02`)

```text
P04 + требование зафиксировать совершённый факт
                     ↓
            Is Submittable / docstatus?
```

`G01` и `G02` **не зависят друг от друга**.

Допустимы разные архитектуры:

```text
status без Workflow и submit
Workflow без submit
docstatus без Workflow
Workflow + docstatus
```

---

## G03 — Equipment Type становится сущностью (`D03`)

```text
P02: Select
   ↓
у типа появились собственные атрибуты и управление
   ↓
Equipment Type DocType + Link
   ↓
P11: проверить миграцию существующих данных
```

Это показывает важный принцип: прежний `Select` не был ошибкой — изменилось требование.

---

## G04 — публичная заявка (`D04`)

```text
P04 + P07 + модель безопасности
          ↓
это Rental или отдельный Rental Request?
          ↓
       Web Form
```

Сначала решается предметная модель, затем UI.

Если появляется `Rental Request`, он заново проходит обычные вопросы DocType: identity, naming, permissions, lifecycle и доставка из App.

---

## G05 — напоминание о возврате (`D05`)

```text
P04 + даты + реальное требование уведомления
                     ↓
                 Notification
```

Scheduler/background job появляется только если реальное требование выходит за семантику Notification.

---

# 18. EXT — интеграционная ветка

| Узел | Требование | Зависимость | Первый механизм |
|---|---|---|---|
| `X01` | `E01` — обычный CRUD внутреннего клиента | `P07` + `P09` | Document REST API |
| `X02` | `E02` — предметная команда `return_rental` | `P05` + `P07` + `P09` | Document/whitelisted method |
| `X03` | `E03` — исходящее событие | конкретное lifecycle-событие | `Webhook` |

REST имеет смысл показывать после серверных правил и permissions: тогда видно, что вне Desk тот же Document продолжает подчиняться серверной модели.

# 19. Контрольные состояния

После `P04`:

```text

```

### C2 — приложение уже полезно пользователю

После `P06` основной сценарий выполняется через стандартный Desk.


# 20. Что нельзя выводить из графа

Граф не означает, что:

```text
каждый Pxx = отдельный урок;
все NEXT обязательны;
все GATE должны быть активированы;
Workflow обязателен;
Submittable обязателен;
API обязателен;
практикум должен иметь заранее заданное число занятий.
```

Несколько узлов могут стать одним практическим этапом. Один сложный узел может потребовать нескольких проходов. Это уже вопрос методики.

---

# 21. Финальная проверка графа

Перед дорожной картой нужно ответить «да» на все вопросы:

```text
1. Каждая стрелка отражает реальную зависимость?
2. NEXT/GATE/EXT не попали обратно в CORE?
3. Каждый механизм появляется после требования?
4. Новый DocType не создаётся ради будущего UI?
5. status, Workflow и docstatus разведены по смыслу?
6. Серверная логика появляется из реального инварианта?
7. Permissions проверяются на реальных Documents и действиях?
8. Tests защищают наши контракты, а не тестируют Framework ради coverage?
9. App-состояние отделено от локальной Site-настройки?
10. Финал — чистая установка, а не только рабочий dev-site?
```

# 22. Следующий артефакт

После согласования графа можно строить **дорожную карту практикума** в формате:

```text
этап
цель
входное состояние
действия ученика
ожидаемый результат
проверка результата
архитектурное объяснение
связанные R/D/E-требования
```

Количество этапов должно получиться из графа и методики, а не задаваться заранее.
