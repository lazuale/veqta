# Граф зависимостей практических этапов Frappe

Статус: **черновик для архитектурной проверки**.

Этот документ продолжает:

- [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md);
- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md).

Он ещё **не является программой занятий** и не фиксирует количество уроков. Его задача — определить только естественную зависимость практических результатов:

```text
что уже должно существовать
        ↓
какое следующее требование теперь можно осмысленно решить
        ↓
какой механизм Frappe для этого проверяется
        ↓
какой наблюдаемый результат становится новой опорной точкой
```

Если два механизма технически можно изучать в любом порядке, граф не создаёт между ними искусственную зависимость.

---

## 1. Правила графа

### 1.1. Узел — законченный рабочий результат

Узел графа — не тема вроде «изучить Link».

Правильно:

> Rental ссылается на существующего Customer и содержит строки существующего Equipment.

Неправильно:

> Урок Link.

### 1.2. Стрелка означает реальную зависимость

```text
A → B
```

означает:

> без результата A этап B либо невозможно выполнить, либо его архитектурный смысл ещё нельзя корректно проверить.

Стрелка **не означает** «так красивее преподавать».

### 1.3. CORE образует обязательный позвоночник

В обязательный маршрут входят только требования `CORE` из матрицы и необходимые технические предпосылки.

`NEXT`, `GATE` и `EXT` подключаются ответвлениями.

### 1.4. Механизм не становится обязательным из-за положения на схеме

Если узел помечен `NEXT`, `GATE` или `EXT`, его можно исключить целиком вместе с зависимыми от него необязательными ветками.

# 3. P00 — готовая совместимая среда

**Тип:** техническая предпосылка.

До начала предметной разработки должны существовать:

```text
совместимый Bench
Frappe v16
рабочий Site
возможность developer mode
Git-репозиторий учебного App
```

Этот этап не изучает архитектуру проката. Он только создаёт среду, в которой архитектурные решения можно сохранять как часть App и проверять повторно.

**Почему раньше всего**  
Standard DocType и другие элементы приложения должны сразу создаваться в правильной границе App/Site, а не сначала как случайные локальные настройки с последующей попыткой «перенести в код».

**Результат**  
Ученик может выполнить команды Bench, открыть Site и работать в developer mode.

**Не включать сюда**  
Полное системное администрирование, production deployment и эксплуатацию сервера. Это отдельная область, а не предмет практикума.

# 4. P01 — создать и установить учебный App

**Тип:** обязательная архитектурная основа.

**Зависит от:** `P00`.

Создаётся отдельный нейтральный App практикума и его Module. App устанавливается на учебный Site.

Ученик должен увидеть различие:

```text
Bench  = среда управления
Site   = конкретный экземпляр
App    = устанавливаемый пакет
Module = организация объектов внутри App
```

**Результат**

```text
учебный App существует в Git
App установлен на Site
Module принадлежит этому App
```

После этого все обязательные Standard DocTypes создаются как часть этого App.

---

# 5. P02 — самостоятельная модель Equipment

**Тип:** `CORE`.

**Требования:** `R01`, `R06`, часть `D00`.

**Зависит от:** `P01`.

Создаётся `Equipment` как Standard DocType.

На этом объекте ученик впервые проходит решение:

```text
самостоятельный объект → DocType
обычное свойство        → DocField
небольшой стабильный набор → Select
```

Одновременно осознанно выбирается стратегия `name` для Equipment.

**Почему naming здесь, а не в конце**  
`name` участвует в ссылках. Сначала создать произвольные записи, связать ими полсистемы, а затем впервые задуматься об идентичности — плохой порядок.

**Результат**

- Equipment создаётся как настоящий `Document`;
- простые свойства не разнесены по лишним справочникам;
- стратегия `name` объяснена;
- запись открывается через стандартный Desk.

---

# 6. P03 — самостоятельная модель Customer

**Тип:** `CORE`.

**Требования:** `R02`, часть `D00`.

**Зависит от:** `P01`.

Создаётся `Customer` как отдельный Standard DocType и выбирается его naming.

`P02` и `P03` **не зависят друг от друга**. Их можно реализовать в любом порядке или в одном практическом этапе.

**Результат**  
Есть две независимые предметные записи, которые далее можно связать через Rental.

---

# 7. P04 — собрать Rental как Document-композицию

**Тип:** `CORE`.

**Требования:** `R03`, `R04`, `R05`, часть `D00`.

**Зависит от:** `P02` + `P03`.

Создаются:

```text
Rental
└── Rental Item [Child DocType]
```

Связи:

```text
Rental.customer       → Link → Customer
Rental.items          → Table → Rental Item
Rental Item.equipment → Link → Equipment
```

Здесь в одном рабочем сценарии соединяются четыре разных смысла:

```text
самостоятельный Document
состав родителя
живая ссылка
поле Table
```

**Результат**  
Пользователь может создать одну операцию проката для существующего Customer и добавить в неё несколько существующих Equipment.

**Ключевая проверка**  
`Rental Item` нигде не превращён в самостоятельную карточку только потому, что технически хранится как отдельный тип записи.

---

# 8. P05 — добавить предметное состояние Rental

**Тип:** `CORE`.

**Требование:** `R08`.

**Зависит от:** `P04`.

Добавляется обычное предметное поле состояния, например:

```text
Planned
Active
Returned
```

**Что специально не появляется**

```text
Workflow
Is Submittable
docstatus как бизнес-статус
Rental Status DocType
```

Пока требование говорит только «хранить текущее состояние», `Select` выражает его точнее.

**Результат**  
Один и тот же Rental можно увидеть в разных рабочих состояниях и фильтровать по ним.

---

# 9. P06 — пройти базовый сценарий через стандартный Desk

**Тип:** `CORE`.

**Требование:** `R16`.

**Зависит от:** `P04`; practically полезно выполнять после `P05`.

До написания собственного UI ученик обязан проверить, что приложение уже рабочее через штатные:

```text
Form
List
Link controls
Child Table UI
filters
```

**Результат**

Пользователь без собственного frontend может:

1. создать Equipment;
2. создать Customer;
3. создать Rental;
4. выбрать Customer;
5. добавить несколько Equipment;
6. сохранить документ;
7. найти его в List.

Это первая вертикальная рабочая версия приложения.

---

# 10. P07 — защитить инварианты одного Rental

**Тип:** `CORE`.

**Требования:** `R09`, `R10`.

**Зависит от:** `P04`.

Добавляется серверная логика Controller:

```text
end_date >= start_date
одно Equipment не повторяется в items одного Rental
```

**Почему после рабочей модели**  
Сначала существует Document и его структура; затем появляется требование гарантировать корректность этой структуры.

**Что ученик должен понять**

```text
Client Script = удобство формы
Controller.validate = гарантия инварианта Document
```

Client Script при желании может дополнить UX, но не заменяет серверную проверку.

**Результат**  
Некорректный Rental нельзя сохранить обычным серверным путём Document.

---

# 11. P08 — проверить правило между несколькими Rentals

**Тип:** `CORE`.

**Требование:** `R11`.

**Зависит от:** `P04` + `P05` + `P07`.

Появляется правило:

> одно Equipment нельзя выдать двум клиентам на пересекающиеся активные периоды.

Это первый случай, когда инвариант одного Rental требует прочитать другие Documents.

**Архитектурная задача**

Не создать отдельный Service только потому, что запрос стал сложнее. Сначала проверить, остаётся ли правило естественной ответственностью Rental Controller.

**Результат**  
Последовательное создание конфликтующего Rental блокируется сервером.

**Обязательная граница**  
Этот учебный вариант не выдаётся за полноценную защиту конкурентного бронирования. Параллельные транзакции и блокировки являются отдельной production-задачей.

---

# 12. P09 — ввести базовую модель прав

**Тип:** `CORE`.

**Требование:** `R13`.

**Зависит от:** рабочей модели `P04`; рекомендуется после `P08`, чтобы уже существовали реальные операции для проверки.

Создаются реальные учебные пользователи/роли, например:

```text
Rental Operator
Rental Manager
```

Права задаются через штатные `Role` + `DocType Permissions`.

**Почему не раньше модели**  
Права проектируются относительно существующих DocTypes и конкретных действий. Роль без предметной модели превращается в абстрактную таблицу разрешений.

**Результат**  
Под разными пользователями фактически различаются разрешённые операции.

**Не делать**

- собственную ACL-таблицу;
- проверки `if "Manager" in frappe.get_roles()` по всему коду;
- безопасность только через скрытые кнопки.

---

# 13. P10 — зафиксировать собственные контракты тестами

**Тип:** `CORE`.

**Требование:** `R23`.

**Зависит от:** `P07` + `P08` + `P09`.

До появления собственных инвариантов тестировать почти нечего: стандартный Link и стандартный Form не являются нашим контрактом.

После `P07–P09` появляются собственные гарантии приложения:

```text
неправильный период отвергается
дублирование Equipment отвергается
конфликт прокатов обнаруживается в учебном сценарии
роль не получает запрещённое действие
```

**Результат**  
`bench run-tests` подтверждает именно поведение нашего App.

**Контроль качества**  
Намеренно сломать одно правило и убедиться, что соответствующий тест падает.

---

# 14. P11 — проверить, что обязательное состояние принадлежит App

**Тип:** `CORE`.

**Требования:** `R21`, `R22`.

**Зависит от:** всех изменений модели, которые объявлены обязательными.

Фактически этот контроль идёт **с самого P01**, но здесь выполняется отдельная приёмка перед чистой установкой.

Проверяется:

```text
Standard DocTypes находятся в App
обязательные метаданные находятся под Git
обязательная конфигурация доставляется штатным механизмом
нет скрытого списка ручных изменений dev-site
нет ручного SQL как части обычного релиза
migrate воспроизводит изменение схемы
patch используется только для реального преобразования существующих данных
```

**Результат**  
Можно объяснить происхождение каждого обязательного элемента приложения: App или локальный Site.

---

# 15. P12 — чистая установка и финальная приёмка

**Тип:** `CORE`, финальный узел.

**Требование:** `R24`.

**Зависит от:** `P10` + `P11`.

Финальная проверка выполняется не на давно настроенном dev-site.

```text
чистый совместимый Frappe Site
+ учебный App из Git
+ install-app
+ migrate
+ tests
= воспроизводимое рабочее приложение
```

После установки проходится основной пользовательский сценарий:

```text
Equipment
   +
Customer
   ↓
Rental
   ↓
Rental Item / Links
   ↓
status
   ↓
server validation
   ↓
permissions
```

**Практикум считается архитектурно завершённым только после этого узла.**

# 16. NEXT — независимые ветки второго контура

Эти узлы не входят в позвоночник автоматически.

## N01. Rental Settings — `R07`

```text
P04 ──► N01
```

Подключается, только если появляется реальное значение уровня всего Site.

Механизм: `Single DocType`.

Он не является обязательным только ради знакомства с Single.

---

## N02. Timeline, Comment, File — `R12`

```text
P04 ──► N02
```

Подключается, если рабочий сценарий действительно требует обсуждения, файлов или просмотра истории.

Цель — показать, что обычные общие ответственности не требуют `Rental History`, `Rental Comment`, `Rental Attachment`.

---

## N03. Права на отдельные поля — `R14`

```text
P09 ──► N03
```

Механизм: `Permission Level`.

Без реального чувствительного поля ветка исключается.

---

## N04. Рабочее назначение — `R15`

```text
P09 ──► N04
```

Механизм: `Assignment` / `ToDo`.

Подключается только если появляется реальная потребность назначать работу человеку.

---

## N05. Workspace — `R17`

```text
P06 ──► N05
```

Механизм: `Workspace`.

Это организация навигации, а не новая бизнес-модель.

---

## N06. Календарное представление — `R18`

```text
P04 ──► N06
```

Механизм: штатное календарное представление.

Узел не создаёт `Rental Calendar Entry`.

---

## N07. Print Format — `R19`

```text
P04 ──► N07
```

Подключается только если нужен реальный акт/печатный документ.

---

## N08. Report Builder — `R20`

```text
P05 + накопленные Rentals ──► N08
```

Сначала решается реальная задача простого реестра. `Query Report` и `Script Report` не добавляются, пока Report Builder соответствует требованию.

# 17. GATE — архитектурные развилки

GATE отличается от NEXT: здесь новое требование **может изменить архитектурное решение**, принятое раньше.

## G00. Naming — `D00`

Naming не является отдельным поздним модулем.

```text
P01
 ├─► P02: naming Equipment
 ├─► P03: naming Customer
 └─► P04: naming Rental
```

Каждый самостоятельный DocType проходит эту проверку при создании.

---

## G01. Ролевое подтверждение выдачи — `D01`

```text
P05 + P09 ──► G01
```

Только после появления одновременно:

```text
предметных состояний
+
разных ролей
+
требования ограничить переход
```

возникает основание проверить `Workflow`.

`Workflow` не является обязательным продолжением `status`.

---

## G02. Транзакционная фиксация — `D02`

```text
P04 + конкретное требование необратимой фиксации ──► G02
```

Проверяется `Is Submittable` / `docstatus`.

**G01 и G02 не зависят друг от друга.**

Возможны варианты:

```text
status без Workflow и без submit
Workflow без submit
docstatus без Workflow
Workflow + docstatus
```

Если выбраны оба механизма, отдельно проверяется их совместная семантика.

---

## G03. Equipment Type становится сущностью — `D03`

```text
P02 (Select)
   ↓
появились собственные атрибуты типа
   ↓
G03: Equipment Type DocType + Link
   ↓
P11: проверить миграцию существующих данных
```

Это особенно полезная архитектурная развилка: ученик видит, что исходное решение `Select` не было ошибкой. Модель изменилась потому, что изменилось требование.

---

## G04. Публичная заявка — `D04`

```text
P04 + P07 + P09
        ↓
предметное решение:
это Rental или Rental Request?
        ↓
Web Form
```

Сначала решается модель, потом представление.

Если появляется новый `Rental Request`, он должен заново пройти обычные проверки самостоятельного DocType: identity, naming, permissions, lifecycle и доставка из App.

---

## G05. Напоминание о возврате — `D05`

```text
P04 + даты + конкретное требование уведомления ──► G05
```

Первый кандидат — `Notification`.

Scheduler/background job появляется только если фактическое требование перерастает семантику Notification.

---

# 18. EXT — интеграционная ветка

Эта ветка не нужна для доказательства базовой архитектуры Frappe-приложения.

## X01. Обычный CRUD из внутреннего клиента — `E01`

```text
P07 + P09 ──► X01
```

До проверки серверных инвариантов и permissions демонстрировать REST как отдельную игрушку бессмысленно.

После них Document REST API показывает важную вещь: тот же Document продолжает жить по серверным правилам вне Desk.

---

## X02. Предметная команда — `E02`

```text
P05 + P07 + P09 ──► X02
```

Только когда появляется операция с предметным смыслом вроде `return_rental`, сравнивается обычный CRUD и command endpoint/метод Document.

---

## X03. Исходящее событие — `E03`

```text
событие жизненного цикла Rental
        ↓
X03: Webhook
```

Если затем нужны гарантированные повторы, сверка, идемпотентность или сложное преобразование, это уже новая интеграционная ответственность, а не повод заранее строить собственный integration framework.

---

# 19. Контрольные точки практикума

Граф даёт четыре естественных контрольных состояния.

## C1. Модель существует

После `P04`:

```text
Equipment
Customer
Rental
Rental Item
Link
Child Table
```

Ученик уже собрал настоящую связанную модель, а не отдельные демонстрации полей.

## C2. Приложение работает как приложение

После `P06`:

основной сценарий полностью выполняется через стандартный Desk.

## C3. Модель защищает себя

После `P10`:

```text
server validation
cross-document rule
permissions
tests
```

Правильность больше не зависит только от того, как пользователь кликает форму.

## C4. App воспроизводим

После `P12`:

приложение устанавливается на чистый Site из Git и проходит тесты.

# 20. Что из графа нельзя выводить

Граф **не доказывает**, что:

```text
каждый Pxx = отдельный урок;
все NEXT нужно проходить;
все GATE нужно активировать;
API обязателен;
Workflow обязателен;
Submittable обязателен;
практикум должен закончиться после фиксированного числа занятий.
```

Несколько соседних узлов могут стать одним занятием. Один сложный узел может потребовать нескольких практических проходов.

Это определяется позже методикой, а не архитектурой.

---

# 21. Проверка графа перед дорожной картой

Перед превращением графа в последовательность практических этапов проверить:

```text
1. Есть ли стрелка, которая выражает только удобство преподавания, а не реальную зависимость?
2. Не попал ли NEXT/GATE/EXT обратно в обязательный позвоночник?
3. Появляется ли каждый механизм после требования, а не до него?
4. Не создаётся ли DocType из-за будущего UI?
5. Не смешиваются ли status, Workflow и docstatus?
6. Появляется ли серверная логика только после появления реального инварианта?
7. Проверяются ли permissions на реальных Documents и действиях?
8. Начинаются ли тесты с наших контрактов, а не с тестирования Framework?
9. Сохраняется ли различие App-состояния и локальной Site-настройки?
10. Завершается ли обязательный маршрут чистой установкой, а не только рабочим dev-site?
```

Если на любой вопрос ответ отрицательный, сначала исправляется граф, и только затем строится дорожная карта.

# 22. Следующий артефакт

После согласования этого графа можно строить **дорожную карту практикума**.

Она уже сможет безопасно определить:

```text
этап
цель
входное состояние
конкретные действия ученика
ожидаемый результат
проверку результата
архитектурное объяснение
связанные требования R/D/E
```

Количество этапов будет следствием графа и методики, а не заранее заданной цифрой.
