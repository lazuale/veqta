# Граф зависимостей практических этапов Frappe

Статус: **черновик для архитектурной проверки**.

Продолжает:

- [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md);
- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md).

Это ещё **не программа занятий**. Документ фиксирует только реальные зависимости между законченными практическими результатами.

---

## 1. Правило

Узел — рабочий результат, а не тема.

```text
не «изучить Link»
а «Rental ссылается на существующего Customer»
```

`A → B` означает настоящую зависимость: без A результат B нельзя корректно получить или проверить. Стрелка не добавляется ради удобства преподавания.

# 2. CORE-узлы

```text
P00  готовая среда Frappe v16
P01  учебный App установлен на Site
P02  Equipment как самостоятельный Document
P03  Customer как самостоятельный Document
P04  Rental + Rental Item + Link + Table MultiSelect
P05  предметный status Rental
P06  рабочий сценарий через Form/List
P07  серверные инварианты одного Rental
P08  правило конфликтующих Rentals
P09  базовые Roles/Permissions
P10  автоматические тесты контрактов
P11  аудит доставки состояния App
P12  чистая установка и финальная приёмка
```

## Реальные зависимости

```text
P00 → P01

P01 → P02
P01 → P03

P02 + P03 → P04

P04 → P05
P04 → P06
P04 → P07
P04 → P09

P05 + P07 → P08

P08 + P09 → P10
P08 + P09 → P11

P06 + P10 + P11 → P12
```

После `P04` UI, status, серверные правила и permissions развиваются независимо. Это принципиально: граф не превращает удобный порядок преподавания в выдуманную архитектурную зависимость.

---

# 3. P00 — среда

**Тип:** техническая предпосылка.

Нужны совместимый Bench, Frappe v16, Site, developer mode и Git.

Цель — не production-администрирование, а среда, где обязательные элементы сразу могут принадлежать App.

---

# 4. P01 — App и Module

**Зависит от:** `P00`.

Создаётся отдельный нейтральный учебный App, его Module и установка на Site.

Ученик различает:

```text
Bench  = среда управления
Site   = экземпляр
App    = устанавливаемый пакет
Module = организация объектов внутри App
```

---

# 5. P02 — Equipment

**Покрывает:** `R01`, `R06`, часть `D00`.

**Зависит от:** `P01`.

Создаётся Standard `Equipment`.

Решения:

```text
самостоятельный объект → DocType
простое свойство        → DocField
малый стабильный набор  → Select
```

Сразу выбирается naming.

---

# 6. P03 — Customer

**Покрывает:** `R02`, часть `D00`.

**Зависит от:** `P01`.

Создаётся Standard `Customer` и выбирается naming.

`P02` и `P03` независимы друг от друга.

---

# 7. P04 — Rental-композиция

**Покрывает:** `R03`, `R04`, `R05`, часть `D00`.

**Зависит от:** `P02` + `P03`.

```text
Rental
└── Rental Item [Child DocType]

Rental.customer       → Link → Customer
Rental.items          → Table MultiSelect → Rental Item
Rental Item.equipment → Link → Equipment
```

Текущее требование — выбрать несколько существующих Equipment, а child row содержит только Link. Поэтому `Table MultiSelect` точнее обычного `Table`; если у строки появятся собственные данные отношения, выбор пересматривается.

---

# 8. P05 — business status

**Покрывает:** `R08`.

**Зависит от:** `P04`.

Пример:

```text
Planned
Active
Returned
```

Пока требуется только хранить состояние, не появляются `Workflow`, `Is Submittable` или отдельный status-справочник.

---

# 9. P06 — стандартный Desk

**Покрывает:** `R16`.

**Зависит от:** `P04`.

Проверяются `Form`, `List`, Link controls, Table MultiSelect и фильтры.

Результат: основной сценарий работает без собственного frontend.

---

# 10. P07 — серверные инварианты

**Покрывает:** `R09`, `R10`.

**Зависит от:** `P04`.

В Controller:

```text
end_date >= start_date
одно Equipment не повторяется дважды в Rental
```

Оба правила должны быть доказаны через обычный серверный `Document.insert()`, а не только через Form.

Ключ:

```text
Client Script       = UX
Controller.validate = гарантия модели на обычном Document path
```

---

# 11. P08 — правило между Rentals

**Покрывает:** `R11`.

**Зависит от:** `P05` + `P07`.

Проверяется пересечение активных периодов одного Equipment.

Это первый инвариант Rental, который читает другие Documents.

Граница фиксируется явно: обычная `validate()`-проверка не является полной стратегией конкурентного бронирования.

---

# 12. P09 — Roles/Permissions

**Покрывает:** `R13`.

**Зависит от:** `P04`.

Используются штатные `Role` + `DocType Permissions`.

`P09` не зависит от P07/P08: после появления реальных DocTypes права можно проектировать независимо от бизнес-проверок.

---

# 13. P10 — tests

**Покрывает:** `R23`.

**Зависит от:** `P08` + `P09`.

Тестируются наши контракты:

```text
даты
дубли Equipment
конфликт Rentals
permissions
```

Не тестируется Framework ради coverage.

---

# 14. P11 — delivery audit

**Покрывает:** `R21`, `R22`.

**Зависит от:** `P08` + `P09` и завершённой CORE-модели.

Проверяется:

```text
обязательные Standard DocTypes находятся в App
метаданные под Git
Controller под Git
обязательная конфигурация доставляется штатно
нет скрытых ручных изменений dev-site
нет ручного SQL как обычного шага релиза
migrate синхронизирует схему
patch используется только для реального преобразования данных
```

---

# 15. P12 — clean install

**Покрывает:** `R24`.

**Зависит от:** `P06` + `P10` + `P11`.

```text
чистый Frappe Site
+ App из Git
+ install-app
+ migrate
+ tests
= рабочее обязательное состояние
```

После установки повторяется основной пользовательский сценарий.

# 17. GATE — архитектурные развилки

## G00 — naming (`D00`)

Naming проходит каждый самостоятельный DocType **при создании**, а не отдельным поздним уроком.

## G01 — Workflow (`D01`)

```text
P05 + P09 + требование ограничить переход по роли
                     ↓
                 Workflow?
```

## G02 — docstatus (`D02`)

```text
P04 + требование зафиксировать совершённый факт
                     ↓
            Is Submittable / docstatus?
```

`G01` и `G02` независимы. Возможны оба, один из них или ни один.

## G03 — Equipment Type (`D03`)

```text
P02: Select
   ↓
появились собственные атрибуты типа
   ↓
Equipment Type DocType + Link
   ↓
проверка миграции
```

Изменилось требование — изменилась модель. Исходный Select не объявляется ошибкой задним числом.

## G04 — Web Form (`D04`)

Сначала решается: публичный ввод создаёт Rental или самостоятельный `Rental Request`? Только потом выбирается Web Form.

## G05 — Notification (`D05`)

Notification появляется после реального требования напоминать о сроке. Scheduler/background job — только если Notification уже недостаточно по семантике.

# 18. EXT — интеграции

| Узел | Требование | Зависимость | Первый механизм |
|---|---|---|---|
| `X01` | `E01` — CRUD | `P07` + `P09` | Document REST API |
| `X02` | `E02` — предметная команда | `P05` + `P07` + `P09` | Document/whitelisted method |
| `X03` | `E03` — исходящее событие | lifecycle-событие | `Webhook` |

REST полезно проверять после серверных правил и permissions: тогда видно, что вне Desk действует та же Document-модель.

---

# 19. Контрольные состояния

```text
C1 после P04 → связанная модель существует
C2 после P06 → приложение полезно через Desk
C3 после P10 → модель защищает себя и покрыта тестами
C4 после P12 → App воспроизводим на чистом Site
```

---

# 20. Что граф не означает

```text
каждый Pxx = отдельный урок
все NEXT обязательны
все GATE должны быть активированы
Workflow обязателен
Submittable обязателен
API обязателен
число занятий известно заранее
```

Это граф архитектурных зависимостей, а не расписание.

# 21. Перед дорожной картой

Проверить:

```text
1. Каждая стрелка реальна?
2. NEXT/GATE/EXT не попали в CORE?
3. Каждый механизм появляется после требования?
4. Новый DocType не создаётся ради UI?
5. status / Workflow / docstatus разведены?
6. Серверный код появляется из реального инварианта?
7. Permissions проверяются на реальных действиях?
8. Tests защищают наши контракты?
9. App и Site не смешаны?
10. Финал — чистая установка?
```

После этого можно строить дорожную карту практикума.
