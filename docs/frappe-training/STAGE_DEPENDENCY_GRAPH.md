# Граф зависимостей практических этапов Frappe

Статус: **черновик для архитектурной проверки**.

Продолжает:

- [`ARCHITECTURE_PASSPORT.md`](ARCHITECTURE_PASSPORT.md);
- [`REQUIREMENTS_MATRIX.md`](REQUIREMENTS_MATRIX.md).

Это ещё **не программа занятий**. Документ фиксирует только реальные зависимости между законченными практическими результатами.

```text
что уже существует
        ↓
какое новое требование теперь можно осмысленно решить
        ↓
какой механизм Frappe проверяется
        ↓
какой рабочий результат становится новой опорной точкой
```

---

## 1. Правила

**Узел — рабочий результат, а не тема.**

Правильно:

> Rental ссылается на существующего Customer и содержит несколько строк существующего Equipment.

Неправильно:

> Изучить Link и Child Table.

**Стрелка — настоящая зависимость.** `A → B` означает, что без A этап B нельзя корректно выполнить или архитектурно проверить. Стрелка не добавляется только ради удобства преподавания.

**CORE — обязательный маршрут.** `NEXT`, `GATE` и `EXT` остаются отдельными ветками и не становятся обязательными из-за наличия в стандарте Frappe.

# 2. Обязательные узлы

```text
P00  готовая среда Frappe v16
P01  учебный App установлен на Site

P03  Customer как самостоятельный Document

P05  предметный status Rental

P07  серверные инварианты одного Rental
P08  проверка конфликтов между Rentals

P10  автоматические тесты контрактов
P11  аудит доставки состояния App
P12  чистая установка и финальная приёмка
```

## Реальные рёбра CORE

```text
P00 → P01

P01 → P02
P01 → P03

P02 + P03 → P04

P04 → P05
P04 → P06
P04 → P07
P04 → P09

P05 + P07 → P08

P08 + P09 → P10
P08 + P09 → P11

P06 + P10 + P11 → P12
```

Это важнее любой линейной нумерации. После `P04` несколько веток развиваются независимо: UI, предметное состояние, серверные правила и permissions не обязаны ждать друг друга.

# 3. P00 — готовая среда

**Тип:** техническая предпосылка.

Нужны совместимый Bench, Frappe v16, рабочий Site, developer mode и Git.

Цель — не изучать production-администрирование, а сразу работать в среде, где Standard DocType и другие обязательные элементы могут принадлежать App.

**Результат:** ученик может работать с Bench, открыть Site и сохранять изменения приложения под Git.

---

# 4. P01 — создать и установить учебный App

**Зависит от:** `P00`.

Создаётся отдельный нейтральный App практикума и его Module. App устанавливается на учебный Site.

Ученик различает:

```text
Bench  = среда управления
Site   = конкретный экземпляр
App    = устанавливаемый пакет
Module = организация объектов внутри App
```

**Результат:** учебный App существует в Git и установлен на Site.

---

# 5. P02 — Equipment

**Требования:** `R01`, `R06`, часть `D00`.

**Зависит от:** `P01`.

Создаётся Standard `DocType` `Equipment`.

На нём проверяются:

```text
самостоятельный объект → DocType
простое свойство        → DocField
небольшой стабильный набор → Select
```

Сразу выбирается стратегия `name`, потому что идентификатор позже участвует в ссылках.

**Результат:** Equipment — самостоятельный Document без лишних справочников вокруг простых свойств.

---

# 6. P03 — Customer

**Требования:** `R02`, часть `D00`.

**Зависит от:** `P01`.

Создаётся Standard `DocType` `Customer` и выбирается naming.

`P02` и `P03` друг от друга не зависят.

**Результат:** есть две независимые сущности, которые далее можно связать через Rental.

---

# 7. P04 — Rental как композиция Documents

**Требования:** `R03`, `R04`, `R05`, часть `D00`.

**Зависит от:** `P02` + `P03`.

```text
Rental
└── Rental Item [Child DocType]

Rental.customer       → Link → Customer
Rental.items          → Table → Rental Item
Rental Item.equipment → Link → Equipment
```

Здесь в одном реальном сценарии соединяются обычный `DocType`, `Child DocType`, `Table` и `Link`.

**Результат:** один Rental связывает существующего Customer с несколькими существующими Equipment.

---

# 8. P05 — предметное состояние

**Требование:** `R08`.

**Зависит от:** `P04`.

Добавляется обычное поле `status`, например:

```text
Planned
Active
Returned
```

Пока требование говорит только о состоянии, не появляются автоматически `Workflow`, `Is Submittable` или отдельный `Rental Status` DocType.

**Результат:** бизнес-состояние хранится отдельно от системного `docstatus`.

---

# 9. P06 — стандартный Desk

**Требование:** `R16`.

**Зависит от:** `P04`.

Проверяются штатные `Form`, `List`, Link controls, Child Table UI и фильтры.

Пользователь без собственного frontend должен суметь создать Equipment, Customer и Rental, добавить строки оборудования, сохранить и найти документ.

**Результат:** первая вертикальная рабочая версия приложения.

---

# 10. P07 — инварианты одного Rental

**Требования:** `R09`, `R10`.

**Зависит от:** `P04`.

В Controller появляются серверные проверки:

```text
end_date >= start_date
одно Equipment не повторяется дважды в одном Rental
```

Ключевое различие:

```text
Client Script       = удобство формы
Controller.validate = гарантия модели
```

**Результат:** неправильный Rental нельзя сохранить обычным серверным путём Document.

---

# 11. P08 — правило между несколькими Rentals

**Требование:** `R11`.

**Зависит от:** `P05` + `P07`.

Проверяется правило: одно Equipment нельзя выдать двум клиентам на пересекающиеся активные периоды.

Это первый инвариант Rental, которому нужно прочитать другие Documents.

**Результат:** последовательное создание конфликтующего Rental блокируется сервером.

**Граница:** учебная проверка в Controller не считается полноценной стратегией конкурентного бронирования. Параллельные транзакции и блокировки — отдельная production-задача.

---

# 12. P09 — Roles/Permissions

**Требование:** `R13`.

**Зависит от:** `P04`.

Создаются реальные роли, например `Rental Operator` и `Rental Manager`, а права задаются через `Role` + `DocType Permissions`.

`P09` **не зависит от P07 или P08**. После появления реальных DocTypes права можно проектировать независимо от бизнес-проверок.

**Результат:** под разными пользователями реально различаются разрешённые операции.

---

# 13. P10 — тесты собственных контрактов

**Требование:** `R23`.

**Зависит от:** `P08` + `P09`.

К этому моменту появились собственные гарантии App:

```text
неправильный период отвергается
дублирование Equipment отвергается
конфликт прокатов обнаруживается в учебном сценарии
permissions ограничивают действия
```

Не тестируется ради coverage сам факт работы стандартного Link или `frappe.get_doc()`.

**Результат:** `bench run-tests` защищает наши контракты.

---

# 14. P11 — аудит доставки App

**Требования:** `R21`, `R22`.

**Зависит от:** `P08` + `P09` и завершённой обязательной модели.

Дисциплина воспроизводимости начинается ещё с `P01`, но здесь выполняется отдельная приёмка:

```text
Standard DocTypes находятся в App
обязательные метаданные под Git
обязательная конфигурация доставляется штатно
нет скрытых ручных изменений dev-site
нет ручного SQL как обычного шага релиза
migrate синхронизирует схему
patch используется только для реального преобразования данных
```

**Результат:** происхождение каждого обязательного элемента — App или Site — можно объяснить.

---

# 15. P12 — чистая установка

**Требование:** `R24`.

**Зависит от:** `P06` + `P10` + `P11`.

```text
чистый совместимый Frappe Site
+ учебный App из Git
+ install-app
+ migrate
+ tests
= рабочее обязательное состояние приложения
```

После установки повторяется основной сценарий через Desk.

**Практикум архитектурно завершён только после этого узла.**

# 16. NEXT — второй контур

Эти ветки подключаются только при реальном требовании.

| Узел | Требование | Зависимость | Первый механизм |
|---|---|---|---|
| `N01` | `R07` — один набор настроек Site | `P04` | `Single DocType` |
| `N02` | `R12` — история, обсуждение, файлы | `P04` | `Version` / `Comment` / `File` |
| `N03` | `R14` — поля только менеджеру | `P09` | `Permission Level` |
| `N04` | `R15` — назначить Rental сотруднику | `P04` + пользователи | `Assignment` / `ToDo` |
| `N05` | `R17` — единая точка входа | `P04` | `Workspace` |
| `N06` | `R18` — Rentals по датам | `P04` | Calendar view |
| `N07` | `R19` — акт выдачи | `P04` | `Print Format` |
| `N08` | `R20` — простой реестр активных Rentals | `P05` + данные | `Report Builder` |

Ни одна ветка `NEXT` не входит в CORE автоматически.

# 17. GATE — архитектурные развилки

## G00 — naming (`D00`)

Naming проходит каждый самостоятельный DocType при создании:

```text
P02 → Equipment
P03 → Customer
P04 → Rental
```

Это не отдельный поздний урок.

## G01 — ролевое подтверждение (`D01`)

```text
P05 + P09 + требование ограничить переход по роли
                     ↓
                 Workflow?
```

`Workflow` появляется только после сочетания состояний, ролей и требования управлять переходами.

## G02 — транзакционная фиксация (`D02`)

```text
P04 + требование зафиксировать совершённый факт
                     ↓
            Is Submittable / docstatus?
```

`G01` и `G02` друг от друга не зависят. Допустимы `Workflow` без submit, `docstatus` без Workflow, оба вместе или ни один.

## G03 — Equipment Type становится сущностью (`D03`)

```text
P02: Select
   ↓
у типа появились собственные атрибуты и управление
   ↓
Equipment Type DocType + Link
   ↓
P11: проверить доставку и миграцию существующих данных
```

Прежний `Select` не был ошибкой — изменилось требование.

## G04 — публичная заявка (`D04`)

```text
P04 + P07 + модель безопасности
          ↓
это Rental или отдельный Rental Request?
          ↓
       Web Form
```

Сначала решается предметная модель, потом UI. Новый `Rental Request`, если он действительно нужен, заново проходит identity, naming, permissions, lifecycle и delivery-проверки.

## G05 — напоминание (`D05`)

```text
P04 + даты + реальное требование уведомления
                     ↓
                 Notification
```

Scheduler/background job появляется только если задача реально перерастает семантику Notification.

# 18. EXT — интеграции

| Узел | Требование | Зависимость | Первый механизм |
|---|---|---|---|
| `X01` | `E01` — обычный CRUD внутреннего клиента | `P07` + `P09` | Document REST API |
| `X02` | `E02` — предметная команда `return_rental` | `P05` + `P07` + `P09` | Document/whitelisted method |
| `X03` | `E03` — исходящее событие | конкретное lifecycle-событие | `Webhook` |

REST полезно проверять после серверных правил и permissions: тогда видно, что вне Desk тот же Document продолжает подчиняться серверной модели.

---

# 19. Контрольные состояния

**C1 — модель существует:** после `P04` есть Equipment, Customer, Rental, Rental Item, Link и Child Table.

**C2 — приложение полезно пользователю:** после `P06` основной сценарий работает через Desk.

**C3 — модель защищает себя:** после `P10` есть серверные инварианты, междокументное правило, permissions и тесты.

**C4 — App воспроизводим:** после `P12` приложение ставится на чистый Site из Git и проходит тесты.

---

# 20. Что нельзя выводить из графа

Граф не означает, что:

```text
каждый Pxx = отдельный урок
все NEXT обязательны
все GATE должны быть активированы
Workflow обязателен
Submittable обязателен
API обязателен
практикум имеет заранее заданное число занятий
```

Несколько узлов могут стать одним практическим этапом. Один сложный узел может потребовать нескольких проходов. Это уже вопрос методики.

---

# 21. Финальная проверка перед дорожной картой

```text
1. Каждая стрелка отражает реальную зависимость?
2. NEXT/GATE/EXT не попали обратно в CORE?
3. Каждый механизм появляется после требования?
4. Новый DocType не создаётся ради будущего UI?
5. status, Workflow и docstatus разведены по смыслу?
6. Серверная логика появляется из реального инварианта?
7. Permissions проверяются на реальных Documents и действиях?
8. Tests защищают наши контракты, а не тестируют Framework ради coverage?
9. App-состояние отделено от локальной Site-настройки?
10. Финал — чистая установка, а не только рабочий dev-site?
```

# 22. Следующий артефакт

После согласования графа можно строить **дорожную карту практикума**:

```text
этап
цель
входное состояние
действия ученика
ожидаемый результат
проверка результата
архитектурное объяснение
связанные R/D/E-требования
```

Количество этапов должно получиться из графа и методики, а не задаваться заранее.
