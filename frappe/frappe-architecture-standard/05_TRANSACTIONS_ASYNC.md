# 05. Транзакции, фоновые задачи и планировщик

Эта глава разбирает три связанные задачи: где Frappe фиксирует изменения в базе, когда работу лучше вынести из HTTP-запроса и как запускать периодические операции.

---

## 1. Транзакционная модель Frappe

**[ДОКУМЕНТАЦИЯ FRAPPE]** Database API описывает стандартные границы транзакций Framework:

- успешный записывающий web-request фиксируется в конце;
- необработанное исключение вызывает rollback;
- фоновая или плановая задача фиксируется после успешного завершения;
- необработанное исключение в задаче вызывает rollback;
- patches также работают в транзакционной модели Frappe.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Для обычной операции приложения это означает, что вручную делать `commit` после каждого изменения не требуется.

Пример одной логической операции:

```text
создать Document A
обновить Document B
создать Document C
```

Если операция завершается успешно, изменения фиксируются вместе. Если возникает необработанное исключение, Framework может откатить транзакцию целиком.

---

## 2. Почему ручной commit меняет смысл операции

Ручной `frappe.db.commit()` посередине бизнес-операции разбивает её на несколько частей.

```text
создали A
COMMIT
обновили B
ошибка при C
```

После такого `commit` обычный rollback уже не вернёт состояние до создания A.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Ручной commit имеет смысл только тогда, когда разделение транзакции является частью требований операции, а не используется «на всякий случай».

Миграции, служебные инструменты и некоторые длинные процессы могут иметь собственные причины управлять транзакцией явно. Это отдельные случаи, а не базовый путь обычного CRUD.

---

## 3. Пойманное исключение и rollback

Если код сам перехватывает исключение и превращает его в успешный ответ, слой базы данных больше не может автоматически определить, что вся операция должна считаться неуспешной.

Пример:

```python
try:
    dangerous_operation()
except Exception:
    frappe.log_error()
    return "ok"
```

Если `dangerous_operation()` уже изменила данные, такой код требует отдельного решения: должны ли изменения сохраниться или быть отменены.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

## 4. Document API и прямые изменения БД

**[ДОКУМЕНТАЦИЯ FRAPPE]** `frappe.db.set_value()` обновляет значение напрямую и не вызывает обычные ORM-события `Document`, например `validate` и `on_update`.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Поэтому два пути имеют разный смысл:

```text
Document API
→ обычное изменение бизнес-данных
→ permissions, validations, lifecycle

Database API напрямую
→ намеренное изменение в обход части lifecycle
```

Прямой доступ к базе может быть полезен для миграции, технического поля или массовой служебной операции. Для обычного бизнес-изменения сначала проверяется стандартный путь `Document`.

## 5. Внешний эффект и commit

Самая неприятная граница появляется, когда операция меняет и Frappe, и внешнюю систему.

```text
1. изменить Document
2. отправить запрос во внешнюю систему
3. позже получить исключение
4. Frappe делает rollback
```

Внешняя система уже могла принять запрос, а локальная транзакция — откатиться.

Frappe предоставляет транзакционные callbacks:

```text
before_commit
after_commit
before_rollback
after_rollback
```

и возможность ставить Background Job после успешного commit.

Источники:

- https://docs.frappe.io/framework/user/en/api/database
- https://docs.frappe.io/framework/user/en/api/background_jobs

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Если внешний эффект имеет смысл только после успешного сохранения локальных данных, его запуск связывается с успешной фиксацией транзакции.

При этом `after_commit` не решает проблему повторов автоматически. Внешняя интеграция всё равно может требовать идемпотентности, идентификатора операции и сверки состояния.

## 6. Background Jobs

**[ДОКУМЕНТАЦИЯ FRAPPE]** Для асинхронной работы Framework предоставляет `frappe.enqueue` и очереди фоновых задач.

Источник:

- https://docs.frappe.io/framework/user/en/api/background_jobs

Фоновая задача естественна, когда операция:

- выполняется долго;
- обрабатывает большой объём данных;
- обращается к внешней системе и не обязана удерживать HTTP-запрос;
- может завершиться независимо от открытой формы пользователя.

Типовая схема:

```text
быстрая транзакция Document
        ↓
успешный commit
        ↓
enqueue_after_commit
        ↓
долгая обработка в worker
```

`enqueue_after_commit=True` полезен, когда worker должен увидеть только уже зафиксированное состояние.

Источник реализации v16:

- https://github.com/frappe/frappe/blob/version-16/frappe/utils/background_jobs.py

## 7. Надёжность фоновой задачи

Перенос работы в очередь не делает её автоматически надёжной. Для важной задачи полезно заранее понимать:

```text
можно ли выполнить её повторно?
что произойдёт при падении worker посередине?
может ли пользователь запустить такую же задачу второй раз?
нужен ли стабильный job_id или дедупликация?
как фиксируется ошибка?
как пользователь узнаёт результат?
```

### Идемпотентность

Идемпотентная операция допускает безопасный повтор или умеет распознать, что нужный эффект уже произошёл.

Это особенно важно для платежей, документов во внешних системах, уведомлений и других действий, где двойное выполнение создаёт новый бизнес-факт.

## 8. Scheduler Events

**[ДОКУМЕНТАЦИЯ FRAPPE]** Периодические задачи App подключаются через hook `scheduler_events`.

Источник:

- https://docs.frappe.io/framework/user/en/api/background_jobs

Примеры:

```text
каждый час проверить просроченные записи
каждую ночь пересчитать агрегаты
раз в неделю выполнить очистку
```

Для периодической задачи конкретного `Site` scheduler Frappe является естественной отправной точкой.

Внешний cron или корпоративный оркестратор уместен, если расписание принадлежит более широкой инфраструктуре, управляет несколькими системами или должно существовать независимо от конкретного Frappe Site.

---

## 9. Notification и Webhook — не то же самое, что Background Job

Frappe имеет отдельные механизмы для отдельных задач:

```text
Notification
→ пользовательское уведомление по событию или условию

Webhook
→ исходящий HTTP-вызов по событию Document

Background Job
→ асинхронное выполнение Python-работы
```

Источники:

- https://docs.frappe.io/framework/notifications
- https://docs.frappe.io/framework/user/en/webhooks
- https://docs.frappe.io/framework/user/en/api/background_jobs

Они могут использоваться вместе, но решают разные ответственности. Например, сложная интеграция с повторами и сверкой состояния обычно выходит за пределы простого Webhook.

---

## 10. Пример

Задача:

> После фиксации документа отправить данные во внешнее API, построить PDF и обработать большой набор строк.

Синхронное выполнение всего процесса в `on_submit` создаёт длинный запрос и связывает локальную транзакцию с внешними эффектами.

Более устойчивое разделение может выглядеть так:

```text
submit Document
      ↓
успешный commit
      ↓
enqueue_after_commit
      ↓
внешняя интеграция и тяжёлая обработка
```

Конкретная схема зависит от требований к гарантированной доставке, повторному запуску и обработке ошибок.

## 11. Что проверить при проектировании

Для операции с транзакциями или фоновой обработкой достаточно ответить на несколько вопросов:

```text
Где находится граница одной бизнес-операции?
Какие изменения должны фиксироваться или откатываться вместе?
Есть ли прямые изменения БД в обход Document lifecycle?
Есть ли внешний эффект до commit?
Может ли операция выполняться повторно?
Нужна ли фоновая задача?
Принадлежит ли расписание конкретному Site или внешней инфраструктуре?
```

Эти вопросы помогают выбрать между обычной транзакцией `Document`, транзакционным callback, Background Job и внешней оркестрацией без создания параллельной инфраструктуры внутри App.
