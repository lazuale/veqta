# 03. Жизненный цикл Document — где должна жить логика

## 1. Controller — владелец поведения своего DocType

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Controller` — Python-класс `DocType`, наследующий `frappe.model.document.Document`.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/controllers

**[ИСХОДНЫЙ КОД]** `frappe/model/document.py` показывает, что `Document.save()` и `insert()` выполняют проверки прав доступа, проверку данных и методы жизненного цикла.

Источник:

- https://github.com/frappe/frappe/blob/version-16/frappe/model/document.py

Это означает: `Controller` — не случайное место, куда «удобно положить код», а часть официальной модели `Document`.

---

## 2. Главное разделение: удобство интерфейса и гарантия данных

### Client Script

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Client Script` выполняется в браузере и влияет на стандартную форму.

Источник:

- https://docs.frappe.io/framework/user/en/desk/scripting/client-script

Подходящие задачи:

```text
показать предупреждение;
скрыть или показать поле;
автоматически заполнить удобное значение;
изменить фильтр Link;
добавить кнопку;
немедленно подсказать ошибку пользователю.
```

### Серверная логика Document

Подходящие задачи:

```text
данные никогда не должны нарушать правило;
неправильный Document нельзя сохранить через API;
правило должно работать при импорте и фоновой обработке;
бизнес-инвариант не зависит от интерфейса.
```

### Ключевое правило

**[АРХИТЕКТУРНЫЙ ВЫВОД]**

```text
Client Script = удобство интерфейса
серверная проверка = гарантия модели
```

Это следует из прямого предупреждения документации: проверка в `Client Script` применяется только в стандартной браузерной форме.

---

## 3. Типовой пример

Правило:

```text
end_date не может быть раньше start_date
```

Неполное решение:

```text
Client Script запрещает выбрать неправильную дату
```

Проблема: `Document` может быть создан через REST API, импорт или серверный код.

Надёжное решение:

```text
Controller.validate()
```

и, при желании, та же проверка на форме для ранней обратной связи.

## 4. Основные методы жизненного цикла

**[ДОКУМЕНТАЦИЯ FRAPPE]** API Controller перечисляет методы жизненного цикла `Document`.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/controllers

Для архитектурного мышления полезна следующая семантика.

### `before_validate`

Подготовить данные перед проверкой.

Пример:

```text
нормализовать введённое значение;
заполнить производное поле, необходимое для validate.
```

### `validate`

Проверить инварианты `Document`.

Пример:

```text
quantity > 0
end_date >= start_date
parent != self
```

### `before_save`

Последняя подготовка перед обычным сохранением.

### `on_update`

Реакция после обновления `Document`.

Нельзя автоматически превращать `on_update` в место для любой тяжёлой интеграции. Внешние эффекты требуют учёта транзакций — см. `06_TRANSACTIONS_ASYNC.md`.

### `before_submit`

Последняя проверка перед переходом в `Submitted`.

### `on_submit`

Реакция на успешный `submit`.

### `before_cancel`

Проверить, допустима ли отмена.

### `on_cancel`

Реакция на `cancel`.

### `before_update_after_submit` / `on_update_after_submit`

Отдельные методы для разрешённых изменений `Submitted Document`.

## 5. Инвариант должен находиться там, где его нельзя обойти

Инвариант — правило, которое должно быть истинно всегда.

Пример:

```text
Inspection нельзя завершить без result.
```

Если правило реализовано только:

- кнопкой;
- клиентской проверкой;
- скрытием поля;
- фильтром формы,

оно не является гарантией данных.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Критические инварианты должны проверяться на серверном пути, через который проходят обычные изменения `Document`.

---

## 6. Server Script — официальный, но особый механизм

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Server Script` позволяет выполнять Python-логику на событии `Document` или как API.

Источник:

- https://docs.frappe.io/framework/user/en/desk/scripting/server-script

Но начиная с v15 `Server Script` **отключён по умолчанию** на общих benches из соображений безопасности; общедоступные shared benches Frappe Cloud его не разрешают.

Отсюда важный вывод.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** `Server Script` не является обязательной промежуточной ступенью между настройкой и Python-кодом приложения.

### Когда Server Script уместен

- автоматизация конкретного сайта;
- ограниченная low-code-настройка;
- логика действительно должна жить как конфигурация сайта;
- среда развёртывания разрешает `Server Script`.

### Когда Controller лучше

- логика является обязательной частью устанавливаемого приложения;
- нужен Git history;
- нужны обычные code review и тесты;
- логика должна одинаково разворачиваться на нескольких сайтах.

## 7. Бизнес-статус, Workflow и docstatus

Это три разных понятия, которые могут взаимодействовать.

### Бизнес-статус

Отвечает:

> Что сейчас происходит с объектом?

Пример:

```text
New
In Progress
Waiting
Done
```

Обычно выражается обычным полем.

### Workflow

Отвечает:

> Какие переходы между состояниями разрешены, кому и при каких условиях?

`Workflow` имеет состояния, переходы, роли и условия.

Официальная документация Workflow:

- https://docs.frappe.io/erpnext/user/manual/en/workflows

### `docstatus`

**[ДОКУМЕНТАЦИЯ FRAPPE]** Системный транзакционный жизненный цикл:

```text
0 Draft
1 Submitted
2 Cancelled
```

Источник:

- https://docs.frappe.io/framework/doctypes/docstatus

`docstatus` отвечает не на вопрос «в какой колонке Kanban находится задача», а на вопрос о системном состоянии транзакционного `Document`.

---

## 8. Они различны, но не изолированы

Нельзя рисовать их как три независимых мира.

`Workflow` может управлять состояниями и участвовать в переходах, связанных с `docstatus`.

Поэтому правильная формулировка:

```text
бизнес-статус = предметный смысл состояния
Workflow      = политика переходов
docstatus     = системный транзакционный жизненный цикл
```

Один `Document` может использовать более одного из этих механизмов.

---

## 9. Когда достаточно обычного status

Пример:

```text
Task
New → In Progress → Waiting → Done
```

Если уполномоченный пользователь может менять состояние без отдельного маршрута согласования, обычного поля может быть достаточно.

### Тревожный признак

Создавать `Workflow` только потому, что у поля есть четыре значения.

`Workflow` имеет смысл, когда действительно нужны управляемые переходы, роли и условия.

---

## 10. Когда рассматривать Workflow

Пример:

```text
Draft
  ↓ Employee: Submit for Review
Manager Review
  ↓ Manager: Approve
Approved
```

Здесь присутствуют:

```text
состояния
переходы
роли
условия
```

и `Workflow` естественно выражает процесс.

### Исключение

Если согласование является сложной динамической координацией:

```text
стоимость × риск × договор × организация × внешний API
```

стандартного `Workflow` может быть недостаточно. Тогда сложная предметная логика может быть оправдана.

Наличие слова «согласование» не является автоматическим требованием использовать `Workflow`.

---

## 11. Когда нужен Is Submittable

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Submittable Documents` используют семантику `Draft → Submitted → Cancelled` и получают ограничения после submit.

Источник:

- https://docs.frappe.io/framework/doctypes/docstatus

Это естественно для документа, где submit означает совершённый или зафиксированный факт.

Примеры:

```text
финансовая операция;
акт;
складская транзакция;
официально подтверждённый документ.
```

### Неправильный мотив

> «У нас задача может быть Done, значит сделаем её Submitted».

`Done` и `Submitted` имеют разный смысл.

---

## 12. Allow on Submit — не способ бесконтрольно редактировать Submitted Document

Некоторые поля могут быть разрешены для изменения после submit.

Архитектурно это следует рассматривать как исключение для конкретных полей, а не как обход транзакционной фиксации.

Перед `Allow on Submit` нужно спросить:

> Это действительно атрибут, изменение которого не меняет смысл уже подтверждённой операции?

---

## 13. Service layer — не запрещён

Аудит официального приложения ERPNext показывает реальные классы сервисов:

- `StockLedgerService`;
- `TaxService`;
- `QualityInspectionService`;
- `AssetService`;
- `SerialBatchBundleService`.

Примеры:

- https://github.com/frappe/erpnext/blob/develop/erpnext/stock/services/stock_ledger_service.py
- https://github.com/frappe/erpnext/blob/develop/erpnext/accounts/services/taxes.py

`StockLedgerService` даже прямо описывает логику, вынесенную из большого `StockController`.

### Следствие

Нельзя утверждать:

```text
вся бизнес-логика обязана жить только в Controller
```

Правильнее:

```text
Controller
  владеет жизненным циклом Document
  и поведением своего Document

Service / предметный модуль
  выделяет сложную отдельную ответственность,
  особенно если она координирует несколько Documents
```

---

## 14. Плохой и хороший Service

### Пустая обёртка

```text
TaskService.save(task):
    task.save()
```

Она ничего не добавляет к API `Document`.

### Реальная ответственность

```text
MonthlySettlementService
```

может:

- собрать данные из нескольких `DocType`;
- выполнить расчёты;
- создать несколько `Documents`;
- вызвать интеграцию;
- работать как фоновая задача.

Тогда выделение сервиса снижает связанность и размер Controllers.

---

## 15. Repository — такой же критерий

Framework не запрещает паттерн `Repository`.

Но обёртка:

```text
TaskRepository.get(name):
    return frappe.get_doc("Task", name)
```

лишь дублирует API Framework.

`Repository` приобретает смысл, если действительно абстрагирует:

```text
несколько источников хранения;
специализированное хранение агрегата;
внешний источник;
сложную ответственность чтения/сохранения.
```

Статус этого правила: **[АРХИТЕКТУРНЫЙ ВЫВОД]**.

---

## 16. Свой DocType или расширение чужого

Если App владеет `DocType`, его `Controller` — естественное место для логики жизненного цикла.

Если другое App лишь реагирует на чужой `DocType`, часто естественнее официальная точка расширения:

```text
doc_events
extend_doctype_class
```

Это позволяет не перехватывать ответственность за чужую модель.

Подробно: `08_EXTENSION_CUSTOMIZATION.md`.

## 17. File, Comment и Version — сначала проверить встроенные спутники Document

Frappe уже предоставляет несколько связанных с `Document` механизмов, которые часто ошибочно моделируют собственными `DocType`.

### Вложения

**[ДОКУМЕНТАЦИЯ FRAPPE]** Файлы можно прикреплять к `Document`; пользователь с правом `Read` на исходный документ получает доступ и к прикреплённым к нему файлам.

Источник:

- https://docs.frappe.io/framework/user/en/desk/attachments

Обычное требование «прикрепить файл к заявке» сначала нужно проверять через `File`/Attach, а не через собственный `Request Attachment`.

### Комментарии

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Document` поддерживает комментарии; REST API v2 также предоставляет стандартный метод `add_comment`.

Источники:

- https://docs.frappe.io/framework/user/en/api/document
- https://docs.frappe.io/framework/user/en/guides/integration/rest_api

Если требование означает обычное обсуждение документа, собственный `Task Comment` не должен появляться автоматически.

### История изменений

**[ОФИЦИАЛЬНАЯ ДОКУМЕНТАЦИЯ ЭКОСИСТЕМЫ]** При включённом `Track Changes` Frappe/ERPNext создаёт журнал версий документа, где видны изменённые поля, время и пользователь.

Источник:

- https://docs.frappe.io/erpnext/document-versioning

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Для обычного требования «кто и что менял» сначала проверить встроенное версионирование. Но `Version` не нужно автоматически считать юридически неизменяемым compliance-журналом. Если требуется отдельный нормативный журнал, собственная модель может быть оправдана.

## 18. Архитектурная проверка жизненного цикла

Перед реализацией правила спросить:

```text
1. Это удобство интерфейса или гарантия данных?
2. Правило относится к одному Document или координирует несколько?
3. Какое событие жизненного цикла соответствует смыслу?
4. Может ли логика быть вызвана повторно?
5. Есть ли внешние эффекты?
6. Что произойдёт при rollback?
7. Это бизнес-статус, политика Workflow или docstatus?
8. Нужна ли транзакционная фиксация через submit?
9. Логика относится к конкретному сайту или является частью App?
10. Нужен ли Service, или Controller остаётся понятным и локальным?
11. Не дублируем ли мы встроенные File, Comment или Version без отдельной бизнес-семантики?
```

Если эти ответы известны, место для логики обычно становится очевидным без искусственных архитектурных слоёв.
