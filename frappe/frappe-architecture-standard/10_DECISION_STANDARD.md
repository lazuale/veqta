# 10. Как выбирать архитектурное решение во Frappe

Предыдущие разделы описывают отдельные механизмы Framework. Эта глава связывает их в один практический способ выбора решения.

Главный вопрос звучит так:

> Какую ответственность решает задача и какой механизм Frappe уже отвечает за эту ответственность?

Такой порядок помогает не начинать проектирование с привычного шаблона, библиотеки или собственного слоя, если нужная возможность уже является частью Framework.

---

## 1. Сначала определить смысл задачи

Одно и то же пользовательское пожелание можно реализовать разными способами, но механизмы Frappe имеют разную семантику.

Например, фраза «нужен статус» сама по себе ещё не говорит, нужен ли `Workflow`.

```text
просто хранить текущее состояние
→ поле предметной модели

ограничивать переходы по ролям и условиям
→ Workflow

транзакционно фиксировать документ
→ Is Submittable / docstatus
```

Поэтому сначала полезно сформулировать не экран или кнопку, а ответственность системы.

---

## 2. Кто владеет изменяемой частью системы

Перед изменением модели важно понять, кому она принадлежит.

```text
собственный App
→ Standard DocType, Controller и код приложения

другое установленное App
→ штатные точки расширения Frappe

конкретный Site
→ локальная настройка Site

внешняя система
→ интеграционный контракт
```

Это различие особенно важно для расширения ERPNext и других Apps. Изменение собственного `DocType` и изменение чужого `DocType` — разные архитектурные задачи.

---

## 3. Карта типовых ответственностей

Таблица ниже показывает, с какого механизма обычно имеет смысл начинать проверку.

| Задача | Механизм Frappe, который проверяется первым | Когда искать другое решение |
|---|---|---|
| Самостоятельная запись | `DocType` | объект не имеет собственной идентичности или жизненного цикла |
| Свойство записи | `DocField` | значение само стало самостоятельным объектом |
| Ссылка на другую запись | `Link` | тип связанной записи определяется динамически или нужен исторический снимок |
| Состав одного документа | Child DocType | строка должна существовать и управляться независимо от родителя |
| Один набор настроек | Single DocType | требуется несколько независимых записей |
| Файл | `File` / `Attach` | нужна отдельная предметная модель файла |
| Комментарии | `Comment` / Timeline | нужен журнал с другой бизнес-семантикой |
| История обычных изменений | `Version` / Track Changes | нужен специализированный неизменяемый журнал |
| Жизненный цикл собственного DocType | `Document Controller` | логика относится к нескольким независимым Documents или внешней системе |
| Простое бизнес-состояние | поле модели | нужны управляемые переходы |
| Переходы по ролям и условиям | `Workflow` | процесс имеет отдельную предметную семантику, которую Workflow не выражает |
| Транзакционная фиксация | `docstatus` / Is Submittable | документ не является транзакционно фиксируемым объектом |
| Доступ к DocType | Role + DocType Permissions | нужны ограничения по строкам, полям или нестандартным действиям |
| Нестандартное действие | Permission Type `[v16+]` | штатная модель прав не выражает нужную политику |
| Рабочее назначение | Assignment / ToDo | ответственность является устойчивым свойством бизнес-объекта |
| Уведомление | `Notification` | нужна сложная гарантированная внешняя доставка |
| Исходящий HTTP-вызов по событию | `Webhook` | нужны преобразования, повторы, сверка или сложная оркестрация |
| Долгая работа | Background Jobs | задача относится не к Site или управляется внешней инфраструктурой |
| Периодическая задача Site | `scheduler_events` | расписание принадлежит внешнему оркестратору |
| Обычный CRUD API | Document REST API | нужен самостоятельный публичный контракт |
| Команда приложения | whitelisted method / service | достаточно обычного CRUD Document |
| Расширение чужого DocType | Custom Field / hooks | требуется принципиально иная модель |
| Обычный внутренний интерфейс | Desk Form / List | пользовательский сценарий действительно требует другого UX |
| Несколько форм одного DocType | DocType Layout `[v16+]` | различаются не представления, а сами бизнес-объекты |
| Простой отчёт | Report Builder | нужны SQL или программные вычисления |
| Публичная форма | Web Form | нужен полноценный внешний интерфейс |
| Доставка схемы | Standard DocType JSON + `migrate` | требуется преобразование существующих данных |
| Доставка конфигурации | fixtures / exported customization | конфигурация создаётся динамически или принадлежит Site |
| Проверка собственного поведения | Frappe tests | нужна дополнительная интеграционная или end-to-end проверка |

Первый механизм в таблице не является обязательным ответом. Он задаёт естественную отправную точку: сначала проверяется возможность, уже существующая во Framework, а затем оценивается, совпадает ли её смысл с задачей.

## 4. Модель данных

Для новой части модели полезно пройти несколько вопросов.

```text
Есть ли у объекта собственная идентичность и самостоятельная жизнь?
├─ нет → поле или состав другого Document
└─ да  → обычный DocType

Принадлежит ли строка только одному родительскому Document?
├─ да  → Child DocType
└─ нет → самостоятельный DocType

Нужна связь с существующим Document?
→ Link

Тип связанного Document определяется во время работы?
→ Dynamic Link

Нужна единственная запись настроек?
→ Single DocType
```

Здесь нет правила «каждое существительное становится `DocType`». Граница проходит по смыслу и самостоятельности данных.

---

## 5. Состояние и жизненный цикл

Во Frappe рядом существуют несколько механизмов, которые легко перепутать.

### Поле состояния

Подходит для обычного предметного значения:

```text
New
In Progress
Done
```

если переходы не требуют отдельного механизма согласования.

### Workflow

Полезен, когда переходы зависят от ролей, условий и разрешённых действий.

### docstatus

Отражает транзакционный жизненный цикл submittable-документа:

```text
Draft → Submitted → Cancelled
```

`docstatus` не является универсальной заменой предметному статусу.

## 6. Где размещать собственную логику

```text
удобство стандартной формы
→ Client Script / клиентский JS

гарантия корректности данных
→ серверный путь Document

поведение собственного DocType
→ Controller

реакция на события чужого DocType
→ hooks / doc_events

логика нескольких Documents
→ предметный service или модуль

долгая операция
→ Background Job
```

Главное различие здесь — между удобством интерфейса и правилом, которое система должна гарантировать независимо от интерфейса.

---

## 7. Права доступа

Базовая модель начинается с `Role` и DocType Permissions. Дополнительные механизмы отвечают за более узкие случаи:

```text
Permission Level
→ доступ к отдельным полям

If Owner
→ отличие прав владельца Document

User Permission
→ ограничение по связанным записям

Share
→ точечный доступ к конкретному Document

Permission Type [v16+]
→ отдельное нестандартное действие

permission_query_conditions / has_permission
→ собственная политика строкового доступа
```

При собственной политике строк важно учитывать и получение списков, и прямое открытие конкретного `Document`.

---

## 8. Транзакции и фоновые задачи

Обычная записывающая операция Frappe уже выполняется в транзакционной модели Framework.

Если появляются ручной `commit`, прямое обновление БД, внешний HTTP-вызов или Background Job, полезно отдельно понять границу операции:

```text
что должно сохраниться вместе?
что может быть выполнено повторно?
что происходит при ошибке?
должен ли внешний эффект начаться только после commit?
```

Для тяжёлой обработки после успешного сохранения Frappe предоставляет, в частности, `enqueue_after_commit`.

Подробнее это разобрано в [главе 05](05_TRANSACTIONS_ASYNC.md).

## 9. API и интеграции

Document REST API уже покрывает обычные операции с `DocType`. Собственный API становится полезен, когда появляется отдельный контракт, а не только другое имя для того же CRUD.

```text
обычный CRUD
→ Document REST API

действие над одним Document
→ метод Document

команда приложения
→ whitelisted method / service

событийный HTTP-вызов
→ Webhook

устойчивый внешний контракт
→ отдельный API
```

Интеграция с повторами, преобразованием данных, сверкой и отдельной авторизацией обычно требует собственной предметной логики поверх базовых возможностей Framework.

## 10. Расширение чужих Apps

Для установленного чужого App первым выбором являются механизмы расширения Frappe:

```text
Custom Field
Property Setter
fixtures / export customizations
doc_events
extend_doctype_class [v16+]
override_doctype_class
```

Чем сильнее механизм меняет поведение чужого App, тем важнее понимать последствия обновления. `override_doctype_class` несёт гораздо больше связанности, чем добавление `Custom Field`.

Прямая правка исходников установленного App создаёт собственную ветку сопровождения и поэтому имеет совсем другую стоимость.

---

## 11. Интерфейс

Представление выбирается после модели, а не наоборот.

```text
один Document
→ Form

реестр Documents
→ List

доска по состоянию или категории
→ Kanban

несколько представлений одной формы
→ DocType Layout [v16+]

простой внешний ввод
→ Web Form

специализированный пользовательский сценарий
→ собственный frontend
```

Сам факт, что стандартный Desk выглядит иначе, чем желаемый дизайн, ещё не создаёт новой бизнес-ответственности. Собственный интерфейс оправдывает себя, когда меняет или существенно улучшает реальный пользовательский сценарий.

---

## 12. Доставка изменений

Работающее приложение на одном dev-Site ещё не означает, что приложение воспроизводимо.

Для каждого обязательного элемента полезно понимать его источник:

```text
Standard DocType
→ JSON в App

переносимая конфигурация
→ fixtures / export customizations

преобразование существующих данных
→ patch

синхронизация Site
→ bench migrate

собственная критичная логика
→ tests
```

Эта граница отделяет состояние приложения от случайной ручной настройки конкретного Site.

---

## 13. Когда стоит остановиться и перепроверить решение

Некоторые формулировки часто указывают, что решение выбрано раньше, чем сформулирована ответственность:

```text
«Так принято в другом framework».
«Сделаем Repository для каждого DocType».
«Проще везде использовать ignore_permissions=True».
«Статусы проверим только в JavaScript».
«Сделаем собственный scheduler».
«После установки администратор руками добавит обязательные поля».
«Поменяем исходник ERPNext напрямую».
«Сделаем отдельный API для create/read/update/delete».
```

Каждый такой вариант иногда может быть оправдан. Полезный вопрос один: какое новое поведение он даёт по сравнению со штатным механизмом Frappe и почему это поведение нужно приложению?

---

## 14. Короткий порядок выбора

Для большинства задач достаточно следующей последовательности:

```text
1. Сформулировать требование без привязки к экрану или технологии.
2. Назвать ответственность системы.
3. Определить владельца: Framework, App, Site или внешняя система.
4. Найти ближайший по смыслу механизм Frappe.
5. Проверить, выражает ли он нужную семантику полностью.
6. Если нет — выбрать официальную точку расширения.
7. Добавить собственный механизм только для той части поведения,
   которой действительно не хватает.
8. Проверить права, жизненный цикл, транзакции и воспроизводимость.
```

Такой подход не запрещает Python, services, SQL, собственные API или frontend. Он просто не добавляет второй экземпляр уже существующей подсистемы Frappe без отдельной задачи.
