# 13. Доступ к данным и производительность

Frappe предоставляет несколько способов читать и изменять данные. Они отличаются не удобством синтаксиса, а тем, какие обязанности Framework при этом участвуют: `Document` lifecycle, permissions, SQL, индексы и cache.

Главный вопрос здесь такой:

> Нужно получить или изменить бизнес-`Document`, либо задача действительно относится к выборке, агрегации или технической обработке данных?

---

## 1. Document остаётся основным путём изменения бизнес-данных

**[ДОКУМЕНТАЦИЯ FRAPPE]** `frappe.get_doc()` возвращает `Document`, а `insert()` и `save()` проходят через permissions и методы жизненного цикла Controller.

Источники:

- https://docs.frappe.io/framework/user/en/api/document
- https://docs.frappe.io/framework/user/en/basics/doctypes/controllers

Для обычного изменения предметного состояния естественный путь выглядит так:

```python
doc = frappe.get_doc("Rental", rental_name)
doc.status = "Active"
doc.save()
```

Так сохраняются серверные проверки и поведение, принадлежащее `Document`.

Database API и прямые методы вроде `db_update()` полезны для специальных задач, но документация прямо предупреждает, что такие операции могут обходить validations и Controller methods.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Скорость или короткий код сами по себе не являются причиной обходить `Document` lifecycle. Сначала определяется, нужна ли операции семантика бизнес-документа.

Связанный раздел: [`05_TRANSACTIONS_ASYNC.md`](05_TRANSACTIONS_ASYNC.md).

---

## 2. get_list и get_all имеют разную семантику доступа

**[ДОКУМЕНТАЦИЯ FRAPPE]** В v16 `frappe.db.get_list()` / `frappe.get_list()` применяет user permissions текущего session user.

`frappe.db.get_all()` / `frappe.get_all()` выполняет похожую выборку **без применения permissions**.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Это не два взаимозаменяемых сокращения.

```text
get_list
→ пользовательская выборка с применением permissions

get_all
→ серверная выборка всех подходящих записей без permission filtering
```

`get_all` естественен для доверенной внутренней логики, миграции, системной сверки или фоновой задачи, которая осознанно работает со всем набором данных.

Он опасен, если результат затем без дополнительной проверки возвращается пользователю.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Граница доступа должна определяться до выполнения запроса. Нельзя сначала получить всё через `get_all`, а затем надеяться, что UI сам скроет лишнее.

---

## 3. Query Builder и SQL решают задачу запроса, а не модель Document

**[ДОКУМЕНТАЦИЯ FRAPPE]** `frappe.qb` предоставляет Query Builder поверх PyPika и позволяет строить сложные SQL-запросы через единый Python API.

Источник:

- https://docs.frappe.io/framework/user/en/api/query-builder

Он полезен для задач вида:

```text
агрегация;
несколько JOIN;
сложный отчёт;
массовая аналитическая выборка;
запрос, который не является загрузкой одного Document.
```

Raw SQL также доступен через Database API, но это самый низкий уровень доступа и требует явного контроля параметров, прав доступа и совместимости с используемой СУБД.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Query Builder или SQL не являются «более правильной архитектурой», чем `Document API`. Они отвечают на другой вопрос: как выразить запрос к данным, когда объектный lifecycle одного `Document` не является центром операции.

Для user-facing выборки нужно отдельно понимать, где и как применяются permissions. Сам факт использования Query Builder не заменяет модель доступа Frappe.

---

## 4. Выбирать нужно минимально достаточный уровень

Практическая карта:

| Задача | Естественная первая точка |
|---|---|
| загрузить один бизнес-документ и работать с его поведением | `frappe.get_doc()` |
| получить разрешённый пользователю список | `frappe.get_list()` / `frappe.db.get_list()` |
| системно получить записи без permission filtering | `frappe.get_all()` / `frappe.db.get_all()` |
| получить одно простое значение | `frappe.db.get_value()` |
| сложная выборка или агрегация | Query Builder |
| специфичный SQL, который нельзя разумно выразить выше | `frappe.db.sql()` |
| обработать большой набор Documents с их поведением | `frappe.get_docs(..., as_iterator=True)` или явная пакетная обработка |

Это не запрет переходить на нижний уровень. Чем ниже уровень, тем больше обязанностей приложения перестаёт выполнять Framework автоматически.

---

## 5. Массовая обработка не означает один гигантский запрос

**[ДОКУМЕНТАЦИЯ FRAPPE]** Document API v16 поддерживает `frappe.get_docs(..., as_iterator=True, chunk_size=...)` для последовательной обработки большого набора документов без загрузки всего результата в память.

Источник:

- https://docs.frappe.io/framework/user/en/api/document

Для больших задач полезно сначала определить, что именно требуется:

```text
нужно выполнить Controller logic каждого Document
→ пакетная работа с Documents

нужно технически изменить большое число строк без lifecycle
→ Database API / bulk operation при осознанном обходе lifecycle

нужно посчитать агрегат
→ запрос, а не загрузка тысяч Documents
```

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Производительность начинается с правильной формы операции, а не с автоматического перехода на raw SQL.

---

## 6. Индекс является частью модели чтения

**[ДОКУМЕНТАЦИЯ FRAPPE]** Database API предоставляет `frappe.db.add_index()` и `frappe.db.add_unique()`.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Если приложение постоянно ищет записи по одному и тому же набору полей, проблема может быть не в Python-коде, а в отсутствии подходящего индекса.

Пример:

```text
Rental
WHERE equipment = ?
  AND status = 'Active'
  AND start_date <= ?
  AND end_date >= ?
```

Такой запрос при росте таблицы нужно анализировать как реальный database access pattern.

Индекс не добавляется «на всякий случай» каждому полю: он ускоряет одни операции ценой места и дополнительной работы при записи.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Индекс появляется из наблюдаемого способа чтения данных. Если индекс является обязательной частью App, его создание также должно быть воспроизводимой частью поставки, а не ручной настройкой одной базы.

---

## 7. Cache — штатная подсистема Frappe

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe использует Redis для встроенного cache. Web и background workers получают доступ к нему через `frappe.cache`.

Framework также предоставляет `frappe.get_cached_doc()` для загрузки `Document` с использованием cache.

Источники:

- https://docs.frappe.io/framework/user/en/guides/caching
- https://docs.frappe.io/framework/user/en/api/document

Cache подходит для данных, которые:

- читаются часто;
- вычисляются заметно дороже чтения из cache;
- не обязаны каждый раз пересчитываться;
- имеют понятный момент устаревания.

---

## 8. Cache не является источником истины

Официальное руководство предлагает два базовых способа борьбы с устаревшими значениями:

```text
TTL
или
явная invalidation при изменении исходных данных
```

Источник:

- https://docs.frappe.io/framework/user/en/guides/caching

Ключ cache должен учитывать всё, от чего зависит результат.

Например, если результат зависит от:

```text
Site
User
Company
Language
Permission context
```

нельзя использовать один общий ключ только потому, что вычисление называется одинаково.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Cache хранит производную копию результата. Источник истины остаётся в данных и правилах приложения; должна существовать понятная стратегия получения правильного значения после изменения исходного состояния.

---

## 9. Cache изолирован по Site, но не решает всю изоляцию приложения

**[ДОКУМЕНТАЦИЯ FRAPPE]** `frappe.cache` добавляет site context к ключам, поэтому одинаковый ключ на двух Sites одного Bench не означает одну и ту же запись Redis.

Источник:

- https://docs.frappe.io/framework/user/en/guides/caching

Это снимает одну часть multitenancy-задачи, но не означает автоматическую изоляцию по пользователю, роли или бизнес-контексту.

Если результат зависит от этих параметров, они остаются ответственностью дизайна cache key.

---

## 10. Сначала измерить, потом оптимизировать

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Recorder` умеет захватывать запросы и background jobs, SQL queries, stack traces и `EXPLAIN`. Frappe также позволяет профилировать методы через Bench.

Источник:

- https://docs.frappe.io/framework/user/en/profiling

Поэтому типичный порядок работы с медленным сценарием:

```text
воспроизвести проблему
↓
измерить запросы и время
↓
понять причину
↓
исправить форму запроса / индекс / количество обращений
↓
добавить cache только если он действительно решает оставшуюся проблему
```

Premature cache часто скрывает плохой запрос и добавляет новую проблему invalidation.

---

## 11. Быстрая карта решения

```text
Нужно изменить бизнес-Document?
→ Document API

Нужен список в пользовательском контексте?
→ get_list

Нужна системная выборка без permissions?
→ get_all с явным пониманием границы доступа

Нужна сложная выборка?
→ Query Builder / SQL по смыслу задачи

Запрос медленный?
→ Recorder / EXPLAIN → форма запроса → индекс

Одинаковый дорогой результат считается снова и снова?
→ cache с TTL или invalidation
```

Критерий тот же, что и в остальных главах стандарта: использовать механизм Frappe по его реальной ответственности, а не по привычке из другого стека.
