# 11. Развёртывание, миграции и тестирование — архитектура должна воспроизводиться

Эта глава отвечает на вопрос, как обязательное состояние App попадает на новый или существующий `Site` и как проверить, что оно воспроизводится. Механизмы `fixtures`, `Export Customizations` и владение настройками подробно разобраны в [главе 08](08_EXTENSION_CUSTOMIZATION.md), а runtime-конфигурация и зависимости Site — в [главе 10](10_CONFIGURATION_OPERATIONS.md).

---

## 1. Архитектура App существует не только на dev-сайте

Система считается спроектированной не тогда, когда она работает на одном настроенном Site, а когда обязательное состояние можно воспроизвести.

Для App, управляемого через Git:

```text
чистый совместимый Frappe Site
+ репозиторий App
+ install-app / migrate
= обязательное состояние приложения
```

Это **[АРХИТЕКТУРНЫЙ ВЫВОД]**, основанный на официальных механизмах Apps, Standard DocType metadata, fixtures и миграций.

---

## 2. Standard DocType metadata живут в исходном коде

**[ДОКУМЕНТАЦИЯ FRAPPE]** В developer mode изменения Standard DocType сохраняются как JSON в исходниках App. При установке или `migrate` схема синхронизируется с metadata.

Источник:

- https://docs.frappe.io/framework/user/en/guides/deployment/migrations

Если обязательное поле существует только потому, что его вручную добавили на одном dev-Site, продукт ещё не воспроизводим.

---

## 3. bench migrate синхронизирует состояние App с Site

**[ДОКУМЕНТАЦИЯ FRAPPE]** `bench migrate` выполняет процесс обновления, включающий hooks миграции, patches, синхронизацию схемы, фоновых задач, fixtures, dashboards и других переносимых элементов.

Источник:

- https://docs.frappe.io/framework/user/en/bench/reference/migrate

Это показывает, что поставка Frappe App — не только обновление Python-кода.

---

## 4. Изменение схемы нужно проектировать вместе с данными

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe синхронизирует DocTypes из metadata и отдельно предупреждает, что обратные миграции схемы не поддерживаются как автоматический механизм rollback.

Источник:

- https://docs.frappe.io/framework/user/en/guides/deployment/migrations

Перед изменением производственного `DocType` нужно понимать:

```text
что произойдёт с существующими записями?
можно ли безопасно добавить поле?
меняется ли тип данных?
что делать со старым полем?
как мигрировать значения?
как будет возвращаться предыдущая версия приложения?
```

Проектировать новую схему так, будто производственных данных ещё нет, опасно.

---

## 5. Удаление поля и удаление данных — не одно и то же

**[ДОКУМЕНТАЦИЯ FRAPPE]** При синхронизации схемы удалённые поля могут сохранять физическую колонку, чтобы избежать немедленной потери данных и позволить миграции использовать старые значения.

Источник:

- https://docs.frappe.io/framework/user/en/guides/deployment/migrations

Для пользователя поле уже может исчезнуть из модели, даже если старая колонка ещё физически присутствует. На неё нельзя продолжать опираться как на штатную часть App.

---

## 6. Data patches изменяют существующие данные

**[ДОКУМЕНТАЦИЯ FRAPPE]** Для одноразовых преобразований данных Frappe использует Python patches, зарегистрированные в `patches.txt`.

Источник:

- https://docs.frappe.io/framework/user/en/guides/deployment/migrations

Пример:

```text
раньше status = "Open"
теперь status = "New"
```

Если существующие записи должны быть преобразованы, это часть миграции App, а не ручная инструкция администратору выполнить SQL после релиза.

Для patch полезно заранее понимать:

```text
что если часть данных уже мигрирована?
какая схема ожидается до и после выполнения?
нужно ли явное управление транзакцией?
как проверить результат?
```

Связанная тема транзакций: [глава 06](06_TRANSACTIONS_ASYNC.md).

---

## 7. Hooks установки и миграции — для специальных действий

Frappe предоставляет hooks жизненного цикла установки App и миграции Site.

Источник:

- https://docs.frappe.io/framework/user/en/python-api/hooks

Они подходят для действий, которые нельзя естественно выразить metadata, fixture или patch. Hook не должен заменять штатный декларативный механизм только потому, что Python быстрее написать.

---

## 8. Переносимая конфигурация должна иметь одного владельца

`fixtures`, `Export Customizations`, Custom Fields и Property Setters здесь рассматриваются только с точки зрения поставки: если элемент принадлежит App, он должен появляться на новом Site воспроизводимо.

Как выбирать между локальной настройкой Site и конфигурацией App, разобрано в [главе 08](08_EXTENSION_CUSTOMIZATION.md). Runtime-конфигурация вроде `site_config.json`, секретов и `required_apps` разобрана в [главе 10](10_CONFIGURATION_OPERATIONS.md).

Таким образом, эта глава не повторяет семантику механизмов, а отвечает только за их доставку и миграцию.

---

## 9. Архитектура зависит от версии Framework

Стандарт ориентирован на Frappe v16. Отдельные возможности имеют границы по версиям, например:

```text
extend_doctype_class → v16+
Packages             → v14+
ограничения Server Script по умолчанию → v15+
IntegrationTestCase / UnitTestCase → актуальная test API v16
```

Решение, зависящее от версии, должно быть совместимо с заявленной линией Frappe. Нельзя использовать механизм v16 и одновременно обещать поддержку v15 без отдельной реализации.

---

## 10. Тестирование проверяет собственные контракты App

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe предоставляет test runner и команду `bench --site ... run-tests`.

Источник:

- https://docs.frappe.io/framework/user/en/testing

**[ИСХОДНЫЙ КОД]** В Frappe v16.33.0 boilerplate Standard DocType генерирует тест через `IntegrationTestCase`.

Источник:

- https://github.com/frappe/frappe/blob/v16.33.0/frappe/core/doctype/doctype/boilerplate/test_controller._py

Старый `FrappeTestCase` в v16 deprecated; актуальное разделение:

```text
IntegrationTestCase
→ тест взаимодействует с БД и Documents

UnitTestCase
→ логика остаётся в памяти и не зависит от БД
```

Источник:

- https://github.com/frappe/frappe/wiki/Migrating-to-version-16#tests

---

## 11. Что тестировать

Тестируется не сам факт существования стандартных возможностей Frappe, а собственное поведение App:

```text
инварианты Document;
жизненный цикл submit/cancel;
права доступа;
предметные переходы;
сервисы и расчёты;
API-команды;
миграции данных;
критические интеграции.
```

Нет смысла писать собственный тест только чтобы доказать, что `Link`, `frappe.get_doc()` или стандартный REST endpoint вообще существуют. Это ответственность Framework.

---

## 12. Tests, БД и user context в v16

**[ИСХОДНЫЙ КОД]** `IntegrationTestCase` добавляет test database setup/teardown и работу с зависимыми test records. Frappe также предоставляет context manager `self.set_user(user)` для временного переключения пользователя.

Источники:

- https://github.com/frappe/frappe/blob/v16.33.0/frappe/tests/classes/integration_test_case.py
- https://github.com/frappe/frappe/blob/v16.33.0/frappe/tests/classes/context_managers.py

Для обычного integration test не нужно вручную добавлять `commit()` / `rollback()` только ради очистки теста. Сначала используется lifecycle тестовой инфраструктуры Framework. Явное управление транзакцией оправдано, когда транзакционная семантика сама является предметом теста.

---

## 13. Проверка обновления отличается от unit test

Для App, который развивается во времени или расширяет другие Apps, нужны сценарии:

```text
чистая установка;
migrate с предыдущей поддерживаемой версии;
совместимость hooks/overrides;
синхронизация переносимой конфигурации;
критические права доступа;
критические пользовательские сценарии.
```

Иначе App может годами работать на одном dev-Site и одновременно не устанавливаться заново.

---

## 14. Воспроизводимость — критерий готовности

Плохая поставка обязательной конфигурации:

```text
1. install app
2. откройте Customize Form
3. создайте поля
4. измените permissions
5. создайте Workflow
6. добавьте Notification
```

Если эти элементы являются частью продукта на каждом Site, они должны приезжать с App штатным воспроизводимым способом.

---

## 15. Итоговая проверка

```text
Можно ли установить App на чистый Site без ручного восстановления его архитектуры?
Что мигрирует schema, а что — данные?
Какие настройки принадлежат App, а какие Site?
Есть ли обязательный ручной SQL и почему?
Какие возможности зависят от версии Framework?
Какие tests защищают собственные контракты?
Проверяется ли чистая установка?
Проверяется ли migrate с предыдущей поддерживаемой версии?
```

Если обязательное состояние существует только на одном давно настроенном Site, архитектура ещё не воспроизводима.
