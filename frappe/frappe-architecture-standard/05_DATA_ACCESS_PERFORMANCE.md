# 05. Доступ к данным и производительность

Эта глава разбирает чтение данных, выбор уровня API, permission boundary, массовые выборки, индексы и cache. Изменение бизнес-`Document` и обход его lifecycle уже разобраны в [главе 03](03_DOCUMENT_LIFECYCLE.md) и [главе 06](06_TRANSACTIONS_ASYNC.md), поэтому здесь они не повторяются.

Главный вопрос:

> Нужно получить данные в пользовательском контексте, выполнить доверенную системную выборку или решить задачу запроса и производительности?

---

## 1. Загрузка Document и право на чтение — не одно и то же

**[ИСХОДНЫЙ КОД]** В Frappe v16.33.0 `frappe.get_doc()` загружает `Document`, но сама загрузка не означает проверку права `read`. API поддерживает явный `check_permission`, а у `Document` есть `check_permission()`.

Источник:

- https://github.com/frappe/frappe/blob/v16.33.0/frappe/model/document.py

Для user-facing метода граница может выглядеть так:

```python
doc = frappe.get_doc("Rental", rental_name, check_permission="read")
```

или:

```python
doc = frappe.get_doc("Rental", rental_name)
doc.check_permission("read")
```

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Нужно различать **загрузку объекта** и **разрешение показать его пользователю**.

Связанный раздел: [`04_SECURITY.md`](04_SECURITY.md).

---

## 2. get_list и get_all имеют разную семантику доступа

**[ДОКУМЕНТАЦИЯ FRAPPE]** `frappe.get_list()` / `frappe.db.get_list()` применяет user permissions текущего пользователя. `frappe.get_all()` / `frappe.db.get_all()` выполняет похожую выборку без permission filtering.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

```text
get_list
→ пользовательская выборка с применением permissions

get_all
→ системная выборка без permission filtering
```

`get_all` естественен для доверенной внутренней логики, миграции, системной сверки или фоновой задачи, которая осознанно работает со всем набором данных.

Он опасен, если результат затем без дополнительной проверки возвращается пользователю.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Граница доступа определяется до выполнения запроса. UI не является механизмом фильтрации уже полученных запрещённых данных.

---

## 3. get_value и другие Database API не добавляют permission boundary автоматически

Database API удобен для точечного чтения значений и технической работы с БД.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Пример:

```python
status = frappe.db.get_value("Rental", rental_name, "status")
```

Такое чтение хорошо подходит внутреннему коду, где граница доступа уже определена. Для публичного метода нельзя считать сам факт вызова Database API доказательством того, что пользователь имеет право видеть запись или поле.

---

## 4. Query Builder и SQL решают задачу запроса, а не модель Document

**[ДОКУМЕНТАЦИЯ FRAPPE]** `frappe.qb` предоставляет Query Builder поверх PyPika и позволяет строить сложные SQL-запросы через Python API.

Источник:

- https://docs.frappe.io/framework/user/en/api/query-builder

Он полезен для задач вида:

```text
агрегация;
несколько JOIN;
сложный отчёт;
массовая аналитическая выборка;
запрос, который не является загрузкой одного Document.
```

Raw SQL доступен через Database API, но это более низкий уровень: приложение само отвечает за параметры, совместимость с СУБД и границу доступа.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Query Builder или SQL не являются «более правильной архитектурой», чем `Document API`. Они отвечают на другой вопрос — как выразить запрос к данным.

---

## 5. Практическая карта чтения

| Задача | Естественная первая точка |
|---|---|
| открыть один Document для пользователя | `frappe.get_doc()` + явная проверка `read` |
| получить разрешённый пользователю список | `frappe.get_list()` / `frappe.db.get_list()` |
| системно получить записи без permission filtering | `frappe.get_all()` / `frappe.db.get_all()` |
| получить одно значение во внутреннем коде | `frappe.db.get_value()` |
| сложная выборка или агрегация | Query Builder |
| специфичный SQL, который нельзя разумно выразить выше | `frappe.db.sql()` |

Чем ниже уровень доступа, тем больше обязанностей приложения перестаёт выполнять Framework автоматически.

---

## 6. Массовая обработка начинается с формы задачи

**[ДОКУМЕНТАЦИЯ FRAPPE + ИСХОДНЫЙ КОД]** В v16 Document API поддерживает последовательную обработку большого набора документов через `frappe.get_docs(..., as_iterator=True, chunk_size=...)`.

Источники:

- https://docs.frappe.io/framework/user/en/api/document
- https://github.com/frappe/frappe/blob/v16.33.0/frappe/model/document.py

Перед оптимизацией полезно разделить три случая:

```text
нужно выполнить Controller logic каждого Document
→ пакетная работа с Documents

нужно технически изменить большое число строк без lifecycle
→ Database API / bulk operation при осознанном обходе lifecycle

нужно посчитать агрегат
→ запрос, а не загрузка тысяч Documents
```

Пакетная загрузка Documents, как и `get_doc()`, сама по себе не является permission boundary для данных, возвращаемых пользователю.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Производительность начинается с правильной формы операции, а не с автоматического перехода на raw SQL.

## 7. Индекс является частью модели чтения

**[ДОКУМЕНТАЦИЯ FRAPPE]** Database API предоставляет `frappe.db.add_index()` и `frappe.db.add_unique()`.

Источник:

- https://docs.frappe.io/framework/user/en/api/database

Если приложение постоянно ищет записи по одному и тому же набору полей, проблема может быть не в Python-коде, а в отсутствии подходящего индекса.

Пример:

```text
Rental
WHERE equipment = ?
  AND status = 'Active'
  AND start_date <= ?
  AND end_date >= ?
```

Индекс не добавляется каждому полю «на всякий случай»: он ускоряет одни операции ценой места и дополнительной работы при записи.

Если индекс обязателен для App, его создание должно быть воспроизводимой частью поставки, а не ручной настройкой одной базы.

## 8. Cache — штатная подсистема Frappe

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe использует Redis для cache; web и background workers работают с ним через `frappe.cache`. Для `Document` также доступен `frappe.get_cached_doc()`.

Источники:

- https://docs.frappe.io/framework/user/en/guides/caching
- https://docs.frappe.io/framework/user/en/api/document

Cache подходит для данных, которые часто читаются, заметно дороже вычисляются и имеют понятный момент устаревания.

Официальное руководство предлагает две базовые стратегии актуальности:

```text
TTL
или
явная invalidation при изменении исходных данных
```

Источник:

- https://docs.frappe.io/framework/user/en/guides/caching

Cache key должен учитывать всё, от чего зависит результат. Site context Frappe добавляет сам, но зависимость от пользователя, роли, компании, языка или другого бизнес-контекста остаётся ответственностью приложения.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Cache хранит производную копию результата, а не новый источник истины.

---

## 9. Сначала измерить, потом оптимизировать

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Recorder` умеет захватывать requests и background jobs, SQL queries, stack traces и `EXPLAIN`. Frappe также позволяет профилировать методы через Bench.

Источник:

- https://docs.frappe.io/framework/user/en/profiling

Практический порядок:

```text
воспроизвести проблему
↓
измерить запросы и время
↓
понять причину
↓
исправить форму запроса / количество обращений / индекс
↓
добавить cache, если он действительно нужен
```

Преждевременный cache часто только скрывает плохой запрос и добавляет новую проблему invalidation.

---

## 10. Итоговая карта

```text
Один Document для пользователя?
→ get_doc + read permission check

Список в пользовательском контексте?
→ get_list

Системная выборка без permissions?
→ get_all с явным пониманием границы доступа

Сложная выборка?
→ Query Builder / SQL по смыслу задачи

Медленный запрос?
→ Recorder / EXPLAIN → форма запроса → индекс

Повторяется дорогой результат?
→ cache с TTL или invalidation
```

Критерий тот же, что и в остальных главах: выбирать механизм Frappe по его реальной ответственности.
