# 01. Основы — как Frappe предполагает строить приложения

## 1. Frappe — не пустой веб-фреймворк

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe официально описывает себя как **фреймворк, основанный на метаданных, полнофункциональный и поставляемый с основными прикладными возможностями из коробки**. В Introduction отдельно сказано, что метаданные рассматриваются как данные, а архитектура Framework сознательно монолитна: Frappe поставляется почти со всем, что требуется современному веб-приложению.

Источники:

- https://docs.frappe.io/framework/user/en/introduction
- https://docs.frappe.io/framework/user/en/basics
- https://github.com/frappe/frappe/blob/version-16/pyproject.toml

На бытовом языке это значит: Frappe похож не на пустую строительную площадку, а на уже оборудованное здание. Пользователи, роли, документы, формы, списки, файлы, комментарии, API, планировщик и фоновые задачи уже существуют.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Поэтому обычное приложение должно в первую очередь добавлять предметную модель и правила, а не заново реализовывать инфраструктуру приложения.

---

## 2. Configuration over code — прямой принцип Frappe

**[ДОКУМЕНТАЦИЯ FRAPPE]** Страница *Why Frappe Framework?* прямо говорит:

- основная философия — писать как можно меньше кода;
- предпочитать configuration over code, то есть настройку вместо программирования там, где этого достаточно;
- универсальную возможность, нужную многим приложениям, помещать непосредственно во Framework.

Источник:

- https://docs.frappe.io/framework/user/en/basics/why

Это один из самых сильных первичных пруфов для всего стандарта.

Но его нельзя толковать как запрет программирования.

Неправильное прочтение:

```text
метаданные хорошо
Python плохо
```

Правильное прочтение:

```text
если Framework уже выражает задачу штатно,
не переписывай тот же механизм кодом без причины
```

Python Controller, hooks, сервисы, фоновые задачи и собственный API — штатные части экосистемы Frappe.

## 3. Монолит — не «всё в одном файле»

**[ДОКУМЕНТАЦИЯ FRAPPE]** Introduction прямо говорит: Frappe придерживается монолитной архитектуры и поэтому предоставляет согласованные прикладные возможности из коробки.

Источник:

- https://docs.frappe.io/framework/user/en/introduction

Под «монолитом» здесь нельзя понимать плохой код или отсутствие модулей. Речь о другом: основные части прикладной платформы работают в одной согласованной системе.

Например:

```text
DocType
  ├─ метаданные
  ├─ хранение
  ├─ права доступа
  ├─ интерфейс Form/List
  ├─ REST-ресурс
  └─ жизненный цикл
```

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Поэтому механическое добавление параллельных слоёв Entity/Repository/ACL/API может разрушить именно ту интеграцию, ради которой используется Frappe.

Исключение: слой решает отдельную реальную ответственность. Например, сложный сервис интеграции или общий сервис расчёта складских операций не дублирует модель `Document`, а организует сложную предметную логику.

---

## 4. Основная единица приложения — DocType

**[ДОКУМЕНТАЦИЯ FRAPPE]** Документация называет `DocType` **core building block** приложений на Frappe — основным строительным блоком.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes

`DocType` задаёт метаданные модели. Обычный `DocType` приводит к созданию структуры в базе данных и получает стандартные представления Framework.

Поэтому архитектура Frappe начинается не с таблиц SQL и не с REST-endpoints, а с вопроса:

> Какие устойчивые документы и записи существуют в предметной области?

При этом не каждое существительное бизнеса обязано стать отдельным `DocType`. Решение разбирается отдельно в `02_DATA_MODEL.md`.

## 5. Document — не просто строка ORM

**[ДОКУМЕНТАЦИЯ FRAPPE]** Каждый Controller `DocType` наследуется от `frappe.model.document.Document`. `Document` управляет загрузкой, сохранением и жизненным циклом документа.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/controllers

**[ИСХОДНЫЙ КОД]** В `frappe/model/document.py` метод `save()` проверяет права доступа, выполняет проверки и методы жизненного цикла.

Источник:

- https://github.com/frappe/frappe/blob/version-16/frappe/model/document.py

Следовательно, Frappe `Document` — более богатая абстракция, чем обычная строка базы данных.

Он находится на пересечении:

```text
метаданные
хранение
права доступа
жизненный цикл
связи
хуки версионирования
события Framework
```

**[АРХИТЕКТУРНЫЙ ВЫВОД]** `Repository`, который только переименовывает `frappe.get_doc()` и `doc.save()`, обычно не добавляет ценности. Но `Repository` или `Service` не запрещены, если действительно изолируют новую ответственность.

## 6. Границы ответственности: Framework, App, Site и внешняя система

Для любого решения сначала нужно понять, **кто им владеет**.

### Framework

Общие инфраструктурные возможности:

```text
модель DocType/Document
движок прав доступа
REST-ресурсы
планировщик и фоновые задачи
hooks
основа Desk
migrate
файлы, комментарии, назначения, уведомления
```

### Приложение (App)

Устанавливаемый пакет, хранящийся в исходном коде:

```text
свои Standard DocType
Controllers
hooks.py
отчёты
публичные ресурсы
patches
fixtures
код интеграций
```

**[ДОКУМЕНТАЦИЯ FRAPPE]** `App` является Python-пакетом; `hooks.py` содержит точки интеграции, `modules.txt` — модули, `patches.txt` — миграции.

Источники:

- https://docs.frappe.io/framework/user/en/basics/apps
- https://docs.frappe.io/framework/user/en/tutorial/create-an-app

### Сайт (Site)

Конкретный экземпляр системы. На нём могут существовать настройки и локальная конфигурация:

```text
Custom Field
Property Setter
Client Script
Server Script
Workflow
Notification
настройки конкретного сайта
```

Часть таких изменений можно экспортировать в App.

### Внешняя система

Система за границей Frappe: ERP, внешний API, поставщик авторизации, хранилище аналитических данных и т. д.

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Ошибка в определении владельца ответственности часто и создаёт костыль. Например, если App требует конкретное поле в чужом `DocType`, это нельзя оставлять только ручным изменением одного dev-сайта: изменение должно стать воспроизводимой частью App.

## 7. App, Module и Package — не одно и то же

### App

**[ДОКУМЕНТАЦИЯ FRAPPE]** Граница установки, исходного кода и зависимостей. `App` имеет Python-пакет, hooks, modules, patches и другие файлы.

Источник:

- https://docs.frappe.io/framework/user/en/basics/apps

### Module

**[ДОКУМЕНТАЦИЯ FRAPPE]** Frappe App организуется в модули. Это способ группировки связанных `DocType` и кода.

Источник:

- https://docs.frappe.io/framework/user/en/basics/apps

Нельзя автоматически приравнивать `Module` к DDD bounded context. Это может быть удобным проектным решением, но Framework этого не требует.

### Package

**[ДОКУМЕНТАЦИЯ FRAPPE]** Начиная с v14 Frappe поддерживает `Packages` — облегчённый механизм упаковки пользовательских `Module Def`, созданных через интерфейс. Package можно выпускать, импортировать и хранить в Git.

Источник:

- https://docs.frappe.io/framework/user/en/guides/deployment/packages

**[АРХИТЕКТУРНЫЙ ВЫВОД]** Для серьёзного приложения, управляемого через Git, обычный `App` остаётся основным инструментом. `Package` полезен, когда задача действительно относится к переносимой low-code-конфигурации.

## 8. Расширяемость — часть замысла, а не обход Framework

**[ДОКУМЕНТАЦИЯ FRAPPE]** Страница Why Frappe прямо говорит об extensible architecture: собственные Apps могут приносить модели и изменять существующие модели Frappe.

Источник:

- https://docs.frappe.io/framework/user/en/basics/why

Hooks официально определены как места, где App может расширять или переопределять стандартную реализацию.

Источник:

- https://docs.frappe.io/framework/user/en/python-api/hooks

Это означает:

```text
не менять файлы ядра
        ↓
найти предусмотренную точку расширения
        ↓
если её недостаточно — обосновать собственное решение
```

В v16 особенно важен `extend_doctype_class`, позволяющий добавлять поведение существующему `DocType` без полной замены Controller.

## 9. Почему стандарт не навязывает Clean Architecture или DDD

Frappe не запрещает применять идеи DDD, сервисы или декомпозицию.

Но стандарт не позволяет использовать их как самостоятельное доказательство решения.

Плохое обоснование:

> «У каждой Entity должен быть Repository, потому что так принято».

Хорошее обоснование:

> «Эта предметная операция координирует пять DocType и внешний API, не принадлежит жизненному циклу одного Document, поэтому выделяем отдельный сервис».

Первое — перенос чужого шаблона.

Второе — объяснение ответственности.

## 10. Минимальная проверка штатности решения для Frappe

Решение проходит базовый фильтр, если на пять вопросов есть ясный ответ:

```text
1. Что является бизнес-требованием?
2. Какой штатный механизм Frappe ближе всего по смыслу?
3. Совпадает ли его смысл с требованием?
4. Если нет — какая официальная точка расширения существует?
5. Какую новую ответственность добавляет собственный код?
```

Ключевой критерий — **совпадение смысла**, а не просто наличие похожей функции в интерфейсе.
