# 13. Типовые архитектурные примеры

Ниже собраны обычные задачи прикладных систем, на которых хорошо видна логика Frappe. Каждый пример начинается с предметной задачи, а механизм Framework появляется только после неё.

---

## 1. Заявка с несколькими позициями

### Задача

Есть заявка на закупку:

```text
Заявитель: Иван
Дата: 02.09.2026

Позиции:
- Бумага, 10 пачек
- Ручки, 50 шт.
- Картридж, 2 шт.
```

Каждая позиция существует только внутри своей заявки и отдельно пользователю не нужна.

### Естественная модель Frappe

```text
Purchase Request
└── items: Table → Purchase Request Item [Child DocType]
```

`Child DocType` предназначен для строк, принадлежащих родительскому `Document`. Framework хранит связь с родителем и порядок строк, а стандартная Form отображает их как таблицу.

Источник:

- https://docs.frappe.io/framework/user/en/basics/doctypes/child-doctype

### Что часто усложняет решение

Создание самостоятельного `DocType` для каждой строки, если у строки нет собственной жизни:

```text
Purchase Request
Purchase Request Item
```

с отдельными списками, правами и ручным управлением связью.

Отдельный обычный `DocType` становится оправдан, если строка сама является самостоятельным объектом: открывается отдельно, имеет собственные права, историю или используется несколькими документами.

Подробнее: [модель данных](02_DATA_MODEL.md).

## 2. Простая рабочая задача со статусом

### Задача

У задачи есть четыре состояния:

```text
New → In Progress → Waiting → Done
```

Пользователь может менять состояние сам. Отдельного согласования по ролям нет.

### Естественная модель Frappe

Обычное предметное поле:

```text
status : Select
```

`Workflow` здесь не добавляет полезной семантики: требование говорит только о текущем состоянии записи.

### Что часто усложняет решение

Сразу вводить одновременно:

```text
status
workflow_state
docstatus
```

и пытаться синхронизировать три разных механизма как одно и то же состояние.

`docstatus` относится к транзакционному lifecycle submittable-документа, а `Workflow` нужен для управляемых переходов. Простое бизнес-состояние может оставаться обычным полем.

Подробнее: [жизненный цикл Document](03_DOCUMENT_LIFECYCLE.md).

## 3. Согласование заявки руководителем

### Задача

Сотрудник создаёт заявку. Руководитель может её одобрить или вернуть. Обычный сотрудник не должен выполнять действие `Approve`.

```text
Draft
  ↓ Submit for review
Review
  ├── Approve → Approved
  └── Return  → Draft
```

### Естественная модель Frappe

Если переходы зависят от ролей и условий, первым кандидатом является `Workflow`.

Если само действие `Approve` существует отдельно от Workflow и требует отдельного права, в Frappe v16 также есть `Permission Type`.

Источник:

- https://docs.frappe.io/framework/permission-types

### Что часто ломает решение

Спрятать кнопку через JavaScript и считать это защитой:

```text
если пользователь не Manager
→ hide Approve button
```

Скрытая кнопка меняет интерфейс, но не создаёт серверного правила доступа. Действие, влияющее на данные, проверяется на серверном пути.

Подробнее: [безопасность](04_SECURITY.md) и [жизненный цикл](03_DOCUMENT_LIFECYCLE.md).

## 4. Добавить поле в DocType другого App

### Задача

Собственному App нужен дополнительный идентификатор во внешней системе для уже существующего `Customer`:

```text
external_customer_id
```

`Customer` принадлежит другому установленному App.

### Естественная модель Frappe

Для добавления поля Frappe предоставляет `Custom Field`. Если изменение должно поставляться вместе с App, соответствующая настройка может экспортироваться штатными средствами.

Источники:

- https://docs.frappe.io/framework/user/en/guides/app-development/exporting-customizations
- https://docs.frappe.io/framework/user/en/guides/app-development/how-to-create-custom-fields-during-app-installation

### Что часто усложняет сопровождение

Три более тяжёлых варианта без отдельной причины:

```text
править JSON чужого App напрямую
создать копию Customer
сделать fork App ради одного поля
```

Все они создают дополнительную стоимость обновлений, хотя Framework уже предусматривает расширение метаданных.

Подробнее: [расширение и настройка](08_EXTENSION_CUSTOMIZATION.md).

## 5. Интеграция делает обычный CRUD

### Задача

Внутренний сервис должен создавать, читать и обновлять записи известного `DocType`.

### Естественная модель Frappe

Frappe уже предоставляет Document REST API. Для обычного CRUD отдельный слой endpoints может не понадобиться.

Источник:

- https://docs.frappe.io/framework/user/en/api/rest

### Что часто дублирует Framework

Создать четыре своих endpoint:

```text
/api/task/create
/api/task/read
/api/task/update
/api/task/delete
```

которые внутри просто вызывают стандартные операции `Document`.

Такой слой имеет смысл только если он создаёт новый контракт: скрывает внутреннюю модель Frappe, агрегирует несколько Documents, поддерживает отдельное версионирование или добавляет предметную команду.

Подробнее: [API и интеграции](07_API_INTEGRATION.md).

## 6. После сохранения нужна тяжёлая обработка

### Задача

После фиксации документа нужно:

- отправить данные во внешнюю систему;
- обработать большой набор строк;
- сформировать тяжёлый результат.

Пользователь не должен ждать завершения всей работы в открытом HTTP-запросе.

### Естественная модель Frappe

Быстрая операция с `Document` завершается отдельно, а тяжёлая работа уходит в Background Job.

Если worker должен стартовать только после успешной фиксации данных, используется путь после commit, например `enqueue_after_commit`.

Источники:

- https://docs.frappe.io/framework/user/en/api/background_jobs
- https://docs.frappe.io/framework/user/en/api/database

### Что часто создаёт проблемы

Выполнить всё синхронно в `on_submit`:

```text
submit
├── HTTP request во внешнее API
├── долгий расчёт
└── тысячи updates
```

Это удлиняет транзакцию и связывает локальный rollback с уже произошедшими внешними эффектами.

Подробнее: [транзакции и фоновые задачи](06_TRANSACTIONS_ASYNC.md).

## 7. Как использовать эти примеры

У всех случаев одна и та же логика:

```text
реальная задача
      ↓
ответственность системы
      ↓
механизм Frappe с подходящим смыслом
      ↓
собственный код только для недостающего поведения
```

Это не означает, что `Child DocType`, `Workflow`, стандартный REST API или Desk всегда являются окончательным ответом. Они являются естественной первой проверкой, когда их семантика совпадает с задачей.

Если требования выходят за эту семантику, решение расширяется через предусмотренные точки Framework или собственный код. Общий порядок выбора разобран в [главе 12](12_DECISION_STANDARD.md).
