# 12. Как выбирать архитектурное решение во Frappe

Предыдущие главы разбирают отдельные механизмы Framework. Здесь они сводятся в один порядок выбора решения без повторного объяснения деталей.

Главный вопрос:

> Какую ответственность решает задача и какой механизм Frappe уже отвечает за эту ответственность?

---

## 1. Сначала сформулировать смысл задачи

Одно пользовательское пожелание может звучать одинаково, но относиться к разным механизмам.

Например, «нужен статус»:

```text
просто хранить состояние
→ поле модели

управлять переходами по ролям и условиям
→ Workflow

транзакционно фиксировать Document
→ Is Submittable / docstatus
```

Поэтому проектирование начинается не с экрана, таблицы или паттерна, а с ответственности системы.

---

## 2. Определить владельца

```text
собственный App
→ Standard DocType, Controller, code, metadata

другое установленное App
→ точки расширения Frappe

конкретный Site
→ локальная настройка / runtime configuration

внешняя система
→ интеграционный контракт
```

Ошибка во владельце часто превращает штатную возможность Framework в ручной костыль.

---

## 3. Карта типовых ответственностей

| Задача | Первая точка проверки |
|---|---|
| самостоятельная бизнес-запись | `DocType` |
| свойство записи | `DocField` |
| состав одного Document | Child DocType |
| ссылка на существующую запись | `Link` |
| одна запись бизнес-настроек | Single DocType |
| поведение собственного DocType | `Document Controller` |
| управляемые переходы | `Workflow` |
| транзакционная фиксация | `docstatus` / Is Submittable |
| базовый доступ | Role + DocType Permissions |
| отдельное нестандартное действие | Permission Type `[v16+]` |
| один Document для пользователя | `get_doc` + явная `read` permission check |
| разрешённый пользователю список | `get_list` |
| доверенная системная выборка | `get_all` |
| сложный запрос / агрегация | Query Builder / SQL |
| повторяющийся дорогой результат | Frappe cache с понятной invalidation |
| длинная работа | Background Job |
| периодическая задача Site | `scheduler_events` |
| обычный CRUD API | Document REST API |
| бизнес-команда | method / whitelisted method / service |
| исходящий HTTP по событию | `Webhook` |
| расширение чужого DocType | Custom Field / hooks |
| обычный внутренний UI | Desk Form / List |
| отчёт | Report Builder / Query Report / Script Report по смыслу |
| runtime-параметр Site | `site_config.json` |
| обязательная зависимость от App | `required_apps` |
| доставка схемы | Standard DocType metadata + `migrate` |
| преобразование существующих данных | patch |
| переносимая конфигурация App | fixtures / exported customization |
| проверка собственного поведения | Frappe tests |

Это не таблица обязательных ответов. Она показывает естественную первую точку, которую стоит проверить до создания собственного механизма.

---

## 4. Модель и жизненный цикл идут раньше интерфейса

Порядок для новой сущности:

```text
что является самостоятельным Document?
↓
какие поля и связи выражают модель?
↓
какие инварианты гарантирует Controller?
↓
какие состояния и переходы существуют?
↓
какие представления нужны пользователю?
```

Так Form, List, Kanban или отдельный frontend не начинают диктовать структуру данных.

Подробнее: [02](02_DATA_MODEL.md), [03](03_DOCUMENT_LIFECYCLE.md), [09](09_UI_REPORTING.md).

---

## 5. Безопасность и чтение данных — одна граница, но разные главы

Глава [04](04_SECURITY.md) отвечает, **кто что имеет право делать**. Глава [05](05_DATA_ACCESS_PERFORMANCE.md) — **каким способом код получает данные и где permissions применяются автоматически, а где нет**.

Ключевое различие:

```text
get_list
→ permission-filtered список

get_all
→ системная выборка без permission filtering

get_doc
→ загрузка Document; для user-facing чтения нужна явная read-check
```

Нельзя компенсировать серверную дыру тем, что UI не показывает запрещённые записи.

---

## 6. Изменение данных и транзакция

Для обычного бизнес-изменения используется путь `Document`, потому что там живут permissions, validation и lifecycle.

Если появляются:

```text
прямое обновление БД;
ручной commit;
внешний HTTP-вызов;
Background Job;
```

нужно отдельно определить границу атомарной операции, rollback и повторного выполнения.

Подробнее: [06](06_TRANSACTIONS_ASYNC.md).

---

## 7. API и интеграции выбираются по контракту

```text
обычный CRUD с DocType
→ Document REST API

действие одного Document
→ method Document

команда приложения
→ whitelisted method / service

простое исходящее событие
→ Webhook

стабильный внешний контракт
→ отдельный API

сложные повторы / сверка / orchestration
→ собственная интеграционная логика + background jobs
```

Подробнее: [07](07_API_INTEGRATION.md).

---

## 8. Изменение чужого App начинается с extension point

Если модель принадлежит Frappe, ERPNext или другому App, сначала проверяются штатные механизмы:

```text
Custom Field / Property Setter
fixtures / export customizations
doc_events
extend_doctype_class [v16+]
override_doctype_class
```

Чем сильнее вмешательство, тем выше связанность с upstream.

Подробнее: [08](08_EXTENSION_CUSTOMIZATION.md).

---

## 9. Runtime-конфигурация, поставка и данные Site не смешиваются

Три разных вопроса:

```text
где живёт параметр окружения?
→ глава 10

как изменение App попадает на Site и мигрирует данные?
→ глава 11

как вернуть пользовательское состояние после аварии?
→ backup / restore из главы 10
```

`site_config.json`, migration patch и database backup решают разные задачи и не заменяют друг друга.

Подробнее: [10](10_CONFIGURATION_OPERATIONS.md), [11](11_DEPLOYMENT_TESTING.md).

---

## 10. Когда собственный механизм оправдан

Собственный Python, service, SQL, API, frontend, ACL hook или внешний scheduler сам по себе не является нарушением Frappe-native подхода.

Полезный критерий:

```text
штатный механизм уже выражает нужный смысл?
├─ да → используем его
└─ нет
    ↓
есть официальная точка расширения?
├─ да → расширяем
└─ нет
    ↓
собственный механизм решает новую ответственность
```

Плохое обоснование: «так принято в другом framework».

Хорошее обоснование: «штатный механизм не выражает конкретное требование X, поэтому добавляется механизм Y, отвечающий только за X».

---

## 11. Короткая последовательность проектирования

```text
1. Сформулировать бизнес-требование.
2. Назвать ответственность системы.
3. Определить владельца: Framework / App / Site / внешняя система.
4. Выбрать ближайший по смыслу механизм Frappe.
5. Проверить модель данных и lifecycle.
6. Проверить permissions и способ чтения данных.
7. Проверить границу транзакции и внешние эффекты.
8. Проверить API / UI / integration boundary.
9. Проверить ownership конфигурации и зависимостей.
10. Проверить, как решение установится и мигрирует на новый Site.
11. Добавить tests для собственных критичных правил.
12. Только после этого добавлять собственный слой там, где он действительно нужен.
```

Эта последовательность и является общей архитектурной логикой стандарта.
