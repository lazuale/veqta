# 11. Практические примеры — правильные и неправильные решения

Этот раздел написан для человека без технического бэкграунда.

Здесь не приводится выдуманная статистика «90% проектов». Выбраны наиболее повторяющиеся классы задач обычных бизнес-приложений: карточки, строки документа, статусы, согласование, права, проверки, API, уведомления, фоновые задачи и расширение чужих `DocType`.

Для каждого примера используется одна схема:

```text
Задача
Интуитивная ошибка
Почему она кажется логичной
Штатное решение Frappe
Почему именно так
Что ухудшится при обходе Framework
Когда исключение оправдано
```

В самих примерах обычные бизнес-названия даются по-русски. Английский сохраняется там, где это реальное имя механизма Frappe, метода, поля или API.

# Правильный пример 1. Заявка с несколькими позициями

## Задача

Есть заявка на закупку:

```text
Заявитель: Иван
Дата: 02.09.2026

Позиции:
- Бумага, 10 пачек
- Ручки, 50 шт.
- Картридж, 2 шт.
```

## Интуитивная ошибка

Создать две полностью самостоятельные системы карточек:

```text
Заявка на закупку
Позиция заявки
```

и потом программировать связь между ними вручную.

## Почему кажется логичной

Если смотреть на обычную базу данных, видны две таблицы: заявка и строки.

## Штатное решение Frappe

```text
Заявка на закупку
  └─ items: Table → Позиция заявки (Child DocType)
```

## Почему

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Child DocType` специально предназначен для записей, являющихся частью родительского `Document`.

Пруф:

- https://docs.frappe.io/framework/user/en/basics/doctypes/child-doctype

Framework сам хранит `parent`, `parenttype`, `parentfield` и порядок `idx`.

## Что ухудшится при обходе

Придётся самостоятельно решать:

- кому принадлежит строка;
- как удалять её вместе с родителем;
- как хранить порядок;
- как показывать её в форме;
- как не оставить «осиротевшую» строку.

## Когда исключение оправдано

Если «позиция» должна жить самостоятельно, иметь свои права, использоваться несколькими документами и открываться отдельно — это уже может быть обычный `DocType`.

# Правильный пример 2. Простая задача с четырьмя состояниями

## Задача

```text
Новая → В работе → Ожидание → Завершена
```

Пользователь имеет право самостоятельно менять состояние.

## Интуитивная ошибка

Сразу строить `Workflow` и пытаться использовать `docstatus`.

## Почему кажется логичной

`Workflow` и `docstatus` тоже связаны со «статусами», поэтому кажется, что это более серьёзный способ.

## Штатное решение Frappe

Обычное поле бизнес-статуса `status`.

## Почему

`docstatus` имеет специальную транзакционную семантику:

```text
Draft / Submitted / Cancelled
```

**[ДОКУМЕНТАЦИЯ FRAPPE]** Пруф:

- https://docs.frappe.io/framework/doctypes/docstatus

`Workflow` нужен, когда важны управляемые переходы, роли и условия, а не просто список значений.

## Что ухудшится при обходе

Модель станет сложнее, а системный `Submitted` будет ошибочно означать обычное «Завершена».

## Когда исключение оправдано

Если переходы зависят от роли или согласования — появляется основание для `Workflow`.

# Правильный пример 3. Заявку должен одобрить руководитель

## Задача

```text
Черновик
  ↓ сотрудник
На согласовании
  ↓ руководитель
Согласовано
```

## Интуитивная ошибка

Сделать `Select status`, а в `Client Script` написать:

```text
если пользователь руководитель — покажи Approve
если сотрудник — спрячь
```

## Почему кажется логичной

На экране всё выглядит правильно: сотрудник не видит кнопку.

## Штатное решение Frappe

Рассмотреть `Workflow`.

## Почему

`Workflow` описывает состояния, переходы, роли и условия — именно то, что требуется задаче.

Пруф:

- https://docs.frappe.io/erpnext/user/manual/en/workflows

## Что ухудшится при обходе

Интерфейс может скрывать кнопку, но другой API или клиент способен поменять `status`. Правила оказываются привязаны к форме, а не к процессу.

## Когда исключение оправдано

Если схема согласования динамическая и существенно сложнее штатных состояний, переходов и условий, отдельная предметная координация может быть лучше.

# Правильный пример 4. Нельзя сохранить неправильную дату

## Задача

```text
end_date >= start_date
```

## Интуитивная ошибка

Проверить только `Client Script`.

## Почему кажется логичной

Пользователь получает ошибку сразу, и при ручном тесте всё работает.

## Штатное решение Frappe

Серверная проверка в пути `Document`/Controller. `Client Script` можно оставить как дополнительную подсказку.

## Почему

**[ДОКУМЕНТАЦИЯ FRAPPE]** Проверка `Client Script` работает только в стандартной браузерной форме.

Пруфы:

- https://docs.frappe.io/framework/user/en/desk/scripting/client-script
- https://docs.frappe.io/framework/user/en/basics/doctypes/controllers

## Что ухудшится при обходе

Неправильная запись может прийти через API, импорт или серверный процесс.

## Когда исключение оправдано

Если правило действительно только визуальное и неправильное значение на сервере допустимо — серверная проверка не нужна.

# Правильный пример 5. Сотрудник видит только свою Company

## Задача

Пользователь работает только с `Company = ACME`.

`Company` здесь оставлена на английском, потому что это реальный `DocType` экосистемы Frappe/ERPNext.

## Интуитивная ошибка

Сразу писать собственный SQL-фильтр во всех списках.

## Штатное решение Frappe

Сначала проверить `Role`/`DocPerm` + `User Permission`.

## Почему

**[ДОКУМЕНТАЦИЯ FRAPPE]** `User Permission` предназначен для ограничения пользователя по связанным записям.

Пруф:

- https://docs.frappe.io/framework/user/en/basics/users-and-permissions

## Что ухудшится при обходе

Собственный фильтр нужно будет поддерживать отдельно в списке, отчёте, API и прямом доступе к документу.

## Когда исключение оправдано

Если политика зависит не от обычных связанных записей, а от сложного динамического набора правил — собственная логика прав может быть оправдана.

---

# Правильный пример 6. Внешняя программа должна создать обычную заявку

## Задача

Внутренняя программа отправляет поля нового `DocType` «Заявка» во Frappe.

## Интуитивная ошибка

Написать новую точку API `/api/request/create`, которая просто делает `doc.insert()`.

## Штатное решение Frappe

Использовать стандартный `Document REST API`.

## Почему

**[ДОКУМЕНТАЦИЯ FRAPPE + ИСХОДНЫЙ КОД]** Frappe автоматически предоставляет CRUD API для `DocType`; путь REST v16 создаёт `Document` через `insert()`.

Пруфы:

- https://docs.frappe.io/framework/user/en/api/rest
- https://github.com/frappe/frappe/blob/version-16/frappe/api/v2.py

## Что ухудшится при обходе

Появится вторая точка API со своей документацией, проверками прав и тестами, хотя она не добавляет нового смысла.

## Когда исключение оправдано

Если нужен стабильный публичный контракт, скрывающий внутренний `DocType`, отдельный API нормален.

# Правильный пример 7. Нужно сообщить внешней системе об обновлении документа

## Задача

После `Quotation.on_update` отправить HTTP-вызов в другую систему.

`Quotation` здесь является реальным `DocType`, поэтому его техническое имя не переводится.

## Интуитивная ошибка

Написать планировщик, который каждые 5 минут ищет изменённые `Quotation`.

## Штатное решение Frappe

Сначала проверить `Webhook`.

## Почему

**[ДОКУМЕНТАЦИЯ FRAPPE]** `Webhook` именно связывает событие `Document` и HTTP-вызов.

Пруф:

- https://docs.frappe.io/framework/user/en/guides/integration/webhooks

## Что ухудшится при обходе

Опрос по расписанию создаёт задержку, лишние запросы и собственную логику поиска изменений.

## Когда исключение оправдано

Если нужны гарантии доставки, повторное воспроизведение, сложные повторы и сверка, отдельный интеграционный поток может быть необходим.

---

# Правильный пример 8. Тяжёлый расчёт после сохранения

## Задача

После создания документа нужно обработать 50 000 строк.

## Интуитивная ошибка

Выполнять весь цикл прямо при сохранении документа.

## Штатное решение Frappe

Сохранить `Document` и поставить работу в `Background Job`; если задача должна видеть только зафиксированные данные — использовать `enqueue_after_commit`.

## Почему

**[ДОКУМЕНТАЦИЯ FRAPPE + ИСХОДНЫЙ КОД]** Frappe имеет систему фоновых задач и `enqueue`, учитывающий транзакцию.

Пруфы:

- https://docs.frappe.io/framework/user/en/api/background_jobs
- https://github.com/frappe/frappe/blob/version-16/frappe/utils/background_jobs.py

## Что ухудшится при обходе

Долгий HTTP-запрос, тайм-аут, длинные блокировки, плохой пользовательский опыт.

## Когда исключение оправдано

Если операция короткая и пользователю нужен синхронный результат, фоновая задача может только усложнить сценарий.

# Неправильный пример 1. «Сделаем свой ACL сразу»

## Задача

Сотрудник видит свои документы, менеджер — отдел, директор — все.

## Решение

Создаются собственные справочники правил доступа и собственные SQL-условия.

## Почему это опасно

Frappe уже имеет `Role`/`DocPerm`, `owner`, `User Permission`, `Share` и permission hooks.

Появляются две системы доступа:

```text
права Frappe
+
наши права
```

Теперь нужно объяснить итог каждого запроса как пересечение двух моделей.

## Правильный подход

Сначала выразить максимум штатными механизмами, а собственный код использовать только для недостающей политики строк.

Пруфы:

- https://docs.frappe.io/framework/user/en/basics/users-and-permissions
- https://github.com/frappe/frappe/blob/version-16/frappe/permissions.py

---

# Неправильный пример 2. «Спрячем поле JavaScript — значит доступа нет»

## Задача

Поле `salary` должен видеть только HR.

## Решение

`Client Script` скрывает поле для остальных.

## Почему неправильно

Видимость в интерфейсе не является границей прав доступа.

Frappe имеет `Permission Level` и права на поля.

Пруф:

- https://docs.frappe.io/framework/user/en/basics/users-and-permissions

## Правильный подход

Настроить серверную модель прав; интерфейс может дополнительно отражать её.

# Неправильный пример 3. get_all, потому что get_list «ничего не возвращает»

## Задача

Разработчик ожидает увидеть записи, но `get_list` их фильтрует.

## Решение

Заменить на `get_all`.

## Почему неправильно

Причина может быть именно в правах. Обход проблемы превращается в обход контроля доступа.

Пруфы:

- https://docs.frappe.io/framework/user/en/api/database
- https://docs.frappe.io/framework/user/en/python-api/hooks

## Правильный подход

Сначала понять модель прав. `get_all` использовать только в осознанном внутреннем или системном контексте.

# Неправильный пример 4. frappe.db.set_value() вместо Document save

## Задача

Нужно изменить бизнес-поле.

## Решение

Прямое обновление БД, потому что короче.

## Почему неправильно

**[ДОКУМЕНТАЦИЯ FRAPPE]** `set_value` не запускает ORM-события вроде `validate` и `on_update`.

Пруф:

- https://docs.frappe.io/framework/user/en/api/database

## Последствие

Бизнес-инварианты могут быть обойдены.

## Когда нормально

Техническое поле или намеренное внутреннее обновление/миграция, где обход осознан.

# Неправильный пример 5. Ручной commit() после каждого шага

## Задача

Операция создаёт три связанных документа.

## Решение

После каждого `insert()` делается `frappe.db.commit()` «для надёжности».

## Почему неправильно

Frappe уже имеет транзакцию запроса. Если третий шаг упадёт, первые два изменения могут остаться зафиксированными.

Пруф:

- https://docs.frappe.io/framework/user/en/api/database

## Правильный подход

Позволить Framework завершить атомарную транзакцию, если нет отдельной причины дробить её.

---

# Неправильный пример 6. Правка файла ядра

## Задача

Нужно добавить одну проверку к стандартному `DocType` другого App.

## Решение

Изменить его `.py` файл прямо в `apps/frappe` или `apps/erpnext`.

## Почему неправильно как вариант по умолчанию

Frappe предоставляет hooks, `doc_events`, `extend_doctype_class` и механизмы переопределения.

Пруф:

- https://docs.frappe.io/framework/user/en/python-api/hooks

## Последствие

Конфликт при обновлении, потеря воспроизводимости и зависимость от локально изменённого установленного кода.

## Когда fork оправдан

Когда организация сознательно поддерживает собственную сборку и принимает постоянную стоимость слияния изменений.

# Неправильный пример 7. Обязательные настройки остаются только на сайте разработки

## Задача

Для работы App нужны 12 `Custom Fields`, `Workflow` и `Role`.

## Решение

Инструкция после установки:

```text
зайдите в Customize Form
создайте поля
потом создайте Workflow
потом настройте права
```

## Почему неправильно для состояния, принадлежащего App

Новый Site не воспроизводится из репозитория.

Frappe имеет fixtures, export customizations, JSON `DocType` и migrations.

Пруфы:

- https://docs.frappe.io/framework/user/en/guides/app-development/exporting-customizations
- https://docs.frappe.io/framework/user/en/python-api/hooks#fixtures
- https://docs.frappe.io/framework/user/en/guides/deployment/migrations

## Когда ручная настройка нормальна

Когда это сознательно локальная конфигурация Site, которую каждый заказчик должен выбирать самостоятельно.

# Неправильный пример 8. Service ради названия Service

## Задача

Нужно сохранять `Task`.

`Task` здесь используется как условное техническое имя `DocType` в примере кода.

## Решение

```text
TaskService
  save(task) → task.save()

TaskRepository
  get(name) → frappe.get_doc("Task", name)
```

## Почему подозрительно

`Document` уже предоставляет абстракцию хранения и жизненного цикла. Новые слои пока не добавляют ответственности.

## Правильный подход

Не создавать слой до появления реальной причины.

## Когда Service становится правильным

Если появляется сложная операция нескольких `Documents`. Официальный ERPNext сам использует сервисные классы для таких задач:

- https://github.com/frappe/erpnext/blob/develop/erpnext/stock/services/stock_ledger_service.py

# Итог для новичка

Перед новым механизмом не спрашивай:

> «Как программисты обычно это делают?»

Сначала спроси:

> **«Есть ли во Frappe механизм именно с таким смыслом?»**

Если есть — используй его как первую точку проверки.

Если не хватает — выясни, что именно не хватает.

Только после этого появляется основание писать собственную конструкцию.
