# Требования к учебному приложению

Практикум строится не вокруг списка возможностей Frappe, а вокруг последовательного изменения требований к одному `Purchase Request`.

## Базовая заявка

1. Пользователь создаёт внутреннюю заявку на закупку.
2. Заявка содержит тему, описание, сумму и требуемую дату.
3. Система хранит текущее состояние заявки.
4. Пока нет правил переходов, состояние должно оставаться обычным полем, без Workflow.
5. В учебном сценарии заявитель совпадает с `Document.owner`; отдельное поле requester не требуется.

## Доступ и процесс

6. Заявитель может создавать и редактировать заявки.
7. Согласующий может читать и редактировать `Purchase Request`, но не создаёт заявки за пользователя.
8. После появления процессного требования заявитель должен уметь отправить `Draft` на согласование.
9. Согласующий должен уметь одобрить или отклонить ожидающую заявку.
10. Отклонённая заявка остаётся draft-документом: заявитель может исправить её и отправить повторно.
11. Пользователь с ролями заявителя и согласующего не должен одобрять собственную заявку.

## Условное согласование

12. Для суммы до `1000` включительно достаточно одного согласующего.
13. Для суммы больше `1000` после первого согласующего требуется `PLT Senior Approver`.
14. Большая заявка не должна миновать второй уровень через ручное изменение `status`.

## Транзакционный lifecycle

15. Пока окончательное согласование означает только процессное состояние, `PLT Approved` остаётся `docstatus = 0`.
16. Когда согласованная заявка должна стать зафиксированным фактом, `Purchase Request` становится `Is Submittable`, а `PLT Approved` получает `docstatus = 1`.
17. `Submit` получают только роли, которые реально выполняют окончательное согласование.
18. Согласованную заявку можно официально отменить без удаления исходного факта.
19. Отмена должна вести в `PLT Cancelled` с `docstatus = 2`.
20. Право `Cancel` получает только `PLT Approver`.
21. После Cancel заявитель может создать исправленную версию штатным Amend path.
22. Новая версия должна быть новым Draft Document и ссылаться на исходный через `amended_from`.

## Поставка приложения

23. Standard metadata `Purchase Request` и его default DocPerm должны находиться в App source.
24. Имена прикладных ролей должны поставляться через Standard DocPerm без дублирующего Role fixture, пока у Role нет отдельного App-owned состояния.
25. Собственные `Workflow State`, `Workflow Action Master` и Workflow должны воспроизводимо поставляться вместе с App.
26. Runtime `Workflow Action`, пользователи, пароли и рабочие `Purchase Request` не должны экспортироваться как конфигурация App.
27. Установка на новый чистый Site не должна требовать ручного восстановления обязательного Workflow.

## Проверка

28. Критические process contracts должны быть закреплены автоматическими tests.
29. Self approval проверяется через фактический `apply_workflow()`, а не имитацией прямой записи `status`.
30. Desk-поведение, которое не является самостоятельной server guarantee, проверяется отдельно как наблюдаемый сценарий.
31. Финальный результат должен устанавливаться на новый Site и проходить полный маршрут без скрытой ручной настройки.

## Что не входит в этот практикум

Без отдельного требования не добавляются:

```text
Assignment / ToDo
Notification
File / Comment / Version
Print Format
REST API
Webhook
background jobs
scheduler
custom frontend
external integration
динамическая approval matrix
настраиваемый администратором approval limit
```

Это самостоятельные ответственности. Они не нужны для изучения `Workflow`, `docstatus`, `Cancel`, `Amend` и поставки lifecycle-конфигурации.
