# Маршрут практикума

Практикум продолжает `rental_training` и показывает, где проходит граница одной бизнес-операции.

```text
готовый rental_training
  ↓
Equipment Movement
  ↓
явная команда issue()
  ↓
Rental + несколько Movement
  ↓
необработанная ошибка
  ↓
rollback
  ↓
ручной commit как антипример
  ↓
пойманное исключение как антипример
  ↓
return_equipment()
  ↓
Document API vs set_value
  ↓
автоматические тесты
  ↓
поставка App
  ↓
чистая установка
```

## Этапы

### S00 — исходное состояние и контрольные Rentals

Начать с актуального `rental_training` после предыдущих практикумов.

Проверить:

```text
Frappe v16.33.0
rental_training установлен
Equipment / Customer / Rental / Rental Item существуют
Rental Controller содержит предыдущие validations
текущие permissions воспроизводятся из App
```

Создать отдельные Site-owned Rentals для экспериментов S02–S07. Они не становятся fixtures и не используются автоматическими тестами.

Цель этапа — не изменить App, а получить безопасный набор данных, который можно намеренно ломать во время транзакционных экспериментов.

### S01 — добавить Equipment Movement

Создать Standard DocType:

```text
Equipment Movement
├── equipment     → Link → Equipment
├── rental        → Link → Rental
├── movement_type → Select: Issue / Return
└── movement_at   → Datetime
```

`Equipment Movement` является самостоятельным журналом и получает собственный `name`.

Permissions:

```text
Rental Manager → Read
Rental Operator → без прямого доступа
```

Прикладные роли не получают `Create`, `Write` и `Delete`.

На этом этапе Movement ещё не создаётся автоматически. Сначала фиксируется сама ответственность журнала.

### S02 — собрать атомарную команду Issue

Требование:

> Выдать Rental и зарегистрировать Issue Movement для каждого Equipment одной бизнес-операцией.

На `Rental` появляется whitelisted controller method:

```python
issue()
```

Команда:

```text
проверяет write permission текущего пользователя
проверяет status = Planned
разрешает внутренний переход Planned → Active
сохраняет Rental через Document API
создаёт Issue Movement для каждого Rental Item
не вызывает frappe.db.commit()
```

Movement создаётся внутренне через `insert(ignore_permissions=True)` только после `self.check_permission("write")` на Rental.

`status` становится read-only в обычной Form, а Controller защищает прямой переход на сервере.

В `rental.js` появляется тонкая кнопка **Issue**, вызывающая:

```javascript
frm.call("issue")
```

После успешного вызова Form перезагружается.

Этап заканчивается успешной выдачей контрольного Rental и проверкой полного набора Movement.

### S03 — увидеть автоматический rollback

Теперь операция временно ломается в середине.

После создания первого или второго Issue Movement добавить контролируемое:

```python
frappe.throw("Rollback experiment")
```

Вызвать Issue через Form.

Ожидается ошибка request.

После перезагрузки БД должна показывать:

```text
Rental.status = Planned
Issue Movement = 0
```

То есть уже выполненные `save()` / `insert()` не означают отдельный commit.

В конце этапа временный `frappe.throw` удаляется, код возвращается к рабочему состоянию.

### S04 — сломать атомарность ручным commit

На отдельном контрольном Rental временно добавить в середину Issue:

```python
frappe.db.commit()
```

после части выполненных записей, а затем снова вызвать исключение.

Теперь rollback request уже не может отменить изменения, зафиксированные до ручного commit.

Ученик должен увидеть фактическое частичное состояние, например:

```text
Rental = Active
Issue Movement = 1 из N
```

Точное место эксперимента фиксируется в задании так, чтобы результат был воспроизводим.

После наблюдения:

1. удалить `frappe.db.commit()`;
2. удалить временное исключение;
3. восстановить только контрольные Site-owned данные;
4. убедиться, что исходники App снова содержат правильную атомарную команду.

Смысл этапа — не научить ручному commit, а показать его реальную семантическую цену.

### S05 — увидеть границу пойманного исключения

Следующий эксперимент показывает другую частую ошибку.

Временно превратить исключение внутри Issue в обработанный результат:

```python
try:
    ...
except Exception:
    frappe.log_error()
    return {"ok": False}
```

Если request завершился успешно, Framework не знает, что бизнес-операцию нужно считать неуспешной.

Ученик снова проверяет фактическое состояние БД и видит, что автоматически рассчитывать на rollback после проглоченного исключения нельзя.

После эксперимента код возвращается к правильной форме:

```text
ошибка, отменяющая всю операцию
→ выходит наружу
→ request завершается ошибкой
→ Frappe выполняет rollback
```

Если приложение намеренно ловит ошибку и хочет продолжить request, решение о rollback становится ответственностью самого приложения. В этом практикуме такая необходимость отсутствует.

### S06 — добавить атомарную команду Return

После понимания транзакционной границы добавляется зеркальная операция:

```python
return_equipment()
```

Требование:

```text
Rental.status = Active
        ↓
Returned
+
Return Movement для каждого Equipment
```

Команда снова:

- проверяет `write` permission;
- проверяет исходное состояние;
- меняет Rental через Document API;
- создаёт Movement;
- не делает ручной commit.

В `rental.js` появляется кнопка **Return** только для подходящего состояния.

Повторный Issue или Return после успешного перехода отклоняется текущим `status`.

### S07 — сравнить Document API и прямое изменение БД

К этому моменту Controller защищает разрешённые переходы состояния.

Сначала попытаться изменить существующий Rental обычным Document API вне команды:

```python
rental.status = "Active"
rental.save()
```

Серверная защита должна отклонить переход.

Затем на отдельной контрольной записи выполнить технический эксперимент:

```python
frappe.db.set_value(
    "Rental",
    rental.name,
    "status",
    "Active",
)
```

Прямой Database API не запускает обычные ORM triggers, поэтому способен обойти controller validation и создать состояние без Movement.

После наблюдения контрольная запись восстанавливается.

Вывод этапа:

```text
Document API
→ бизнес-изменение с lifecycle

прямой Database API
→ технический путь с другой семантикой
```

Performance сам по себе не является причиной обходить Document lifecycle.

### S08 — закрепить собственные контракты тестами

Автоматические integration tests защищают собственное поведение App:

- прямой `Planned → Active` через `save()` запрещён;
- прямой `Active → Returned` через `save()` запрещён;
- `issue()` разрешён пользователю с `write` на конкретный Rental;
- оператор не может issue чужой Rental после `If Owner` из предыдущего практикума;
- успешный Issue создаёт ровно один Issue Movement на каждый Equipment;
- повторный Issue отклоняется;
- успешный Return создаёт полный набор Return Movement;
- повторный Return отклоняется;
- прикладные роли не имеют прямого `Create` на Equipment Movement;
- `Rental Manager` имеет `Read` на журнал.

Не нужно писать автоматический тест на то, умеет ли сам Frappe откатывать необработанный POST request: это ответственность Framework, которую S03 проверяет наблюдением на живом Site.

Не нужно фиксировать тестом временные антипримеры S04 и S05 — они не остаются в итоговом коде.

### S09 — проверить границу App-owned / Site-owned

Перед чистой установкой разобрать, что должно поставляться приложением.

App-owned:

```text
Equipment Movement DocType metadata
его permissions
изменённая metadata Rental.status
Rental Controller
Rental Form Script
автоматические тесты
```

Site-owned:

```text
Users
Equipment
Customer
Rental
Rental Item
Equipment Movement как рабочие записи
контрольные данные экспериментов
```

Рабочие Movement не экспортируются как fixtures.

### S10 — проверить чистую установку

Установить итоговый `rental_training` на новый чистый Site той же совместимой версии Frappe.

После установки без ручной настройки должны существовать:

```text
Equipment Movement
его default permissions
Rental с защищённым status
controller methods issue / return_equipment
Form Script с кнопками
```

На чистом Site не должны автоматически появляться рабочие Rentals или Equipment Movement.

После создания минимальных данных выполнить хотя бы одну успешную выдачу и возврат и убедиться, что транзакционный сценарий работает из состояния App, а не из скрытых настроек исходного Site.

## Почему порядок именно такой

Сначала появляется бизнес-факт `Equipment Movement`, а уже затем команда, которая обязана его создавать.

Успешная команда строится до экспериментов с ошибкой, чтобы ученик сначала видел правильную конечную модель.

Rollback проверяется до ручного commit: сначала нужно увидеть штатное поведение Framework, затем осознанно его сломать.

Пойманное исключение вынесено отдельно, потому что оно нарушает автоматический rollback по другой причине, чем `commit()`.

Return добавляется после транзакционных экспериментов, чтобы не дублировать код до понимания базовой границы операции.

`frappe.db.set_value` появляется последним среди механизмов изменения данных: сначала ученик уже знает, какой lifecycle он способен обойти.

Background jobs не входят в маршрут, потому что локальная выдача и возврат не требуют асинхронности.
