# Требования практикума

Практикум начинается с одной прикладной проблемы: выдача и возврат Rental теперь должны оставлять отдельный журнал по Equipment, а изменение Rental и создание журнала должны быть одной согласованной операцией.

| Требование | Что появляется | Этап |
|---|---|---|
| Практикум должен начинаться с воспроизводимого состояния `rental_training` и отдельного набора контрольных Rentals | проверка App/Site и Site-owned учебные данные | S00 |
| Нужно хранить самостоятельную историю фактической выдачи и возврата Equipment | Standard DocType `Equipment Movement` | S01 |
| Пользователь не должен вручную создавать или переписывать журнал движения | read-only аудитория Movement; создание только из авторизованной серверной команды | S01–S02 |
| Новый Rental не должен появляться сразу как `Active` или `Returned`, иначе состояние возникнет без соответствующей операции | серверное правило `new Rental → Planned` | S02 |
| Выдача Rental должна быть отдельной бизнес-командой, а не обычным редактированием `status` | `Rental.issue()`, `frm.call()`, серверная защита перехода `Planned → Active` | S02 |
| Изменение Rental и создание всех Issue Movement должны фиксироваться или откатываться вместе | одна транзакция обычного POST request без ручного `commit` | S02 |
| Ошибка на промежуточном Movement не должна оставлять Rental Active или частичный журнал | эксперимент с необработанным исключением и автоматическим rollback | S03 |
| Ученик должен фактически увидеть, почему `frappe.db.commit()` посередине бизнес-операции меняет её атомарность | временный контролируемый эксперимент с partial commit и последующий откат учебного кода | S04 |
| Пойманное и превращённое в успешный ответ исключение не должно ошибочно восприниматься как автоматический rollback | контролируемый эксперимент со swallowed exception и явный разбор ответственности | S05 |
| Возврат должен выполнять зеркальную согласованную операцию `Active → Returned` + Return Movement | `Rental.return_equipment()` | S06 |
| Обычный бизнес-переход не должен обходить controller lifecycle прямым DB update | сравнение Document API и `frappe.db.set_value` | S07 |
| Permission boundary и транзакционные бизнес-контракты приложения должны проверяться повторяемо | автоматические integration tests | S08 |
| Новый обязательный DocType, metadata Rental, Form Script и controller code должны принадлежать App, а рабочие Movement — Site | проверка App-owned / Site-owned состояния | S09 |
| Новый чистый Site должен получить итоговую модель и код из `rental_training` без ручного восстановления | clean-install проверка | S10 |

Без отдельного требования практикум не добавляет `frappe.enqueue`, `enqueue_after_commit`, worker queues, scheduler, Webhook, внешний API, retry loop, cache, raw SQL или собственную инфраструктуру транзакций.

Модель описана в [`APPLICATION_MODEL.md`](APPLICATION_MODEL.md), последовательность — в [`ROADMAP.md`](ROADMAP.md).
