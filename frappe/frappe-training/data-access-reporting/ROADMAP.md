# Маршрут практикума

Практикум продолжает готовый `rental_training` и последовательно усложняет задачу чтения данных. Каждый следующий механизм появляется только после того, как предыдущий перестаёт выражать требование достаточно хорошо.

```text
готовый rental_training
  ↓
реальная граница доступа по owner
  ↓
List View
  ↓
Report permission + Report Builder
  ↓
пользовательское и системное чтение
  ↓
Query Report
  ↓
Script Report
  ↓
Recorder
  ↓
frappe.qb.get_query
  ↓
автоматические тесты
  ↓
чистая установка
```

## Этапы

### S00 — исходное состояние и контрольные данные

Начать с завершённого приложения `rental_training`, проверить его состояние и подготовить на учебном Site контролируемый набор Equipment, Customer и Rental от нескольких пользователей.

Цель этапа — получить данные, на которых последующие различия видны фактически. Учебные Users и Documents остаются Site-owned данными и не становятся fixtures.

### S01 — ограничить оператора своими Rental

Изменить Standard DocType Permissions `Rental` так, чтобы `Rental Operator` работал только с Documents, где он является `owner`, а `Rental Manager` по-прежнему видел все Rentals.

Используется штатный `If Owner`. Собственный permission hook или ACL-таблица не нужны, потому что текущее требование полностью выражается стандартной моделью Frappe.

После изменения доступ проверяется под двумя операторами и менеджером через обычный Desk.

### S02 — решить рабочую выборку через List View

Пользователю нужно находить Rentals по:

```text
status
customer
start_date
end_date
```

Сначала используется стандартный `List View`: колонки, фильтры, сортировка и сохранённые представления.

На этом этапе не создаётся отдельный Report или собственная страница, потому что обычный рабочий реестр уже является ответственностью стандартного Desk.

### S03 — построить простую сводку через Report Builder

Менеджеру нужна сохраняемая табличная сводка по Rental с группировкой и подсчётом количества записей.

До этого момента `Rental Manager` не нуждался в permission `Report`: в первом практикуме отдельного требования к отчётам не было. Теперь permission появляется вместе с самой задачей отчётности.

Standard DocType Permissions `Rental` получают:

```text
Rental Manager
→ Report = yes
```

После этого используется `Report Builder` без Python и SQL.

На текущей модели достаточно `Group By + Count`: числовое поле не добавляется только ради демонстрации `Sum` или `Average`.

Этап должен показать границу механизма: Report Builder хорошо решает задачу одного DocType и его Child Tables, но не обязан превращаться в универсальный язык для любой аналитической выборки.

### S04 — увидеть границу пользовательского чтения

До собственного отчёта нужно понять, что разные Database API имеют разную семантику доступа.

На контролируемых пользователях проверяются:

```text
get_list
→ пользовательская выборка с применением permissions

get_all
→ доверенная системная выборка без permission filtering

get_doc
→ загрузка одного Document;
  право read проверяется явно, когда данные читаются в пользовательском контексте
```

Ключевая проверка: оператор не должен получить Rental другого оператора только потому, что серверный код умеет прочитать строку из базы.

Этот этап не добавляет отдельный API ради демонстрации. Он формирует правило, которое понадобится собственным отчётам и любому будущему user-facing серверному коду.

### S05 — Equipment Rental History через Query Report

Менеджеру нужен отчёт за выбранный период, объединяющий:

```text
Equipment
← Rental Item
← Rental
→ Customer
```

Каждая строка показывает конкретное использование Equipment в Rental.

Требование естественно выражается одним запросом, поэтому используется Standard `Query Report` с параметризованными filters.

Отчёт показывает все Rentals и предназначен только для `Rental Manager`. Разрешённые роли задаются в Standard Report и поставляются вместе с App.

Это принципиальная граница: SQL Query Report выполняется как доверенный запрос и сам по себе не наследует document-level filtering `If Owner`. Поэтому доступ к отчёту ограничивается ролью, которая по предметному требованию имеет право видеть весь набор Rentals.

Raw SQL здесь появляется не как «быстрый способ читать данные», а потому что ответственность Query Report буквально состоит в выполнении одного SQL-запроса для отчёта.

### S06 — Equipment Utilization через Script Report

Следующее требование уже не сводится только к выборке строк. Для каждого Equipment нужно:

1. проверить обязательные `from_date` и `to_date` и условие `from_date <= to_date`;
2. считать отчётный диапазон включительно по обеим датам;
3. ограничить каждый Rental выбранным отчётным периодом;
4. отбросить интервалы, которые после ограничения не пересекают период;
5. объединить пересекающиеся интервалы;
6. посчитать уникальные занятые календарные дни без двойного счёта;
7. вычислить процент занятости.

Для этой программной логики используется Standard `Script Report`.

Как и Query Report, он показывает данные всех Rentals и предназначен только для `Rental Manager`. Роль отчёта и `Report` permission остаются границей доступа; Python-код расчёта не заменяет модель авторизации.

Первая реализация должна быть корректной и максимально понятной. Допускается прямолинейное получение дополнительных данных внутри обработки, чтобы получить наблюдаемый baseline до оптимизации.

### S07 — измерить отчёт через Recorder

Не предполагать, что реализация медленная или быстрая по внешнему виду кода.

Запустить `Recorder`, выполнить Script Report и посмотреть:

```text
фактические SQL queries
их количество
stack traces
EXPLAIN
```

На контролируемом наборе данных должна стать видна проблема N+1, если отчёт выполняет дополнительные запросы для каждой строки или Equipment.

Результат этапа — измеренная причина, а не новая оптимизация.

### S08 — убрать N+1 через `frappe.qb.get_query`

После измерения переписать подготовку данных в set-based форму через `frappe.qb.get_query`.

Для Equipment и Rental используются запросы с:

```text
ignore_permissions = False
user = frappe.session.user
```

Python оставляет ответственность за расчёт интервалов, а `frappe.qb.get_query` отвечает за получение нужного набора строк по DocType metadata, включая Child Table field `items.equipment`.

Manager-only роли Report по-прежнему определяют, кто может запустить функциональность. Permission-aware query дополнительно не требует обходить доступ ради производительности.

После изменения снова выполнить Recorder и доказать одновременно два свойства:

```text
результат расчёта не изменился

количество SQL-запросов уменьшилось
```

Точное число SQL-запросов не фиксируется как автоматический контракт: служебные запросы Framework могут меняться. Здесь важно наблюдаемое устранение N+1 при сохранении результата.

Индекс и cache не добавляются, если измерение не показало отдельной причины для них.

### S09 — закрепить собственные контракты тестами

Автоматические проверки должны защищать то, что приложение добавило само:

- `Rental Operator` не читает чужой Rental;
- `Rental Manager` читает все Rentals;
- `Rental Manager` имеет обязательный `Report` permission на `Rental`;
- оба Standard Reports существуют и разрешены только нужной аудитории;
- `from_date > to_date` отклоняется;
- один календарный день даёт `period_days = 1`;
- Rental, касающийся границы периода, учитывает этот день;
- пересекающиеся интервалы одного Equipment не удваивают календарные дни;
- оптимизированная выборка не меняет результат расчёта.

Не нужно тестировать сам Frappe на предмет того, умеет ли стандартный Report Builder группировать строки или Recorder записывать SQL. Также не нужно закреплять тестом точное количество внутренних SQL-запросов Framework.

### S10 — проверить поставку на чистом Site

Установить итоговый `rental_training` на новый чистый Site и проверить, что из App воспроизводятся:

```text
Standard DocType Permissions:
  Rental Operator → If Owner
  Rental Manager  → Report

Standard Query Report и его manager-only роли
Standard Script Report и его manager-only роли/исходники
автоматические тесты приложения
```

На новом Site не должны автоматически появляться:

```text
учебные Users
пароли
Equipment
Customer
Rental
Rental Item
персональные сохранённые варианты Report Builder
```

Это завершает границу между обязательным состоянием App и рабочими данными Site.

## Почему порядок именно такой

`List View` и `Report Builder` идут раньше собственного кода, потому что сначала проверяются штатные средства представления уже существующей модели.

`Report` permission появляется вместе с первым отчётным требованием, а не заранее только потому, что такой permission существует во Framework.

Permission boundary появляется до Query Report и Script Report, чтобы собственная выборка проектировалась с пониманием того, кому разрешено видеть результат.

Query Report появляется раньше Script Report, потому что первый пользовательский отчёт естественно выражается одним запросом. Python добавляется только когда возникает самостоятельная вычислительная ответственность — обработка календарных интервалов.

Recorder используется после появления работающего отчёта. Производительность сначала измеряется, затем исправляется конкретная найденная причина.

`frappe.qb.get_query` появляется не как обязательная замена SQL, а как подходящий permission-aware способ получить set-based данные внутри Python-отчёта после того, как Recorder показал N+1.

Модель и расчёты описаны в [`APPLICATION_MODEL.md`](APPLICATION_MODEL.md), исходные требования — в [`REQUIREMENTS.md`](REQUIREMENTS.md), практические задания — в [`stages/`](stages/README.md).
