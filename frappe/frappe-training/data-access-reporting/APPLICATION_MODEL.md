# Модель и учебный сценарий

Практикум не создаёт новый App и не вводит новую предметную модель. Он продолжает `rental_training`, построенный в практикуме [«Первое приложение»](../first-app/README.md).

## Исходная модель

```text
Equipment
Customer
Rental
└── Rental Item
```

### Equipment

Самостоятельная единица оборудования.

### Customer

Самостоятельный клиент.

### Rental

Рабочий `Document`, который связывает клиента, период проката, набор оборудования и предметное состояние.

Основные данные:

```text
customer
start_date
end_date
status
items
```

Состояния:

```text
Planned
Active
Returned
```

### Rental Item

Child DocType, связывающий `Rental` с одним `Equipment`.

## Новая граница доступа

В первом практикуме `Rental Operator` и `Rental Manager` получают `Read` на `Rental`, поэтому оба пользователя могут видеть все записи.

Для этого практикума появляется новое требование:

> Оператор работает только со своими Rental, а менеджер видит все Rental.

Штатная модель доступа становится такой:

```text
Rental Operator
→ Read/Create/Write только для Documents, где owner = текущий пользователь

Rental Manager
→ Read/Create/Write/Delete для всех Rental
```

Для `Rental Operator` используется стандартный флаг `If Owner` в DocType Permissions. Новая собственная ACL-таблица или permission hook для этого требования не нужны.

Эта граница нужна не ради демонстрации permissions. Она создаёт реальную разницу между пользовательской и доверенной системной выборкой данных, которую затем можно проверить через Desk, `get_list`, `get_all`, отчёты и автоматические тесты.

Когда в практикуме появляется первое требование к отчёту, `Rental Manager` дополнительно получает стандартный permission `Report` на `Rental`. Он не выдаётся заранее: в первом приложении отчётов ещё не было.

## Учебные данные

На Site нужны контролируемые данные минимум от двух операторов и одного менеджера:

```text
operator-a@example.test
operator-b@example.test
manager@example.test
```

Должны существовать Rentals с разными `owner`, клиентами, статусами и пересекающими выбранный отчётный период датами.

Эти пользователи и рабочие записи являются **данными Site**. Они не становятся fixtures приложения и не поставляются на новый Site как обязательная конфигурация.

## Какие вопросы должен уметь решать пользователь

Практикум последовательно отвечает на четыре прикладных вопроса.

### 1. Какие Rentals сейчас требуют внимания

Менеджеру и оператору нужны обычные рабочие выборки по:

```text
status
customer
start_date
end_date
```

Это задача стандартного списка и фильтров, а не причина сразу писать собственный отчёт.

### 2. Как распределены Rentals

Менеджеру нужна простая сводка по статусам и клиентам.

Для текущей модели достаточно:

```text
выбрать колонки
применить filters
сгруппировать
посчитать количество записей
```

Поэтому сначала используется `Report Builder` с `Group By + Count`.

Числовое поле не добавляется в `Rental` только ради демонстрации `Sum` или `Average`.

### 3. Где и когда использовалось Equipment

Нужен отчёт за выбранный период, где каждая строка показывает использование конкретного Equipment в конкретном Rental:

```text
Equipment
Rental
Customer
Status
Start Date
End Date
Owner
```

Для этого нужно связать:

```text
Equipment
← Rental Item
← Rental
→ Customer
```

Такой отчёт естественно выражается одним параметризованным запросом и становится учебным `Query Report`.

Отчёт предназначен для `Rental Manager`, потому что он показывает данные всех Rentals. Ограничение доступа к самому Standard Report является частью конфигурации App.

### 4. Насколько Equipment было занято в периоде

Менеджеру нужен учебный показатель загрузки Equipment за диапазон дат.

Для каждого Equipment учитываются интервалы Rentals со статусом:

```text
Active
Returned
```

`Planned` не считается фактической занятостью в этом учебном показателе.

Отчётный диапазон задаётся двумя обязательными датами:

```text
from_date
to_date
```

и считается **включительно по обеим границам**. Должно выполняться:

```text
from_date <= to_date
period_days = (to_date - from_date) + 1 календарный день
```

`start_date` и `end_date` Rental уже обязательны в исходной модели первого практикума. Для каждого учитываемого Rental его интервал сначала ограничивается выбранным отчётным периодом:

```text
start = max(rental.start_date, from_date)
end   = min(rental.end_date, to_date)
```

Если после ограничения `start > end`, Rental не вносит занятых дней в выбранный период.

Если интервалы одного Equipment пересекаются, общий календарный день учитывается один раз. Для каждого объединённого интервала:

```text
occupied_days = (end - start) + 1 календарный день
```

Итоговый показатель:

```text
utilization_percent = occupied_days / period_days * 100
```

Это именно **учебный показатель по данным текущей модели Rental**, а не универсальная метрика реальной эксплуатации техники.

Задача требует не только получить строки из БД, но и обработать интервалы. Поэтому она даёт самостоятельное основание для `Script Report`.

Как и Query Report, этот Script Report показывает данные всех Rentals и предназначен только для `Rental Manager`. Python-код отчёта не становится отдельной системой авторизации: аудитория задаётся штатными permissions и ролями Standard Report.

## Производительность как наблюдаемая характеристика

Первую корректную реализацию расчётного отчёта можно сделать прямолинейно и получить данные дополнительными запросами внутри цикла.

После этого `Recorder` позволяет увидеть фактическое количество SQL-запросов и обнаружить N+1.

Только после измерения выборка переписывается в set-based форму через `frappe.qb.get_query`.

В финальной реализации запросы выполняются с:

```text
ignore_permissions = False
user = frappe.session.user
```

Это позволяет убрать N+1 без обхода permission-модели ради производительности.

При этом роли Standard Report и permission `Report` по-прежнему определяют, кто вообще имеет право запускать отчёт. Permission-aware query и аудитория Report — связанные, но разные границы.

Учебный контракт:

```text
результат отчёта до оптимизации
=
результат отчёта после оптимизации

количество обращений к БД после оптимизации
<
количество обращений к БД до оптимизации
```

Сравнение количества запросов является наблюдением через Recorder, а не жёстким автоматическим контрактом на конкретное число SQL-запросов Framework.

Индекс и cache не являются обязательной частью этой модели: они добавляются только если отдельное измерение покажет соответствующую проблему.

## Что принадлежит App

К концу практикума App должен воспроизводимо содержать:

- `If Owner` для `Rental Operator` в Standard DocType Permissions;
- `Report` permission для `Rental Manager` в Standard DocType Permissions;
- Standard Query Report и его manager-only аудиторию;
- Standard Script Report и его manager-only аудиторию;
- Python/JS исходники Script Report;
- автоматические тесты собственных контрактов.

## Что остаётся Site-owned

На конкретном Site остаются:

- Users и их пароли;
- Equipment, Customer, Rental и Rental Item;
- контрольные учебные данные;
- пользовательские сохранённые варианты Report Builder, если они не являются обязательной конфигурацией App.

Маршрут реализации описан в [`ROADMAP.md`](ROADMAP.md), требования — в [`REQUIREMENTS.md`](REQUIREMENTS.md), практические этапы — в [`stages/`](stages/README.md).
