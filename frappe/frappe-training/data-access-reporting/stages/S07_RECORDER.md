# S07. Измерить Script Report через Recorder

S06 дал корректный `Equipment Utilization`, но его Python-код делает запросы внутри циклов.

Пока это только подозрение.

Новое требование:

> Перед оптимизацией нужно увидеть фактические SQL-запросы работающего отчёта и доказать причину лишней нагрузки измерением.

Для этого используется штатный `Recorder` Frappe.

Связанные материалы:

- [`S06_SCRIPT_REPORT.md`](S06_SCRIPT_REPORT.md);
- [`../../../frappe-architecture-standard/05_DATA_ACCESS_PERFORMANCE.md`](../../../frappe-architecture-standard/05_DATA_ACCESS_PERFORMANCE.md).

Первичный источник:

- https://docs.frappe.io/framework/user/en/profiling

---

## 1. Сначала убедиться, что отчёт корректен

До профилирования снова выполните:

```text
Equipment Utilization
From Date = 2026-09-01
To Date   = 2026-09-10
```

Контрольные значения A/B/C должны оставаться:

```text
50%
50%
10%
```

Если расчёт неверен, сначала исправляется функциональная ошибка. Recorder не нужен для маскировки неправильного результата.

---

## 2. Открыть Recorder

Войдите как:

```text
Administrator
```

Через Awesomebar откройте:

```text
Recorder
```

Нажмите `Start` и включите запись SQL-запросов.

Для этого этапа cProfile не обязателен: нас интересует форма доступа к БД.

Recorder добавляет собственные накладные расходы, поэтому абсолютное время всего request не используйте как benchmark приложения. Нас интересуют:

```text
какие SQL выполнялись
сколько раз повторялся один класс запросов
stack trace
EXPLAIN
```

---

## 3. Выполнить один чистый запуск отчёта

После запуска Recorder откройте `Equipment Utilization` в другой вкладке как `Administrator` и выполните один запрос:

```text
2026-09-01 → 2026-09-10
```

Для профилирования здесь допустим `Administrator`: permission boundary отчёта уже отдельно проверена на S06, а сейчас измеряется форма SQL.

Не выполняйте параллельно другие действия на учебном Site, чтобы capture было проще читать.

---

## 4. Остановить Recorder

Вернитесь в Recorder и нажмите `Stop`.

Найдите captured request, связанный с выполнением Report.

Откройте список SQL queries.

---

## 5. Найти повторяющийся шаблон

Первая реализация S06 устроена так:

```text
получить Equipment
↓
для каждого Equipment получить Rental Item
↓
для каждого Rental Item загрузить Rental
```

Поэтому в capture должны быть видны повторяющиеся запросы к:

```text
Equipment
Rental Item
Rental
```

Особенно важный признак N+1:

```text
количество однотипных запросов растёт вместе с количеством Equipment/Rental
```

а не остаётся примерно постоянным для одной операции отчёта.

Не привязывайтесь к точному общему числу SQL в Recorder: Frappe выполняет и служебные запросы для permissions, metadata, Report и других механизмов.

---

## 6. Использовать stack trace

Для повторяющегося SQL откройте stack trace.

Нужно связать запрос не с предположением, а с конкретной строкой нашего Report-кода.

Ожидаемые источники:

```text
_get_equipment_intervals_naive()
→ frappe.get_all("Rental Item", ...)

цикл item_rows
→ frappe.get_doc("Rental", item.parent)
```

Теперь причина наблюдаема:

```text
наш цикл
→ вызывает DB operation многократно
→ Recorder показывает повторение
```

---

## 7. Посмотреть EXPLAIN, но не искать проблему только там

Recorder показывает `EXPLAIN` SQL-запросов.

Посмотрите его для нескольких повторяющихся SELECT.

На этом этапе не нужно автоматически делать вывод:

```text
видим scan
→ срочно добавить индекс
```

Текущая проблема выше уровнем:

```text
мы выполняем слишком много запросов одного класса
```

Даже быстрый отдельный SELECT становится дорогим паттерном, если его число растёт вместе с объёмом данных.

Сначала исправляется форма операции. Индекс рассматривается отдельно только если после этого измерение покажет самостоятельную проблему плана запроса.

---

## 8. Зафиксировать baseline для себя

Запишите локально два наблюдения:

```text
1. сколько примерно запросов Rental Item выполняется за один report run
2. сколько примерно загрузок Rental выполняется за один report run
```

Не добавляйте в публичные исходники отдельный audit-файл с PASS/FAIL и снимком Recorder.

Эти числа нужны только для сравнения с S08 на вашем Site.

---

## 9. Не оптимизировать на S07

На этом этапе не меняйте:

```text
Equipment Utilization Python
DocType indexes
cache
Redis
Prepared Report
background jobs
```

Результат S07 — доказанная причина:

> Подготовка данных имеет N+1, потому что запросы выполняются внутри циклов.

Только после этого появляется основание для следующего изменения.

---

## 10. Git остаётся чистым

Recorder хранит диагностические данные Site и не создаёт обязательного состояния App.

Проверьте:

```bash
cd ~/frappe/rental-training-bench
git -C apps/rental_training status --short
```

После коммита S06 рабочее дерево должно оставаться чистым.

---

## Результат этапа

К концу S07:

```text
работающий Report измерен
N+1 подтверждён фактическими SQL
stack trace связал запросы с нашим кодом
EXPLAIN просмотрен в контексте, а не как повод добавить индекс
оптимизация ещё не выполнялась
```

На S08 изменится только одна ответственность: получение исходных строк станет set-based, а календарный расчёт останется прежним.
