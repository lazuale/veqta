# VEQTA

VEQTA — проект приложения на **Frappe Framework** для управления рабочими единицами через настраиваемый процесс.

> **Frappe даёт инструменты. VEQTA даёт модель работы. Пользователь задаёт процесс.**

## Зачем этот проект

Готовые системы часто заставляют описывать работу их терминами: проектами, тикетами, спринтами, заявками и заранее заданными процессами.

В VEQTA сейчас проверяется более простой подход: оставить технические механизмы Frappe и добавить минимальную предметную модель, достаточную для обычной управляемой работы.

## Что мы реально создаём в v0.1

Собственных DocType VEQTA сейчас **ровно два**:

```text
Work Type  → какой это вид работы
Work Item  → конкретная единица работы
```

Всё остальное в первом prototype **не является новой сущностью VEQTA**. Это уже существующие механизмы Frappe, которые мы настраиваем на `Work Item` и проверяем:

```text
Frappe Workflow / Workflow State  → состояния и переходы
Assign To / ToDo                  → назначения людей
Version / Timeline / comments     → история
Desk                              → штатный интерфейс
Kanban                            → доска
```

Зачем их проверять: если штатный механизм Frappe работает корректно, VEQTA не должна писать второй такой же механизм и хранить тот же факт второй раз.

На стенде используются два вида работы:

```text
TASK:  New → In Progress → Done
CHECK: New → In Progress → Review → Done
```

Это не описание готового продукта. Это текущая гипотеза, которую должен подтвердить или опровергнуть живой стенд.

## Что именно должен доказать prototype

### 1. Два наших DocType работают как одна модель

`Work Type` отличает разные виды работы, а `Work Item` остаётся одной общей сущностью. Проверяем ссылки и безопасное переименование отображаемого названия типа.

### 2. Штатный Workflow можно использовать вместо собственного lifecycle engine

Проверяем, может ли один Frappe Workflow обслуживать `TASK` и `CHECK` с разными маршрутами и серверно запрещать недопустимые переходы.

### 3. Штатный Assignment можно использовать вместо поля ответственного

Проверяем `Assign To` и связанные `ToDo`: одно назначение, несколько назначений и снятие одного назначения без повреждения остальных.

### 4. Штатной истории либо хватает, либо мы фиксируем конкретный недостаток

Проверяем, можно ли из `Version`, Timeline и Workflow comments получить машинно читаемые `from_state`, `to_state`, `changed_by`, `changed_at` и время в состоянии.

### 5. Desk и Kanban не ломают модель

Проверяем обычную работу через Desk и отдельно — не позволяет ли Kanban drag-and-drop обойти ограничения Workflow.

### 6. Принятое состояние действительно живёт в Git

То, что принято на dev-стенде, должно существовать как воспроизводимый код или штатно экспортированная конфигурация приложения.

Контрольный результат:

```text
чистый совместимый Frappe site
+ repository VEQTA
+ install-app / migrate
= то же принятое состояние без повторного ручного накликивания
```

Точный сценарий каждого испытания — **`docs/PROTOTYPE_V0_1.md`**. Там для каждого шага должны быть действия, ожидаемый результат и критерий PASS/FAIL.

## Термины

- **Frappe Framework** — платформа, на которой запускается VEQTA.
- **DocType** — описание типа данных во Frappe: поля, форма, хранение и поведение записи.
- **Desk** — штатный веб-интерфейс Frappe, где работают с DocType и настройками.
- **Workflow** — штатный механизм состояний и разрешённых переходов между ними.
- **ToDo** — штатная запись Frappe, через которую `Assign To` хранит назначение пользователя на документ.
- **Bench** — инструмент и каталог dev-среды Frappe: приложения, sites и команды управления ими.
